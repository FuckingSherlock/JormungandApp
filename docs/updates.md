# Обновление приложения — дизайн

Статус: **ядро (`core/lib/src/appupdate.dart`) и инструменты публикации сделаны, в макете — блок
«App updates» (Settings → Data); установка (Android / Windows) и связка с `CoreService` — нет**:
здесь она только описана для Flutter-части.

Приложение ставится **без Google Play и без ручных перескачиваний**: оно само узнаёт о новой
версии, скачивает её, проверяет и отдаёт системе на установку. Репозиторий приватный, поэтому
хостинг обновлений — любой: приложение знает **список адресов лент** и ничего не знает про
GitHub / Cloudflare. Пользователи часто в России, где хосты блокируют: сначала напрямую, потом
через работающий туннель (тем же способом, что подписки «через прокси» — `tunnel-in`, `core.md` →
«Входы sing-box»).

Принцип доверия: **хост не доверенный**. Всё, что с него пришло, проверено подписью, зашитой в
приложение (Ed25519), и хешем файла из подписанного манифеста. Взломанная лента или зеркало
не могут подсунуть код; они могут только промолчать.

---

## 1. Что где лежит

Лента — это URL-префикс. Под ним:

```
<лента>/manifest-stable.json        манифест канала stable
<лента>/manifest-stable.json.sig    отделённая подпись манифеста
<лента>/manifest-beta.json
<лента>/manifest-beta.json.sig
```

Файлы установки лежат там, куда указывает манифест (`urls`), по умолчанию — рядом с манифестом
(`<лента>/<file>`). Один и тот же набор можно выложить на несколько лент (зеркала): манифест и
файлы одинаковые, подпись общая.

Лента **может быть** (приложение с этим не связано):

| хостинг | как выглядит | заметки |
|---|---|---|
| GitHub Releases публичного репозитория релизов (не основного, он приватный) | лента = `https://github.com/<орг>/<репо>/releases/download/feed`: релиз с постоянным тегом `feed`, в нём лежат четыре файла манифестов (перезаписываются на каждом выпуске); установщики — в релизах `v0.2.0` и т. д., в манифесте абсолютные `urls` | бесплатно, CDN; в РФ периодически режется — для этого есть запасные ленты и туннель |
| Cloudflare R2 + Worker | лента = `https://updates.<домен>` (Worker отдаёт объекты бакета, у нас уже есть `jormungand-design`) | отдельный домен, не `workers.dev`; можно за своим доменом, до которого РКН не добрался |
| любой статический хостинг / VPS | тот же четыре файла + установщики | |

Какие именно хосты и в каком порядке — решение владельца (`releaseFeeds` в `appupdate.dart`,
пока пуст, TODO). Минимум для устойчивости: две ленты на разной инфраструктуре (например GitHub
+ Cloudflare) — одну режут, вторая работает.

## 2. Манифест

JSON (UTF-8), подписывается **байтами файла как есть** (никакой канонизации: что лежит на
хосте, то и проверено). Размер ≤ 256 КБ.

```json
{
  "schema": 1,
  "app": "jormungand",
  "channel": "stable",
  "version": "0.2.0",
  "build": 12,
  "publishedAt": "2026-10-03T12:00:00Z",
  "minSupported": "0.1.5",
  "page": "https://example.org/jormungand/download",
  "notes": { "en": "Faster Auto…", "ru": "Auto стал быстрее…" },
  "android": { "signerSha256": ["<hex sha256 сертификата подписи APK>"] },
  "assets": {
    "android-arm64-v8a":   { "file": "jormungand-0.2.0-arm64-v8a.apk", "size": 61234567, "sha256": "<hex>", "kind": "apk",
                             "urls": ["https://github.com/…/releases/download/v0.2.0/jormungand-0.2.0-arm64-v8a.apk"] },
    "android-armeabi-v7a": { … },
    "android-x86_64":      { … },
    "windows-x64":         { "file": "jormungand-0.2.0-windows-x64.zip", "size": 48000000, "sha256": "<hex>", "kind": "zip" }
  }
}
```

| поле | смысл |
|---|---|
| `schema` | формат манифеста, сейчас 1. Больше, чем знает приложение → ошибка `schema` («это обновление нужно скачать вручную», показывается `page`) |
| `app` | всегда `jormungand`; другое → `wrongApp` |
| `channel` | `stable` / `beta`; должен совпасть с файлом, в котором лежит (beta в слоте stable отвергается) |
| `version` | semver `x.y.z[-pre]`, без `+build` |
| `build` | целое ≥ 1, растёт с каждым выпуском (на Android — `versionCode`) |
| `publishedAt` | информативно (когда) |
| `minSupported` | semver; версии ниже обязаны обновиться (раздел 8). Не больше `version` |
| `page` | страница, где человек возьмёт файл руками, если автообновление невозможно |
| `notes` | заметки к релизу по языкам; показывается язык интерфейса, иначе `en` |
| `android.signerSha256` | SHA-256 сертификата(ов) подписи APK (hex); список — на время смены сертификата |
| `assets[<платформа>]` | файл для платформы: `file` (только `[A-Za-z0-9._-]`, без путей — это имя в папке обновлений), `size`, `sha256` (hex), `kind` (`apk` / `installer` / `zip`), `urls` — абсолютные адреса или относительные к ленте (под каждой лентой); нет `urls` → `<лента>/<file>` |
| `assets[…].deltas` | необязательный список патчей «старый полный файл → этот»: `[{from, file, size, sha256, urls?}]` — `from` = sha256 **старого полного файла** (hex), остальное как у файла (`file` — по тем же правилам имени, `sha256` — самого патча, `urls` как у файла). До 16 штук; неверная форма → `badManifest`. Раздел 7 → «Дельта-обновления». Старые клиенты неизвестное поле актива не читают и качают файл целиком, поэтому `schema` остаётся 1 |

Платформы: `android-arm64-v8a`, `android-armeabi-v7a`, `android-x86_64`, `windows-x64`. С 2026-10-12
публикуется только `android-arm64-v8a` (32-битный ARM и x86_64 не собираются; формат и ядро их по-прежнему
понимают). В репозитории релизов хранятся 3 последние беты (`KEEP_BETAS`) и стабильные. Актив
неизвестной платформы пропускается (новый релиз может добавить свои). Приложение берёт первый
из списка предпочтений устройства (`updatePlatforms`: на Android — ABI в порядке
`Build.SUPPORTED_ABIS`).

Невалидный манифест (форма, значения, имя файла с `..`, неверный sha256, неизвестный канал)
целиком отвергается ошибкой `badManifest`, даже если подпись верна.

## 3. Подпись и ключи

- **Ed25519**, подпись — над байтами `manifest-<канал>.json`. Файл `.json.sig` — base64 от 64 байт
  подписи (допустимо несколько подписей, по одной на строку: на время смены ключа).
- **Публичные ключи зашиты в приложение** (`releasePublicKeys`, base64 по 32 байта). Пустой
  список = любая проверка падает с `noKey`: лучше без обновлений, чем с непроверенными.
- **Ключ** (создан 03.10.2026, публичный `wNAvpxCr+EQCOFnwSmZtzkPgxLNc4akDBzFhhFBNRo4=`), приватный —
  в трёх местах: машина публикующего (`%USERPROFILE%\.jormungand\release-signing.key`), секрет
  GitHub Actions `JORM_RELEASE_KEY` основного репо (подпись в CI), резервная копия в secrets-mcp
  (`JORM_RELEASE_KEY`, хост `backup-only.invalid` — никуда не отправляется).
- Манифест принят, если **любая** подпись из файла проверяется **любым** известным ключом.
- Приватный ключ хранится **вне репозитория** (инструмент отказывается писать в любое git-дерево
  и не перезаписывает файл); копия — в менеджере паролей / на офлайн-носителе. Потеряли ключ —
  выпустить обновление вручную нельзя: уже установленные копии принимают только подписанное
  им. Поэтому: **резервная копия обязательна**.
- **Смена ключа** (плановая или при утечке): выпустить версию N с **двумя** ключами (старый +
  новый), подписанную старым; когда N разошлась — подписывать новым (старый убрать из следующих
  сборок). При утечке старого — те, кто не обновился до N, не защищены; их спасает только ручная
  установка.
- Пакет: **`cryptography`** (^2.9, dint.dev). Чистый Dart (без FFI и платформенных вставок),
  активно поддерживается, Ed25519 «из коробки»; на Dart-стороне тянет только `crypto`,
  `meta`, `typed_data`, `collection`. Проверка подписи — миллисекунды (манифест мал).
  Рассмотрен `pinenacl` (меньше, но давно не обновлялся); `crypto` из стандартной
  поставки Ed25519 не умеет, sha256 берём из него.
- Дополнительная подлинность на Android — подпись самого APK (раздел 7): Android не даст
  обновить приложение пакетом с другим сертификатом, даже если бы все проверки выше обошли.

Что защищает: подмену файла на хосте (sha256), подмену манифеста (подпись), чужой сборкой (подпись
APK). Что **не** защищает: **заморозку** (хост молча отдаёт старый подписанный манифест — приложение
не узнает о новом; поэтому несколько лент) и **откат** — старый манифест не заставит поставить старое:
версия должна быть новее запущенной, а Android и сам отказывает в понижении.

## 4. Ленты и порядок попыток

`releaseFeeds` — список лент по порядку. Каждый запрос (манифест, подпись, файл) идёт через служебный
трафик ядра (`ServiceFetch`, `core.md` → «Служебный трафик», `purpose: appupdate`): адрес **гонится
по всем путям сразу** (прямой и пути туннеля, если он поднят), без «круга напрямую, потом круга через
туннель». Каждый путь читает первые ~64 КиБ; при равенстве выигрывает **прямой** (`prefer: direct`:
лента дешевле туннеля), туннель — когда прямой не дал ответа. Туннеля нет — путь один, прямой. Ленты
перебираются по порядку; в попытке ленты одна запись на ленту, исходы путей лежат внутри (`paths`).

Первый манифест, у которого подпись верна и содержимое валидно, побеждает. Лента с неверной
подписью или битым манифестом — такой же сбой ленты, как «не отвечает»: проверка идёт к
следующей (взломанное зеркало не должно блокировать обновления). Итоговая ошибка, если не
вышло нигде, — самая «говорящая»: `badSignature` > `schema` / `wrongApp` > `badManifest` >
`network`; все попытки (`url`, `route`, `code`, `error`) идут в журнал.

Гонка по путям, а не «лента 1 напрямую → лента 1 через туннель → лента 2…»: заблокированный хост
(долгий таймаут) не задерживает ответ, а рабочая прямая лента дешевле туннеля.

**Файл установщика** — по `urls` актива (относительные — под каждой лентой, сначала лента, давшая
манифест), тоже гонкой: победитель продолжает тело, остальные пути закрываются; оборвался поток —
докачка `Range` (с `If-Range`) по следующему пути. Обрыв внутри первых ~64 КиБ (образца) не оставляет
`.part` — следующая попытка начинается с нуля (теряется не больше 64 КиБ). Неверный размер / хеш
с одного адреса — сбой адреса (идём дальше). Ни одного пути — ошибка
`network`, UI подсказывает: «подключитесь к VPN и повторите» (для Auto-режима туннель обычно
есть).

**Сбой проверки.** Ручная проверка пишет и показывает ошибку сразу (`updateFailed`, `warn`). Плановая, на
которую не ответил ни один путь, идёт в Стража (`onSvcFailed` → подозрение `svc.fetch`, `purpose:
appupdate`): `core/updateFailed` пишется только при вердикте `confirmed` и не повторно (`failures.md`);
`lastError` ставится в любом случае. Сбой из-за нашего перезапуска ядра молчит — ни события, ни `lastError`,
проверка повторяется, когда ядро устоялось.

## 5. Каналы и сравнение версий

- Каналы **stable** (по умолчанию) и **beta**. Стабильный пользователь манифест beta не
  видит. Бета-пользователь смотрит **оба** манифеста (beta и stable) и берёт **новейший**:
  чтобы не застрять ниже вышедшего релиза. Не ответил один из двух — результат второго.
- **Нет манифеста = пустой канал, а не ошибка.** Ответ `404` / `410` на сам `manifest-<канал>.json`
  (в канал ещё ничего не выпускали, например stable до первого релиза) — «up to date», без ошибки
  и со сброшенным `lastError`; в журнал уходит `core/updateChannelEmpty` (info, `{channel,
  attempts}`). Канал пуст, если хотя бы одна достижимая лента ответила 404/410, а остальные
  недоступны только по сети; неверная подпись / битый манифест на любой ленте остаются ошибкой, а
  если все ленты недоступны — `network`. `403`, 5xx и отсутствие `.sig` при живом манифесте — не «пусто».
- Порядок версий (`AppVersion`): semver (`0.3.0-beta.2` < `0.3.0`, числовые идентификаторы
  числом, а не строкой), при равном semver — по `build`. Новее ⇒ предложение; равная / более
  старая — «up to date».
- Релиз-инженеру: **номер `build` не повторяется и не уменьшается никогда**, даже между каналами.
  Beta `0.3.0-beta.1+14` → stable `0.3.0+15`.
- Один счётчик `build` на оба канала: CI берёт `3000 + номер запуска` единственного workflow
  `release-android.yml` (раздел 13), он только растёт. Версия beta выбирается так, чтобы стоять
  **выше последнего stable**: основа = большее из `X.Y.Z` из `pubspec.yaml` и «последний
  опубликованный stable с `patch + 1`» (после stable `0.1.0` беты идут `0.1.1-beta.N`; иначе
  бета-пользователь застрял бы ниже релиза: `0.1.0-beta.9` < `0.1.0`).
- Номер беты `N` считается **по основе**, а не по номеру запуска: самая новая бета в ленте
  (`manifest-beta.json`) той же основы + 1, иначе 1 (новая основа → `0.1.1-beta.1`); повторный
  запуск того же прогона (тот же `build`) сохраняет свой номер. Ведущих нулей нет (`beta.01` — не semver).
  Новая основа — поднять `X.Y.Z` в `app/pubspec.yaml`.
- Локальные сборки (`build_apk.ps1` без `-BuildName` / `-BuildNumber`) берут из ленты (оба манифеста)
  самый новый релиз R и собираются с `versionCode = R.build` и `versionName = <R.version>.dev`
  (`0.1.0-beta.4` → `0.1.0-beta.4.dev`; если R — stable или основа следующей беты выше R — то
  `<основа>-beta.0.dev`). Такая сборка встаёт `adb install -r` поверх CI-сборки R (равный versionCode
  ставится; понижения нет) и **ниже** следующей CI-беты (`0.1.0-beta.4.dev` < `0.1.0-beta.5`:
  сравнение идентификаторов `4 < 5`), так что её обновление предлагается; выше R, так что сам R
  не предлагается как «обновление». `.dev` — отдельный идентификатор (в `AppVersion` дефис внутри
  идентификатора недопустим).
- Android: `versionCode` APK **равен** `build` манифеста для всех ABI. Flutter при
  `--split-per-abi` по умолчанию прибавляет к versionCode смещение ABI (+1000 / +2000 / +4000) —
  его отключает `build_apk.ps1` при `-BuildNumber` (`force-version-code-ignoring-abi=true`), иначе
  проверка `versionCode == build` на платформенной стороне не сойдётся.

## 6. Проверка, расписание, состояния

- **Расписание** (`AppUpdater.startSchedule`): при запуске приложения (через 10 с, чтобы не
  мешать подключению) и затем раз в 24 ч, пока оно работает и включено «Auto-check». На Android
  фоновой проверки нет, пока процесса нет (WorkManager — «Фоновая проверка при закрытом процессе» ниже).
- **Check now** — вручную, всегда. Сбой ручной проверки — состояние «ошибка» с причиной; сбой
  по расписанию молчит (`lastError` — мелкая строка, событие уровня `info`).
- **Автоскачивание** (`genCfg.updAutoDownload`, раздел 11; `AppUpdater.setAutoDownload`): после
  проверки **по расписанию**, нашедшей `available`, ядро само запускает `download()`, если
  `always`, либо `wifi` и сеть не платная (`metered == false`). Включение настройки или смена
  `metered` на `false` при уже ожидающем `available` запускают загрузку тогда же; при выключенном
  «Auto-check» не качает вообще. `forced` — те же правила. Сбой автозагрузки молчит, как сбой
  проверки по расписанию: статус возвращается в `available` (предложение остаётся), причина — в
  `lastError`, событие `updateFailed` пишется, следующая попытка — по смене настроек / сети или
  со следующей проверкой; ручное «Download» работает как обычно. **Ставит только человек**:
  автоскачивание заканчивается на `ready`, установка — кнопкой Install или (Android) системным
  диалогом сразу после «Download & install», см. «Установка сразу после загрузки» ниже. `metered` приходит от
  платформы вместе с остальными настройками (`updateSettings {autoCheck, channel, autoDownload,
  metered}`): на Windows/десктопе всегда `false`; на Android — см. раздел 9.
- Проверка во время проверки — присоединяется к идущей. Скачанный, но не установленный файл не
  теряется при повторной проверке (остаётся `ready`).
- **Состояния** (`UpdateStatus.phase`, `toJson()` — для API): `idle` → `checking` → `upToDate` |
  `available` (предложение: версия, заметки, размер, `forced`, лента, путь) | `failed`; `available` →
  `downloading` (`received` / `total`) → `ready` (файл проверен) | `failed` (предложение остаётся,
  можно повторить). При запуске `restore()` поднимает уже скачанный и проверенный заново файл
  (`ready.json` в папке обновлений).
- **API** (когда `CoreService` будет готов; макет уже ходит через шов `backend`, раздел 12):
  `GET /api/update` → status; `POST /api/update/check` `{channel, manual}`; `POST /api/update/download`;
  `POST /api/update/cancel`. Установку jormd не делает — она платформенная.

### Установка сразу после загрузки

Политика живёт в приложении (`app/lib/core/update_flow.dart`, `UpdateFlow`; владелец — `HomeShell`),
ядро её не знает: нажатие различимо уже в `LiveCoreHost.downloadUpdate` (UI), а `AppUpdater.download()`
одинаково вызывается и кнопкой, и расписанием.

- **«Download & install»** (человек нажал сам): `LiveCoreHost.downloadUpdate` ставит флаг
  `updateInstallWanted`; когда фаза становится `ready` (файл скачан и проверен) и приложение на
  экране — файл сразу уходит установщику (`installUpdate`), системный диалог «Update» открывается без
  второго нажатия. Флаг гаснет при `ready`-установке, при `cancelUpdate` и если загрузка кончилась не
  `ready`. Кнопка **Install** в карточке остаётся: диалог закрыли / установщик отказал /
  разрешение «Install unknown apps» не выдано — файл в `ready`, нажать можно снова. Пока установщик
  занят (`updateInstalling`), кнопка заменена статусом «Installing…».
- **Загрузка кончилась, пока приложение за другим окном** (фаза `ready` при `inBackground`): диалог
  поверх чужого приложения не открываем. Вместо этого уведомление «Update X ready · Tap to install»
  с кнопкой **Install** (`UpdateNote.install`). Установка по флагу стартует, когда приложение вернулось
  на передний план (`onResumed`); кнопка Install работает и без приложения (см. ниже).
- **Кнопка Install уведомления «ready» не открывает приложение.** Уведомление несёт путь скачанного APK
  (`UpdateNote.file`; шлют и `UpdateFlow`, и фоновое задание), и кнопка — `PendingIntent.getActivity` на
  прозрачную `UpdateInstallActivity` (без окна, вне Recents; не приёмник: с Android 12 уведомление не может
  запускать activity из `BroadcastReceiver`/сервиса, а диалог подтверждения установщика требует приложения на
  переднем плане). Активность не доверяет уведомлению: `ReadyUpdate.verified` сверяет файл с `ready.json`
  рядом с ним (имя, размер, sha256), `UpdateInstaller` делает свои проверки (пакет, versionCode, сертификат),
  пишет `state.json → installing` (как `beginInstall`, чтобы следующий старт сказал `updateInstalled` /
  `updateFailed`) и открывает системный диалог тем же `PackageInstaller`-путём, что и приложение. Файла нет /
  не совпал / установщик ответил `verify` — открывается приложение на карточке обновлений (`ACTION_OPEN_UPDATE`).
  Отказ в диалоге или «Install unknown apps» снимают `installing` и оставляют уведомление — нажать можно снова.
  Тап по телу такого уведомления просто открывает карточку обновлений (без диалога); уведомление без `file`
  (старый путь) ведёт себя как раньше — кнопка открывает приложение, и `openedFromShade` запускает установку
  (нажатие в течение 5 с после автоустановки на возврате не спрашивает установщика второй раз).
  После замены пакета `ResumeReceiver` убирает устаревшее уведомление обновления.
- **Автоскачивание** (расписание) диалог не открывает **никогда**: никто не просил «ставить сейчас», а замена
  пакета обрывает VPN и перезапускает приложение (в самый неожиданный момент — посреди работы).
  В фоне — то же уведомление «Update ready · Install»; на экране — тихо, карточка с кнопкой Install и есть
  новость. (Явное решение: человеческое «Install» остаётся единственным способом поставить то, что скачано само.)
- **Ничего нового при старте.** Файл, восстановленный `restore()`, и предложение, уже лежавшее
  при старте, не считаются новостью; повторный `ready → checking → ready` той же версии не повторяет
  установку/уведомление (учёт «последней разобранной версии», а не переходов фаз).
- **Уведомление «Update X available»** — если новая версия найдена, когда приложение за другим окном
  (суточный тик процесса, который держит VPN): раз на версию, запись «объявлено» (`jorm_update/announced`
  в SharedPreferences, канал `updateAnnounced` / `setUpdateAnnounced`) общая для приложения и будущего
  фонового задания, поэтому одна версия не объявляется дважды. На экране — тихо.
- Оба уведомления подчиняются Settings → Notifications: мастер-выключатель и флаг `notifCfg.updateAvailable`
  (строка «New version», по умолчанию вкл).

### Фоновая проверка при закрытом процессе (Android)

Сделано (`app/android_overlay/kotlin/UpdateJob.kt.tmpl`, `app/lib/core/update_job.dart`,
`app/lib/platform/update_job_channel.dart`). WorkManager (`androidx.work:work-runtime-ktx`, зависимость
добавляет `apply_android_overlay.mjs`) держит `PeriodicWorkRequest` ~24 ч, `NetworkType.CONNECTED`, уникальную
работу `jorm-update-check` (`KEEP`; первый запуск — через сутки после регистрации, при каждом старте
приложение и так проверяет само). Воркер ничего не проверяет в Kotlin: он поднимает **второй, безголовый
`FlutterEngine`** с Dart-входом `updateJobMain` (`package:jormungand/core/update_job.dart`) и ждёт, пока
изолят скажет `done`. Изолят строит тот же `AppUpdater` (манифест, подпись, ленты, дельта) на папке
`<support>/core/updates` — той же, что у приложения, поэтому скачанное заданием поднимет `restore()` при
следующем запуске (`ready`) — и работает только по прямому маршруту (туннеля нет). `CoreService` не создаётся,
VPN не трогается: в движке задания только канал уведомлений (`NotifyChannel.register(primary = false)`:
не перехватывает `dart` у приложения) и `jormungand/updatejob`.

- **Настройки.** `LiveCoreHost._syncUpdateJob` при каждом реальном изменении шлёт `UpdateJobSettings`
  (`autoCheck`, `channel`, `autoDownload`, `notify` = мастер ∧ `notifCfg.updateAvailable`, `lang`) в канал
  `jormungand/updatejob` `sync`; Kotlin кладёт их в SharedPreferences `jorm_updatejob` и регистрирует работу
  либо снимает её при выключенном Auto-check. Остальное (версия/versionCode, ABI, APK установленного пакета,
  метрическая ли сеть — `NetworkChannel.isMetered`) Kotlin читает в момент запуска и отдаёт изолятору вместе
  с настройками (`input`): отзеркаленное устарело бы.
- **Пропуск.** Задание не делает ничего, пока процесс приложения жив (`AppEngine.isAlive` или работает
  `JormungandVpnService`) или Auto-check выключен. Если приложение поднялось во время запуска, Kotlin
  проверяет это каждые 2 с и сворачивает задание (недокачанное — `.part` — продолжит приложение); сам
  изолят тоже сверяется (`alive` во входе). Жёсткий предел — 9 мин (WorkManager режет около 10).
- **Что делает прогон** (`runUpdateJob`): `restore()` → `check(channel)` → при `available`: если
  автоскачивание разрешает (`always`, либо `wifi` и сеть не метрическая) — `download()` и уведомление «Update X
  ready · Install» (кнопка ставит без окна приложения, см. «Установка сразу после загрузки»); иначе, или если
  загрузка не дошла до конца, — «Update X available». «Объявлено» (`jorm_update/announced`) общее с
  `UpdateFlow`: «available» раз на версию, «ready» — всегда после скачивания в этом прогоне; готовый файл,
  найденный `restore()`, новостью не считается. Уведомления подчиняются `notify` (без них скачивание всё равно
  идёт, как у живого процесса). Диалог установки задание не открывает никогда. Язык — выбранный в приложении,
  иначе системный, иначе английский.
- **Сбои молчат, но пишутся.** Сбой проверки/загрузки, таймаут (8 мин в Dart) — без уведомления; строки
  прогона — в logcat (`JormungandUpdateJob`, `[update job]`) и в `<support>/update_job.log` (последние 80
  строк, вместе с событиями `AppUpdater`: `updateAvailable`, `updateFailed`…). В журнал приложения они пока
  не попадают.
- **После перезагрузки** WorkManager возвращает работу сам; **после замены пакета** `ResumeReceiver`
  (`MY_PACKAGE_REPLACED`) вызывает `UpdateJob.ensure` (JobScheduler мог потерять задание).
- **Проверять на телефоне:** `adb shell cmd jobscheduler run -f dev.jormungand.app <id>` (id задания —
  `dumpsys jobscheduler | grep jormungand`) при закрытом (смахнутом) приложении: в logcat `JormungandUpdateJob:
  started … done`, при новой версии в ленте — уведомление; при выключенном Auto-check работа исчезает из
  `dumpsys jobscheduler`.

## 7. Загрузка и проверки

В `<dataDir>/updates/` (на Android — приватная папка приложения; PackageInstaller получает файл
потоком, FileProvider не нужен):

1. Файл пишется в `<file>.part`. Остался `.part` от прошлой попытки — докачка заголовком
   `Range: bytes=N-` (ответ 206 — дописать; 200 — сервер не умеет, начать сначала; 416 — удалить
   и начать сначала). Обрыв соединения оставляет `.part` для докачки.
2. По ходу: тело не больше `size` (больше — ошибка `size`, файл удаляется); нет данных 30 с —
   обрыв.
3. В конце: длина == `size`, SHA-256 всего файла == `sha256` манифеста. Не совпало (`hash`) —
   `.part` удаляется, следующий адрес пробуется с нуля.
4. Файл переименовывается в `<file>`, пишется `ready.json` (предложение целиком), событие
   `updateDownloaded`.
5. Платформенная часть **ещё раз** проверяет перед установкой то, что может только она (ниже).

Размер установщика ограничен 600 МБ. Права: запись только в папку приложения. Ошибка диска —
`disk` (UI: «нет места / нет доступа»).

### Дельта-обновления

APK весит ~100 МБ, из них `libbox.so` (81 МБ) и `libflutter.so` (12 МБ) почти не меняются, а
`libapp.so` (9 МБ) и dex — каждый выпуск. Поэтому манифест может приложить к активу **патчи** от
прежних выпусков (`deltas`, раздел 2), и приложение качает патч вместо файла целиком.

**Формат патча** (наш, чистый Dart: `core/lib/src/delta.dart` — и генератор, и применялка, одни и те же в
CI и в приложении). В духе rsync: старый файл режется на блоки по 4 КиБ, у каждого слабый скользящий
хеш (Adler-подобный) и сильный (64 бита MD5); новый файл просматривается скользящим окном, совпавшее
окно → операция `COPY(смещение в старом, длина)` (соседние копии сливаются в одну; совпадение
продлевается назад по накопленным «новым» байтам и вперёд за последний блок), остальное — `LITERAL`.
Файл: заголовок (магия `JDLT`, версия формата 1, размер и sha256 старого, размер и sha256 нового) + gzip-поток
операций (`0x00` END, `0x01` COPY varint varint, `0x02` LITERAL varint байты). Всё потоком: генератор
держит индекс блоков старого файла (~16 байт на блок) и окно 1 МиБ, применялка — один кусок распакованного
потока и буфер копирования 64 КиБ; целиком файлы в память не читаются (на 50 МБ — десятки МБ RSS).
Что бы патч ни утверждал, результат пишется в `.part`, хешируется по ходу и обязан дать sha256 нового
файла (из заголовка **и** из подписанного манифеста); патч не к тому файлу, битый или обрезанный —
`DeltaException`. Замер на реальном APK arm64 (102,7 МБ): те же APK — патч 1 КБ; изменён весь
`libapp.so` (9,4 МБ, каждый блок) — 4,2 МБ (это его сжатый размер); 40 локальных правок — 9 КБ;
генерация ≈ 3 с, применение ≈ 1,2 с.

**Выбор.** Платформа сообщает ядру путь **установленного пакета** (`installedPackage`: на Android
`applicationInfo.sourceDir`, канал `jormungand/files` → `installedPackage`; на десктопе нет — всегда файл
целиком). При проверке (когда найден новый выпуск) ядро считает sha256 этого файла — **один раз**:
значение запоминается по `путь|размер|mtime` (в памяти и в `updates/installed.json`, перезапуск не
хеширует 100 МБ заново) — и ищет в `deltas` актива запись с `from` == хеш. Есть → предложение
(`UpdateOffer.delta`) отдаёт `delta: true` и `deltaSize` (в `size` остаётся размер файла целиком; UI
Settings → Data показывает размер патча). Нет (`from` не совпал, например локальная сборка, или пути нет) —
как раньше.

**Загрузка.** Патч качается по тем же правилам, что и файл (два круга, `urls`, докачка `.part`, размер и
sha256 патча из манифеста), прогресс `received/total` — по размеру патча. Затем применяется к
установленному файлу в `<файл>.new.part`, проверяются размер и sha256 результата (sha256 актива), файл
переименовывается в `<файл>`, патч удаляется. **Любая неудача** — нет совпадения / патч недоступен / битый /
не тот / результат не сошёлся / диск — **молча** переходит к загрузке файла целиком (статус
`downloading` перезапускается с `total` = размер файла; у `failed` предложение остаётся с патчем, повтор
сначала снова пробует патч) и пишет событие `updateDeltaFailed` (info). Отмена отменяет всё. Результат —
обычный `ready`-файл: проверки платформы перед установкой (Android: подпись, versionCode) те же, патч их
не обходит.

**Платная сеть** (Android): решает настройка «Auto-download» (раздел 6, 11): `wifi` — только
неплатная сеть. Платформа сообщает ядру `metered`; ручное «Скачать» всегда качает, что бы ни было
(человек нажал сам).

## 8. Принудительное обновление (`minSupported`)

Если запущенная версия ниже `minSupported` манифеста, предложение помечено `forced: true`.
Причины — несовместимость протокола с лентами, критичная уязвимость. UI: полноэкранный лист
«Update required» с Download & install вместо необязательной карточки. **Подключение VPN не
блокируется**: если ленты недоступны напрямую, пользователь должен суметь подключиться и
повторить (лист получает вторую кнопку «Not now», пока проверка не удалась; при удавшейся
проверке «Not now» нет). Если для устройства нет файла (`noAsset`) — лист показывает `page`.
(Решение по UX — предложено, ждёт подтверждения владельца.)

Замечание: `minSupported` защищён подписью, но «заморозка» старым манифестом скроет
принудительное обновление — известное ограничение (раздел 3).

## 9. Платформенная часть (Flutter) — спецификация

Интерфейс, который реализует приложение под каждую платформу (ядро о нём не знает):

```
UpdateInstaller
  canInstall()        -> bool            // Android: PackageManager.canRequestPackageInstalls()
  requestPermission() -> void            // Android: экран «Install unknown apps» для нашего пакета
  install(file, offer)-> InstallResult   // перед вызовом — AppUpdater.beginInstall()
```

Порядок для обоих: `AppUpdater.download()` → `ready` → кнопка Install → `beginInstall()` → установка →
после рестарта `reconcile()` (раздел 10).

### Android

- Манифест приложения: `REQUEST_INSTALL_PACKAGES`.
- **Первый раз** — «Install unknown apps»: `canRequestPackageInstalls()` ложно → перед системным
  экраном объясняем одной фразой («Android нужно разрешить Jormungand ставить свои обновления»),
  открываем `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` с `package:<наш пакет>`, после возврата
  проверяем снова; отказ — остаёмся в `ready` с подсказкой, файл не теряется.
- Перед установкой платформенная часть проверяет APK: `PackageManager.getPackageArchiveInfo(…,
  GET_SIGNING_CERTIFICATES)` — имя пакета == наше, `versionCode` == `build` манифеста и **больше**
  установленного, SHA-256 сертификата подписи ∈ `android.signerSha256` манифеста **и** равен
  сертификату установленного приложения. Не сошлось — не ставим, событие `updateFailed` (stage
  `verify`). (Android и так откажет с `INSTALL_FAILED_UPDATE_INCOMPATIBLE` — но мы говорим причину
  человеческим языком и ничего не показываем пользователю про «чужой пакет».)
- **Дельта-обновления.** Установленный APK ядру нужен как основа патча и для его выбора по хешу: канал
  `jormungand/files`, метод `installedPackage` → `applicationInfo.sourceDir` (читается самим приложением;
  это тот самый файл, что был установлен, побайтно — PackageInstaller копирует его как есть). Раздел 7 →
  «Дельта-обновления».
- **Платная сеть для автоскачивания.** Канал `jormungand/network` (`NetworkChannel.kt.tmpl`; Dart —
  `NetworkPort` / `NetworkChannel`, в тестах подменяется): `metered` и поток изменений
  (`NetworkCallback`). Наш VPN объявляет себя неплатным, поэтому `activeNetwork` при включённом
  туннеле врёт — смотрим **нижележащие** сети: неплатно = есть сеть с INTERNET, без TRANSPORT_VPN,
  VALIDATED и NOT_METERED; иначе (или не удалось узнать) — платная. `LiveCoreHost` читает значение
  при старте, слушает смены и шлёт ядру в `updateSettings {metered}`.
- **Установка** — `PackageInstaller`: `createSession(MODE_FULL_INSTALL)`, у параметров
  `setAppPackageName`, для API 31+ `setRequireUserAction(USER_ACTION_NOT_REQUIRED)`;
  `openWrite` ← потоком файл; `commit(IntentSender)`. Приёмник результата:
  `STATUS_PENDING_USER_ACTION` → запускаем `EXTRA_INTENT` (системный диалог: **одно нажатие
  «Update»**), `STATUS_SUCCESS` — процесс будет убит системой при замене, `STATUS_FAILURE_ABORTED`
  (пользователь отказался) и прочие → `AppUpdater.installFailed(причина)`.
- **Когда зовётся установка.** После «Download & install» — сразу, как только файл `ready` и приложение на
  экране (раздел 6 → «Установка сразу после загрузки»); в фоне и после автоскачивания — только по уведомлению
  «Update X ready · Install» / кнопке Install (у уведомления с файлом — `UpdateInstallActivity` без окна
  приложения, раздел 6). `UpdateInstaller` отвечает «busy», если диалог уже висит, —
  повторный вызов безвреден. Уведомления обновлений: канал `update` (общий с `ResumeNotifier`), id 4,
  тап — `ACTION_OPEN_UPDATE` (+`EXTRA_INSTALL`) → Dart `openUpdate` / `takeLaunchUpdate` при холодном старте →
  Settings → Data (+ диалог, если уведомление говорило «Install»); запись «объявлено» — SharedPreferences
  `jorm_update/announced`.
- **Без нажатия.** `USER_ACTION_NOT_REQUIRED` на Android 12+ может пропустить диалог, но
  только при выполнении набора условий системы (установщик-«хозяин» пакета, `targetSdk` не ниже
  31, обновление не понижает `targetSdk`, на новых версиях — владение обновлением и «приложение не
  в активном использовании»…), точный список зависит от версии Android и прошивки.
  **Рассчитывать на него нельзя; проверять на реальных устройствах** (Pixel и популярная оболочка
  — Samsung / Xiaomi). Базовый сценарий — одно нажатие пользователя; тихая установка — бонус.
- **Play Protect** на некоторых прошивках показывает «Проверить приложение» для неизвестного
  источника — это вне нашего контроля, упоминается в подсказке на экране.
- Замена приложения убивает процесс и вместе с ним VPN-сервис (трафик на время идёт напрямую; при
  системном «Always-on VPN» с блокировкой — не идёт вообще). Подключение возвращается само, без
  открытия приложения — раздел «Подключение после обновления» ниже («connect on launch» тут ни при чём).
- Приложение, запущенное после обновления, вызывает `reconcile()`.

#### Подключение после обновления (Android)

Запись «VPN был включён» хранит **нативная сторона** (SharedPreferences `jorm_resume`,
`ResumeAfterUpdate.kt.tmpl`: `ResumeStore`), потому что она должна быть верной и без Dart, и
переживать замену пакета:

| поле | кто пишет |
|---|---|
| `connected` | служба туннеля: `true`, когда libbox поднялся; `false` при любой явной остановке (кнопка дока, плитка, кнопка уведомления) и при `onRevoke` / неудачном старте. Это и закрывает **обновление вне приложения** (APK из браузера, `adb install -r`): отдельной «записи перед установкой» ему не нужно |
| `entry`, `fromCode` | Dart перед установкой (`LiveCoreHost.installUpdate`: сохраняет каталог, `ResumePort.save(connected: isOn, entry: effectiveConnectId)`), затем `UpdateInstaller` перед `commit` (`beforeInstall`: `fromCode` = старый `versionCode`, `connected` ИЛИ служба работает) |
| `armedAt` | приёмник `ACTION_MY_PACKAGE_REPLACED` (`ResumeReceiver`): ставит метку, только если `connected` и `versionCode` изменился. Нет замены — нет метки: **сбой или убийство процесса само по себе ничего не переподключает** |

Процесс, стартовавший без туннеля и без метки (`AppEngine.get` → `processStarted`), сбрасывает
`connected`: приложение, умершее само (краш, убийство системой), не считается «было включено» для
более позднего обновления. Явное отключение пользователем сбрасывает флаг сразу.

**Исключение — гонка «окно раньше приёмника».** Процесс может стартовать от Activity (кнопка
«Открыть» в установщике пакетов, тап по иконке или плитке) раньше, чем система доставит
`MY_PACKAGE_REPLACED`. Тогда `armedAt` ещё 0, и безусловный сброс стёр бы `connected`, а `arm()`
позже ничего бы не нашёл (так VPN не вернулся после beta.17 → beta.18). Поэтому `processStarted`,
увидев `connected` и `fromCode` ≠ текущего `versionCode` (запись от заменённой сборки), **сам ставит
`armedAt`**; сбрасывает только запись того же `versionCode` (краш / убийство) и просроченную метку
(старше 10 минут). `arm()` идемпотентен с этим: свежая метка остаётся как есть, повторного
взведения нет; если Dart уже взял запись (`take` гасит `connected`), приёмник ничего не взводит.
`AppEngine.startDart` на уже исполняющем Dart движке ничего не запускает (двойного старта нет), а
`take` отдаёт запись один раз, так что в любом порядке подключение одно.

**Журнал решений (`trail`).** Logcat на телефоне пользователя нет, поэтому `ResumeStore.note`
пишет в `jorm_resume` последние 30 строк «время, `vN` (versionCode), что решили и почему»: старт
процесса (оставил / взвёл / сбросил), приёмник (взвёл / нет и почему, Dart запущен / уже
работал), `take`, поднятие и остановка туннеля с причиной (`stop` / `revoked` / `start failed`),
`save` / `beforeInstall`, `onDestroy` службы, отпускание `goAsync` (и по какой причине).
`ResumePort.trail()` (канал `jormungand/resume`, метод `trail`) отдаёт их Dart, и
`LiveCoreHost.resumeAfterUpdate` на **каждом** старте пишет их в журнал приложения (Настройки →
Журнал, строки `[resume] …`), а следом итог `[resume] Dart: <ResumeOutcome>`. Если VPN после
обновления не вернулся, причина читается там: по строкам видно, кто и когда сбросил `connected`
(например `tunnel down (revoked)` или `process start … -> cleared`).

Порядок после замены:

1. `ResumeReceiver` ставит метку и **без окна** (запуск Activity из фона запрещён) поднимает движок
   процесса: `AppEngine.startDart` запускает Dart `main` на движке без вида. `main()` ждёт вид перед
   `runApp` (`ViewGate`, один запуск по первому из двух сигналов: метрики вида —
   `PlatformDispatcher.onMetricsChanged` — и нативное `windowAttached` из `MainActivity.onStart` по
   каналу `jormungand/resume`; ответ `attached` не теряется, если окно пришло раньше Dart), а ядро
   поднимает сразу (`resumeInBackground`). Приёмник держит процесс (`goAsync`) до подключения / сбоя / «готово» от
   Dart (не дольше 45 с) — права на запуск службы переднего плана из фона у него есть, пока
   идёт широковещательное сообщение.
2. `LiveCoreHost.resumeAfterUpdate`: `ResumePort.take()` отдаёт запись **один раз** (взятие её
   гасит — второго подключения не будет). Подключаемся, только если: `connected`; метка не старше
   10 минут (`resumeWindow`); `versionCode` сейчас ≠ `fromCode` (тот же код — не обновление; обычная
   переустановка `adb install -r` с тем же `versionCode` не возвращает VPN); VPN ещё не включён
   (`alreadyOn`: усыновлён туннель / идёт подключение). Тогда обычный `connect()` — **записи каталога
   достаточно**, чтобы выбрать тот же вход: активный вход / профиль / цепочка и режим хранятся в
   сохранённом состоянии; `entry` из записи — только для журнала и проверок.
3. Нет согласия VPN (`VpnService.prepare` не `null`, окна для диалога нет) — не подключаемся,
   показывается уведомление «Обновлено — нажмите, чтобы подключиться» (канал `update`, тексты —
   `jorm_notif_strings.xml`); тап открывает приложение с тем же запросом `connect`, что у плитки
   (согласие → подключение → приложение уходит назад). Согласие VPN обновление обычно переживает,
   так что это редкий случай. Уведомление снимается при подъёме туннеля.
4. После подключения Dart сам сообщает плитке и уведомлению VPN имя входа (окна, а значит
   `TileSync` / `SystemNotifier`, нет). Открытое позже окно подхватывает всё как обычно (движок уже
   исполняет Dart, `FlutterActivity` только подключает вид).

Имя входа в уведомлении VPN переживает **перезапуск** службы внутри того же подключения (новый план,
усыновление): `AppNotifier.vpnNode` сбрасывается не при каждом `leave()`, а только если новый старт
службы позже, чем через 15 с после остановки.

Подозрения без доказательств (по `trail` будет видно): система вызывает `onRevoke` у службы во время
замены пакета (тогда `tunnel down (revoked)` стёр бы флаг; в `Vpn.java` при замене не отзывает, но
не проверено); вендорский «убийца» убивает процесс до `startDart`; 45 с удержания `goAsync` меньше
времени запуска ядра на слабом телефоне (после этого запуск службы из фона уже не гарантирован).

Не проверено на устройстве: что запуск службы переднего плана из `MY_PACKAGE_REPLACED` разрешён на
всех версиях / прошивках; что движок без вида запускает `main` и вид потом подцепляется
(`onMetricsChanged` → `runApp`); поведение при убийстве процесса между приёмником и стартом службы
(вендорские «убийцы задач»).

**Windows.** Апдейтер (`jorm-updater.exe`, раздел «Windows» выше) и установка из приложения ещё не
написаны (`canInstallUpdate` = false), поэтому ничего не меняется: восстановление после обновления
только на Android. Когда появится, достаточно реализовать `ResumePort` файлом в каталоге данных
(`save` перед запуском апдейтера, `take` при старте нового приложения) — логика
`resumeAfterUpdate` общая.

### Windows

- Формат: `zip` (папка приложения целиком; ставится в `%LOCALAPPDATA%\Programs\Jormungand`,
  админские права для замены файлов не нужны) или `installer`. В этой спецификации основной путь —
  **zip + маленький апдейтер**; установщик (Inno Setup / MSI) — тот же вызов с `/SILENT`, если
  понадобится.
- Установка: приложение копирует `jorm-updater.exe` (маленький отдельный exe, в поставке) во
  временную папку (чтобы он мог заменить и самого себя) и запускает:
  `jorm-updater.exe --pid <pid приложения> --zip <файл> --sha256 <hex> --target <папка> --restart <exe>`,
  после чего приложение штатно завершается (системный прокси возвращается по обычным правилам
  выхода, kill switch — по своим настройкам; sing-box умирает вместе с приложением из-за Job
  Object, `core.md` → «Запуск»).
- Апдейтер: ждёт выхода процесса (до 60 с) и **exit всех процессов из `<target>`** (sing-box уже
  завершён Job Object'ом) → ещё раз проверяет sha256 zip → распаковывает в `<target>.new` → папки
  `<target>` → `<target>.old`, `<target>.new` → `<target>` (переименования на одном томе) → запускает
  приложение. **Любая ошибка на шаге замены** — возврат `<target>.old` на место и запуск прежней
  версии с `--update-failed=<причина>` (приложение пишет `updateFailed`, stage `install`).
- **Сторож**: новое приложение при успешном старте ядра пишет `updates/started.json`
  `{build}`; апдейтер ждёт этот файл 30 с, нет — откат на `.old` как выше; есть — удаляет
  `<target>.old` и заканчивает.
- Нет прав на запись в `<target>` (приложение лежит в `Program Files`) — апдейтер запрашивает UAC
  (`runas`). TUN-режим работает от администратора: процесс уже поднят — апдейтер наследует права.
- SmartScreen / Authenticode: файл скачан самим приложением (без Mark-of-the-Web) — предупреждения
  не будет; подпись кодом (Authenticode) — вне этого дизайна.

## 10. Сбои, откат, события

| ситуация | что происходит |
|---|---|
| нет лент / не отвечает ни одна (прямо и через туннель) | `network`; ручная — ошибка с «Retry», по расписанию — тихо |
| подпись не сошлась на всех лентах | `badSignature`: красная строка («Update information could not be verified»), ничего не качается |
| манифест новее формата | `schema`: «обновите вручную», `page` |
| нет файла для устройства | `noAsset` |
| скачивание оборвалось | `.part` остаётся, Retry докачивает |
| патч (дельта) не подошёл / не скачался / не применился | тихо: `updateDeltaFailed` (info), качается файл целиком, раздел 7 |
| размер / sha256 не сошлись | файл удалён, следующий адрес; все адреса — `failed` (`hash` / `size`) |
| Android: пользователь отказался в диалоге | `installFailed`: файл остаётся, статус `ready`, можно нажать ещё раз |
| Android: установка не удалась (`INSTALL_FAILED_*`) | `installFailed(причина)`, файл остаётся |
| Windows: ошибка замены | апдейтер откатывает `.old`, прежняя версия запущена, `updateFailed` stage `install` |
| Windows: новая версия не стартовала | сторож через 30 с откатывает на `.old` |
| приложение запущено, версия не выросла после `beginInstall` | `reconcile()` → `updateFailed` stage `install`; тот же файл можно ставить снова |
| версия выросла | `reconcile()` → `updateInstalled`, папка обновлений очищена |
| любой старт | `restore()` подметает папку: установщики, на которые не ссылается `ready.json` (обновились другим путём, вышла новее), и `.part` старше 3 дней; свежий `.part` ждёт докачки, `.json` не трогаются |

**Плохой релиз.** Понизить версию нельзя ни на Android, ни у нас. Если выпуск оказался плохим:
(1) убрать манифест с лент (или вернуть манифест предыдущей версии — не обновившиеся клиенты
перестанут его видеть), (2) выпустить исправление с **бо́льшим** `build`. Для раскатки
осторожно: сначала `beta`, потом `stable`.

**События журнала** (`cat: core`, `data` — только поля, как в `core.md` → «Журнал событий»):

| событие | когда | `data` |
|---|---|---|
| `core/updateAvailable` info | проверка нашла версию, которой раньше не предлагали (раз на версию) | `{version, build, channel, forced, via}` |
| `core/updateDownloaded` info | файл скачан и проверен | `{version, build, size, via}`; по патчу ещё `delta: true, downloaded` (байт патча) |
| `core/updateDeltaFailed` info | патч не удалось использовать (нет / не скачался / битый / не к тому файлу / результат не сошёлся / диск) — дальше качается файл целиком, раздел 7 | `{code: 'network'\|'delta'\|'disk', error, from, attempts?}` |
| `core/updateFailed` warn (`info` — тихая проверка по расписанию) | сбой проверки / скачивания / проверки файла / установки | `{stage: 'check'\|'download'\|'verify'\|'install', code, error, attempts?, from?, to?}` |
| `core/updateChannelEmpty` info | манифест канала отсутствует (404/410), раздел 5 | `{channel, attempts}` |
| `core/updateInstalled` info | после рестарта версия == цель | `{from, to}` |

Уведомления Android «Update X available» и «Update X ready · Install» (раз на версию, флаг
`updateAvailable` в `notifCfg`, строка «New version» в Settings → Notifications) — из процесса приложения,
когда оно за другим окном (`UpdateFlow`, раздел 6); при закрытом процессе их шлёт фоновое задание WorkManager
(раздел 6). Это не события журнала (`eventNotifKind` не меняется): тап открывает карточку обновлений в
Settings → Data, а не Logs.

## 13. Публикация

Инструменты ядра (`core/tool/`):

```
dart run tool/release_keys.dart <файл-приватного-ключа>     # один раз; ключ вне репозитория
dart run tool/release_manifest.dart --key <файл> --version 0.2.0 --build 12 --channel stable --out dist/ \
   --asset android-arm64-v8a=<apk> --asset android-armeabi-v7a=<apk> --asset android-x86_64=<apk> --asset windows-x64=<zip> \
   [--min-supported 0.1.5] [--notes-en n.en.txt] [--notes-ru n.ru.txt] \
   [--url-base https://…/v0.2.0]… [--signer-sha256 <hex>]… [--page https://…] \
   [--delta android-arm64-v8a=<патч>,<sha256 старого apk>]…

dart run tool/make_delta.dart <старый apk> <новый apk> <патч> [--block 4096] [--no-verify]
```

`make_delta` пишет патч (раздел 7 → «Дельта-обновления»), сразу применяет его к старому файлу и сверяет с
новым (`--no-verify` отключает) и печатает `from=` (sha256 старого — это `from` записи манифеста), `to=`,
`size=`, `sha256=` патча и `ratio=` (процент от размера нового). `--delta` (повторяемый) добавляет патч в
`deltas` актива той платформы, `urls` — по тем же `--url-base`.

`release_keys` пишет приватный ключ (base64 seed) в указанный файл — отказывается писать внутрь
любого git-дерева и поверх существующего файла — и печатает публичный ключ в виде готовой
константы для `releasePublicKeys`. `release_manifest` собирает актив из файла (размер, sha256, `kind`
по расширению), пишет `manifest-<канал>.json` и `.json.sig`, а перед записью **прогоняет те же
проверки, что приложение** (разбор манифеста + проверка собственной подписи).

Порядок выпуска (вручную; Android beta и stable делает CI — ниже):

1. Собрать APK (все ABI, `versionCode == build`) и zip для Windows.
2. `release_manifest` → два файла.
3. Выложить установщики по адресам из `--url-base` (или рядом с манифестом на каждой ленте).
4. Выложить `manifest-<канал>.json` и `.sig` **на все ленты**, `.sig` — вместе с манифестом (между
   ними подпись у клиента может не сойтись — неверная подпись считается сбоем ленты, клиент
   пойдёт на следующую).
5. Проверить с чистой установки / устройства («Check now»).

### Сборка и ключ Android APK

`pwsh app/tool/build_apk.ps1` (подробности — `app/README.md`) собирает по одному релизному APK на ABI
(`--split-per-abi`; `-BuildNumber` = `build` манифеста). Ключ подписи —
`%USERPROFILE%\.jormungand\android-release.jks` (alias `jormungand`). **Любая** сборка, локальная и CI,
подписывается им: режима «подпись debug-ключом» нет (APK с другой подписью не обновляется поверх —
debug- и релизный APK не уживаются на телефоне). Пароль: переменная `JORM_ANDROID_KS_PASS`, иначе
первая строка `%USERPROFILE%\.jormungand\android-release.pass`; скрипт его не печатает. Ключ **должен
быть сохранён**: другой ключ — другой подписант, и установка поверх невозможна; поэтому отсутствующее
хранилище — **ошибка**, а не повод создать новое (создаёт только явный `-NewKeystore`, один раз при
первой настройке). Создан 2026-10-04 со случайным паролем в `android-release.pass`; копии: секреты
GitHub Actions `JORM_ANDROID_KEYSTORE_B64` / `JORM_ANDROID_KS_PASS` (для CI, обратно не читаются) и
secrets-mcp с теми же именами (хост `backup-only.invalid` — только резерв). Перед сборкой скрипт
проверяет, что хранилище открывается с этим паролем и алиасом; в конце печатает SHA-256 сертификата —
его (hex в нижнем регистре, без двоеточий) кладут в `android.signerSha256` манифеста (`--signer-sha256`).
`-DryRun` печатает выбранные версию / versionCode и источник подписи (без секретов) и ничего не собирает.
С `-BuildNumber` (и по умолчанию, когда версию выбирает скрипт) он передаёт Flutter
`--android-project-arg force-version-code-ignoring-abi=true`: `versionCode` всех ABI равен `build`
(раздел 5), без смещений `1000 × ABI`. Другой файл ключа — `-KeystorePath` / `JORM_ANDROID_KEYSTORE`
(CI). Локальная версия по умолчанию — раздел 5 (поверх CI-сборки `adb install -r`, следующая CI-бета
всё равно предлагается); лента недоступна — запасная `<pubspec>-beta.0.dev` с versionCode из pubspec
(**не** встанет поверх CI-сборки: понижение), скрипт предупреждает; тогда задать `-BuildName` /
`-BuildNumber`.

### CI: Android beta и stable (`.github/workflows/release-android.yml`)

Один workflow, два канала; запуск определяет канал:

| событие | канал | версия |
|---|---|---|
| `workflow_dispatch`, поле `channel` (`beta` по умолчанию) | как выбрано | beta — `<основа>-beta.<номер>`, основа — раздел 5; stable — только с тега `vX.Y.Z` или основной ветки, версия = `X.Y.Z` из pubspec |
| push тега `vX.Y.Z` | **stable** | `X.Y.Z` из тега |

Пуши и мержи в ветки ничего не собирают: **beta выпускается только ручным запуском**, который ведущий
делает по явному подтверждению пользователя («деплой»):

```sh
gh workflow run release-android.yml --ref claude/karing-fork-environment-a45c2c -f channel=beta
```

Запуски одного ref и канала идут по очереди и не отменяют друг друга.

**Выпустить stable** (`pubspec.yaml` уже имеет `version: 0.1.0+…`, всё закоммичено в основной ветке):

```sh
git tag v0.1.0 && git push origin v0.1.0
```

Версия тега обязана совпасть с `X.Y.Z` из `app/pubspec.yaml` (иначе запуск падает в самом начале:
поднять версию, закоммитить, перенести тег) и быть **выше** опубликованного в ленте stable (равная
допустима только при повторном запуске того же run). Stable-релиз не удаляется чисткой. Тег ставить на
коммит основной ветки (CI собирает то, на что указывает тег; принадлежность ветке не проверяется).

Что делает (ubuntu-latest; JDK 17, Flutter 3.47.6, Go + gomobile + NDK 28.2.13676358 как в
`core/tool/build_libbox.ps1`, который работает и на Linux под `pwsh`):

1. `libbox.aar` — из кэша (ключ: версия sing-box, NDK, хеш `build_libbox.ps1`), при промахе собирается
   (`SING_BOX_VERSION` в workflow — держать равной версии `core/tool/bin/sing-box`).
2. Канал и версия (шаг «Channel and version»). `build` (versionCode) = `3000 + номер запуска`
   (`BUILD_OFFSET`) для **обоих** каналов: один workflow — один счётчик, он только растёт, коллизий
   нет; 3000 — выше любого `versionCode`, который давали локальные сборки. Опубликованный stable
   читается из `manifest-stable.json` ленты (404 — stable ещё нет; любой другой сбой — ошибка, а не
   «нет»); beta берёт основу = max(pubspec `X.Y.Z`, stable с `patch + 1`) — раздел 5.
3. `build_apk.ps1 -BuildName … -BuildNumber … -KeystorePath …` — три APK, подпись релизным ключом.
   Проверяется, что каждый APK подписан именно им (`apksigner`) и что `versionCode == build` (`aapt2`).
4. «Delta patches» (`continue-on-error`, ничто здесь не может провалить выпуск): для каждого ABI —
   патч от APK **последних `DELTA_FROM` (3) релизов того же канала**, которые ещё лежат в
   `jormungand-releases` (beta: пререлизы `v…-beta.N`; stable: обычные `vX.Y.Z`; не `feed`, не текущий;
   отбор по `createdAt`). Старый APK скачивается `gh release download`, патч — `make_delta.dart`
   (`jormungand-<версия>-<abi>-from-<старая версия>.delta`, с самопроверкой применением). Не скачался APK /
   не вышел патч / патч больше `DELTA_MAX_PERCENT` (60 %) от APK — этот патч пропускается с предупреждением.
   Оставшиеся — в `deltas.txt` (`<платформа>=<патч>,<sha256 старого apk>` на строку). Шаг идёт до публикации,
   а значит до чистки старых релизов (она после, оставляет 10 ≥ `DELTA_FROM`); патчи лежат в релизе своей
   версии и уходят вместе с ним.
5. `release_manifest.dart --channel <beta|stable>` с `--signer-sha256` (SHA-256 сертификата из keytool),
   `--url-base https://github.com/FuckingSherlock/jormungand-releases/releases/download/v<версия>` и
   `--delta …` на каждую строку `deltas.txt`, заметки — ниже, «Заметки к релизу».
6. Публикация через `gh` в **FuckingSherlock/jormungand-releases**: релиз `v<версия>` с APK
   `jormungand-<версия>-<abi>.apk` и патчами из `deltas.txt` (beta — prerelease, stable — обычный,
   `--latest`); релиз `feed`
   создаётся, если его нет; **после** APK в `feed` заливаются `manifest-<канал>.json` и `.sig`
   (`--clobber`). Чистка — только после beta: остаются 10 новейших beta-релизов
   (`^v\d+\.\d+\.\d+-beta\.\d+$`), старые удаляются вместе с тегами — `feed` и stable не трогаются.
7. «Announce in Telegram» (`continue-on-error`): анонс в Telegram-группу через Worker отчётов
   (`POST /v1/release`, `workers/reports/README.md` → «Анонсы релизов»): русские заметки (у beta — без
   строки-заголовка). Нет секрета `JORM_NOTIFY_TOKEN` → шаг пропускается. Повторный
   запуск того же выпуска (та же версия + build) второй раз не постит.

#### Заметки к релизу

Один текст и в приложении (карточка обновления, «What's new», `notes` манифеста), и в GitHub-релизе, и
в Telegram. Простой текст (приложение показывает его как есть), строки списка — `• `. Файлы — в
`release-notes/` (правила там же, `README.md`):

Шаг «Release notes» идёт до сборки (нет заметок — запуск падает за минуту, а не после сборки) и пишет
`notes.txt` (en) и `notes.ru.txt`; в манифест идут оба, в GitHub-релиз и Telegram — русский.

- **beta** — `release-notes/beta.txt`: **русское** саммари беты (тот же текст, которым ведущий сообщает
  пользователю, что вошло в сборку), для обоих языков. Ведущий **перезаписывает** его перед ручным запуском беты (коммит + пуш,
  затем запуск). Заметки = строка
  `Beta <версия> (build N, commit abc1234)` (в `ru` — `Бета … (сборка N, коммит …)`), пустая строка и тело —
  `.github/scripts/beta_notes.sh`: `beta.txt` как есть, если он менялся после коммита прошлой beta (он
  берётся из строки-заголовка `notes.en` в `manifest-beta.json` ленты). Файл — всегда полный текст с прошлой
  вышедшей beta, поэтому упавший запуск ничего не теряет, а правка текста не даёт дублей; прошлый коммит
  неизвестен — файл как есть.
  `beta.txt` с прошлой beta не менялся / пуст → **beta не выпускается** (ошибка с подсказкой: запушить
  саммари и запустить снова). Темы коммитов в заметки не идут.
- **stable** — `release-notes/X.Y.Z.ru.txt`, кратко обо всём, что изменилось с прошлого stable. Пишется в
  тот же проход, что русский перевод интерфейса (`docs/i18n.md`); без него stable не выпускается.
  `X.Y.Z.en.txt` пока не пишется (тестируют только русскоязычные): нет его — русский текст идёт и в `en`.

Секреты основного репозитория (Settings → Secrets → Actions):

| секрет | что |
|---|---|
| `JORM_ANDROID_KEYSTORE_B64` | base64 от `android-release.jks` (alias `jormungand`); в CI пишется во временный файл вне workspace и удаляется в конце |
| `JORM_ANDROID_KS_PASS` | пароль хранилища и ключа (одинаковый) |
| `JORM_RELEASE_KEY` | приватный ключ подписи манифеста (раздел 3; уже задан) |
| `JORM_RELEASES_TOKEN` | fine-grained PAT, `Contents: write` на `FuckingSherlock/jormungand-releases` |
| `JORM_NOTIFY_TOKEN` | необязательный: тот же случайный токен, что секрет `RELEASE_NOTIFY_TOKEN` Worker'а `jormungand-reports` (анонс в Telegram); в задании `gate` не проверяется |

Артефакты workflow не выкладываются. Один раз руками:

```powershell
# 1. хранилище ключа (если ещё нет %USERPROFILE%\.jormungand\android-release.jks); сделать копию вне репозитория!
$env:JORM_ANDROID_KS_PASS = '<пароль>'
pwsh app/tool/build_apk.ps1 -NewKeystore -BuildName 0.1.0 -BuildNumber 1   # создаст хранилище (только в самый первый раз) и соберёт APK
# 2. секреты
$ks = "$env:USERPROFILE\.jormungand\android-release.jks"
[Convert]::ToBase64String([IO.File]::ReadAllBytes($ks)) | gh secret set JORM_ANDROID_KEYSTORE_B64 --repo FuckingSherlock/JormungandApp
$env:JORM_ANDROID_KS_PASS | gh secret set JORM_ANDROID_KS_PASS --repo FuckingSherlock/JormungandApp
gh secret set JORM_RELEASES_TOKEN --repo FuckingSherlock/JormungandApp        # спросит значение токена
```

Получение beta на устройстве: Settings → Data → App updates → Channel = **Beta** (по умолчанию stable — в интерфейсе он подписан **Release** / «Релиз»,
внутреннее имя канала, файлы ленты и `updChannel` остаются `stable`;
бета-пользователь смотрит оба канала, раздел 5). Локальные сборки и CI-релизы подписаны одним
ключом и сосуществуют: локальная (`<версия CI>.dev`, раздел 5) ставится поверх CI-сборки, а следующий
CI-релиз — поверх локальной. Старый debug-подписанный APK (до перехода на единый ключ) поверх не
ставится — удалить один раз.

## 14. Ядро

`core/lib/src/appupdate.dart` (экспортируется из `jormungand_core.dart`): `AppVersion`,
`UpdateManifest` / `UpdateAsset` / `UpdateDelta` (`parse`, `toJson`), `chooseAsset`, `updatePlatforms`,
`verifyManifestSignature`, `UpdateGet` (шов HTTP; `httpUpdateGet(proxyPort:)` — настоящий),
`AppUpdater` (`check`, `download`, `cancelDownload`, `restore`, `beginInstall`, `installFailed`,
`reconcile`, `cleanup`, `startSchedule`, `changes`), `UpdateStatus` / `UpdateOffer` /
`UpdateException` (`UpdateError`). `appupdate_release.dart` — сторона издателя (ключи, подпись,
сборка актива); пакетом не экспортируется, им пользуются `tool/release_*.dart`. Зависимость:
`cryptography`.

`core/lib/src/delta.dart` (тоже из барреля): `makeDelta(oldPath:, newPath:, outPath:, blockSize:)` →
`DeltaStats`, `applyDelta(oldPath:, patchPath:, outPath:, expectOldSha256:, expectNewSha256:)` →
`DeltaHeader` (`DeltaException` на любой патч, который нельзя применить; выход при ошибке удаляется),
`readDeltaHeader`. `CoreService(installedPackage:)` → `AppUpdater(installedPackage:)` — путь установленного
пакета (Android: `applicationInfo.sourceDir`; `platform_seams.dart` берёт его у канала `jormungand/files`, метод
`installedPackage`); без него дельт нет.

Как подключить `CoreService`: `AppUpdater(dir: <dataDir>/updates, current: <версия приложения>,
platforms: updatePlatforms(os:, abis:), get: httpUpdateGet(proxyPort: () => <_innerPort>),
tunnelUp: () => <_innerPort> != null, onEvent: (type, level, data) => events.add('core', type, level, data))`;
при старте — `reconcile()`, потом `restore()`, `startSchedule(autoCheck: () => genCfg.updates,
channel: …)`.

Тесты (`core/test/appupdate_test.dart`, только loopback): порядок версий; разбор манифеста и все
отказы; подпись (верная / подделанный манифест / чужой ключ / мусор / смена ключа); выбор актива;
фолбэк лент (мёртвая / 404 / неверная подпись → следующая; прямо → туннель; туннель не пробуется без
туннеля); каналы; `minSupported`; загрузка (sha256, размер, докачка с Range, сервер без Range, обрыв,
отмена, диск); перезапуск (`restore`, `reconcile`); расписание; автоскачивание (off / wifi / always,
платная сеть → неплатная, Auto-check выкл., тихий сбой и повтор); дельты (манифест с `deltas` и отказы,
патч выбран по хешу установленного файла и применён вместо загрузки файла, докачка патча, другой
установленный файл / нет пакета → целиком, битый / чужой / не тот патч / 404 / мусор → тихий откат на
файл целиком); настоящий `httpUpdateGet` через loopback-прокси.
`core/test/delta_test.dart`: генератор и применялка на синтетических файлах (одинаковые, сдвиг, середина,
дописанное, пустой старый / новый, короче блока, нули, случайные правки, разные размеры блока), отказы
(битый байт, обрезка, не патч, версия, чужая база, другой хеш), поток 50 МБ с ограничением памяти.

## Открытые вопросы

- Решено: лента — публичный репо `FuckingSherlock/jormungand-releases` (релиз `feed`), другие
  (Cloudflare R2…) — потом; ключ — см. раздел 3; Windows — zip + `jorm-updater.exe`, который
  запускается только для замены файлов (не висит в фоне: проверку делает ядро в приложении, когда
  приложение закрыто — обновлять некому); Android — фоновая проверка через WorkManager, без
  отдельного процесса.
- Тихая установка на Android 12+ — проверить на устройствах.
- Фоновая проверка на Android (WorkManager) и кнопка Install без окна приложения сделаны (раздел 6); на
  устройстве не проверены (Doze/ограничения фона производителей, подтверждение установщика поверх прозрачной
  activity). Строки `update_job.log` пока не попадают в журнал приложения.
- Принудительный лист (раздел 8): окончательное решение по UX.
