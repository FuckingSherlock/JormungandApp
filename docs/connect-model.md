# Модель подключения: источники, профили, цепочки

Что из макета (`design/src/js/`) нужно перенести в логику приложения. Макет — эталон
поведения; этот файл — его описание для бэка (Dart-сервисы + сборка конфига sing-box).
Обновлять при каждом изменении логики в макете.

---

## Сущности

| Сущность | Поля (макет) | Смысл |
|---|---|---|
| **Source** | `kind: sub \| node \| file`, `enabled`, `nodes[]`, `gone[]`, `offNodes[]`, `disabledNodes[]`, `updateInterval`, `inAuto`; у `sub` ещё настройки формы (`url`, `userAgent`, `hwid`, `filter`, `channel`, `reloadAfterUpdate`, `testAfterUpdate`…) и серверные поля (`uaStrategy`, `discoveredAt`, `usage`, `expire`, `format`, `providerInterval`, `webPage`, `supportUrl`, `announce`, `updatedAt` — пишет только ядро, см. subscription-parsing.md); у `file` — `name`, `nodes[]`, `format`, `updatedAt` (время импорта) и общие переключатели, без `url` | Подписка (`sub`), ручной набор серверов (`node`) или серверы из импортированного файла (`file`, см. «Локальный источник»). Живёт на вкладке Nodes. |
| **Node** | `id`, `protocol`, `address`, `port`, креды, `flag`, `name` | Один сервер (outbound sing-box). |
| **Profile** | `sources[]`, `nodes[]` (`sid::nid`), `inAuto` | Режим «Профили»: набор целых источников и/или отдельных нод. |
| **Chain** | `inId`, `outId`, `inOff[]`, `outOff[]`, `inOn[]`, `outOn[]`, `exitMode`, `exitOrder[]`, `inAuto` | Вход (первый хоп) → выход. Концы — «юниты» активного режима. |

`sid::nid` — ключ ноды внутри источника (в макете `refKey`).

## Идентичность ноды

`node.id` = идентичность **варианта сервера**, а не позиция в списке. Новая нода получает
id = `key` (сервер + вариант подключения, см. `subscription-parsing.md` → «Дедупликация
нод»). Имя в ключ не входит. Если провайдер поменял у сервера вариант (SNI, fingerprint…),
нода сохраняет старый id, когда это однозначно: у сервера (`base`) ровно одна
несопоставленная старая нода и одна новая. Иначе новая — это новая нода, старая уходит в
`gone`. Сопоставление делает ядро при слиянии обновления (`core/lib/src/merge.dart`).

Все настройки ссылаются на `id`: `offNodes`, `disabledNodes`, `profile.nodes`, `chain.inOff/outOff/inOn/outOn/exitOrder`.
Поэтому провайдер может перетасовать или переименовать ноды — выбор пользователя не съедет.

## Пропавшие ноды (`gone`) — кэш выбора

При обновлении подписки нода, которой больше нет в ответе, **не удаляется**, а
переносится в `source.gone[]` с `goneAt`. Настройки, которые на неё ссылаются, не трогаются.

- Нода вернулась в следующем обновлении (тот же `id`) → переезжает обратно в `nodes[]`
  и сразу оказывается с прежней галочкой и на прежнем месте в приоритете выхода.
- Новая нода (раньше не было) → включена, в приоритете выхода — в конце.
- В UI пропавшие ноды показываются свёрнутым блоком «Unavailable · N» везде, где есть
  список нод (Nodes, настройка источника, редактор профиля), только для чтения, с
  сохранённым состоянием галочки. В редакторе цепочки блока нет (решение пользователя):
  выход и вход показывают только живые серверы; сохранённые `inOff` / `outOff` пропавших
  остаются в данных до их возврата или забывания.
- **Срок хранения — 15 дней на каждый сервер отдельно** (`GONE_KEEP_DAYS`), от его
  собственного `goneAt`. Истёкшие вычищаются вместе с настройками (`purgeExpiredGone`) при
  старте и после каждого обновления. В строке — «N d left» (≤ 3 дней — жёлтым).
- `gone` хранится в объекте источника: удалили источник — пропавшие и их настройки
  удаляются вместе с ним.
- **Forget all** (в Nodes) удаляет все `gone` источника; тап по строке пропавшей ноды —
  меню с «Forget now» для неё одной. Оба вычищают её `id` из всех настроек
  (`purgeNodeSettings`).
- Групповые действия (All / None, перетаскивание приоритета) меняют только живые ноды;
  записи пропавших остаются на своих местах (`dragShown` в `80-drag.js`).

## Источник или сервер, выключенный в Nodes

Два переключателя на вкладке Nodes: у источника (`enabled`) и у каждого сервера
(`source.disabledNodes[]` — id выключенных). Оба **никогда не меняют настройки** тех, кто
их использует: включил обратно — источник / сервер снова в тех же профилях и цепочках, с
теми же галочками и приоритетом.

UI выбора серверов везде одинаковый — без чекбоксов и тумблеров: используемый /
выбранный сервер **обведён рамкой**, тап переключает. Галочка целого источника в
редакторе профиля осталась (у неё есть состояние «частично»).

**Режим редактирования** (чтобы в обычном виде нечего было задеть случайно):
- Nodes: кнопка ✎ слева от вкладок Simple / Profiles, в правке — ✓.
  Обычный вид: без ⋮⋮, тумблеров и рамок; тап по
  серверу — его меню, тап по мс — пинг; выключенные приглушены, у выключенного источника
  метка OFF. Режим правки: ⋮⋮ источников, тумблер источника, рамки у серверов, тап по
  серверу — вкл / выкл. Шапка не меняется: поиск, «пинг всех», ⋮ и «+» доступны и в правке.
  Цепочки (на обеих вкладках) в правке: ⋮⋮, у каждого конца — все его серверы в рамках, тап —
  вкл / выкл только для этой цепочки (`inOff` / `outOff`, как галочки в редакторе цепочки).
- Строка под именем источника — коротко, чтобы редко переносилась: формат · «18 nodes» · возраст
  обновления («2h», «1d»). Если есть нерабочие (выключенные или пропавшие из подписки) —
  «16/18 nodes»: рабочие / все. Если не влезает, переносится между пунктами, а не обрезается.
- Route: режим правки — ✎ слева от Simple / Profiles (✓ пока включён; при каждом открытии
  выключен). В правке видны ⋮⋮ записей, а в развёрнутой строке — переключатель Fastest /
  Priority и ⋮⋮ серверов; без правки их нет, строка лишь подписывает, как выбирает сервер
  (номера в Priority видны всегда). Случайно закрепить запись нельзя — закрепляет только
  кнопка AUTO / MANUAL на строке, тап по карточке лишь разворачивает её.
- Редакторы записи / профиля / цепочки отдельного режима не имеют.

Выключенный сервер остаётся в Nodes (без рамки, приглушён и зачёркнут, в мете «N off»), а
везде остальном его нет: в записях, в редакторах профиля / источника / цепочки, в выборе
ноды, в Auto, в «пинговать все». Групповые действия (All / None, перетаскивание) его
галочку и место не трогают. Для остального приложения источник = `liveNodes(s)`.

Пока выключен:
- его собственная запись в режиме «Простой» скрыта, в пикерах цепочек его нет;
- запись / профиль / сторона цепочки, у которых без выключенного **не осталось ни одной
  ноды**, — «сломанные» (`brokenBy(id)` — что включить: `{sid}` источник или
  `{sid, nid}` сервер; считается как «живых нет, а со всем включённым в Nodes — есть»):
  серые, с красной рамкой, тег OFF, под списком (место в приоритете хранится), Auto их
  пропускает, закреплённая вручную такая запись — ошибка подключения (Manual строгий, см. «Manual на запись»), не подмена Auto. Тап — объяснение «то, через
  что она работает, выключено в Nodes» + «Switch on X» для каждого + «Edit …»;
- в Простом режиме запись источника, у которого выключены все отмеченные для неё
  серверы, тоже «сломанная»;
- профиль, у которого есть другие рабочие источники, работает на них без пометки;
- в редакторе профиля выключенный, но используемый источник показан серым
  («off in Nodes»), галочкой его можно только убрать; если профилю без выключенных нечего
  использовать — жёлтое предупреждение с их именами, сохранение заблокировано; в
  редакторе цепочки так же для каждого конца.

Разница с галочками записей: выключение в Nodes — глобальное («этот сервер мне сейчас не
нужен нигде»), галочки (`offNodes`, `profile.nodes`, `inOff/outOff`) — выбор конкретной
записи.

### Сервер, выключенный в подписке, но включённый для цепочки (`inOn` / `outOn`)

Серверы, которые собственный редактор подписки выключил (`offNodes`, «N off» в Nodes), редактор
цепочки раньше не показывал. Теперь у конца-источника (у профиля `offNodes` не читается — блока
нет) под списком серверов — свёрнутый по умолчанию блок «Disabled in subscription · N» (N — ещё
не включённые). Тап по строке включает сервер **только для этой цепочки**: ключ `sid::nid` идёт в
`chain.inOn` / `chain.outOn`, сервер переезжает в основной список конца (рамка, порядок Priority)
и входит в группу: план (`entry` / `main`), Auto, пары и пинг, развёрнутая строка Route
(`chainEntryRefs` / `chainExitRefs` / `chainExitOrder` = серверы юнита + `chainForcedRefs`).
Тап по такому серверу в списке возвращает его в блок (ключ уходит из `inOn` / `outOn`); All /
None его не трогают. В самой подписке, в Simple / профилях (`unitRefs`) и в Nodes он остаётся
выключенным. Серверы, выключенные глобально в Nodes (`disabledNodes`), сюда не попадают.
Цепочка, у которой на конце остались только такие серверы, валидна.

Живёт по идентичности ноды: переживает обновление подписки; пока провайдер сервер убрал
(`gone`), в группе его нет, ключ хранится и возвращается вместе с ним; забывается вместе с
остальными настройками (`purgeNodeSettings`: истёк срок `gone`, Forget, удаление ноды / источника).
Если сервер снова включён в подписке, ключ в `inOn` безвредно лежит (в группе он уже есть);
выключат снова — вернётся в цепочку. Смена / обмен концов: ключи едут / забываются как `inOff` /
`outOff`. В снимок и бэкап пишутся только непустыми.

## Подписка не загрузилась

Первая загрузка или обновление подписки упали → на карточке источника красная полоса
(SourceErrorStrip): «Could not load» (серверов ещё нет) или «Update failed» + сколько
назад, текст ошибки и **Retry**. Хранится с источником (`s.lastError = {msg, at}`,
переживает перезапуск), снимается следующей удачной загрузкой. Неудачное обновление по
таймеру ядра пишет его так же (subscription-parsing.md → «Автообновление»). Серверы прошлой удачной
загрузки продолжают работать. Retry = обновление; источник, который ни разу не
загрузился, загружается заново как новый.

## Сервер вручную, ссылка сервера, QR

Форма сервера (Nodes → + → Server; ✎ сервера в ручной группе):
- **Share link** — многострочное поле: ссылка заполняет поля ниже; несколько ссылок
  (по одной на строку) — вместо полей подпись «N servers» и кнопка «Add N servers»,
  добавляются все, каждая со своим именем из `#фрагмента`. Разбирает ядро (тот же парсер,
  что у подписок): vmess base64-JSON, ss legacy и SIP002, IPv6 в скобках, anytls, hy2 с
  диапазоном портов. Со ссылкой адрес вручную не нужен («Address is required» — только без
  ссылки).
- **Без ссылки** — протокол (VLESS, VMess, Trojan, SS, HY2, TUIC, AnyTLS, SOCKS), адрес,
  порт и секрет; подпись поля секрета по протоколу: UUID; Password; Method:password (ss);
  UUID:password (tuic); User:password, необязательно (socks). Outbound строит ядро
  (`manual.dart`). Имя, набранное руками, важнее имени из ссылки; флаг в нём уходит во флаг.
- **Один сервер дважды**: id — хэш сервера, в группе он один раз; повтор не добавляется
  («already in the group», при пачке — «Added N, M already there»).
- **Правка** меняет адрес / порт / секрет / имя и **outbound** (тот же протокол: TLS,
  транспорт, flow сохраняются), а id остаётся прежним — профили, цепочки, закрепление и
  правила со ссылкой на сервер не теряют его. Пинг — уже по новому адресу (кэш по серверу).

⋮ источника: **Copy URL** — URL подписки в буфер обмена; **Show QR code** — QR этого URL.
⋮ сервера: **Copy share link** / **Show QR code** — ссылка сервера (ядро, `share.dart`:
vless/vmess/trojan/ss/hy2/hysteria/tuic/anytls/socks); у http / wireguard и `unsupported`-серверов ссылки нет —
тост вместо копирования. QR-лист (ShareSheet): код тёмным по светлому в любой теме, под ним
текст (выделяется тапом) и Copy.

## Локальный источник (импорт файла)

Nodes → «+» → **Import config file** (на Simple; на Profiles такой строки нет — профиль собирается из
уже существующих источников). Пользователь выбирает файл; ядро (`localsource.dart`, `addSourceFromText`,
`POST /api/sources/import`) читает его тем же разбором, что тело подписки (`subscription-parsing.md` →
«Детектирование формата»: sing-box JSON, Clash YAML, список ссылок обычный или в base64), и из серверов
получается **локальный источник** — `kind: 'file'`:

- **Без URL и без обновления.** Нет `url`, `userAgent`, `filter`, `updateInterval` и т.п.; таймер ядра его не берёт
  (`autoUpdatePeriod` — только `sub`), на карточке нет кнопки Update / ⟳ в Route, нет полосы ошибки загрузки, строки
  расхода трафика, пунктов ⋮ «Copy URL» / «Show QR code» / «Update with all user agents». Сохранение из UI не сливается с
  версией ядра (это только для `sub`). Вызов `fetchSource` для такого источника — ошибка «import the file again».
  **Изменить его можно только новым импортом** — это новый источник; прежний пользователь удаляет сам (серверы с тем же
  `id` в разных источниках независимы: ссылки идут по `sid::nid`).
- **Серверы** — как у подписки: те же `id` (`Идентичность ноды`), дедупликация по `id` (первый из совпавших остаётся),
  нумерация одинаковых имён (`VK-1`, `VK-2`), флаг из имени, ноды без поддержки sing-box — в списке с `unsupported`.
  Файл хранится не телом, а разобранными `nodes[]` (как у любого источника: снимок живёт офлайн, `outbound` готов к
  конфигу); `gone` всегда пуст — серверы пропадают только вместе с источником.
- **Имя** — имя файла без расширения (`.json` `.yaml` `.yml` `.txt` `.conf` `.list`; другие точки остаются; пусто —
  «Local file»), правится как у любого источника: ⋮ → **Rename** (форма только с именем, как у ручной группы).
  Источник включён и в Auto сразу (`enabled`, `inAuto`), встаёт в конец вкладки Simple.
- **Карточка**: метка `local file` (вместо формата; формат — во всплывающей подсказке «Read as …»), число серверов,
  возраст импорта (`updatedAt`). ⋮: Rename, Route settings, Delete. Серверы ведут себя как у подписки: свои меню,
  включение / выключение, пинг, Route, профили, цепочки, правила.
- **Ошибка** — ничего не распознано (или файл больше 16 МБ): тост «Could not import <файл>: No servers found in the
  file», источник не добавляется, снимок не меняется (`FormatException` ядра, 400 у `jormd`).
- **Снимок и бэкап.** Источник — обычный элемент `sourcesData` / `sourceOrder`, поэтому `ui-state.json`, **Export backup**
  (`snapshot` целиком) и **Restore** несут его без отдельной логики; `Catalog` Dart-модели читает и пишет `kind: 'file'`
  как есть.
- **Удаление** — то же подтверждение «This will affect» (`deleteSourceImpact`), текст «The imported file and its N
  servers are removed».
- Идентификатор источника выдаёт владелец каталога (мокап: `src<N>`; приложение — `Catalog.addSource`): ядро возвращает
  источник без `id`.

## Удаление источника / сервера

Всегда с подтверждением. В нём — что станет с каждым, кто это использует (`deleteImpact`:
списки обоих режимов пересчитываются «как будто этих серверов нет», `simExclude`):
- текущее подключение идёт через удаляемое → переподключится через следующий рабочий;
- цепочка, у которой удаляемый источник — конец → удаляется вместе с ним (красным);
- запись / профиль / конец цепочки остаётся без серверов → не подключится, пока не
  отметить другой (красным);
- профиль теряет N из M серверов; цепочка: «вход / выход теряет N» (для Priority-выхода —
  «выпадает из порядка приоритета») (жёлтым);
- правила и приложения, у которых цель — удаляемое (источник, его нода, цепочка, которая
  удаляется вместе с ним) → «loses its target — traffic goes …» по их «If unavailable»
  (`targetImpact`, см. `rules.md` §0) (жёлтым);
- ничего не затронуто → «Not used in any profile, chain, rule or app».

Удаление профиля / цепочки — кнопкой Delete внутри их редактора (✎ на карточке), тоже с подтверждением
(`confirmDeleteEntry`): цепочки, у которых удаляемый профиль — конец, переезжают на первый
другой профиль (если оба конца совпали — удаляются); правила с этой целью — как выше.
Последний профиль тоже удаляется (его цепочки — вместе с ним): «нет профилей» — обычное
состояние, док пишет «No profiles yet · Create one in Nodes» (см. «Главный экран»).
После удаления все настройки, ссылающиеся на эти серверы, удаляются насовсем (включая
`gone` удаляемого источника). Ноды подписки не удаляются по одной (вернутся при
обновлении) — для них есть выключение.

## Каталог (Nodes) и Route

Всё, куда можно слать трафик, создаётся, редактируется и удаляется **только в Nodes**. У Nodes
две вкладки — каталог двух режимов (`catalogOrder`):
- **Simple** (`simple`): подписки, группы серверов и цепочки из двух источников;
- **Profiles** (`profiles`): профили и цепочки из двух профилей.

Вкладки переключаются тапом или свайпом всего списка (палец ведёт список, >20% ширины —
переключение; начинается только при явно горизонтальном движении; не ближе 24 px к краю
экрана — там жест «назад» Android). Вкладка — только просмотр: режим маршрута она не меняет;
точка на вкладке — режим, который сейчас использует Route. «+» на Simple — подписка /
сервер / цепочка, на Profiles — профиль / цепочка. Карточки профилей и цепочек: из чего
состоит, через какой сервер пойдёт сейчас и пинг (цепочка — вход → выход и сумма), раскрытие —
её серверы; на карточке прямо кнопки ⚡ (пинг) и ✎ (редактор; Delete — внутри редактора), без меню ⋮. У источника в ⋮ — «Route settings»
(серверы этой записи, Fastest / Priority, в Auto). ✎ — перетаскивание порядка внутри вкладки.

**Route** (бывший список Simple / Profiles, открывается с главной) отвечает только за
основной поток. Лист открывается над нижним блоком: доходит до верхней кромки дока, низом
уходит под вкладку с кнопкой питания; док и нижняя навигация остаются поверх и работают
(тап по доку закрывает Route, переход на другую вкладку — тоже). Под шапкой — переключатель режима Simple / Profiles (анимированный:
подсветка переезжает, список въезжает с той же стороны). **Переключатель только показывает режим**
(как вкладки Nodes): точка у названия — режим, по которому Route идёт сейчас; тап по другому режиму
ядро не трогает. У показанного, но не используемого режима сверху плашка «The route uses X now» с
кнопкой **Use this mode** (`setConnectMode` — только она меняет режим и перезапускает подключение,
как раньше) и список его записей только для чтения; ✎ и бейдж Auto / Manual в шапке при этом
недоступны / скрыты (они про режим в работе). Режим, в котором нечего подключать
(`Catalog.modeEmpty(mode)`: нет видимых записей — профилей / источников), активировать нельзя: вместо
кнопки пустое состояние «No profiles yet» (Simple — «No servers yet») и кнопка **Create profile**
(Simple — «Add subscription or server»), она закрывает Route и открывает Nodes на «+» этой вкладки —
тупика нет. Тот же пустой экран у используемого режима, если он опустел. В шапке — бейдж Auto / Manual.
Строка: ⋮⋮ (перетаскивание приоритета, только в режиме правки ✎) · карточка · ⚡ справа — пинг
всех серверов записи (всегда, и в правке). Строка названия карточки начинается с кнопки
AUTO / MANUAL (одной ширины, на всех строках на одном месте), за ней в правке — тумблер
«Use in Auto» (без правки вместо него у выключенной записи бейдж «not in Auto»), потом
название. Шеврона нет — разворачивает тап по карточке. Флаг в строке мелкий, справа только
⚡ — чтобы влезало больше имени ноды. Флаг везде — часть имени ноды: длинное имя переносится
под флаг, а не рядом с ним; пинг в шапке строки стоит на уровне первой строки имени. Кнопка на текущей строке показывает режим (AUTO / MANUAL,
подсвечена), на остальных — MANUAL приглушённо; тап по ней на другой строке закрепляет
её (Manual), на закреплённой — возвращает Auto. Тап по карточке разворачивает её (у
цепочки раскрытие только для чтения, как в Nodes: «Entry · имя» и «Exit · имя» с серверами
каждой стороны, текущий отмечен, пинг как в каталоге, тап по серверу — пинг; закрепления
сервера и правки у цепочки в Route нет; развёрнутые строки независимы — раскрытие одной не сворачивает другие): Fastest / Priority (только в правке; без неё — подпись режима), серверы (в
Priority с номерами, ⋮⋮ — в правке). **Кнопки на карточке** (Flutter): ⟳ обновить стоит
постоянно рядом с ⚡ (у подписки; у профиля — все подписки, из которых он берёт серверы; ручные
группы, локальные файлы и цепочки не обновляются, кнопки нет), не только в развороте; кнопки действий
(⚡, ⟳, ✎, ⋮ в Route и Nodes) — цель нажатия 48 dp, иконка 22 dp (`IconBtn(large: true)`).
**Недоступные в развороте** (только Route, не Nodes): серверы, про которые известно, что они
мертвы (`knownDead`; у выходов цепочки — по паре, `chainExitKnownDead`), уходят из основного списка
в блок «Unavailable · N» (вид как у «removed by provider»): первые 2, «Show all N» раскрывает
остальные, «Show less» сворачивает; рабочие и ещё не измеренные остаются в списке в обычном порядке
(при перетаскивании Priority в правке список целиком). **Manual на сервер**: тап по серверу развёрнутой строки —
Manual на эту запись и на этот сервер (`pinnedNode` = `sid::nid`, подсвечен как бейдж MANUAL);
соединение идёт только через него, без failover, даже если он не отвечает. Повторный тап —
закрепление сервера снимается, запись остаётся Manual и выбирает по Fastest / Priority. Любой
другой выбор (другая запись, AUTO / MANUAL, бейдж Auto) снимает закрепление сервера. Для ядра —
`selector`, удерживаемый на нём (`default` = закреплённый сервер).
**Закрепление строгое: туннель идёт только через выбранный сервер, работает он или нет, и ни через
какой другой.** Потеряно закрепление — сервер пропал из подписки (в т. ч. после её обновления),
выключен в Nodes, сам или вместе с записью, или sing-box такой протокол не умеет (`Catalog.pinLoss()`) — это
ошибка, не подмена: подключение отклоняется (`CatalogException('pinLost')`; на уровне конфига то же —
`SingBoxError` для закреплённой группы без своего сервера), а уже работающее заканчивается ошибкой
(приложение: отключение, `error` и уведомление `connectFailed`). Текст (английский) называет сервер и причину
(«Manual pick "…" (источник) is unavailable: … The tunnel is not moved to another server — choose a server in
Route.»); запись сама сервер не выбирает, закрепление не снимается — пользователь выбирает сервер в Route.
Ядро закреплённую группу не двигает ни при каком старте: кэш sing-box (`cache_id` включает признак закрепления, чужой
выбор Auto не восстанавливается), перезапуск после сбоя / re-resolve / обновление списков (`planWithChosen` не
трогает `chosen` закреплённой группы) и усыновлённый sing-box — всё это возвращается на закреплённый сервер
(`AutoService.refresh()` кладёт группу обратно, одна строка журнала `auto: … put back on the pinned …`).
**Manual на запись (сервер не закреплён) строгий так же**: запись удалена, выключена в Nodes (она сама или всё, на чём она
стоит), без серверов или только с теми, которые sing-box не умеет, — это та же потеря (`Catalog.pinLoss()`, `_entryLoss`):
подключение отклоняется (`pinLost`), работающее заканчивается ошибкой и уведомлением `connectFailed`. Текст называет запись и
причину («Manual pick "…" is unavailable: … The tunnel is not moved to another entry — choose an entry in Route.»).
`effectiveConnectId` в Manual всегда возвращает закреплённую запись (и скрытую / сломанную), выбор Auto её не подменяет.
Запись, которая просто не отвечает, потерей не считается (Manual — выбор пользователя, как и у сервера). Удаление записи
пользователем (с окном последствий) по-прежнему переносит закрепление на первую запись списка.
Тап по мс — по-прежнему пинг. Остальное редактирование записей — в Nodes.

Приоритет: по умолчанию Route **следует порядку каталога** (`routeCustom[mode] = false`).
Перетаскивание в Route даёт маршруту свой порядок (`routeCustom[mode] = true`, подпись «Own
priority order»): порядок в Nodes больше на него не влияет, новые записи добавляются в конец;
«Follow Nodes order» (под списком или в ⋯) возвращает к каталогу. `syncCatalog()` держит
каталог, `sourceOrder` и оба маршрута согласованными после добавлений / удалений.

## Режимы

`connectMode`: `simple` (по умолчанию) | `profiles`. У каждого режима свои:
список приоритета (`order`), закреплённая запись (`active`), флаг Auto (`auto`); меняется
только в Route.

- **Простой**: записи — сами источники + цепочки из двух источников. У источника
  `offNodes` — выключенные для этой записи ноды.
- **Профили**: записи — профили + цепочки из двух профилей. Профиль: целый источник
  (включая будущие ноды) или отдельные ноды.

Юнит (то, чем является запись или конец цепочки) → список нод: `unitRefs(id)` — живые
ноды включённых источников минус выключенные.

## Auto / Manual

- Auto: подключается первая запись списка с `inAuto`, которая **не заведомо мёртвая**
  (`mayWork`: хоть один её сервер не мёртв; для цепочки — хоть один вход не мёртв **и** хоть один
  выход не мёртв **через вход в работе** — по замеру пары, см. «Пинг»; прямой пинг выхода
  цепочку не убивает).
  Мёртвый (`knownDead`) = `failAfter` таймаутов подряд, последний замер свежее 5 минут
  (`PING_FRESH_MS`; пока сервер перемеряется, прежний счёт держится). Незамеренные серверы
  (свежий старт до пинга при запуске, новая подписка), один потерянный пинг и старый
  таймаут запись не выбивают: после перезапуска Auto не отдаёт первое место следующей
  записи только потому, что верхнюю ещё не пинговали. Замеры пингов хранятся в снимке
  состояния и переживают перезапуск.
- **Auto в ядре** (пока подключено) — AutoService (`core/lib/src/auto.dart`, общий для
  jormd и Flutter; API — `docs/core.md`):
  - План — не одна запись, а маршруты: **все записи Auto** (якорь — та, с которой
    стартует `selector`); **в Manual состав тот же** (все записи Auto, `plan.manual: true`) —
    только контроллер Auto остаётся на выбранной записи: между маршрутами ничего не
    проверяет и не переключает (серверы внутри маршрута лечатся как обычно, закреплённый не
    двигается). Если Manual стоит на записи вне Auto — в плане она одна. Над маршрутами —
    `selector`. Переход на любую запись — переключение селектора, **без перезапуска**
    sing-box; перезапуск — только когда меняется состав плана.
  - **Auto ↔ Manual и Manual на другую запись — вживую**, без перезапуска и без нового плана:
    приложение шлёт ядру `POST /api/auto {manual, entry}`, ядро включает/выключает контроллер и
    в Manual переводит селектор `proxy` на запись (без события `auto/switched`: это выбор
    пользователя). `manual` не входит в `planSig`. **Закрывать соединения при смене маршрута**
    (Settings → Connection, `connCfg.closeOnSwitch`, по умолчанию вкл., в снимке/бэкапе пишется
    только выкл.): уже открытые соединения остаются на прежнем маршруте, пока не закончатся;
    при вкл. ручной живой переход Manual на другую запись закрывает те соединения основного
    потока, чья цепочка содержит `proxy` и тег прежнего маршрута (по id, через sbapi) —
    Direct / Block, цели правил и другие маршруты не трогаются, туннель и sing-box тоже. Выкл. —
    соединения доживают на старом, новые идут по новому. На собственные переходы Auto настройка
    не распространяется: при отказе маршрута застрявшие соединения закрывает уже имеющийся
    свип (`StallSweeper`), возврат на высший маршрут (`back`) соединения не рвёт. Ядро получает
    настройку через `updateSettings {closeOnSwitch}` (как `ignoredSites`, без переподключения;
    приложение шлёт при старте и при смене). Новый план нужен, только если записи нет в
    плане (вне Auto) или меняются группы: закрепить сервер (Manual на сервер) или снять закрепление
    — группа становится/перестаёт быть Priority-`selector`. Мокап (заморожен) строит Manual одной
    записью — `Catalog.mockupPlan` (golden-тесты) сохраняет это поведение.
  - Каждые `checkEvery` ядро меряет сервер, на котором стоит текущий маршрут и маршруты
    выше (с `returnTo: never` — только текущий), раз в `warmEvery` — ещё `standby` запасных
    ниже. Замер — одна функция ядра (`_ping` в `auto.dart`); шаг «несколько чекеров, живой,
    если ответил хоть один» (раздел ниже) заменит только её. Идёт через общий пул замеров
    (раздел «Пинг»): свежий ответ того же сервера (пинг UI, замер «If unavailable») берётся
    вместо нового теста, а «нет сети» / сомнение — общее состояние сети пула (`up` / `down` /
    `unknown`), его читают и остальные модули. Недоступные узлы (не ответили `failAfter` раз и не в
    работе) в этот обход не входят каждый раунд: их спрашивает лесенка (пункт 4 ниже); узлы, чей срок
    наступит в ближайшие 2 мин, едут в той же пачке, если в раунде есть узел с наступившим сроком
    (радио просыпается раз на пачку, у каждого узла шаги свои).
  - Сервер текущего маршрута не меряется в раунде, если его работу доказывает живой трафик: с прошлой
    проверки через него получили данные соединения пользователя (`down > 0`; свои проверки ядра не в счёт),
    упавших запросов через маршрут не было, сервер до этого не промахивался. Раунд засчитывает ответ
    (задержка прежняя), в Raw — одна строка за раунд (`auto: … not tested this round: live traffic …`). Нет
    трафика или он падает — замер как обычно. Маршруты выше и запасные меряются как раньше.
  - Выход цепочки меряется через вход в работе, поэтому его промахи (`fails`) — счёт **пары**
    (вход + выход): ушёл вход (Fastest-группа входа выбрала другой, отказ) — у выхода через
    новый вход счёт начинается с нуля, у старой пары остаётся свой. Ядро сообщает пары в
    `status.auto.pairs` (`{entry, key, ms, fails, oks, at}`), UI кладёт их в кэш пар (раздел
    «Пинг»), так что выход, не отвечающий напрямую, не считается мёртвым.
  - Текущий не ответил → повторы только его, с паузой `retryPause` (0,5 с); `failAfter`
    промахов подряд → маршрут мёртв: сразу вместе меряются маршруты выше и запасные,
    ответил кто-то — переход на первый по приоритету. Нет — следующие маршруты по приоритету
    **пачкой по 10** параллельно, первый ответивший по приоритету. Молчит и вся пачка —
    **«нет сети»** (`noNet`): ничего не переключается (селекторы, системный прокси), никто не
    помечается мёртвым и не штрафуется, раунд раз в 10 с. Прямых запросов мимо VPN нет.
  - **Событие `auto/switched` — только о том, что видит трафик**: переход между маршрутами и смена
    сервера внутри *текущего* маршрута (`failover` / `back`; `auto/fastest` — тоже только текущий).
    Смена сервера внутри маршрута, по которому трафик не идёт (запасной ниже, маршрут выше), —
    хозяйство: ни события, ни уведомления, ни `switches` / `lastSwitch` статуса, ни перепроверки
    выхода; только строка журнала `auto: standby <запись>: server A → B (причина)`. Когда на такую запись
    потом перейдут, это обычное событие перехода между маршрутами.
  - Причина возврата на сервер выше в Priority-группе: `back` («снова работает — вернулись») — только если
    этот сервер раньше промахивался (метка в `AutoMemory`, переживает пересоздание сервиса и перезапуск
    приложения, `docs/failures.md` «Auto и „Если недоступно“»); иначе `preferred` («выше по порядку —
    перешли на него»): группа просто стартовала ниже (план берёт стартовый сервер по пингам UI, где
    нужного ещё не знали). **Переподключение сохраняет выбор каждой группы**: `status.auto.routes[]` отдаёт
    `server` / `entryServer` каждого маршрута, запасных тоже, каталог держит их в `coreGroups`
    (`coreNode` показывает, `coreGroupNode` даёт плану в `chosen`; в `planSig` это не входит — у
    маршрутов `chosen` в подписи только закреплённый). Нет сведений от ядра — первый сервер порядка, который
    не заведомо мёртв (`_firstAlive` / выход цепочки в Priority): **незамеренный — кандидат**, пропускается
    только `knownDead`. `preferred` в первые `failAfter` раундов после
    подключения — только строка журнала (`auto: <запись>: server A → B (preferred, right after the connect)`),
    позже — обычное событие `auto/switched`.
  - Раунд, в котором не ответил никто, никого не помечает: промахи всех маршрутов, кроме
    текущего (он копит счёт до `failAfter`), откатываются. Так «в дороге связь то есть, то
    нет» не выбивает записи.
  - **Без разрыва соединений**: у `proxy` и у групп маршрутов (все — `selector`)
    `interrupt_exist_connections: false` — и при отказе, и при возврате открытые
    соединения остаются на старом маршруте. Ядро их проактивно не рвёт; после ухода с
    мёртвого маршрута (или Priority/Fastest-сервера) смотрит таблицу соединений (поток API service sing-box) и
    закрывает только **зависшие**: счётчики байт не менялись 10 с (повтор каждые 10 с, до 6
    раз, пока на старом что-то есть и туда не вернулись). Соединения, по которым идут байты,
    живут дальше.
  - Возврат наверх — `returnTo` (Settings → Auto mode): `always` (по умолчанию) — маршрут выше
    ответил `failAfter` раз подряд и не медленнее текущего больше чем на `threshold`;
    `faster` — только если быстрее текущего на `threshold`; `never` — не возвращаться до
    переподключения. То же правило — для Priority-сервера внутри маршрута.
  - **Защита от мигания** (`flapGuard`, по умолчанию вкл): падение записи — `failAfter`
    промахов, пока в том же раунде ответил **другой** маршрут (не ответил никто — это «нет
    сети», не падение). Каждое падение удваивает испытательный срок: запись получает трафик
    обратно, только проотвечав подряд 1, 2, 4 … мин, но не больше `flapMax` (30 мин). Счёт
    сбрасывается после `flapReset` (15 мин) стабильной работы на ней (текущая и отвечает) и при смене сети. Счёт,
    испытательный срок и счётчик «нестабильна» помнятся вне сервиса (переподключение и перезапуск приложения их не
    обнуляют; `docs/failures.md`).
    На отказ (уход с мёртвой) срок не влияет — только на возврат. Со второго падения —
    событие «запись X нестабильна» (`status.auto.lastUnstable`), уведомление «Unstable entry»
    (Settings → Notifications).
  - Внутри маршрута обе группы — `selector`, сервер выбирает ядро. Fastest: после `failAfter` промахов
    подряд ядро меряет кандидатов пачками и берёт самый быстрый из первых ответивших; раз в `checkEvery`
    шаг улучшения (топ-5 других, переход, если быстрее текущего на `threshold`). Priority: после
    `failAfter` таймаутов ядро переводит группу на первый ответивший по порядку, а на сервер выше
    возвращает по правилу маршрутов. Сервер, закреплённый в Manual, ядро не двигает.
  - **При подключении** (`docs/core.md` → «Подключение: проверка перед стартом»): пока sing-box не
    запущен, ядро проверяет верх группы маршрута, с которого стартует (главная группа; у цепочки —
    группа входа, затем выход парами через выбранный вход), и цели правил через прокси — всё
    параллельно; стартует на выбранном сервере по тому же правилу (Fastest — самый быстрый из
    первых ответивших, Priority — самый высокий из ответивших). Подключение не ждёт пинга каталога и
    не начинает с первого сервера списка, даже если он мёртв; нет сети — стартует на первом по рангу, а
    Auto лечит. Закреплённый в Manual сервер и группа из одного сервера не проверяются, запасные маршруты
    Auto тоже. Если через вход цепочки не ответил никто, выход стартует на первом сервере (warn).
    Подключение ждёт выбор маршрута и до 1.5 с — выбор целей; не успевшие цели ядро ставит на их
    сервер уже после старта. Connect при работающем sing-box (смена плана, обновление списков, `reresolve`)
    сохраняет выбор ядра у маршрутов, выходов цепочек и целей и проверяет только группы без своего
    сервера у ядра; перезапуск после падения sing-box стартует на выборе ядра без проверки; свежий
    connect проверяет заново.
  - UI показывает то, что сообщило ядро: док и Route — запись и сервер, на которых оно стоит
    (`coreRoute`, а не своя догадка); его замеры идут в кэш пингов (так `knownDead` UI
    согласен с ядром); при переключении записи или Priority-сервера — тост, если включено
    Notifications → «When Auto switches». Пинг и переключения ядра sing-box не перезапускают;
    переподключение — только когда меняется состав плана (порядок / Use in Auto / серверы
    записей, закреплённый сервер, Global, системный прокси, `checkEvery` / `threshold` — они в
    `urlTest` плана; **не** Auto ↔ Manual и Manual на другую запись Auto — см. выше).
    Остальные настройки Auto mode уходят в работающее ядро без переподключения
    (`POST /api/auto`).
  - sing-box упал: ядро сразу возвращает системный прокси (браузеры не смотрят в мёртвый
    порт), перезапускает sing-box с тем же планом на маршруте, где был Auto (паузы 1 / 4 /
    15 с, счёт сбрасывается после минуты работы), UI — тостами «starting it again» / «started
    again». Три неудачи — отключено с ошибкой.
- Все записи выключены из Auto (`inAuto` нигде нет) — Auto не выбирает ничего (первую
  запись «по умолчанию» не берёт). Док пишет «Nothing in Auto · turn on Use in Auto in Route»;
  кнопка питания не подключает, а показывает алерт с причиной и кнопкой «Open Route» (Route
  сразу в режиме правки, где тумблеры). Manual (MANUAL на строке) работает как обычно. Если
  последнюю запись выключили при подключении — туннель не рвётся, держится на своём сервере
  до отключения (тост об этом).
- Settings — список разделов (Auto mode, Appearance, General, Connection, Data); каждый
  пункт открывает своё окно (sheet), в Appearance подписью видна текущая тема.
- Appearance → **Text size** 90–120% (шаг 5%): масштабирует списки, карточки и тела окон
  целиком; заголовки, вкладки и нижняя навигация не меняются. Верхняя граница выбрана так,
  чтобы на экране 320 px ничего не вылезало (проверяется). Flutter: `textScaler` с тем же
  ограничением, заголовки — `TextScaler.noScaling`.
- Все окна (sheets) открываются до верха экрана и закрываются свайпом шапки вниз. Нижняя
  навигация видна и работает всегда: окна и затемнение кончаются над ней; тап по вкладке
  закрывает открытые окна и переключает вкладку.
- Системное «назад» (телефон, браузер, мышь, Esc) закрывает верхнее окно (меню и диалоги —
  тоже окна), а не приложение. Если окно открыто из пункта другого окна, которое при этом
  закрылось (Add → Subscription, ⋮ → Delete → подтверждение), «назад» возвращает то окно
  в прежнем виде. Закрытие ×, свайпом, тапом мимо или кнопкой Done «назад» не запоминает.
  Без открытых окон «назад» со вкладки Nodes или Settings ведёт на Home, с Home — выход.
  Во Flutter это PopScope и навигатор.
- Настройки — **Settings → Auto mode** (`autoCfg`, `55-automode.js`); карточка Auto mode
  на главной — просто ссылка (иконка, название, ›): открывает то же окно Auto mode поверх главной,
  без перехода во вкладку Settings (так же карточка DNS → окно DNS). Вкл / выкл Auto —
  бейдж Auto в списке Simple / Profiles (в настройках тумблера нет):
  | Поле | Значения | Контрол | Смысл |
  |---|---|---|---|
  | `threshold` | 0–1000 мс, **50** | поле ввода | гистерезис: сервер сменяет текущий, только если быстрее на столько; неверный ввод — откат |
  | `checkEvery` | 10 с – 60 мин, **1 мин** | окно: число + единица (seconds / minutes) | период проверки текущего маршрута и маршрутов выше |
  | `standby` | 0–20, **2**; 0 = выкл | слайдер «Spare servers», число над ним («next 2» / «off») | сколько следующих по приоритету записей (запасных) пинговать заранее; заменил тумблер `keepWarm` (старый план с `keepWarm: false` = 0) |
  | `warmEvery` | 10 с – 60 мин, **1 мин** | окно: число + единица; строка видна при `standby` > 0 | период пинга запасных; меряются на проверке текущего, так что не чаще `checkEvery` (раньше срока до 1 с — ок) |
  | `failAfter` | 1–5, **2** | степпер ‹ › | таймаутов подряд до ухода с сервера |
  | `retryPause` | 0,1–10 с, **0,5 с**; выключения нет | поле ввода (десятые, запятая тоже), «s» | пауза между повторами текущего после промаха; заменила зашитые 10 с |
  | `returnTo` | `always` / `faster` / `never`, **always** | выпадающий список «Return to a higher entry» (группа «Going back up» с [?]) | когда запись выше забирает трафик обратно (см. выше); старый план без поля = always |
  | `flapGuard` | **да** | тумблер «Flap protection» | защита от мигания |
  | `flapMax` | 1–60 мин, **30** | поле ввода, «min»; видно при `flapGuard` | потолок испытательного срока |
  | `flapReset` | 5–60 мин, **15** | поле ввода, «min»; видно при `flapGuard` | стабильной работы до сброса счёта падений |
  | `siteRetry` | `off` / `3` / `all`, **3** | выпадающий список «Retry a failed site through other routes» (Off / Up to 3 / All), подсказка в строку о доверии сервисов | сколько других отвечающих записей (по порядку Auto) пробовать для сайта, который не открылся через живую ноду; Off — ни одного запроса к сайту пользователя через не выбранные им записи; ядро читает из `plan.auto.siteRetry`, смена — без переподключения; старый план без поля = 3 |
  | `siteCheck` | **да** | тумблер «Check with an external checker» (под «Retry a failed site…») | спрашивать ли check-host.net о сайте, не открывшемся ни по одному маршруту (см. «Внешний чекер»); ядро читает из `plan.auto.siteCheck` (в плане и в снимке пишется только `false`, по умолчанию ключа нет), смена — без переподключения |
  | `speedOnFail` | нет | тумблер | после неудачных запросов ещё и замер скорости текущего сервера (логику порога / реакции — позже) |
  | `pauseScreenOff` | **да** | тумблер | не проверять при выключенном экране, проверить при пробуждении |
  | `subsEvery` | секунды, 10 с – 30 д, **12 ч**; 0 = выкл | окно: число + единица (seconds / minutes / hours / days); показ «30 min» / «12 h» / «2 d» | глобальный период обновления подписок; про свой период подписки — в [?] |
- `source.updateInterval`: `'auto'` (по умолчанию) = период провайдера
  (`profile-update-interval`, не чаще раза в час), если он его прислал, иначе `subsEvery`;
  `subsEvery` = 0 выключает и его. Число секунд — свой период (0 = не обновлять; в форме число + единица секунды / минуты / часы, минимум 10 с). В форме
  подписки пустое поле = auto. Обновляет по таймеру ядро (subscription-parsing.md →
  «Автообновление»).
- `source.reloadAfterUpdate` («Reconnect after update»): выкл — обновление подписки не
  перезапускает sing-box, её новые серверы войдут в конфиг при следующем переподключении по
  другой причине; вкл — переподключение сразу, если план изменился.
- **Запасные (`standby`, «Spare servers»)**: внутри юнита sing-box сам ничего не меряет (группы —
  `selector`, замеры делает ядро); standby нужен для перехода между *записями* списка (и для
  Priority-выхода). Стоимость: один URL-тест ≈ 1–5 КБ; 3 маршрута раз в минуту — порядка
  сотен КБ в сутки; при 20 запасных стоит поднять `warmEvery`. Реальная цена на мобильном — пробуждения радио, поэтому пинги
  standby идут пачкой в том же тике, что и проверка текущего, и ставятся на паузу при
  выключенном экране / режиме энергосбережения. Выигрыш — переключение без поиска: сразу
  на заведомо живой.
- Тап по записи закрепляет её (Manual), повторный тап — назад в Auto.
- Скрытые записи (выключенный источник) в выборе не участвуют.

## Отказ ноды: упавшие запросы и запасные проверки

Цепочка решений ядра (`auto.dart`; уведомления — по Settings → Notifications, см. ниже):

1. **Запуск** — sing-box закрыл соединение через текущую запись, не получив ни байта ответа.
   Источник — поток закрытых соединений **API service** sing-box (gRPC, `sbapi.dart`), а не лог:
   в событии есть сервер (тег outbound'а), цепочка, адрес и сколько байт ушло / пришло.
   Отправлено 0 — соединение не открылось (нода: dial, handshake, сервер лежит); отправлено > 0 —
   запрос ушёл, ответа нет (нода или сайт). В логе клиента второго случая не видно вовсе
   (VLESS и т. п. ничего не сообщают), поэтому только API. Первый такой запрос сразу запускает
   проверку записи (не ждёт `checkEvery`); следующие за `failWindow` (10 с) копятся к ней.
   Незаметного повтора самого запроса нет: о падении мы узнаём, когда соединение уже закрыто
   (повтор на этапе dial возможен только внутри sing-box — отложено).
   Сбой **при смене сети** (`docs/failures.md` → «Смена сети: возмущение, ворота, устойчивость») запросом маршрута не
   считается: соединение, закрытое в момент падения сети или позже, пока сеть не устойчива (и открытое до падения —
   ещё 60 с после устойчивости), идёт в `requestFailsNet` (строка в журнале `auto: a request through … while the
   network changes`), без проверки маршрута и без запоминания сайта. **Auto перед тем, как судить маршрут и перед
   переключением, спрашивает ворота `Sentinel.networkGate`:** пока сеть не устойчива (нет входящих данных по новой сети,
   предел 30 с с сигналом платформы / 10 с без), раунд, в котором текущий маршрут не ответил, **не судится**
   (`netHeldRounds`): никто не помечен, маршрут не оставлен, повтор через `retryPause`. Сеть устойчива — мёртвый
   маршрут судится как обычно и уходит в failover.
   Каждый упавший запрос запоминается как сайт, и те, что ничего не отправили (`up == 0`, мгновенные отказы); сайты
   проверяются (п. 3) только если маршрут ответил.
2. **Проверка ноды с запасными проверками** — сначала тест-URL; не ответил — сразу все
   **запасные проверки** (Settings → Connection → Backup checks: по умолчанию
   cp.cloudflare.com, gstatic, msftconnecttest, captive.apple.com; пресеты и свои адреса).
   **Живая, если ответила хоть одна**; время — тест-URL'а, иначе первой ответившей. Так же
   меряет и пинг каталога. TCP-пинг до порта сервера живость не доказывает (мост RU → EU с
   мёртвым EU-плечом, провайдер, режущий трафик истёкшей подписки) — только запрос через ноду.
   Запасные проверки идут с настройками Auto (`plan.auto.checkers`), смена — без переподключения.
3. **Нода живая** → сайты, по которым запрос ушёл без ответа (порты 443 — TLS-рукопожатие,
   80 — HEAD; другие порты и IP на 443 не проверяются). Проверка идёт только по сбою приложения
   пользователя, своих таймеров у сайтов нет. Порядок: (1) через ту же ноду снова — открылся →
   микросбой, только Raw; (2) нет → **разведчик**: одна рабочая нода контроллера (не напрямую: не
   светить адрес провайдеру), лучше той же подписки и другой страны выхода, и **параллельно** внешний
   чекер; (3) разведчик не открыл, а чекер открыл → рабочие ноды **других подписок / наборов**
   (чекер «не открывается у всех» — шаг пропускается). Сколько рабочих нод пробовать всего — настройка
   `siteRetry` (Settings → Auto mode → «Retry a failed site through other routes»: Off / Up to 3,
   по умолчанию / All). Открылся → событие `site/blocked` (⚠️ N, ✅ M — та, где открылся) с кнопкой
   **Create rule** (форма правила: домен A → цель M; если открыла другая нода той же записи, цель —
   эта нода, `viaTarget`). Не открылся нигде, или нет рабочей ноды, или повторы выключены → событие
   **`site/unreachable`**: у пользователя может просто не
   быть подходящей ноды, это надо сказать явно, а не только в сыром логе (карточка «A does not
   open»: ⚠️ запись в работе и ⚠️ каждая проверенная запись, у каждой Open; без проверенных —
   приглушённая строка «No other working route to try» либо, при `siteRetry: off`, «Retries
   through other routes are off»; Create rule нет — цели нет). Оба события не отбрасываются при
   повторе: после вердикта отвалы пары запись + сайт игнорируются (только считаются на том же событии:
   `data.repeat` — число, время первого/последнего, метки; строка «×N» и время последнего в ленте; сырой
   лог пишет строку; новых проб нет), уведомление только за первое появление. «Мёртв у всех» (чекер не
   открыл) — событие без уведомления, игнор 90 мин, затем перепроверка одним чекером; остальные вердикты —
   игнор по лестнице 5 → 15 → 30 → 60 → 60 мин. Успешное соединение с сайтом через маршрут снимает
   вердикт сразу, смена сети — лестницу (подробнее `docs/failures.md` → Проверки сайтов). Повторы сбоя при открытом корне и серии `conn/failing`
   тоже считаются на прежнем событии. Каждая проба — запрос к реальному сайту пользователя через сервер, который он
   не выбирал; поэтому Off вообще не шлёт таких запросов (некоторые сервисы снижают доверие к
   клиенту, который заходит с многих адресов), а All лучше не включать без нужды. Ответ «не
   удалось выяснить» (`reach` = null) не засчитывается как «пробовали»: так отвечает и проба,
   которая не состоялась (проверочный inbound не принял имя пользователя / его нет) — «не
   открывается» говорится только про запрос, который реально прошёл через сервер. Сразу после
   (пере)запуска группа ещё не названа ядром, и упавшее соединение числится за группой
   `route0`, а не за листом: сайт пробуется через сервер маршрута, который сейчас в работе, а
   если он неизвестен — не пробуется вовсе (ни `blocked`, ни `unreachable`). Не сделано: сводное
   уведомление по нескольким сайтам, «Не показывать для A».
4. **Нода не отвечает** → повторы с `retryPause`, `failAfter` → переход (шаг 3a: без разрыва,
   перебор всех записей пачками по 10, первая ответившая по приоритету). Все проверенные
   серверы одной подписки так, а сервер другого источника отвечает → тост «X: its servers do not
   respond — contact the subscription provider's support» (раз, пока хоть один не ответит).
   Помеченную запись перепроверяет **лесенка** (docs/core.md → «Недоступные узлы»): 1 → 2 → 4 → 8 → 15 → 20 мин
   и дальше раз в 20 мин, один лёгкий запрос за шаг (тест-URL без запасных проверок); лесенка не сбрасывается
   (переподключение, перезапуск приложения, месяцы простоя), переподключение и смена сети дают одну
   внеочередную проверку, ручной пинг тоже считается; вернулась — по защите от мигания. То же для цели
   правила «If unavailable»: упавшая цель перепроверяется по лесенке, а не каждый раунд.
   Отдельного значка «не пропускает трафик» в UI пока нет (как и раньше — мёртвый пинг).
5. **Нет сети** — ОС без сети (sing-box пишет в лог `missing default interface`, вернулась —
   `updated default interface`, тогда сразу проверка) или при переборе не ответил никто.
   Прямых запросов мимо VPN не делаем. Никого не помечаем и не штрафуем, перепроверка раз в
   10 с (в «нет сети» — только текущая и первая пачка). Всё заморожено: системный прокси не
   снимается, селекторы не трогаются, «If unavailable» не срабатывает — трафик остаётся в
   туннеле, утечки при возврате сети нет.

Параллельно с этой цепочкой ядро ведёт книгу неудач (`FailureBook`, `docs/core.md` →
«Неудачные соединения»): те же закрытые соединения, но по каждому приложению и адресу, а не по
записи Auto. Три отказа одного адреса за минуту без успеха — событие `conn/failing`
(приложение, адрес, outbound, вид отказа), даже когда нода живая и `site/*` молчит; отказ,
которого Auto не видит вовсе (TCP из TUN не доходит до маршрутизации), — `core/tunTcpDead`.
Их числа — основа будущего «Direct → если не открылось → цель».

## Выбор ноды внутри юнита

- Запись (источник в Простом режиме, профиль), `pickMode` (по умолчанию `fastest`):
  - `fastest` — самая быстрая живая (`bestAlive`) из отмеченных; sing-box: `selector`, сервер выбирает ядро;
    списки серверов в режиме Fastest (карточки профилей и цепочек, редакторы, настройка записи)
    всегда отсортированы по пингу: быстрейший сверху, мёртвые внизу. При подключении ядро проверяет
    верх группы и стартует на самом быстром из первых ответивших (первая пачка 5, окно 1 с);
  - `priority` — первая живая по `pickOrder` (ключи `sid::nid`) сверху; sing-box —
    `selector`, как у Priority-выхода ниже.
  Это настройка **записи**, не подписки: у источника она хранится рядом с `offNodes`
  (его запись в Простом режиме), у профиля — в профиле. В Nodes порядка нет.
  UI: переключатель Fastest / Priority (`PickModeSwitch`: плашка переезжает, как у Simple / Profiles в
  Route; тап или свайп; справа от него — ⚡ «пинг всех» в редакторах профиля и цепочки) в настройке записи (в Priority — ⋮⋮ и номера у всех
  серверов, отключённые для записи тоже упорядочены, как у выхода цепочки) и в редакторе
  профиля (блок «Connect through»: в Priority — список выбранных серверов с ⋮⋮). В
  списке у такой записи метка PRIORITY. То же прямо в Route: строка источника или профиля
  (не цепочки) разворачивается тапом по карточке — переключатель и серверы записи (в Priority с ⋮⋮ и
  номерами); исключать серверы там нельзя, это в редакторах. Невидимые сейчас серверы (выкл. в Nodes,
  пропавшие) при перетаскивании сохраняют место; при удалении / Forget ключи чистятся.
- Вход цепочки: всегда самая быстрая живая из отмеченных (выбор ядра; `selector`).
- Выход цепочки, `exitMode`:
  - `fastest` — самая быстрая живая из отмеченных (`selector`, выбор ядра);
  - `priority` — первая живая по `exitOrder` сверху, при падении — следующая.
    В sing-box нет outbound'а «по порядку»: `selector` — тот, что выбрали. Поэтому обе группы выхода —
    `selector`, который **переключает наш Dart-код** (через API service sing-box) по результатам пингов: первая живая
    сверху.
  Ноды, которых нет в `exitOrder`, идут после — в порядке `pickOrder` юнита выхода (приоритет,
  заданный подписке / профилю), если он задан, иначе в порядке источника. Так новая цепочка
  сразу наследует приоритет подписки.
- Цепочка = выходной outbound с `detour` на входной.
- Редактор цепочки: вариант, занятый другим концом («used as exit · tap to swap»), по тапу
  меняет вход и выход местами (снятые серверы уходят со своим концом, порядок выхода — заново);
  при двух профилях / источниках иначе цепочку не развернуть. В строках серверов цепочки
  источник не подписывается, если конец из одного источника (он уже в заголовке конца).

## Валидация: хотя бы одна нода

- Профиль, вход и выход цепочки: если не отмечено ни одной живой ноды — жёлтое
  предупреждение, сохранение заблокировано.
- Настройка источника (Простой режим) применяется сразу; если при закрытии не отмечено
  ничего — выбор откатывается к состоянию на момент открытия.

## Пинг

- После подключения приложение в фоне мерит живые серверы подписок активного маршрута: сначала собственные серверы
  маршрута (Fastest: лучшие известные, слабый ответ — после сильных; Priority: по порядку выбора), у цепочки
  входы, затем остальные серверы тех же подписок; выходы цепочки — парами через вход. Подключение этого не ждёт.
  Сервер, который уже мерится, второй раз одновременно не мерится: вызов ждёт идущий замер и возвращается с его ответом.
- Слабый ответ (получен только резервной проверкой, не основной) в ранге идёт после всех сильных и до неизмеренных;
  `bestAlive` сравнивает по этому рангу. `chosen` Fastest-группы плана — подсказка, не закрепление (`docs/core.md`).
  Так же и у пар «выход через вход» (флаг хранится в снимке, приходит как `byChecker` в строке пинга и `weak` в
  `status.auto.pairs`): выбор и порядок выходов цепочки — по рангу, слабая пара после сильных. В списках и у выходов
  цепочки слабый ответ показан числом с точечным подчёркиванием и подсказкой «Answered only a backup check».

- **Что меряем** — задержку по уже открытому соединению через ноду: два запроса к тест-URL
  подряд, показываем второй (как Karing). Время открытия нового соединения (с рукопожатиями,
  у мостов в 3–4 раза больше) не показываем. Реализация — docs/core.md → Пинг.
- Один кэш на всё приложение, ключ — **вариант ноды** (`pingKey` = `protocol://address:port#id`;
  `id` различает варианты одного сервера — SNI, отпечаток, транспорт…, см.
  subscription-parsing.md → дедуп): мёртвый вариант не выглядит живым из-за соседнего, а один
  и тот же вариант из двух подписок — одна запись и один пинг. Значение: мс, `-1` = таймаут,
  время замера, `fails` = таймаутов подряд (для `failAfter`, сбрасывается ответом). Сюда же
  пишутся замеры Auto в ядре (новее имеющихся; пинг в полёте важнее).
- **Пул замеров в ядре** (docs/core.md → «Пул замеров»): все модули — пинг каталога (⚡, пинг
  при запуске), Auto, «If unavailable» — меряют через один пул с ключом «сервер (отпечаток
  outbound, не тег / не id источника) + тест-URL + запасные проверки»; цепочка (выход через
  вход) — отдельный ключ. Результат пинга UI попадает в пул, и Auto / «If unavailable» стартуют
  с него (не мерят заново, пока ответ моложе окна повторного использования), замер, идущий в
  этот момент, не дублируется. Промах повторно не отдаётся (больше 3 с — никогда): «вернулся
  ли сервер» — всегда настоящий тест. UI-кэш выше остаётся источником сохранённых значений
  (пул — память демона). Если ни один сервер пинга не ответил, ядро проверяет ещё и прямой путь
  и отвечает полем `network`: `down` = нет сети (UI может показать «нет сети» вместо «все
  мертвы»), `up` = мертвы серверы, не сеть, `unknown` = не ясно.
- Сохранённые замеры старого формата (ключ `protocol://address:port`) переносятся, только если
  у сервера ровно один вариант (среди нод и пропавших); иначе они ничьи и отбрасываются.
  Старый `-1` = один таймаут.
- Прочерк вместо мс значит только «ни разу не мерян» (или значение забыто): пинг, который не смог
  запуститься (тестер не стартовал, ошибка вызова), ничего не измерил и **возвращает старое значение**
  (`PingBook.unmarkTesting`; в макете — `pingNodes` в `15-ping.js`), а не стирает его и не пишет `-1`.
- «Не мерян» ≠ «мёртв»: `-1` — вердикт пробы (таймаут / ошибка ответа). Узел, который ядро не может протестировать
  (нет outbound, `unsupported`), в пинг не уходит вовсе и остаётся «не проверен» (прочерк), а не `-1`.
- Свежесть 5 минут (`PING_FRESH_MS`): старше — перемерить перед использованием.
- Пинг пары (вход → выход) — выход через `detour` на вход. Выход на UDP (HY2, TUIC, WireGuard) идёт
  через UDP входа: VLESS / VMess несут его как xudp (`packet_encoding`, в узлах стоит), Trojan / SS /
  SOCKS5 — по устройству протокола (не проверялось); вход без UDP (`http`, SOCKS4) такой выход не пропустит — пара честно `-1`, остальные
  замеры не страдают. Конфиг пинга и боевой туннель собираются одинаково (тот же outbound с `detour`),
  проверено на loopback (`core/test/pair_udp_test.dart`): HY2 и TUIC через VLESS (с vision и без)
  отвечают. Если у пары HY2 `-1`, а у REALITY-выхода через тот же вход нет, причина скорее на
  стороне сервера входа (UDP наружу с него: файрвол, Xray-маршрутизация, hairpin на собственный адрес), а не
  в конфиге клиента; причину пишет лог ядра: `Ping: N … did not answer (failed tests: …)`.
- **Выход цепочки живёт по паре, а не по прямому пингу.** Выход может не отвечать напрямую
  (его принимает только вход) и работать через вход. Поэтому рядом с кэшем пингов есть **кэш
  пар** (`PairBook`, `snapshot.pairs`, те же поля мс / время / `fails`, переживает перезапуск),
  ключ — `pingKey(вход) + '>' + pingKey(выход)`. Здоровье выхода в цепочке (`Catalog.chainPair`)
  — пара через **вход в работе** (`coreNode(entryServer)`, иначе быстрейший живой вход
  `chainEntryNode`); если с этим входом выход не мерили — самый быстрый **свежий ответ** этого
  выхода через другой вход цепочки (промах через чужой вход ничего не доказывает). Пара не мерена
  — выход не «заведомо мёртв» (`knownDead` — только по паре, `failAfter` и свежесть как у сервера);
  показать и выбрать выход без замера пары можно по его прямому ответу, но только живому
  (прямой промах о пути через вход не говорит). Читают пару: `chainExitNode`, `mayWork` /
  `knownDead` цепочки, `isUsable`, `effectiveConnectId`, порядок и выбор выхода в плане
  (Fastest — по мс пары, Priority — первый живой по паре), задержка цепочки (док, карточка:
  замеренная пара «вход в работе → выход в работе» = вся цепочка; сумма двух хопов — только пока
  пары нет), строки выходов в карточке цепочки / Route / редакторе (мс пары, тап по строке
  меряет пару). Прямой пинг сервера остаётся его значением в списке его источника / профиля.
  Пары меряют: ⚡ цепочки, «ping all» выходов в редакторе, пинг при запуске (цепочки из верха
  Auto и цели правил — входы напрямую, выходы парами через лучший вход), проверка маршрута
  цепочки (каждая пара пишется), и ядро: `status.auto.pairs` — замеры выходов через вход в
  работе (UI кладёт их в кэш пар новее имеющихся; пинг в полёте важнее).
- **Общий пинг** (⚡ в шапке Nodes): все включённые источники одной пачкой, серверы
  вперемешку по источникам (1-й каждого, 2-й каждого…) — все сеты заполняются одновременно.
- **Порядок пачки** (любой «пинг всех», пинг при открытии): по кэшу — сначала живые по
  возрастанию мс, потом ни разу не мерянные, мёртвые (`-1`) в конце (`byPingRank`). Ядро
  пингует в порядке списка, так что рабочие серверы получают свежие цифры первыми, а мёртвые
  (каждый ждёт полный таймаут) не занимают воркеры в начале.
- **При открытии приложения** (Settings → General → «Check servers on launch», по умолчанию вкл):
  пингуются все серверы первых `1 + standby` записей с `inAuto` **от верха** приоритета Route
  (не от текущего выбора: после перезапуска текущий выбор может оказаться ниже только потому,
  что верхнюю ещё не мерили), в Manual — ещё и закреплённая запись, плюс все цели включённых
  правил и приложений (`src:` / `node:` / `profile:` / `chain:`) — поток правил проверяется так
  же, как основной. Сервер из нескольких записей пингуется один раз. У цепочки напрямую
  пингуются только входы, а выходы — парами через вход в работе (после ответа входов; кэш
  пар). Цель: список, Fastest и failover сразу работают на свежих цифрах.
- **Тап по задержке в доке** (число + «ms» в постоянной рамке): пинг идёт пачками, пока не
  ответят 10 серверов (`DOCK_PING_ENOUGH`) или не будут измерены все. Первая пачка — первые
  3 сервера первых 4 записей Auto по приоритету (в Manual первой идёт закреплённая; сервер —
  в порядке записи: Priority — по списку, Fastest — лучшие по кэшу; цепочка — по 3 с каждого
  конца). Дальше — остальные серверы списка Route (сначала записи Auto, потом прочие) по 8.
  Пока идёт — по рамке бежит огонёк; повторный тап останавливает (пачка в полёте
  досчитывается) и обновляет цифры. Route при этом не открывается. Порядок — чистая логика ядра
  (`Catalog.dockPingBatches`, ход — `DockPingRun`, `core/lib/src/catalog/dock_ping.dart`); выход
  цепочки — элемент «пара через вход в работе» (`pingChain(exits:, entries: false)`), считается живым
  по паре, а не по прямому пингу. Flutter: `CoreHost.toggleDockPing` / `dockPinging`, огонёк —
  один `AnimationController` в `_LatencyBox` (только пока идёт, не тикает под `TickerMode` off).

### Speed Test сервера
Nodes → ⋮ сервера → **Speed test**: штатный network quality test sing-box через этот сервер
(отдельный sing-box с одним сервером, подключение не трогается; серверы Apple mensura).
Лист SpeedCard (заголовок «Speed test», под ним флаг, имя и протокол сервера):
- **спидометр** — дуга 240°, логарифмическая шкала до 1 Гбит/с; внешнее кольцо — загрузка (accent),
  внутреннее — отдача (purple), в центре крупно загрузка в Мбит/с. sing-box сначала меряет задержку,
  потом загрузку и отдачу **одновременно** (фазы в прогрессе чередуются 1/2), поэтому растут оба кольца;
- **строка цифр**: Upload (Мбит/с), Latency (мс, задержка без нагрузки), Responsiveness (RPM под
  нагрузкой, со словом Low < 300 ≤ Medium < 1000 ≤ High, по шкале Apple);
- **статус** («Measuring latency…» / «Measuring speed…» / «Done» / «Stopped» / «Test failed»),
  секунды и полоска прогресса (~20 с);
- **ошибка** — понятной фразой (не ответил вовремя / отказал в соединении / адрес не резолвится /
  оборвал соединение), под ней сырой текст sing-box и подсказка «сервер может лежать, пингани или
  попробуй позже»;
- кнопка **Stop** во время замера (цифры остаются) и **Run again** после (перезапуск в том же листе).
Закрыли лист — замер останавливается.

### Speed Test текущего подключения (карточка Home)
Карточка **Speed Test** на Home (`NavCards`) меряет **само подключение**: тот же network quality test
sing-box, но через **главный поток** — исходящий `proxy` (`topTag`) **работающего** sing-box по его API
service, без отдельного бокса. Поэтому замер идёт по реальному пути со всем, что на нём стоит
(Auto-маршрут, цепочка вход → выход, TUN / прокси), а не по одному серверу. Ядро: `CoreService.speedTest({current: true})`
(тот же поток прогресса, что у теста сервера; на Android — тот же libbox, `BoxRunner.api`). Flutter: `CoreHost.toggleSpeedTest` /
`speedTesting` / `speedProgress` / `speedError` / `lastSpeed`.
- **Не подключено** (фаза не `connected`): карточка приглушена, тап показывает тост «Connect first»,
  ничего не стартует. Ядро на `current` без подключения отвечает одной строкой `{error: 'Not connected', final: true}`.
- **Тап** запускает замер; пока идёт — вокруг иконки карточки бежит кольцо (заполняется за ~20 с),
  в подписи «Measuring latency…», затем «Speed test: ↓ N · ↑ M Mbps» по ходу. **Повторный тап
  отменяет** (подписка закрывается, sing-box останавливает тест; ничего не сохраняется и не пишется
  в журнал). Пропало подключение — тест прерывается так же.
- **Результат** (последний завершённый): загрузка / отдача Мбит/с, задержка без нагрузки (мс) и RPM под
  нагрузкой (хранится; на карточке — первые три) и время (HH:mm, при давности ≥ 20 ч — с датой). Хранится
  в ядре: `<data>/last-speed.json` `{down, up (бит/с), latency, rpm, at (мс)}`, отдаётся в `status.speed`, поэтому
  переживает перезапуск приложения и виден сразу. Карточка показывает его двумя строками
  («↓ 87 · ↑ 22 Mbps» / «34ms · 12:41»); без результата — «No test yet».
- **Сбой** (sing-box вернул ошибку, поток закончился без итога): подпись «Test failed» до следующего
  запуска, прежний результат не затирается; в журнал — `speed/failed` (warn).
- **Журнал** (Logs → Events, категория `speed`, без уведомления): `speed/done` — «Speed test: ↓ N · ↑ M Mbps» и
  «Latency N ms» (данные `down` / `up` в бит/с, `latency`, `rpm`) и `speed/failed` — с текстом ошибки. Строка
  пишется и в raw-лог.
- Тест сервера из Nodes ⋮ карточку Home **не** обновляет: «последний результат» — это всегда замер самого
  подключения.

## Settings → General

`genCfg`: язык (выбор из списка; пока только English, Русский в списке выключен с меткой
«soon»), **Startup** — запуск вместе с системой,
старт свёрнутым (десктоп, в трей), подключаться при открытии, проверка серверов при
открытии (см. «Пинг»); **Other** — ссылки в буфере
обмена (при открытии предложить добавить скопированную подписку / сервер). Проверка
обновлений приложения (Auto-check, канал Stable / Beta) переехала в Settings → Data → App
updates, см. `updates.md` (раз в день, без установки без спроса).
Настройки General хранятся вместе с остальным состоянием. «Подключаться при открытии»
срабатывает только на свежем старте (ядро ещё не подключено), а не при повторном открытии
окна поверх уже работающего подключения; Auto подключается сразу, не дожидаясь пинга при
запуске (его итог при необходимости переключит запись). При старте, после загрузки
состояния, удаляются только «Unavailable»-серверы, чьи 15 дней истекли.

Отдельный экран (NotificationSettings), настройки `notifCfg`; в корне Settings строка «Notifications»
с итогом: «All on» / «5 of 8 on» / «Off». Хранится вместе с остальным состоянием (снимок, бэкап);
старые `genCfg.statusNotif` / `switchNotif` при загрузке переносятся (status; autoSwitch + unstable).

- **Мастер** `enabled` [вкл]: выключен — группы тускнеют, все фоновые уведомления молчат (статусное тоже).
- **Status** — `status` [вкл]: постоянное уведомление Android (запись, сервер; скорость — позже). Выключен
  (или выключен мастер) — уведомление **скрывается совсем** (`NotifCfg.vpnStatusShown`; служба уходит с
  переднего плана, VPN работает дальше — `platforms.md` → «Системные уведомления»); значок ключа в строке
  состояния остаётся — он от Android. Кнопки «Disconnect» тогда нет: отключаются кнопкой дока или плиткой.
  Под переключателем на Android подсказка об этом. *Mockup TODO:* мокап (заморожен) подсказки не знает.
- **Connection**: `autoSwitch` [вкл] Auto перешёл на другую запись или сменил сервер в текущей (не в запасной — это только строка журнала); `unstable` [вкл] запись
  нестабильна (flap guard); `connLost` [вкл] «VPN не работает» (`conn/vpnDown`: ядро не поднялось за 30 с после
  падения или нет сети — одно уведомление, причина меняется на месте, «VPN снова работает» в конце) / не отвечает
  ни один маршрут (`status.auto.noNet`) и возврат. Переключателя `coreCrash` нет (решение 2026-10-17): падение,
  поднявшееся за 30 с, — только журнал; `vpnRevoked` [вкл] (только Android) «VPN выключил другой VPN или
  система» (`conn/disconnected by: 'system'`, `core.md` → «Отзыв туннеля»; решение 2026-10-17); `blocked` [вкл] «сайт не открывается через запись» с кнопкой Create rule.
- **Subscriptions and rules**: `subUpdated` [выкл] фоновое обновление прошло (имя, число серверов);
  `subFailed` [вкл] фоновое обновление не удалось / провайдер убрал серверы / серверы вернулись /
  серверы подписки не отвечают → обратитесь в поддержку; `ruleSets` [вкл] набор правил не скачался
  (событие `rules/ruleSetFailed`).
- **Pop-ups on PC** — `desktopStyle`: `own` [по умолчанию] — собственные всплывающие окна в углу
  экрана | `system` — системные уведомления. Причина умолчания: продвинутые пользователи глушат
  центр уведомлений Windows, а собственное окно показывается и при выключенных системных, и когда
  приложение закрыто в трей. На телефоне это всегда системные уведомления. В мокапе поле только
  хранится (снимок, бэкап), окон в углу нет.
- В приложении уведомление — тост; у «сайт не открывается» под текстом две кнопки — Create rule (только
  `site/blocked` с `via`) и Ignore site (у Snackbar место только под одно действие, поэтому кнопки
  внутри содержимого; нажатие снимает тост, «Ignore site» показывает «{host} ignored · Undo»); тап по
  тексту открывает Logs → Events на этом событии, а уходя
  сам, тост «улетает» в пункт Logs нижней навигации (~0.4 с, transform + opacity; при
  `prefers-reduced-motion` — просто гаснет).
- На Android, пока приложение не на переднем плане (не `resumed`), то же событие — системное
  уведомление (в тост оно тогда не идёт: одно из двух) с теми же кнопками (Create rule открывает приложение с формой правила;
  **Ignore site приложение не открывает**: хост сразу попадает в игнорируемые, а это же уведомление заменяется
  короткой «{host} added to ignored sites» с кнопкой Undo, `platforms.md`); тап открывает Logs → Events на нём
  (тап по свёрнутой сводке — на самом новом событии группы); несколько подряд сворачиваются в одну сводку. Разрешение Android 13+ просится один раз при первом подключении
  и при включении переключателя; если заблокировано — на странице Notifications строка с кнопкой в
  системные настройки. В мокапе этого нет (нет системных уведомлений); подробности —
  `platforms.md` → «Системные уведомления».

**Источник уведомлений — журнал событий** (Logs → Events). Фоновое уведомление рождается из НОВОГО
события журнала: `id` больше последнего, увиденного при загрузке страницы (история не
уведомляет никогда), `own: false`. Соответствие тип → переключатель: `auto/switched|fastest` →
`autoSwitch`; `rules/targetLost|targetFound` → `autoSwitch` (цель правила или приложения потеряна / вернулась, `rules.md` §0 «Недоступная цель»); `auto/unstable` → `unstable`; `conn/vpnDown|vpnUp|lost|restored` → `connLost` (`conn/offline|online` без
подключения и `core/crashed|restarted|restartFailed` — только журнал); `conn/disconnected` `by: system` → `vpnRevoked`; `site/blocked` → `blocked` (кнопки Create rule и Ignore site), `site/unreachable` → тот же `blocked` (только Ignore site; хост игнорируемого сайта уведомлений не даёт никогда);
`sub/updated` → `subUpdated`; `sub/failed|removed|back|dead` → `subFailed`; `rules/ruleSetFailed`
→ `ruleSets`. Остальные события уведомлений не дают. Текст — та же строка, что заголовок и
пояснение строки события. Счётчики статуса ядра (`switches`, `unstable`, `blocked`, `restarts`)
для уведомлений больше не читаются.

**Правило:** переключатели гасят только ФОНОВЫЕ события (мастер и свой переключатель). Прямой
ответ на действие пользователя — ручное Update / Retry / Add / Ping, ошибки валидации,
«Backup saved» — показывается всегда тостом (события с `own: true` не уведомляют).

## Вкладка Logs

LogsView в нижней навигации, две вкладки: **Events** (по умолчанию при открытии Logs) и **Raw**.
Иконка вкладки — линия пульса; на ней две точки: красная — есть непросмотренные события `error`,
жёлтая — непросмотренные `warn` (могут гореть обе; точки не сдвигают раскладку навигации).

### Events

Журнал событий (`backend.events(since)`, контракт — `docs/core.md`): `{id, at, cat, type, level,
own, log?, data}`, `data` — только структура, готовых английских фраз нет (Flutter локализует).
Ядро пишет свои события (Auto, сайты, подписки по таймеру, набор правил, sing-box); то, что знает
только UI, UI дописывает через `backend.addEvent`: результат ручного обновления подписки
(`sub/updated`, `sub/failed`), «провайдер убрал серверы / вернул» (`sub/removed|back`, в том числе
при обновлении по таймеру: разницу `gone` считает UI), «серверы подписки не отвечают» (`sub/dead`),
действия пользователя (`cat: 'user'`, `own: true`: connect, disconnect, pin, mode, route,
sysProxy). Для событий, добавленных UI, `log` нет — кнопки «In raw log» у них нет.
- **Лента** EventRow: старые сверху, новые снизу, открывается прокрученной вниз. Разделители
  дней (Today / Yesterday / дата). Строка: иконка и цвет категории (только переменные темы),
  время, заголовок одной строкой из структуры («Auto: Germany → Netherlands»), вторая строка —
  причина / детали («Germany failed 3 checks»). Идентификаторы (запись, сервер `sid::nid`,
  подписка) переводятся в имена через каталог; нет в каталоге — показывается сырой id.
  warn / error помечены цветной полосой и меткой WARN / ERROR.
- **Кнопки** по применимости: **Copy site** (любое событие `site/*` с хостом: копирует домен, тост
  «Site copied»), Create rule (то же условие: форма правила на этот домен; у `site/blocked` с `via` цель
  предзаполнена «записью, через которую сайт открывается») и **Ignore site** (то же условие: хост в список
  игнорируемых, тост «{host} ignored · Undo», см. «Игнорируемые сайты» ниже), Retry (`sub/failed` — ручное обновление этой подписки), Open
  (запись / подписка в Nodes — на той вкладке, где она живёт: источник и цепочка Simple — Simple,
  профиль и цепочка Profiles — Profiles, `catalog.modeOf`; набор правил — Rules → Rule sets), «In raw log» (вкладка Raw на строку
  `log`, строка коротко подсвечивается; если строка уже выпала из 2000 — тост).
- **Карточка `site/blocked`:** заголовок «<host> does not open», под ним две строки как в меню:
  ⚠️ запись, через которую не открывается (малым — её сервер) и ✅ запись, через которую открывается
  (если есть `via`; её сервер — если известен), у каждой своя кнопка **Open**; ниже Create rule и
  In raw log. Текст уведомления — та же пара: «⚠️ A (сервер)   ✅ M».
- **Карточка `site/unreachable`:** тот же заголовок «<host> does not open»; ⚠️ запись в работе
  (её сервер малым) и по ⚠️-строке на каждую проверенную запись (`tried`), у каждой **Open**; если
  `tried` пуст — приглушённая строка «No other working route to try» (`retries: 'off'` — «Retries
  through other routes are off»). Внизу только In raw log (Create rule нет: рабочей цели нет),
  Back возвращает к событию как у остальных. Текст уведомления — «⚠️ A (сервер)   ⚠️ B (сервер)»
  или та же строка-причина; тип в фильтре — в категории Sites рядом с `site/blocked`, ключ свёртки
  повторов тот же (host + entry).
- **Строки причины (обе карточки `site/*`).** Над ⚠️/✅-строками — строки в стиле меню: что решило
  маршрут запроса (`data.rule`) и кто его послал (`data.process`). «Rule  <имя> ›» — своё правило;
  «App  <имя> ›» — правило приложения; «Service  <имя> ›» — сервис; «Rule  Block ads / My region direct
  ›» — быстрое правило; «Rule  None — main flow ›» — правило не сработало (основной поток).
  Отдельная строка «App  <процесс>» — когда запрос послало приложение, а решило не его правило.
  Имя берётся из текущих данных UI (переименованное правило показывается новым именем), нет в
  каталоге — имя из события, без шеврона (удалённое правило); правило, которое ядро не смогло назвать,
  — его сырой текст. Тап: своё правило → его форма; правило приложения / процесс из списка → диалог
  этого приложения; сервис / быстрое правило → лист Rules, строка прокручена и мигнула (сервис —
  раскрытый список Services); основной поток → Route; Back возвращает к событию (`evLeave`). Текст
  уведомления / экспорта дописывает «Rule X   App Y» (или «No rule, main flow»); в деталях строки
  `Rule` и `App` читаемо вместо объектов. События без `rule` (старые) строк причины не имеют.
  **Приложение процесса** (`process.name`, `Telegram.exe` → `Telegram`, либо пакет) ищется в списке
  Per-app routing: найдено — строка «App  Telegram ›» с именем из списка и ссылкой на диалог
  приложения; нет — просто имя файла, без ссылки.
  **Приложение на Android** (`data.app` — пакет): строка «App» со значком (20 dp, кэш хоста, буква на
  плитке, пока значка нет) и именем из списка установленных приложений; пакет, которого в списке нет —
  сам id пакета; системный `android` — «Android System». Тап всегда открывает диалог этого приложения
  (Rules → Apps), даже если у него ещё нет своего маршрута. Та же пара значок + имя — в Live connections
  (строка соединения и «App» в деталях, тап закрывает лист и открывает диалог) и после строки
  `found package name: …` в Raw log. Только показ: новых кнопок игнора / правила нет, «Create rule»
  там, где был.
  **Конфликт приложение ↔ правило:** сработало ровно одно (то, что сообщил sing-box), второе — то, что
  ему уступило — показывается приглушённой строкой с тем же переходом. Под именем малым: куда ведёт
  строка сейчас (`→ цепочка X` / Proxy / Direct / Block) и метка. (1) Сработало правило, а у приложения
  процесса есть собственный маршрут (хоть одна половина TCP / UDP не Default) → строка приложения
  «overridden by rule» («not applied», если вместо правила был основной поток), у сработавшего правила
  метка «applied». (2) Сработало правило приложения (`kind: app`) → ниже строки правил, которые поймали
  бы этот адрес, но уступили приложению: «overridden by app» (метка «applied» у строки приложения).
  Приложение без собственного маршрута меток не даёт. Вердикт строится по **текущим** настройкам UI, не
  по состоянию на момент события; порядок движка (приложения → правила → быстрые → остальное) не
  меняется — метки читают то, что реально сработало. Кто мог бы поймать адрес, решает лёгкий
  `rulesCatching` (40-rules.js): включённые правила, Block ads, сервисы, My region direct; читает
  домены (domain / suffix / keyword / regex / geosite), IP и порты; чего по `host:port` не понять
  (rule set, GeoIP, «локальные сети» для имени, IP-правило для имени и наоборот, network / protocol,
  source, process, JSON-композиты) — пропускает: правило может не попасть в список, но лишнего не будет.
  Flutter-приложению нужен тот же разбор (в ядре его нет: он зависит от правил и настроек UI).
- **Возврат назад.** Open и «In raw log» уводят из журнала (в Nodes, в Raw, в лист Rules / DNS); Back
  (телефон / браузер / Esc) возвращает в Logs → Events: строка события в видимой области, раскрыта и
  коротко подсвечена (если фильтр её скрывал — он сбрасывается). Для листа поверх журнала возврат —
  когда Back закрыл этот лист; закрытие вручную или смена вкладки возврат забывает. Один механизм
  для всех действий журнала, уводящих из него.
- **Тап по строке** раскрывает детали: время (у свёрнутых повторов — все времена), тип события и
  все поля `data` в читаемом виде (длительности «Down for 41 s», флаги On / Off).
- **Повторы сворачиваются:** одно и то же событие (категория, тип, ключевые поля: `site/blocked` —
  host + entry, `auto/switched` — route + from + to, `auto/unstable` — id, `sub/*` — source,
  `rules/*` — tag, `user/*` — все данные) в пределах 10 минут от последнего повтора — одна
  строка «×N» со временем последнего; строка стоит там, куда её ставит последнее время.
- **Прокрутка:** событие пришло, а лента внизу — плавная (не скачком) прокрутка к нему; если
  пользователь прокрутил вверх — вид не двигается, рядом с плашкой «↓ Latest» появляется число
  новых («↓ 3 new»); тап — плавно вниз. Та же плашка и логика «следить, пока не прокрутил вверх»
  на вкладке Raw.
- **Фильтр** (кнопка в шапке Events открывает лист): поиск; «Only problems» (warn + error);
  категории Connection, Auto, Sites, Subscriptions, Rules, Core — у каждой чекбокс из трёх
  состояний (все / часть / ничего), раскрывается в отдельные ТИПЫ событий (тонкий фильтр по типу:
  выключить `auto/unstable`, оставив остальные Auto). Нажатие на чекбокс категории: все включены →
  выключить все, иначе → включить все. Активный фильтр — бейдж с числом на кнопке (плашки «Filtered: …»
  над лентой нет, Reset — в листе фильтра). **Эти выборы временные: сбрасываются при перезапуске
  приложения, в состояние не сохраняются.**
- **«Show my actions»** — единственная постоянная настройка ленты (`logCfg.showOwn`, по умолчанию
  выкл: события `cat: 'user'` скрыты). Хранится в снимке состояния (бэкап). В листе фильтра
  стоит отдельной группой «Kept with your settings» с пометкой, что переключатель, в отличие от
  фильтра, сохраняется.
- **Точки на вкладке:** событие «просмотрено», если его строка была в видимой области ленты
  (или пользователь тапнул уведомление, открывшее его). Хранятся id просмотренных
  `warn`/`error` (`logCfg.seen`, в снимке — точки переживают перезапуск; id, выпавшие из
  журнала, чистятся). Скрытые фильтром события считаются непросмотренными.
- **Clear** — с подтверждением, очищает журнал (`backend.clearEvents()`; id продолжают
  нумероваться), Raw не трогает. **Export** — один текстовый файл `jormungand-logs-<дата>.txt`:
  события читаемым текстом и сырой лог.
- Журнал опрашивается раз в секунду при открытой вкладке Events, иначе раз в 3 с (из него
  идут фоновые уведомления, см. Settings → Notifications): `backend.events(since)` — события с
  `id ≥ since` (без `since` — последние 200), `next`, `first` (самый старый сохранённый id: так
  видно очистку или обрезку). Оба `since` ядро находит по номеру (бинарный поиск), цена ответа — число
  новых записей, а не размер журнала.
- **Приложение (Flutter), `LogsController`:** поток строк / событий только будит таймер ~300 мс
  (всплеск = одно чтение, не по чтению на строку; в приложении Raw собирает пачки по 500 мс, события — по
  300 мс, страховочный опрос раз в 5 с — `docs/logs.md` → «Экран Logs»). События читаются всегда (тосты, точки на пункте
  Logs — их несёт отдельный `unseenNotifier`, навбар слушает его, а не контроллер), но страница
  слышит изменения и производные списки (свёртка событий, группы Raw, счётчики) строятся только
  пока вкладка Logs на экране и приложение впереди; списки кэшируются по версии и не пересчитываются
  на каждый кадр / чужой rebuild. Скрытая страница отдаёт последнюю собранную себя без перестройки.
  Сырой лог при скрытой вкладке не читается вовсе (нет подписки на поток строк): при показе страница
  догоняет с курсора `next`, всё пришедшее за это время — непрочитанное (как и раньше).

### Игнорируемые сайты

Мёртвый сайт, в который что-то ломится, забивает журнал («does not open»), тосты и сырой лог. Список
**Ignored sites** глушит такой хост и его поддомены (`example.com` покрывает `api.example.com`; запись
чистится — регистр, схема, путь, порт, `*.`). Только показ: на маршрутизацию список не влияет, Auto
по-прежнему проверяет узел после упавших запросов.
- **Где.** Меню ⋮ в шапке Logs (обе вкладки) → «Ignored sites»: лист со списком (поле + Add с проверкой
  «Enter a site, like example.com» / «{0} is already in the list», крестик у записи убирает, «Clear all»,
  пусто — «No ignored sites»). Туда же ведут «Ignore site» на событии, тосте и системном уведомлении
  (тост «{host} ignored · Undo» — Undo убирает хост).
- **Что глушится.** События `site/blocked|unreachable` с таким хостом ядро больше не пишет (ни в журнал,
  ни в уведомления; старые события остаются), уведомление приложение не показывает и подавно; строки Raw
  — как выше (чип). Список в `notifCfg.ignoredSites` (снимок, бэкап), ядру уходит в
  `updateSettings {ignoredSites}` при каждом изменении и при старте — без переподключения
  (`docs/core.md` → LogBook). Старые строки Raw скрываются сразу (приложение сортирует их само по текущему
  списку), у ядра строки новых запросов попадают в малое кольцо (не вытесняют ошибки).

### Фоновые ошибки (экран выключен, Android)

Сайт, который не открывается, пока экран телефона выключен, — фоновая ошибка (кто-то в кармане ломится в
мёртвый хост). Ядро пишет `site/blocked|unreachable` как обычно, но с `bg: true` (момент судится при
находке: флаг экрана ядру уходит от платформы сразу при каждой смене, `updateSettings {screenOn}`; не
сообщали — экран включён; на Windows всегда включён). Журнал хранит такие события всегда.
- **Уведомления.** Settings → Notifications → «Errors while screen is off» (`notifCfg.bgErrors`, по умолчанию
  выкл., только Android, не входит в счёт «N of M on»; лежит в группе Connection под «Site does not open»).
  Выкл.: bg-событие не даёт ни тоста, ни системного уведомления. Вкл.: уведомляет как обычное (по своему
  переключателю `blocked` и мастер-переключателю). Решает флаг события (`eventNotifies` в `log_view.dart`,
  вызывается в `LogsController`), а не состояние экрана в момент показа, поэтому уведомление, которое
  показывается позже, судится верно.
- **Events.** Строка bg-события помечена маленькой луной и «background»; в листе фильтра Events строка
  «Background» («Found while the screen was off») показывает / скрывает такие события (по умолчанию
  показаны; строка есть, только когда в журнале есть bg-событие или фильтр включён; временный фильтр,
  считается в бейдже фильтра; Reset сбрасывает). Экспорт
  помечает строки `[bg]`. Raw не размечается (у строк sing-box нет флага).

### Внешний чекер (check-host.net)

`site/unreachable` — сайт не открылся ни по одному маршруту — это либо «мёртв для всех», либо «закрыт только
отсюда». Отличает внешний чекер, и только он решает, будить ли пользователя.
- **Когда.** Чекер спрашивается **параллельно разведчику** (рабочей ноде контроллера), один раз за разбор,
  если не выключен; его ответ решает, идти ли к нодам других подписок (`opens` — идти, `down` — нет).
  Событие `site/unreachable` с перебором (нет `retries: 'off'`; при выключенных повторах пробовалась
  одна нода — «все» не доказано, событие уведомляет как раньше, без `check`). Если разведчик открыл сайт
  (`site/blocked`), запрос к чекеру отменяется сразу, как только она открыла: опрос прекращается, ответ не нужен, в событии
  нет `check`, в кэш чекера (10 мин) прерванный запрос не попадает; то же, если сайт открыла любая другая наша проба, пока
  запрос ещё идёт. Событие уведомляет как раньше. Если разведчик не открыл, ответ чекера используется как обычно.
  После вердикта «down» чекер сам, без проб нод, перепроверяет сайт на первом отвале после 90 мин игнора.
  Игнорируемый хост не шлётся никогда (события для него нет вовсе).
- **Событие тихое** (журнал, без тоста и системного уведомления; решает `eventNotifies`), пока в
  `data.check` нет `state: 'opens'`. Состояния `data.check`: `pending` (спрашиваем, `at`), `opens` — с
  узлов чекера открывается (≥ 2 узлов; любой HTTP-статус = сервер достижим) — «Opens elsewhere, not through
  your routes», **уведомляет** (событие меняется на месте, приложение уведомляет по смене `rev`, один
  раз), `down` — недоступен и для чекера — «Down everywhere (check-host)», тихо; такое событие не упоминает наши
  узлы и маршруты вовсе (нет строк «⚠️ маршрут», списка перебранных, заметок про перебор; поля `entry`/`server`/`tried`/`retries`
  скрыты и в раскрытой карточке — остаются в `data`, `trail` и сыром логе); `failed` (чекер не
  ответил, мало узлов успело ответить, лимит, сеть; `error` — причина), тихо; `off` — автопроверка выключена
  (Settings → Auto mode → «Check with an external checker», по умолчанию вкл.), тихо. Пока `pending`, `failed`
  или `off` — только журнал; кнопка ниже всё равно доступна.
- **Результат целиком** лежит в событии: `check = {state, at, kind: 'http'|'tcp', via: 'tunnel'|'direct', ok,
  total, nodes: [{cc, country, city?, ok, code?, ms?, error?}], error?, manual?}` — в раскрытой строке «Checker»:
  вердикт и по строке на узел («Germany, Frankfurt — OK 200 · 200ms» / текст ошибки).
- **Кнопка «Check with checker»** на `site/*` событиях (Flutter, строка действий; под ней «Checking…», пока
  идёт спрос) → `POST /api/site-check {event}`: то же событие сначала `pending`, потом результат (`manual:
  true` — пользователь смотрит, уведомления нет, обходит кэш и лимит). Нового события не появляется.
- **Как спрашиваем** (`sitecheck.dart`): `check-http?host=<https://host | http://host[:port]>&max_nodes=8` (для
  IP и не-веб-портов `check-tcp?host=host:port`), затем `check-result/<id>` каждые ~2 с до ~20 с; узел `null` —
  ещё считает. Запрос идёт через туннель (tunnel-in — check-host может быть закрыт напрямую в РФ), при
  недоступном туннеле — напрямую (`via`). Результат кэшируется по сайту на 10 минут (автопроверка), не
  больше 4 автопроверок в минуту, одновременные спросы одного сайта — один запрос; ошибки не кэшируются.
  Тесты подменяют HTTP-клиент (`CoreService(siteChecker:)`), сети в них нет.

### Raw

Строки sing-box и заметки ядра (подключено / не подключилось, предупреждение системного прокси,
упавшие запросы — с меткой «core») одной лентой, старые сверху. Время, метка WARN / ERROR, префикс
соединения sing-box `[id мс]` приглушён.
- Фильтр: All / Warnings & errors / **Connections**; поиск (подсветка совпадений). Строки sing-box об
  УДАЧНЫХ соединениях (`inbound/… : inbound connection to …`, `outbound/… : outbound connection …`,
  `packet connection`, а также строки `router: found package name: …` / `found process path: …` —
  по одной на соединение; шаблон `isNoiseLine` в `logbook.dart`) по умолчанию скрыты — чип Connections
  (выключен по умолчанию, выбор хранится в `logCfg.showConns`) их возвращает. Ядро умеет не отдавать их
  вовсе (`log(conns: false)`, ответ несёт `hidden`; docs/logs.md). Warn / error строки
  (упавшие соединения) показываются всегда — кроме строк игнорируемых сайтов: warn / error строка, где
  упомянут игнорируемый хост или его поддомен, скрыта, пока не включён чип «N from ignored sites» (появляется,
  когда такие строки есть; `logCfg.showIgnored`, выкл. по умолчанию; «In raw log» на такую строку сам включает
  чип; бейджи непрочитанных их не считают). Счётчик в шапке считает строки без скрытых; бейджи чипов
  тоже. «In raw log» на строку-соединение сам включает чип. Число на чипе — круглый бейдж на углу, считает НЕПРОЧИТАННЫЕ строки (All — любого уровня, Warnings & errors — warn + error), при 0 скрыт, больше 99 — «99+», ширина чипа не зависит от числа. Цвет = худший непрочитанный уровень: красный error, жёлтый warn, зелёный info. Учёт по строкам (как «просмотрено» в Events): строка прочитана, только когда она хоть частично (≥ 8 px) побывала в видимой области ленты при открытой вкладке Raw и видимом приложении (`document.visibilityState`); строки внутри записи-группы судятся каждая по своему месту. Новые строки, пришедшие, пока лента прокручена вверх (или вкладка закрыта / приложение скрыто), непрочитаны, и бейджи растут сразу; если пользователь внизу и следит за лентой, новые строки попадают в область и читаются сразу. Скрытые фильтром или поиском строки прочитанными не становятся (бейдж при этом считает все непрочитанные, независимо от фильтра). Бейджи обновляются при каждой новой строке, прокрутке, перерисовке, смене фильтра / поиска и вкладки. Хранится компактно вместе с состоянием (`logCfg`): `rawUnread` — диапазоны номеров непрочитанных `[от, до, от, до…]` и `rawTop` — номер самой новой строки, которую UI уже учёл (строка выше него, не входящая в непрочитанные, — прочитана; строка за ним — новая). Первый запуск (`rawTop` нет): строки, что уже лежат в буфере ядра, считаются прочитанными, непрочитанными бывают только пришедшие после начала учёта. Номера ниже самой старой строки, что ещё хранит ядро (последние 2000), отбрасываются. Если ядро перезапустилось и нумерация (с 0) началась заново (`next` меньше сохранённого `rawTop`) — всё, что оно держит сейчас, считается новым (непрочитанным). Clear (корзина) — всё прочитано. В приложении `rawUnread` / `rawTop` пишутся в состояние, когда вкладку покидают или приложение уходит в фон (не на каждую строку: полное сохранение снимка стоит больше, чем поток строк); первый запуск без сохранённого `rawTop` берёт номер следующей строки ядра сразу при старте (строки читать для этого не нужно).
- Между записями тонкие разделители. Подряд идущие строки с одной секундой, уровнем и источником склеиваются в одну запись: одна мета-строка (время · уровень · источник), под ней сообщения, каждое на своей строке, без разделителей внутри.
- Событие Events — две строки: мета (уровень, ×N, время), заголовок под ней. Кнопки шапки Logs стоят в фиксированных слотах (поиск их не сдвигает).
- Событие Auto между серверами с одинаковым именем: к имени добавляется протокол («· HY2»), при одинаковом протоколе — адрес:порт (ядро шлёт ключи sid::nid, протокол берётся из каталога).
- Автопрокрутка: лента держится внизу, пока пользователь не прокрутит вверх; тогда внизу
  плашка «↓ N new», тап — обратно вниз и снова следить.
- Copy all — показанные строки (с учётом фильтра и поиска) в буфер; Clear — очистить (и в
  ядре). (В приложении Copy нет совсем: ⋮ → Download log отдаёт весь отчёт файлом, ⋮ → Clear очищает.)
- Пока вкладка Raw открыта и приложение видно — раз в секунду `backend.log(since)` (ядро отдаёт
  строки с номера `since` и `next`, `logbook.dart`: два кольца, см. docs/core.md «LogBook»).
- **Приложение (Flutter).** Чип «Connections» — переключатель в листе фильтра Raw (иконка фильтра в
  шапке, бейдж = сколько настроено не по умолчанию): пока он выключен, опрос идёт с `conns: false`, ядро
  вовсе не отдаёт строки успешных соединений, а под вкладками стоит строка «N lines · Connections hidden
  (K)» (тап — лист фильтра). Включение — полный перезапрос с начала с сохранением места в ленте. Лента
  не выводится, пока вкладка Raw не на экране; обновления собираются пачками. Подробно — `docs/logs.md` →
  «Экран Logs».

## Проверка маршрута цепочки (информационная)

1. Входные ноды: кэш, если все моложе 5 мин, иначе пинг всех.
2. Живые входы от быстрых к медленным; для каждого — пинг всех выходов через него
   (выходы параллельно, входы по очереди). Нода не пингуется сама через себя.
3. Если кэш использован и первые 2 входа не дали ни одной пары — кэш устарел:
   перепинговать входы и начать заново (один раз).
4. Результат: рабочие пары по задержке пары. Каждая замеренная пара (и промах) пишется в кэш пар
   (раздел «Пинг»): после проверки карточка цепочки и Auto видят выходы по ней. Вызов, упавший
   целиком (тестер ядра не запустился; `CoreHost.pingPairs` вернул пустой список), — не вердикт:
   в кэш пар ничего не пишется (промах «все мертвы» — только ответ тестера). Выбор цепочки и
   Auto сама проверка не меняет. Пользователь
   может остановить проверку вручную (досрочной остановки по N пар нет — решено).

## Главный экран (ConnectDock)

Показывает, через что идёт трафик сейчас:
- Простой: `Sub|Servers` + имя источника; строка ниже — нода;
- Профили: `Profile` + имя; ниже — источник › нода;
- Цепочка: `Chain` + имя; ниже — нода входа → нода выхода.
Справа — задержка (для цепочки — замеренная пара «вход → выход» целиком, пока пары нет — сумма
двух хопов) в рамке: тап — пинг (см. «Пинг»), бейдж
AUTO / MANUAL. Иконки слева и стрелки справа нет; тап по остальному доку открывает Route.
При подключении запись и серверы — те, на которых реально стоит Auto в ядре (см. «Auto / Manual»).

**Состояния дока по `status`** (kill switch и перезапуск — rules.md §7):
- *Recovering* (`status.recovering`, sing-box перезапускается в фоне, `down` ещё нет): док и кнопка
  питания **точно как Connected** — ни тоста, ни смены состояния (события остаются в журнале).
- *Down* (`status.down = {since, attempt, proxy}`: перезапуск не удался за 30 с): кнопка питания **остаётся
  включённой** (тап = отключиться = перестать пытаться), но красная; бейдж вверху «VPN is down»; в доке
  красная строка «VPN is down · <сколько> · retrying». На главной сверху красная плашка: «VPN is down —
  internet is blocked» (`proxy: 'kept'`) или «VPN is down — traffic goes direct» (`removed` / `released`);
  кнопки **Retry** (`backend.retry()` → `POST /api/retry`) и, пока прокси держится, **Disable sys proxy**
  (`backend.releaseSysProxy()` → `POST /api/sysproxy/release`; после него `proxy: 'released'`, кнопка
  уходит). Кнопки «Disconnect» в плашке нет — это кнопка питания. Событие `core/sysProxy {on:false,
  by:'user'}` (`own`) в журнале.
- *Blocking* (`status.blocking = {since, reason: 'disconnect'|'closed', proxy}`, док при этом Disconnected):
  на главной плашка «Kill switch: internet is blocked until you connect» с кнопкой **Remove**
  (`releaseSysProxy`); подключение её убирает. UI опрашивает `/api/status` и при отключении, чтобы
  увидеть `blocking` после старта приложения (`reason: 'closed'`).

**Пустой каталог** (первый запуск или всё удалено — в текущем режиме нечего подключать):
док пишет «No servers yet · Add in Nodes» (Профили — «No profiles yet · Create one in
Nodes»); тап по доку или по кнопке питания ведёт в Nodes и открывает «+» (без источников —
на вкладке Simple: профилю не из чего собираться) — **только если пусты оба режима**. Если пуст
текущий, а другой нет (застрявшее состояние: режим переключили на пустой Profiles), тап по доку / кнопке
питания открывает Route на другом режиме — там «Use this mode»; режим молча не переключается ни при
загрузке, ни по тапу. Вкладка Nodes в нижней навигации «+» сама не открывает никогда. В live-режиме «This session» до первого
подключения — 0 B.

- **Проверка по неудачным запросам** (всегда, без настройки): `checkEvery` — это проверка
  текущего маршрута (+ standby) по таймеру; кроме неё, если через текущий сервер пошли
  неудачные запросы, он пингуется сразу, не дожидаясь таймера (дальше — как обычно:
  `failAfter` таймаутов подряд → уход). Источник сигнала в sing-box — ошибки соединений
  outbound'а — поток закрытых соединений API service (сделано в 3.7, см. «Отказ ноды»).

Окно периода — маленький диалог по центру: поле числа + выбор единицы, Cancel / Save
(Enter = Save). Хранится в базовой единице (секунды / часы); открывается в самой
крупной единице, на которую значение делится нацело (48 ч → 2 days). Поле числа
узкое, единицы в окне — полными словами; в строке настройки — коротко (2 d, 1 min). Вне диапазона —
тост с допустимым диапазоном, окно не закрывается.

## Лист Live connections (карточка Connections на главной)

Данные — `traffic().conns` (раз в секунду, см. `core.md`). Под заголовком строка
инструментов фиксированного размера (метки не меняют её ширину): поиск, Filter (значок с
числом выбранных значений), Sort (короткая метка текущей сортировки), ⋮.

- **Правило в строке** — имя, которое ядро выводит из сырого текста sing-box (`ruleName`,
  `core.md` «Правило соединения»): своё правило, приложение («Discord (TCP)»), сервис,
  Block ads / My region direct, системное (Private networks, Core checks…); «Default /
  final» — ни одно не сработало (в строке не показывается). Ядро не смогло назвать
  (`ruleKind` пуст) — сырой текст `rule`. Имя — в строке, в секции Rule фильтра, в поиске
  (ищет и по сырому тексту) и в Copy; в раскрытой строке под именем приглушённо сырой текст
  sing-box.
- **Sort and group** (лист Sort: секция сортировки и секция «Group by»). Sort: Newest (по
  умолчанию), Download speed, Upload speed, Downloaded, Uploaded, Duration (самые долгие
  первыми). Group by: **Service** (по умолчанию), App, None. Service — известный сервис
  (список Rules → Services и его домены/адреса; правило-сервис / правило приложения этого
  сервиса определяет его напрямую), иначе регистрируемый домен хоста (`api.github.com` →
  `github.com`, `bbc.co.uk`), иначе для голого IP — приложение, иначе «Other». App —
  basename процесса («Unknown»); на Android — приложение по пакету: имя из списка установленных
  (как в событиях), «Android System» для `android`, id пакета — только для неизвестного /
  удалённого; то же имя — в секции App фильтра и в поиске; ключ группы остаётся пакетом, список
  приложений читается при старте, а пришедший позже подхватывается без переоткрытия листа.
  Заголовок группы: значок (у приложения Android — его значок, иначе буква), имя, число соединений,
  суммарные ↓ ↑ скорость, шеврон; тап сворачивает (свёрнуто держится до конца сессии, по
  режиму группировки; при непустом поиске ничего не свёрнуто), × закрывает показанные
  соединения группы. Сортировка работает внутри группы и между группами по их сумме
  (Newest — по самому новому соединению группы, Duration — по самому старому). Filter, поиск,
  Pause, Copy (перед группой строка `# имя · N connections · ↓ ↑`), Close shown работают с
  соединениями, а не с группами (свёрнутые входят в «показанные»). Живёт до конца сессии.
- **⋮**: Pause / Resume; Copy — показанный список текстом, по строке на соединение:
  `net host:port · приложение · правило · маршрут · ↓ ↑ байты · возраст`; Filter by exit…
  (лист фильтра только с секцией Exit); Close all — без фильтра и поиска, «Close N shown» —
  с ними: закрываются только показанные (`closeConn(id)` каждому; без фильтра и не на паузе —
  один `closeConn(null)`).
- **Pause**: список замирает (снимок), карточки на главной идут дальше. Сверху полоса
  «Paused · N new connections» + Resume (N — соединения, которых не было в снимке).
  × на строке при паузе работает. Закрытие листа снимает паузу.
- **Filter** (вложенный лист; Back / × не применяют ничего, ✓ применяет, корзина сбрасывает
  выбор; поиск в шапке ищет значения во всех секциях). Секции: Protocol (TCP / UDP), App
  (basename процесса, «Unknown» без него), Rule (имя правила, пусто = «Default / final»),
  Exit (сервер, через который соединение выходит: `out[0]`, Direct; у цепочки выход, а вход
  приглушённой подписью «via …»), Host (домены и IP). У значения — число текущих соединений;
  выбранное, которого больше нет, остаётся в списке с 0. Внутри секции — ИЛИ, между
  секциями — И; поиск по строке листа работает вместе с фильтром. Секция с > 8 значений
  показывает 8 + «Show all N». Выбор держится до конца сессии.
- **Строка** по тапу раскрывается (одна за раз): полный host:port, сеть, правило, маршрут
  вход → выход, полный путь процесса, время старта, ↓ и ↑ отдельно; действия: Close, Copy,
  «Open rule» (только для своего правила — его форма, и для правила приложения, если
  приложение есть в списке — диалог его маршрута), «Rule for this host…» (форма нового
  правила с условием Exact domain = хост; для IP — IP / CIDR), «Rule for this app…» (условие
  Process = имя процесса; только если он известен).
- Пустые состояния: «Not connected», «Nothing matches», «No open connections».

## Подсказки [?]

Круглая кнопка «?» у заголовков сложных экранов открывает компактный лист поверх всего
(уровень 3) с 3–6 строками «термин — что делает», простыми словами. Где: Nodes, список
Simple / Profiles, настройка записи, редактор профиля, редактор цепочки, Settings →
Auto mode и Subscriptions, Advanced в форме подписки. Тексты — `HELP` в `58-help.js`.
