# Модель подключения: источники, профили, цепочки

Что из макета (`design/src/js/`) нужно перенести в логику приложения. Макет — эталон
поведения; этот файл — его описание для бэка (Dart-сервисы + сборка конфига sing-box).
Обновлять при каждом изменении логики в макете.

---

## Сущности

| Сущность | Поля (макет) | Смысл |
|---|---|---|
| **Source** | `kind: sub \| node`, `enabled`, `nodes[]`, `gone[]`, `offNodes[]`, `disabledNodes[]`, `updateInterval`, `inAuto`; у `sub` ещё настройки формы (`url`, `userAgent`, `hwid`, `filter`, `channel`, `reloadAfterUpdate`, `testAfterUpdate`…) и серверные поля (`uaStrategy`, `discoveredAt`, `usage`, `expire`, `format`, `providerInterval`, `webPage`, `supportUrl`, `announce`, `updatedAt` — пишет только ядро, см. subscription-parsing.md) | Подписка (`sub`) или ручной набор серверов (`node`). Живёт на вкладке Nodes. |
| **Node** | `id`, `protocol`, `address`, `port`, креды, `flag`, `name` | Один сервер (outbound sing-box). |
| **Profile** | `sources[]`, `nodes[]` (`sid::nid`), `inAuto` | Режим «Профили»: набор целых источников и/или отдельных нод. |
| **Chain** | `inId`, `outId`, `inOff[]`, `outOff[]`, `exitMode`, `exitOrder[]`, `inAuto` | Вход (первый хоп) → выход. Концы — «юниты» активного режима. |

`sid::nid` — ключ ноды внутри источника (в макете `refKey`).

## Идентичность ноды

`node.id` = идентичность **варианта сервера**, а не позиция в списке. Новая нода получает
id = `key` (сервер + вариант подключения, см. `subscription-parsing.md` → «Дедупликация
нод»). Имя в ключ не входит. Если провайдер поменял у сервера вариант (SNI, fingerprint…),
нода сохраняет старый id, когда это однозначно: у сервера (`base`) ровно одна
несопоставленная старая нода и одна новая. Иначе новая — это новая нода, старая уходит в
`gone`. Сопоставление делает ядро при слиянии обновления (`core/lib/src/merge.dart`).

Все настройки ссылаются на `id`: `offNodes`, `disabledNodes`, `profile.nodes`, `chain.inOff/outOff/exitOrder`.
Поэтому провайдер может перетасовать или переименовать ноды — выбор пользователя не съедет.

## Пропавшие ноды (`gone`) — кэш выбора

При обновлении подписки нода, которой больше нет в ответе, **не удаляется**, а
переносится в `source.gone[]` с `goneAt`. Настройки, которые на неё ссылаются, не трогаются.

- Нода вернулась в следующем обновлении (тот же `id`) → переезжает обратно в `nodes[]`
  и сразу оказывается с прежней галочкой и на прежнем месте в приоритете выхода.
- Новая нода (раньше не было) → включена, в приоритете выхода — в конце.
- В UI пропавшие ноды показываются свёрнутым блоком «Unavailable · N» везде, где есть
  список нод (Nodes, настройка источника, редактор профиля, редактор цепочки), только
  для чтения, с сохранённым состоянием галочки.
- **Срок хранения — 15 дней на каждый сервер отдельно** (`GONE_KEEP_DAYS`), от его
  собственного `goneAt`. Истёкшие вычищаются вместе с настройками (`purgeExpiredGone`) при
  старте и после каждого обновления. В строке — «N d left» (≤ 3 дней — жёлтым).
- `gone` хранится в объекте источника: удалили источник — пропавшие и их настройки
  удаляются вместе с ним.
- **Forget all** (в Nodes) удаляет все `gone` источника; тап по строке пропавшей ноды —
  меню с «Forget now» для неё одной. Оба вычищают её `id` из всех настроек
  (`purgeNodeSettings`).
- Групповые действия (All / None, перетаскивание приоритета) меняют только живые ноды;
  записи пропавших остаются на своих местах (`dragShown` в `80-drag.js`).

## Источник или сервер, выключенный в Nodes

Два переключателя на вкладке Nodes: у источника (`enabled`) и у каждого сервера
(`source.disabledNodes[]` — id выключенных). Оба **никогда не меняют настройки** тех, кто
их использует: включил обратно — источник / сервер снова в тех же профилях и цепочках, с
теми же галочками и приоритетом.

UI выбора серверов везде одинаковый — без чекбоксов и тумблеров: используемый /
выбранный сервер **обведён рамкой**, тап переключает. Галочка целого источника в
редакторе профиля осталась (у неё есть состояние «частично»).

**Режим редактирования** (чтобы в обычном виде нечего было задеть случайно):
- Nodes: кнопка ✎ слева от вкладок Simple / Profiles, в правке — ✓.
  Обычный вид: без ⋮⋮, тумблеров и рамок; тап по
  серверу — его меню, тап по мс — пинг; выключенные приглушены, у выключенного источника
  метка OFF. Режим правки: ⋮⋮ источников, тумблер источника, рамки у серверов, тап по
  серверу — вкл / выкл. Шапка не меняется: поиск, «пинг всех», ⋮ и «+» доступны и в правке.
  Цепочки (на обеих вкладках) в правке: ⋮⋮, у каждого конца — все его серверы в рамках, тап —
  вкл / выкл только для этой цепочки (`inOff` / `outOff`, как галочки в редакторе цепочки).
- Строка под именем источника — коротко, чтобы редко переносилась: формат · «18 nodes» · возраст
  обновления («2h», «1d»). Если есть нерабочие (выключенные или пропавшие из подписки) —
  «16/18 nodes»: рабочие / все. Если не влезает, переносится между пунктами, а не обрезается.
- Route: режим правки — ✎ слева от Simple / Profiles (✓ пока включён; при каждом открытии
  выключен). В правке видны ⋮⋮ записей, а в развёрнутой строке — переключатель Fastest /
  Priority и ⋮⋮ серверов; без правки их нет, строка лишь подписывает, как выбирает сервер
  (номера в Priority видны всегда). Случайно закрепить запись нельзя — закрепляет только
  кнопка AUTO / MANUAL на строке, тап по карточке лишь разворачивает её.
- Редакторы записи / профиля / цепочки отдельного режима не имеют.

Выключенный сервер остаётся в Nodes (без рамки, приглушён и зачёркнут, в мете «N off»), а
везде остальном его нет: в записях, в редакторах профиля / источника / цепочки, в выборе
ноды, в Auto, в «пинговать все». Групповые действия (All / None, перетаскивание) его
галочку и место не трогают. Для остального приложения источник = `liveNodes(s)`.

Пока выключен:
- его собственная запись в режиме «Простой» скрыта, в пикерах цепочек его нет;
- запись / профиль / сторона цепочки, у которых без выключенного **не осталось ни одной
  ноды**, — «сломанные» (`brokenBy(id)` — что включить: `{sid}` источник или
  `{sid, nid}` сервер; считается как «живых нет, а со всем включённым в Nodes — есть»):
  серые, с красной рамкой, тег OFF, под списком (место в приоритете хранится), Auto их
  пропускает, закреплённая вручную такая запись уступает Auto. Тап — объяснение «то, через
  что она работает, выключено в Nodes» + «Switch on X» для каждого + «Edit …»;
- в Простом режиме запись источника, у которого выключены все отмеченные для неё
  серверы, тоже «сломанная»;
- профиль, у которого есть другие рабочие источники, работает на них без пометки;
- в редакторе профиля выключенный, но используемый источник показан серым
  («off in Nodes»), галочкой его можно только убрать; если профилю без выключенных нечего
  использовать — жёлтое предупреждение с их именами, сохранение заблокировано; в
  редакторе цепочки так же для каждого конца.

Разница с галочками записей: выключение в Nodes — глобальное («этот сервер мне сейчас не
нужен нигде»), галочки (`offNodes`, `profile.nodes`, `inOff/outOff`) — выбор конкретной
записи.

## Подписка не загрузилась

Первая загрузка или обновление подписки упали → на карточке источника красная полоса
(SourceErrorStrip): «Could not load» (серверов ещё нет) или «Update failed» + сколько
назад, текст ошибки и **Retry**. Хранится с источником (`s.lastError = {msg, at}`,
переживает перезапуск), снимается следующей удачной загрузкой. Неудачное обновление по
таймеру ядра пишет его так же (subscription-parsing.md → «Автообновление»). Серверы прошлой удачной
загрузки продолжают работать. Retry = обновление; источник, который ни разу не
загрузился, загружается заново как новый.

## Сервер вручную, ссылка сервера, QR

Форма сервера (Nodes → + → Server; ✎ сервера в ручной группе):
- **Share link** — многострочное поле: ссылка заполняет поля ниже; несколько ссылок
  (по одной на строку) — вместо полей подпись «N servers» и кнопка «Add N servers»,
  добавляются все, каждая со своим именем из `#фрагмента`. Разбирает ядро (тот же парсер,
  что у подписок): vmess base64-JSON, ss legacy и SIP002, IPv6 в скобках, anytls, hy2 с
  диапазоном портов. Со ссылкой адрес вручную не нужен («Address is required» — только без
  ссылки).
- **Без ссылки** — протокол (VLESS, VMess, Trojan, SS, HY2, TUIC, AnyTLS, SOCKS), адрес,
  порт и секрет; подпись поля секрета по протоколу: UUID; Password; Method:password (ss);
  UUID:password (tuic); User:password, необязательно (socks). Outbound строит ядро
  (`manual.dart`). Имя, набранное руками, важнее имени из ссылки; флаг в нём уходит во флаг.
- **Один сервер дважды**: id — хэш сервера, в группе он один раз; повтор не добавляется
  («already in the group», при пачке — «Added N, M already there»).
- **Правка** меняет адрес / порт / секрет / имя и **outbound** (тот же протокол: TLS,
  транспорт, flow сохраняются), а id остаётся прежним — профили, цепочки, закрепление и
  правила со ссылкой на сервер не теряют его. Пинг — уже по новому адресу (кэш по серверу).

⋮ источника: **Copy URL** — URL подписки в буфер обмена; **Show QR code** — QR этого URL.
⋮ сервера: **Copy share link** / **Show QR code** — ссылка сервера (ядро, `share.dart`:
vless/vmess/trojan/ss/hy2/hysteria/tuic/anytls/socks); у http / wireguard и `unsupported`-серверов ссылки нет —
тост вместо копирования. QR-лист (ShareSheet): код тёмным по светлому в любой теме, под ним
текст (выделяется тапом) и Copy.

## Удаление источника / сервера

Всегда с подтверждением. В нём — что станет с каждым, кто это использует (`deleteImpact`:
списки обоих режимов пересчитываются «как будто этих серверов нет», `simExclude`):
- текущее подключение идёт через удаляемое → переподключится через следующий рабочий;
- цепочка, у которой удаляемый источник — конец → удаляется вместе с ним (красным);
- запись / профиль / конец цепочки остаётся без серверов → не подключится, пока не
  отметить другой (красным);
- профиль теряет N из M серверов; цепочка: «вход / выход теряет N» (для Priority-выхода —
  «выпадает из порядка приоритета») (жёлтым);
- правила и приложения, у которых цель — удаляемое (источник, его нода, цепочка, которая
  удаляется вместе с ним) → «loses its target — traffic goes …» по их «If unavailable»
  (`targetImpact`, см. `rules.md` §0) (жёлтым);
- ничего не затронуто → «Not used in any profile, chain, rule or app».

Удаление профиля / цепочки — кнопкой Delete внутри их редактора (✎ на карточке), тоже с подтверждением
(`confirmDeleteEntry`): цепочки, у которых удаляемый профиль — конец, переезжают на первый
другой профиль (если оба конца совпали — удаляются); правила с этой целью — как выше.
Последний профиль тоже удаляется (его цепочки — вместе с ним): «нет профилей» — обычное
состояние, док пишет «No profiles yet · Create one in Nodes» (см. «Главный экран»).
После удаления все настройки, ссылающиеся на эти серверы, удаляются насовсем (включая
`gone` удаляемого источника). Ноды подписки не удаляются по одной (вернутся при
обновлении) — для них есть выключение.

## Каталог (Nodes) и Route

Всё, куда можно слать трафик, создаётся, редактируется и удаляется **только в Nodes**. У Nodes
две вкладки — каталог двух режимов (`catalogOrder`):
- **Simple** (`simple`): подписки, группы серверов и цепочки из двух источников;
- **Profiles** (`profiles`): профили и цепочки из двух профилей.

Вкладки переключаются тапом или свайпом всего списка (палец ведёт список, >20% ширины —
переключение; начинается только при явно горизонтальном движении; не ближе 24 px к краю
экрана — там жест «назад» Android). Вкладка — только просмотр: режим маршрута она не меняет;
точка на вкладке — режим, который сейчас использует Route. «+» на Simple — подписка /
сервер / цепочка, на Profiles — профиль / цепочка. Карточки профилей и цепочек: из чего
состоит, через какой сервер пойдёт сейчас и пинг (цепочка — вход → выход и сумма), раскрытие —
её серверы; на карточке прямо кнопки ⚡ (пинг) и ✎ (редактор; Delete — внутри редактора), без меню ⋮. У источника в ⋮ — «Route settings»
(серверы этой записи, Fastest / Priority, в Auto). ✎ — перетаскивание порядка внутри вкладки.

**Route** (бывший список Simple / Profiles, открывается с главной) отвечает только за
основной поток. Лист открывается над нижним блоком: доходит до верхней кромки дока, низом
уходит под вкладку с кнопкой питания; док и нижняя навигация остаются поверх и работают
(тап по доку закрывает Route, переход на другую вкладку — тоже). Под шапкой — переключатель режима Simple / Profiles (анимированный:
подсветка переезжает, список въезжает с той же стороны). В шапке — бейдж Auto / Manual.
Строка: ⋮⋮ (перетаскивание приоритета, только в режиме правки ✎) · карточка · ⚡ справа — пинг
всех серверов записи (всегда, и в правке). Строка названия карточки начинается с кнопки
AUTO / MANUAL (одной ширины, на всех строках на одном месте), за ней в правке — тумблер
«Use in Auto» (без правки вместо него у выключенной записи бейдж «not in Auto»), потом
название. Шеврона нет — разворачивает тап по карточке. Флаг в строке мелкий, справа только
⚡ — чтобы влезало больше имени ноды. Флаг везде — часть имени ноды: длинное имя переносится
под флаг, а не рядом с ним; пинг в шапке строки стоит на уровне первой строки имени. Кнопка на текущей строке показывает режим (AUTO / MANUAL,
подсвечена), на остальных — MANUAL приглушённо; тап по ней на другой строке закрепляет
её (Manual), на закреплённой — возвращает Auto. Тап по карточке разворачивает её (у
цепочек разворота нет; развёрнутые строки независимы — раскрытие одной не сворачивает другие): Fastest / Priority (только в правке; без неё — подпись режима), ⟳ обновить (подписку строки; у профиля — все подписки, из которых он берёт
серверы; ручные источники не обновляются, кнопки нет), серверы (в
Priority с номерами, ⋮⋮ — в правке). **Manual на сервер**: тап по серверу развёрнутой строки —
Manual на эту запись и на этот сервер (`pinnedNode` = `sid::nid`, подсвечен как бейдж MANUAL);
соединение идёт только через него, без failover, даже если он не отвечает. Повторный тап —
закрепление сервера снимается, запись остаётся Manual и выбирает по Fastest / Priority. Любой
другой выбор (другая запись, AUTO / MANUAL, бейдж Auto) снимает закрепление сервера; сервер
пропал или выключен — запись выбирает сама. Для ядра — `selector`, удерживаемый на нём.
Тап по мс — по-прежнему пинг. Остальное редактирование записей — в Nodes.

Приоритет: по умолчанию Route **следует порядку каталога** (`routeCustom[mode] = false`).
Перетаскивание в Route даёт маршруту свой порядок (`routeCustom[mode] = true`, подпись «Own
priority order»): порядок в Nodes больше на него не влияет, новые записи добавляются в конец;
«Follow Nodes order» (под списком или в ⋯) возвращает к каталогу. `syncCatalog()` держит
каталог, `sourceOrder` и оба маршрута согласованными после добавлений / удалений.

## Режимы

`connectMode`: `simple` (по умолчанию) | `profiles`. У каждого режима свои:
список приоритета (`order`), закреплённая запись (`active`), флаг Auto (`auto`); меняется
только в Route.

- **Простой**: записи — сами источники + цепочки из двух источников. У источника
  `offNodes` — выключенные для этой записи ноды.
- **Профили**: записи — профили + цепочки из двух профилей. Профиль: целый источник
  (включая будущие ноды) или отдельные ноды.

Юнит (то, чем является запись или конец цепочки) → список нод: `unitRefs(id)` — живые
ноды включённых источников минус выключенные.

## Auto / Manual

- Auto: подключается первая запись списка с `inAuto`, которая **не заведомо мёртвая**
  (`mayWork`: хоть один её сервер не мёртв; для цепочки — так у входа и у выхода).
  Мёртвый (`knownDead`) = `failAfter` таймаутов подряд, последний замер свежее 5 минут
  (`PING_FRESH_MS`; пока сервер перемеряется, прежний счёт держится). Незамеренные серверы
  (свежий старт до пинга при запуске, новая подписка), один потерянный пинг и старый
  таймаут запись не выбивают: после перезапуска Auto не отдаёт первое место следующей
  записи только потому, что верхнюю ещё не пинговали. Замеры пингов хранятся в снимке
  состояния и переживают перезапуск.
- **Auto в ядре** (пока подключено) — AutoService (`core/lib/src/auto.dart`, общий для
  jormd и Flutter; API — `docs/core.md`):
  - План — не одна запись, а маршруты: **все записи Auto** (якорь — та, с которой
    стартует `selector`); в Manual — одна запись. Над маршрутами — `selector`. Переход на
    любую запись — переключение селектора, **без перезапуска** sing-box; перезапуск — только
    когда меняется состав плана.
  - Каждые `checkEvery` ядро меряет сервер, на котором стоит текущий маршрут и маршруты
    выше (с `returnTo: never` — только текущий), раз в `warmEvery` — ещё `standby` запасных
    ниже. Замер — одна функция ядра (`_ping` в `auto.dart`); шаг «несколько чекеров, живой,
    если ответил хоть один» (раздел ниже) заменит только её.
  - Текущий не ответил → повторы только его, с паузой `retryPause` (0,5 с); `failAfter`
    промахов подряд → маршрут мёртв: сразу вместе меряются маршруты выше и запасные,
    ответил кто-то — переход на первый по приоритету. Нет — следующие маршруты по приоритету
    **пачкой по 10** параллельно, первый ответивший по приоритету. Молчит и вся пачка —
    **«нет сети»** (`noNet`): ничего не переключается (селекторы, системный прокси), никто не
    помечается мёртвым и не штрафуется, раунд раз в 10 с. Прямых запросов мимо VPN нет.
  - Раунд, в котором не ответил никто, никого не помечает: промахи всех маршрутов, кроме
    текущего (он копит счёт до `failAfter`), откатываются. Так «в дороге связь то есть, то
    нет» не выбивает записи.
  - **Без разрыва соединений**: у `proxy` и у групп маршрутов (Priority-`selector`, Fastest-
    `urltest`) `interrupt_exist_connections: false` — и при отказе, и при возврате открытые
    соединения остаются на старом маршруте. Ядро их проактивно не рвёт; после ухода с
    мёртвого маршрута (или Priority/Fastest-сервера) смотрит таблицу соединений (поток API service sing-box) и
    закрывает только **зависшие**: счётчики байт не менялись 10 с (повтор каждые 10 с, до 6
    раз, пока на старом что-то есть и туда не вернулись). Соединения, по которым идут байты,
    живут дальше.
  - Возврат наверх — `returnTo` (Settings → Auto mode): `always` (по умолчанию) — маршрут выше
    ответил `failAfter` раз подряд и не медленнее текущего больше чем на `threshold`;
    `faster` — только если быстрее текущего на `threshold`; `never` — не возвращаться до
    переподключения. То же правило — для Priority-сервера внутри маршрута.
  - **Защита от мигания** (`flapGuard`, по умолчанию вкл): падение записи — `failAfter`
    промахов, пока в том же раунде ответил **другой** маршрут (не ответил никто — это «нет
    сети», не падение). Каждое падение удваивает испытательный срок: запись получает трафик
    обратно, только проотвечав подряд 1, 2, 4 … мин, но не больше `flapMax` (30 мин). Счёт
    сбрасывается после `flapReset` (15 мин) стабильной работы на ней (текущая и отвечает).
    На отказ (уход с мёртвой) срок не влияет — только на возврат. Со второго падения —
    событие «запись X нестабильна» (`status.auto.lastUnstable`), тост под General → «When
    Auto switches» (экран Notifications — позже).
  - Внутри маршрута: Fastest — `urltest`; не ответил его сервер — ядро просит группу
    перемерить всех (urltest сразу берёт живой, молчащие считаются таймаутами). Priority —
    `selector`: после `failAfter` таймаутов ядро переводит его на первый ответивший по
    порядку, а на сервер выше возвращает по правилу маршрутов. Сервер, закреплённый в Manual,
    ядро не двигает.
  - UI показывает то, что сообщило ядро: док и Route — запись и сервер, на которых оно стоит
    (`coreRoute`, а не своя догадка); его замеры идут в кэш пингов (так `knownDead` UI
    согласен с ядром); при переключении записи или Priority-сервера — тост, если включено
    General → «When Auto switches». Пинг и переключения ядра sing-box не перезапускают;
    переподключение — только когда меняется состав плана (порядок / Use in Auto / серверы
    записей, Manual, Global, системный прокси, `checkEvery` / `threshold` — они в urltest).
    Остальные настройки Auto mode уходят в работающее ядро без переподключения
    (`POST /api/auto`).
  - sing-box упал: ядро сразу возвращает системный прокси (браузеры не смотрят в мёртвый
    порт), перезапускает sing-box с тем же планом на маршруте, где был Auto (паузы 1 / 4 /
    15 с, счёт сбрасывается после минуты работы), UI — тостами «starting it again» / «started
    again». Три неудачи — отключено с ошибкой.
- Все записи выключены из Auto (`inAuto` нигде нет) — Auto не выбирает ничего (первую
  запись «по умолчанию» не берёт). Док пишет «Nothing in Auto · turn on Use in Auto in Route»;
  кнопка питания не подключает, а показывает алерт с причиной и кнопкой «Open Route» (Route
  сразу в режиме правки, где тумблеры). Manual (MANUAL на строке) работает как обычно. Если
  последнюю запись выключили при подключении — туннель не рвётся, держится на своём сервере
  до отключения (тост об этом).
- Settings — список разделов (Auto mode, Appearance, General, Connection, Data); каждый
  пункт открывает своё окно (sheet), в Appearance подписью видна текущая тема.
- Appearance → **Text size** 90–120% (шаг 5%): масштабирует списки, карточки и тела окон
  целиком; заголовки, вкладки и нижняя навигация не меняются. Верхняя граница выбрана так,
  чтобы на экране 320 px ничего не вылезало (проверяется). Flutter: `textScaler` с тем же
  ограничением, заголовки — `TextScaler.noScaling`.
- Все окна (sheets) открываются до верха экрана и закрываются свайпом шапки вниз. Нижняя
  навигация видна и работает всегда: окна и затемнение кончаются над ней; тап по вкладке
  закрывает открытые окна и переключает вкладку.
- Системное «назад» (телефон, браузер, мышь, Esc) закрывает верхнее окно (меню и диалоги —
  тоже окна), а не приложение. Если окно открыто из пункта другого окна, которое при этом
  закрылось (Add → Subscription, ⋮ → Delete → подтверждение), «назад» возвращает то окно
  в прежнем виде. Закрытие ×, свайпом, тапом мимо или кнопкой Done «назад» не запоминает.
  Без открытых окон «назад» со вкладки Nodes или Settings ведёт на Home, с Home — выход.
  Во Flutter это PopScope и навигатор.
- Настройки — **Settings → Auto mode** (`autoCfg`, `55-automode.js`); карточка Auto mode
  на главной — просто ссылка (иконка, название, ›): открывает то же окно Auto mode поверх главной,
  без перехода во вкладку Settings (так же карточка DNS → окно DNS). Вкл / выкл Auto —
  бейдж Auto в списке Simple / Profiles (в настройках тумблера нет):
  | Поле | Значения | Контрол | Смысл |
  |---|---|---|---|
  | `threshold` | 0–1000 мс, **50** | поле ввода | гистерезис: сервер сменяет текущий, только если быстрее на столько; неверный ввод — откат |
  | `checkEvery` | 10 с – 60 мин, **1 мин** | окно: число + единица (seconds / minutes) | период проверки текущего маршрута и маршрутов выше |
  | `standby` | 0–20, **2**; 0 = выкл | слайдер «Spare servers», число над ним («next 2» / «off») | сколько следующих по приоритету записей (запасных) пинговать заранее; заменил тумблер `keepWarm` (старый план с `keepWarm: false` = 0) |
  | `warmEvery` | 10 с – 60 мин, **1 мин** | окно: число + единица; строка видна при `standby` > 0 | период пинга запасных; меряются на проверке текущего, так что не чаще `checkEvery` (раньше срока до 1 с — ок) |
  | `failAfter` | 1–5, **2** | степпер ‹ › | таймаутов подряд до ухода с сервера |
  | `retryPause` | 0,1–10 с, **0,5 с**; выключения нет | поле ввода (десятые, запятая тоже), «s» | пауза между повторами текущего после промаха; заменила зашитые 10 с |
  | `returnTo` | `always` / `faster` / `never`, **always** | выпадающий список «Return to a higher entry» (группа «Going back up» с [?]) | когда запись выше забирает трафик обратно (см. выше); старый план без поля = always |
  | `flapGuard` | **да** | тумблер «Flap protection» | защита от мигания |
  | `flapMax` | 1–60 мин, **30** | поле ввода, «min»; видно при `flapGuard` | потолок испытательного срока |
  | `flapReset` | 5–60 мин, **15** | поле ввода, «min»; видно при `flapGuard` | стабильной работы до сброса счёта падений |
  | `speedOnFail` | нет | тумблер | после неудачных запросов ещё и замер скорости текущего сервера (логику порога / реакции — позже) |
  | `pauseScreenOff` | **да** | тумблер | не проверять при выключенном экране, проверить при пробуждении |
  | `subsEvery` | секунды, 10 с – 30 д, **12 ч**; 0 = выкл | окно: число + единица (seconds / minutes / hours / days); показ «30 min» / «12 h» / «2 d» | глобальный период обновления подписок; про свой период подписки — в [?] |
- `source.updateInterval`: `'auto'` (по умолчанию) = период провайдера
  (`profile-update-interval`, не чаще раза в час), если он его прислал, иначе `subsEvery`;
  `subsEvery` = 0 выключает и его. Число часов — свой период (0 = не обновлять). В форме
  подписки пустое поле = auto. Обновляет по таймеру ядро (subscription-parsing.md →
  «Автообновление»).
- `source.reloadAfterUpdate` («Reconnect after update»): выкл — обновление подписки не
  перезапускает sing-box, её новые серверы войдут в конфиг при следующем переподключении по
  другой причине; вкл — переподключение сразу, если план изменился.
- **Запасные (`standby`, «Spare servers»)**: внутри юнита sing-box `urltest` и так пингует все свои
  outbound'ы по `interval`; standby нужен для перехода между *записями* списка (и для
  Priority-выхода). Стоимость: один URL-тест ≈ 1–5 КБ; 3 маршрута раз в минуту — порядка
  сотен КБ в сутки; при 20 запасных стоит поднять `warmEvery`. Реальная цена на мобильном — пробуждения радио, поэтому пинги
  standby идут пачкой в том же тике, что и проверка текущего, и ставятся на паузу при
  выключенном экране / режиме энергосбережения. Выигрыш — переключение без поиска: сразу
  на заведомо живой.
- Тап по записи закрепляет её (Manual), повторный тап — назад в Auto.
- Скрытые записи (выключенный источник) в выборе не участвуют.

## Отказ ноды: упавшие запросы и запасные проверки

Цепочка решений ядра (`auto.dart`; уведомления пока тостами, экран Settings → Notifications — позже):

1. **Запуск** — sing-box закрыл соединение через текущую запись, не получив ни байта ответа.
   Источник — поток закрытых соединений **API service** sing-box (gRPC, `sbapi.dart`), а не лог:
   в событии есть сервер (тег outbound'а), цепочка, адрес и сколько байт ушло / пришло.
   Отправлено 0 — соединение не открылось (нода: dial, handshake, сервер лежит); отправлено > 0 —
   запрос ушёл, ответа нет (нода или сайт). В логе клиента второго случая не видно вовсе
   (VLESS и т. п. ничего не сообщают), поэтому только API. Первый такой запрос сразу запускает
   проверку записи (не ждёт `checkEvery`); следующие за `failWindow` (10 с) копятся к ней.
   Незаметного повтора самого запроса нет: о падении мы узнаём, когда соединение уже закрыто
   (повтор на этапе dial возможен только внутри sing-box — отложено).
2. **Проверка ноды с запасными проверками** — сначала тест-URL; не ответил — сразу все
   **запасные проверки** (Settings → Connection → Backup checks: по умолчанию
   cp.cloudflare.com, gstatic, msftconnecttest, captive.apple.com; пресеты и свои адреса).
   **Живая, если ответила хоть одна**; время — тест-URL'а, иначе первой ответившей. Так же
   меряет и пинг каталога. TCP-пинг до порта сервера живость не доказывает (мост RU → EU с
   мёртвым EU-плечом, провайдер, режущий трафик истёкшей подписки) — только запрос через ноду.
   Запасные проверки идут с настройками Auto (`plan.auto.checkers`), смена — без переподключения.
3. **Нода живая** → сайты, по которым запрос ушёл без ответа (порты 443 — TLS-рукопожатие,
   80 — HEAD; другие порты и IP на 443 не проверяются): через ноду снова — открылся → разовый
   сбой; нет → через **другую запись Auto, которая отвечает** (не напрямую: не светить адрес
   провайдеру): там открылся → тост «A does not open via N — it does via M» с кнопкой **Rule**
   (форма правила: домен A → цель M); пара запись + сайт не чаще раза в час; там тоже нет —
   сайт лежит, только лог. Не сделано: сводное уведомление по нескольким сайтам, «Не показывать для A».
4. **Нода не отвечает** → повторы с `retryPause`, `failAfter` → переход (шаг 3a: без разрыва,
   перебор всех записей пачками по 10, первая ответившая по приоритету). Все проверенные
   серверы одной подписки так, а сервер другого источника отвечает → тост «X: its servers do not
   respond — contact the subscription provider's support» (раз, пока хоть один не ответит).
   Помеченную запись перепроверяет обычный раунд; вернулась — по защите от мигания.
   Отдельного значка «не пропускает трафик» в UI пока нет (как и раньше — мёртвый пинг).
5. **Нет сети** — ОС без сети (sing-box пишет в лог `missing default interface`, вернулась —
   `updated default interface`, тогда сразу проверка) или при переборе не ответил никто.
   Прямых запросов мимо VPN не делаем. Никого не помечаем и не штрафуем, перепроверка раз в
   10 с (в «нет сети» — только текущая и первая пачка). Всё заморожено: системный прокси не
   снимается, селекторы не трогаются, «If unavailable» не срабатывает — трафик остаётся в
   туннеле, утечки при возврате сети нет.

## Выбор ноды внутри юнита

- Запись (источник в Простом режиме, профиль), `pickMode` (по умолчанию `fastest`):
  - `fastest` — самая быстрая живая (`bestAlive`) из отмеченных; sing-box: `urltest`;
    списки серверов в режиме Fastest (карточки профилей и цепочек, редакторы, настройка записи)
    всегда отсортированы по пингу: быстрейший сверху, мёртвые внизу;
  - `priority` — первая живая по `pickOrder` (ключи `sid::nid`) сверху; sing-box —
    `selector`, как у Priority-выхода ниже.
  Это настройка **записи**, не подписки: у источника она хранится рядом с `offNodes`
  (его запись в Простом режиме), у профиля — в профиле. В Nodes порядка нет.
  UI: переключатель Fastest / Priority (`PickModeSwitch`: плашка переезжает, как у Simple / Profiles в
  Route; тап или свайп; справа от него — ⚡ «пинг всех» в редакторах профиля и цепочки) в настройке записи (в Priority — ⋮⋮ и номера у всех
  серверов, отключённые для записи тоже упорядочены, как у выхода цепочки) и в редакторе
  профиля (блок «Connect through»: в Priority — список выбранных серверов с ⋮⋮). В
  списке у такой записи метка PRIORITY. То же прямо в Route: строка источника или профиля
  (не цепочки) разворачивается тапом по карточке — переключатель и серверы записи (в Priority с ⋮⋮ и
  номерами); исключать серверы там нельзя, это в редакторах. Невидимые сейчас серверы (выкл. в Nodes,
  пропавшие) при перетаскивании сохраняют место; при удалении / Forget ключи чистятся.
- Вход цепочки: всегда самая быстрая живая из отмеченных (`urltest`).
- Выход цепочки, `exitMode`:
  - `fastest` — самая быстрая живая из отмеченных (`urltest`);
  - `priority` — первая живая по `exitOrder` сверху, при падении — следующая.
    В sing-box нет outbound'а «по порядку»: `urltest` берёт самый быстрый (с `tolerance`),
    `selector` — тот, что выбрали. Поэтому Priority = `selector` из нод выхода, который
    **переключает наш Dart-код** (через API service sing-box) по результатам пингов: первая живая
    сверху.
  Ноды, которых нет в `exitOrder`, идут после, в порядке источника.
- Цепочка = выходной outbound с `detour` на входной.
- Редактор цепочки: вариант, занятый другим концом («used as exit · tap to swap»), по тапу
  меняет вход и выход местами (снятые серверы уходят со своим концом, порядок выхода — заново);
  при двух профилях / источниках иначе цепочку не развернуть. В строках серверов цепочки
  источник не подписывается, если конец из одного источника (он уже в заголовке конца).

## Валидация: хотя бы одна нода

- Профиль, вход и выход цепочки: если не отмечено ни одной живой ноды — жёлтое
  предупреждение, сохранение заблокировано.
- Настройка источника (Простой режим) применяется сразу; если при закрытии не отмечено
  ничего — выбор откатывается к состоянию на момент открытия.

## Пинг

- **Что меряем** — задержку по уже открытому соединению через ноду: два запроса к тест-URL
  подряд, показываем второй (как Karing). Время открытия нового соединения (с рукопожатиями,
  у мостов в 3–4 раза больше) не показываем. Реализация — docs/core.md → Пинг.
- Один кэш на всё приложение, ключ — **вариант ноды** (`pingKey` = `protocol://address:port#id`;
  `id` различает варианты одного сервера — SNI, отпечаток, транспорт…, см.
  subscription-parsing.md → дедуп): мёртвый вариант не выглядит живым из-за соседнего, а один
  и тот же вариант из двух подписок — одна запись и один пинг. Значение: мс, `-1` = таймаут,
  время замера, `fails` = таймаутов подряд (для `failAfter`, сбрасывается ответом). Сюда же
  пишутся замеры Auto в ядре (новее имеющихся; пинг в полёте важнее).
- Сохранённые замеры старого формата (ключ `protocol://address:port`) переносятся, только если
  у сервера ровно один вариант (среди нод и пропавших); иначе они ничьи и отбрасываются.
  Старый `-1` = один таймаут.
- Свежесть 5 минут (`PING_FRESH_MS`): старше — перемерить перед использованием.
- Пинг пары (вход → выход) — выход через `detour` на вход.
- **Общий пинг** (⚡ в шапке Nodes): все включённые источники одной пачкой, серверы
  вперемешку по источникам (1-й каждого, 2-й каждого…) — все сеты заполняются одновременно.
- **Порядок пачки** (любой «пинг всех», пинг при открытии): по кэшу — сначала живые по
  возрастанию мс, потом ни разу не мерянные, мёртвые (`-1`) в конце (`byPingRank`). Ядро
  пингует в порядке списка, так что рабочие серверы получают свежие цифры первыми, а мёртвые
  (каждый ждёт полный таймаут) не занимают воркеры в начале.
- **При открытии приложения** (Settings → General → «Check servers on launch», по умолчанию вкл):
  пингуются все серверы первых `1 + standby` записей с `inAuto` **от верха** приоритета Route
  (не от текущего выбора: после перезапуска текущий выбор может оказаться ниже только потому,
  что верхнюю ещё не мерили), в Manual — ещё и закреплённая запись, плюс все цели включённых
  правил и приложений (`src:` / `node:` / `profile:` / `chain:`) — поток правил проверяется так
  же, как основной. Сервер из нескольких записей пингуется один раз. Цель: список, Fastest
  и failover сразу работают на свежих цифрах.
- **Тап по задержке в доке** (число + «ms» в постоянной рамке): пинг идёт пачками, пока не
  ответят 10 серверов (`DOCK_PING_ENOUGH`) или не будут измерены все. Первая пачка — первые
  3 сервера первых 4 записей Auto по приоритету (в Manual первой идёт закреплённая; сервер —
  в порядке записи: Priority — по списку, Fastest — лучшие по кэшу; цепочка — по 3 с каждого
  конца). Дальше — остальные серверы списка Route (сначала записи Auto, потом прочие) по 8.
  Пока идёт — по рамке бежит огонёк; повторный тап останавливает (пачка в полёте
  досчитывается) и обновляет цифры. Route при этом не открывается.

### Speed Test сервера
Nodes → ⋮ сервера → **Speed test**: штатный network quality test sing-box через этот сервер
(отдельный sing-box с одним сервером, подключение не трогается; серверы Apple mensura).
Лист SpeedCard: Download / Upload (Мбит/с), Latency (мс), Responsiveness (RPM); цифры растут по
ходу замера (задержка → загрузка → отдача, до ~20 с), подсвечена текущая фаза; внизу статус
(«Download…», «Done» или текст ошибки) и Run again. Закрыли лист — замер останавливается.

## Проверка маршрута цепочки (информационная)

1. Входные ноды: кэш, если все моложе 5 мин, иначе пинг всех.
2. Живые входы от быстрых к медленным; для каждого — пинг всех выходов через него
   (выходы параллельно, входы по очереди). Нода не пингуется сама через себя.
3. Если кэш использован и первые 2 входа не дали ни одной пары — кэш устарел:
   перепинговать входы и начать заново (один раз).
4. Результат: рабочие пары по сумме задержки. Цепочку и Auto не меняет. Пользователь
   может остановить проверку вручную (досрочной остановки по N пар нет — решено).

## Главный экран (ConnectDock)

Показывает, через что идёт трафик сейчас:
- Простой: `Sub|Servers` + имя источника; строка ниже — нода;
- Профили: `Profile` + имя; ниже — источник › нода;
- Цепочка: `Chain` + имя; ниже — нода входа → нода выхода.
Справа — задержка (для цепочки — сумма двух хопов) в рамке: тап — пинг (см. «Пинг»), бейдж
AUTO / MANUAL. Иконки слева и стрелки справа нет; тап по остальному доку открывает Route.
При подключении запись и серверы — те, на которых реально стоит Auto в ядре (см. «Auto / Manual»).

**Пустой каталог** (первый запуск или всё удалено — в текущем режиме нечего подключать):
док пишет «No servers yet · Add in Nodes» (Профили — «No profiles yet · Create one in
Nodes»); тап по доку или по кнопке питания ведёт в Nodes и открывает «+» (без источников —
на вкладке Simple: профилю не из чего собираться). В live-режиме «This session» до первого
подключения — 0 B.

- **Проверка по неудачным запросам** (всегда, без настройки): `checkEvery` — это проверка
  текущего маршрута (+ standby) по таймеру; кроме неё, если через текущий сервер пошли
  неудачные запросы, он пингуется сразу, не дожидаясь таймера (дальше — как обычно:
  `failAfter` таймаутов подряд → уход). Источник сигнала в sing-box — ошибки соединений
  outbound'а — поток закрытых соединений API service (сделано в 3.7, см. «Отказ ноды»).

Окно периода — маленький диалог по центру: поле числа + выбор единицы, Cancel / Save
(Enter = Save). Хранится в базовой единице (секунды / часы); открывается в самой
крупной единице, на которую значение делится нацело (48 ч → 2 days). Поле числа
узкое, единицы в окне — полными словами; в строке настройки — коротко (2 d, 1 min). Вне диапазона —
тост с допустимым диапазоном, окно не закрывается.
