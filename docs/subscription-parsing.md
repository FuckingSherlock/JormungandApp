# Логика парсинга подписок

## Проблема

Серверы подписок возвращают разные форматы и разные наборы нод в зависимости от User-Agent запроса. Karing решает это перебором UA до первого успешного ответа — теряет ноды и не оптимален по запросам.

Цель: получить максимально полный список нод с минимальным количеством HTTP-запросов.

---

## Форматы подписок

| Формат | Детект | Типичный UA |
|--------|--------|-------------|
| sing-box JSON | `Content-Type: application/json` или тело начинается с `{` + есть `"outbounds"` | `sing-box/1.x.x` |
| Clash/Meta YAML | `Content-Type: text/yaml` или строка `proxies:` в начале строки | `mihomo/1.x.x`, `clash-verge` |
| Base64 URI-list | тело — валидный base64, после decode строки `vmess://`/`vless://`/`trojan://`/`ss://` | `v2rayN`, `NekoBox` |
| URI-list (plain) | строки начинаются с известных схем без base64 | любой |

Формат определяется **по телу ответа** (с подсказкой `Content-Type`), не по UA — это позволяет
слать один запрос и знать что получили. Base64, внутри которого sing-box JSON или Clash YAML,
уходит в нужный парсер. Определённый формат приходит в UI для чипа на карточке
(`source.format`: `sing-box` / `clash` / `base64` / `links`; при нескольких UA — формат первого
UA, давшего ноды).

---

## Стратегия: Discovery + Cache

### Первое добавление подписки

1. Слать **параллельно** запросы с тремя UA:
   - `sing-box/1.14.2` — нативный формат, часто содержит Reality/Hysteria2
   - `mihomo/1.19.28` — Clash.meta YAML, широко поддерживается
   - `ClashMeta` — запасной вариант clash
2. Для каждого ответа: детектировать формат → парсить → получить список нод
3. Дедупликация по `(address, port, protocol, uuid/password)` — не по имени, имена могут отличаться
4. Записать в кеш подписки:
   ```
   subscription.ua_strategy = [
     { ua: "sing-box/1.14.2", unique_node_count: 47, etag: "abc123" },
     { ua: "mihomo/1.19.28",  unique_node_count: 12, etag: "def456" },  // 12 нод которых нет в sing-box ответе
   ]
   ```
   Если UA давал 0 уникальных нод — он исключается из стратегии.

### Обновление подписки (повторные запросы)

1. Слать запросы **только по закешированным UA** (обычно 1, редко 2)
2. Добавлять заголовки `If-None-Match: <etag>` и `If-Modified-Since: <date>`
3. Получили `304 Not Modified` → ноды не изменились, пропускаем парсинг
4. Получили новый контент → парсить → обновить ETag в кеше. Копия явно старее применённой (по `fresh` записи
   стратегии, «Какая копия свежее» ниже) не применяется: список остаётся, строка в Raw, обновление считается выполненным

**Happy path обновления: 1 запрос + 304 = 0 работы.**

5. Сравнить новый список с текущим по `id` ноды (ключ дедупликации): пропавшие ноды не
   удаляются, а уходят в `source.gone[]` вместе с выбором пользователя; вернувшиеся —
   обратно в список с прежними настройками. Подробно — `connect-model.md` → «Пропавшие ноды».
   Пропавшие старше 15 дней (у каждой свой `goneAt`) вычищаются вместе с настройками.
6. Период обновления: `source.updateInterval` — `'auto'` (по умолчанию) или своё число секунд (в форме — число + единица: секунды / минуты / часы, минимум 10 с)
   (0 = вручную). `'auto'` = период провайдера из `profile-update-interval` (не чаще раза в
   час), если он его прислал, иначе глобальный из Auto mode (12 ч). Глобальный 0 выключает
   автообновление всех подписок, в том числе `'auto'` с периодом провайдера.

ETag / Last-Modified шлются, только если запись стратегии сделана этой же версией парсера
(`parser`, сейчас 3) и с тем же фильтром (`filter`): иначе 304 оставил бы список, собранный
по старым правилам. На 304 `subscription-userinfo` всё равно читается. Смешанный ответ (одни
UA — 304, другие — новый список) переспрашивает UA с 304 без условных заголовков, чтобы
собрать список целиком.

### Пересмотр стратегии

Пересматривать стратегию (заново делать discovery) при:
- Ручном запросе пользователя: ⋮ подписки → «Update with all user agents» (есть только при UA `Auto`)
- Смене URL, User-Agent или HWID в форме подписки: UI сбрасывает `uaStrategy` (с ETag) и
  `discoveredAt` и сразу запрашивает заново. Новый фильтр — просто полный запрос
- Количество нод в ответе (до фильтра) упало >20% от предыдущего — возможно сервер сменил поведение
- Прошло >7 дней с последнего discovery

### Автообновление (ядро)

Подписки обновляет ядро, по своему таймеру (`core/lib/src/updater.dart`), и при закрытом UI:
раз в минуту (первый раз — через 20 с после старта) смотрит снимок `ui-state.json` и берёт
включённые подписки (`kind: 'sub'`) с URL (локальные источники из файла — `kind: 'file'`, без URL — не берёт никогда), у которых `updatedAt + период` прошёл. Обновление то же, что
ручное (fetch + merge с `gone`), по одной подписке за раз. Неудача — следующая попытка через
30 мин, ошибка в лог и в `lastError` подписки (`{msg, at}`, `updatedAt` не меняется; карточка
показывает её с Retry, connect-model.md → «Подписка не загрузилась»); удачное обновление
`lastError` снимает.

Конфликты с правками в UI:
- ядро пишет в снимок только **серверные поля** источника: `nodes`, `gone`, `count`,
  `uaStrategy`, `discoveredAt`, `usage`, `expire`, `format`, `providerInterval`, `webPage`,
  `supportUrl`, `announce`, `updatedAt`, `lastError`. Поля пользователя (имя, URL, UA, фильтр, off-списки,
  переключатели) — никогда;
- результат отбрасывается, если за время запроса в UI поменяли URL / UA / фильтр / HWID,
  обновили или удалили подписку (`url`, `userAgent`, `filter`, `hwid`, `gone`, `updatedAt`
  сверяются с тем, что было в начале);
- подписку, которую сейчас обновляет UI, таймер пропускает;
- `updatedAt` — время ядра и версия серверных полей. Сохранение из UI со старой копией
  подписки (тот же URL, `updatedAt` старше) оставляет серверные поля ядра, остальное берёт из
  UI; более новая копия из UI побеждает целиком;
- `/api/status` отдаёт `sourcesRev`, он растёт с каждым обновлением по таймеру. UI (раз в 5 с)
  видит новый `sourcesRev`, забирает снимок и копирует серверные поля подписок, которые ядро
  обновило позже него, а при том же `updatedAt` — более новый `lastError` (неудача таймера).
  Дальше — как после ручного обновления: чистка `gone` старше 15 дней,
  пинг, если включён «Test latency after update» (он идёт, только пока UI открыт).

**Предрезолв адресов.** После удачного обновления (по таймеру и ручного) ядро в фоне разрешает имена серверов
новых и изменившихся нод вне туннеля и кладёт в постоянный кэш адресов, чтобы следующий connect не ждал DNS
(`rules.md` §6, «Предрезолв адресов узлов и DNS-серверов»). Обновление от него не зависит и не ждёт его.

«Reconnect after update» (`source.reloadAfterUpdate`): выключен — обновление не перезапускает
sing-box, новые серверы попадут в конфиг при следующем переподключении по другой причине
(сменили точку входа, выключили сервер…). Включён — если обновление меняет план подключения,
UI переподключается сразу.

### Заголовки ответа

| Заголовок | Куда |
|-----------|------|
| `subscription-userinfo` (`upload=; download=; total=; expire=`) | `usage` (ГБ) и `expire`; числа бывают дробными и в e-нотации; `expire` > 1e11 — в мс; читается и на 304 |
| `profile-title` (можно `base64:…`) | имя новой подписки, если пользователь его не задал |
| `content-disposition` (`filename*=` / `filename=`) | запасное имя (без `.yaml` / `.json` / `.txt` / `.conf`) |
| `profile-update-interval` (часы) | `providerInterval` → период для `'auto'` |
| `profile-web-page-url` | `webPage` → «Open website» в ⋮, если пользователь не задал свой сайт |
| `support-url` | `supportUrl` → пункт «Support» в ⋮ |
| `announce` (можно `base64:…`) | `announce` — плашка на карточке подписки (до 3 строк; хранится не больше 500 символов) |

Ссылки принимаются только `http(s)://` и `tg://` без пробелов и кавычек; текст — UTF-8 (dart:io
читает заголовки как Latin-1, ядро перекодирует). На 304 провайдерские поля только
дополняются тем, что пришло; полный ответ заменяет их (чего нет — стирается).

### Настройки подписки, которые исполняет ядро

- **User-Agent**: `Auto` — стратегия выше; чипы `sing-box` / `mihomo` / `v2ray` шлют
  `sing-box/1.14.2` / `mihomo/1.19.28` / `v2rayN/7.0` — один запрос без discovery (ETag хранится
  для этого UA).
- **Send X-HWID** (по умолчанию выключен): `x-hwid` (случайный 32-hex id устройства, создаётся
  один раз в `device.json` каталога данных), `x-device-os` (`Windows` / `macOS` / `Linux`…),
  `x-ver-os` (например `10.0.26200`), `x-device-model` (из BIOS / DMI, иначе `PC`). Только ASCII.
- **Filter**: регулярное выражение (с учётом регистра) по имени сервера; проверяются имя и
  «флаг + имя», так что работает и `🇩🇪`. Применяется в ядре после парсинга, до слияния UA;
  проверка сжатия (>20%) считает серверы до фильтра. Ничего не подошло или выражение неверное —
  ошибка обновления, список не трогается (неверное выражение не пропускает уже форма).
  Серверы, которые отсёк фильтр, не попадают в `gone` («удалён провайдером»): их убрал
  пользователь, а не провайдер (`updater.dart`).
- **Download via**: `Auto` (по умолчанию) / `Proxy` / `Direct`; старые `Direct first` / `Proxy first`
  и отсутствующее значение читаются как `Auto`. Запрос идёт через служебный трафик
  (`ServiceFetch`, `docs/core.md` → «Служебный трафик», цель `subscription`, ключ повторов
  `subscription:<id источника>`). `Auto`: один запрос сразу по всем путям (direct, главный поток,
  маршруты), при ничьей побеждает туннель. `Proxy`: только пути туннеля, direct никогда; туннель
  не поднят — сбой `noPath`. `Direct`: только direct. Хороший ответ другой стороны, пришедший целиком
  за ≤ 2 с после победителя (`collect`), сравнивается по набору серверов, а не по байтам. Сторона, не
  давшая данных, — не ответ, а её сбой: пустое тело (200 без байтов — путь падает с кодом `empty`, гонка
  идёт дальше), тело без единого сервера, 304 при полном ответе другой стороны, HTTP-ошибка. Берётся копия
  другой стороны, события нет — данные получены, как именно, неважно. Если обе копии с серверами, но наборы
  серверов (по идентичности узла, не по порядку, заголовкам и байтам) различаются — применяется более
  свежая копия (ниже), а `sub/diverged` (warn, без уведомления; в приложении подробности свёрнуты) пишет:
  число серверов каждой копии, чем отличаются (не больше 10 имён с каждой стороны и полные счётчики),
  статус и время завершения (мс) каждой стороны, заголовки свежести обеих копий (`directFresh` /
  `tunnelFresh`, имена как в ответе), `used` (`tunnel` / `direct` / `merged`), `why` и `usedNodes`.
  Одинаковые наборы в другом порядке или с другими байтами — один и тот же ответ, события нет. Обе стороны
  без данных — обычный сбой запроса.

  **Какая копия свежее.** Причина расхождения обычно не в «стране» запроса: разные узлы CDN держат разные
  версии часто обновляемого файла (так у `raw.githubusercontent.com`). Берутся заголовки `Age`, `Date`,
  `Last-Modified`, `ETag`, `Cache-Control`, `Expires` — какие есть (в событие идут все, `ETag` и
  `Cache-Control` только для разбора, на выбор они не влияют).
  1. Есть `Last-Modified` у обеих копий — сравниваются они (время самого файла). Разница ≥ 1 с — позже изменённая
     свежее (`why` = `newer: lastModified`; секунда — точность заголовка, любое различие — другая версия).
     Равные значения при разных наборах — свежесть неизвестна (одна версия файла; разница моментов запроса о
     версии ничего не говорит), `Date − Age` тогда не смотрится.
  2. Иначе момент, когда копия вышла от источника, = `Date − Age` (нет `Age` = 0; нет `Date` у любой копии или
     `Age` — не неотрицательное целое = неизвестно). Копия, вышедшая позже, содержит версию не старее. `Date` и
     `Age` — целые секунды с округлением вниз, оценка каждой копии ошибается меньше чем на секунду в обе стороны, разница двух
     оценок — меньше чем на две; поэтому свежее считается копия с разницей ≥ 2 с (`why` = `newer: age`), меньшая
     разница — неизвестно. Предположение: `Date` ответа — момент выдачи ответом узла (так делает CDN GitHub).
  3. Неизвестно (`why` = `unknown`) — копии **объединяются**: серверы туннельной копии по порядку, затем те, что
     есть только у прямой, в её порядке; один и тот же сервер (по ключу узла) входит один раз; `used` = `merged`,
     формат и заголовки провайдера (имя, остаток трафика) берутся от туннельной копии.

  После расхождения `ETag` / `Last-Modified` ответа в стратегию не записываются: следующий запрос идёт без
  условий и обе копии сравниваются заново (иначе 304 одной стороны отдал бы победу устаревшей копии другой
  без единого слова). Discovery (первое чтение, раз в 7 дней, сжатие > 20 %) спрашивает три UA, у каждого свой
  запрос по обеим сторонам и своё событие `sub/diverged` (поле `ua`, три записи в одну секунду — норма);
  применённый список — объединение серверов всех UA (при совпадении побеждает первый UA), то есть
  он не меньше копии, названной в `used` любого из событий. Событие `sub/updated` считает разницу всего
  применённого списка с прежним, а не одной копии: если в соседних обновлениях одна сторона оказалась без
  данных (опоздала дольше окна в 2 с, сбой), список переключается на копию другой стороны, и в журнале это два
  разных запуска. Сбой по всем путям идёт
  в Сторож (`svc.fetch`); `sub/failed` пишется только при `confirmed`, сбой собственного перезапуска
  молчит и повторяется на следующем тике.

  **Копия старее применённой.** Расхождение двух сторон — не единственный путь к устаревшему списку: если ответила
  одна сторона (вторая пуста, опоздала, упала), её копию не с чем сравнить, и устаревший узел CDN заменил бы
  более свежий применённый список. Поэтому к записи стратегии применённой копии (`uaStrategy[].fresh`, рядом с
  `etag`) пишется её свежесть — `{lastModified, origin}` в мс (`Last-Modified` и `Date − Age`, те же значения и правила,
  что выше; у объединённых копий — более поздние из известных моментов каждого вида; нет ни одного — поля нет) — и
  переживает перезапуск вместе с остальным состоянием источника. Новый ответ сравнивается с записью **того же UA**
  (запись той же версии парсера и с тем же фильтром) по тем же правилам и полям `Last-Modified` → `Date − Age` с
  теми же допусками (1 с / 2 с), любая сторона и выбранная из двух. **Явно старее** (и ни один из сравнимых
  ответов не новее) — список не применяется: серверы остаются, в `gone[]` ничего не уходит, заголовки ответа
  (трафик, анонс) не берутся, обновление считается выполненным (`updatedAt` двигается, повторной попытки раньше
  срока нет — следующий плановый запрос идёт как обычно), а в Raw каждый раз пишется строка `sub: <имя> (<UA>): the
  received copy (N servers; <моменты>) is older than the applied one (<моменты>), older: lastModified | older: age: not
  applied …` (warn; события нет). Новее, равно или не определить — применяется как раньше. Память сбрасывается там, где
  сбрасывается стратегия: смена URL / User-Agent / HWID (UI очищает `uaStrategy`), ручной «Update with all user agents»
  (`rediscover`: сравнивать не с чем), другой фильтр (запись с другим `filter` не сравнивается). Пересмотр раз в 7
  дней память не сбрасывает.
- **Decrypt password**: хранится, но не применяется — зашифрованных подписок с паролем в
  спецификации пока нет.

Ограничения: тело не больше 16 МБ, весь запрос (с медленным телом) не дольше 40 с.

## Детектирование формата

```
detect(body, content_type):
  if content_type contains "json" OR body.trimmed starts with "{":
    if body contains "\"outbounds\"":   → sing-box
    if content_type не yaml:            → unknown   (YAML flow-map тоже начинается с "{")
  if content_type contains "yaml" OR есть строка "^proxies:":
    → clash
  → links (plain URI-list), если в нём есть ноды

parse(body, content_type):
  r = detect(body)
  if ничего не нашли:
    r = detect(base64_decode(body.trim()))   // sing-box JSON / Clash YAML в base64 — в свой парсер
    URI-list из base64 помечается base64
```

Тот же разбор (`parseSubscription`) читает и файл, выбранный в Nodes → + → Import config file: тело файла
определяется по содержимому (без `Content-Type`), дальше те же дедупликация, имена и флаги; из серверов получается
локальный источник без URL и без обновления (`connect-model.md` → «Локальный источник»).

Неизвестные схемы ссылок и типы Clash не выбрасываются: они приходят нодой с `unsupported`
(причина в имени) и видны в списке, но в конфиг не идут. Сейчас это WireGuard (в sing-box он
только endpoint), SSR, juicity / mieru / naive / brook / snell, VLESS с `encryption` ≠ `none`,
socks поверх TLS, hysteria v1 не по UDP, QUIC-транспорт с шифрованием, XHTTP. Поддерживаются:
vless, vmess (base64-JSON и URI-форма), trojan, ss, hysteria2, hysteria (v1), tuic, anytls,
socks (`socks://` в стиле v2rayN с base64 и `socks5://user:pass@`), http, ssh (Clash);
транспорты ws / grpc / h2 / httpupgrade (в т.ч. Clash `ws-opts.v2ray-http-upgrade`) / quic.

## Дедупликация нод

Ключ дедупликации (`key`): `sha256(protocol + address + port + identity + вариант)`.
Сервер без варианта (`base`): `sha256(protocol + address + port + identity)`.

Где `identity`:
- vmess/vless: uuid
- trojan: password
- ss: method + password
- hysteria2: password
- tuic: uuid

**Вариант** — только поля, от которых зависит подключение, в одинаковом виде из любого
формата: TLS вкл., SNI (`sni=off` → `disable_sni`), insecure, ALPN, uTLS fingerprint,
Reality pbk/sid, flow, транспорт (type, path, Host, service_name), obfs hy2, мультипорт,
плагин ss. Провайдеры (особенно обходы белых списков) публикуют один сервер много раз с
разными SNI / fingerprint — это разные рабочие варианты, не дубли. Сливаются только
полностью совпадающие. Поля, которые формат дописывает сам (tag, domain_strategy…), в
вариант не входят — одна нода из ссылки, Clash и sing-box JSON остаётся одной.

Нормализация hysteria2 / tuic / hysteria (QUIC), чтобы один сервер из ссылок и из Clash
не раздваивался: Remnawave в Clash сам дописывает каждой hy2-ноде `client-fingerprint: chrome`
и `alpn: [h3]`, а `pinSHA256` из ссылки превращает в `skip-cert-verify: true`.
- uTLS fingerprint у QUIC-протоколов отбрасывается (sing-box: «unsupported usage for uTLS» —
  нода с ним не подключается вообще);
- у hysteria2 `alpn` = `h3` — значение по умолчанию, в вариант не входит (другой ALPN — вариант);
- `pinSHA256` hysteria2 → `tls.insecure` (закрепление самоподписанного сертификата в sing-box
  недоступно: его `certificate_public_key_sha256` считается от публичного ключа, а не от
  сертификата), как и в Clash-выдаче провайдера.

ETag / Last-Modified хранятся в стратегии вместе с `parser` — версией парсера
(`parserVersion`); после изменения разбора условные заголовки не шлются, первое обновление
читает подписку целиком (иначе 304 оставил бы ноды в старом виде).

Имя ноды (`tag`) — **не** часть ключа, разные UA могут называть одну ноду по-разному.
Слова-протоколы из имени убираются (`stripProtocol`: vless, vmess, trojan, ss/ssr/shadowsocks,
hysteria/hysteria2/hy2, tuic, anytls, wireguard, reality — только целыми словами, вместе с
повисшими разделителями `|`, `-`, `/`, пустыми скобками): протокол показывает свой бейдж
справа. «VLESS RU-SPB» → «RU-SPB», «NL | Hysteria2 | Reality» → «NL». Если от имени ничего
не остаётся — оно не трогается. Бейдж (`protoLabel`): VLESS поверх Reality — `reality`,
отдельно от обычного VLESS + TLS.
Одинаковые имена внутри источника нумеруются: `VK-1`, `VK-2` (одинаковые имена с разным
бейджем — нет: «VLESS X» и «HY2 X» остаются просто «X»). Номер закреплён за
нодой (`num`, исходное имя в `rawName`) и не меняется при обновлениях; новая нода
берёт наименьший свободный номер своего имени; оставшаяся одна — без номера.

При конфликте (одинаковый ключ, разные параметры) — предпочитать sing-box формат как наиболее полный (там могут быть дополнительные поля типа `multiplex`, `tls.reality`).

## Ранжирование нод после получения

После сбора полного списка — первичная сортировка ещё до тестирования latency:

1. **Фильтр явно нерабочих**: ноды с истёкшим сроком (если сервер пишет expiry в имени), дубли после дедупликации
2. **Протокольный приоритет** (настраивается пользователем): Reality > Hysteria2 > VLESS > VMess > Trojan > SS
3. **Latency-тест**: параллельно для всех нод, timeout 5 сек, URL выбирается автоматически из списка ниже
4. Финальная сортировка: работающие по latency ASC, нерабочие в конец

### Fallback-список URL для latency-теста

**Сделано (мокап + ядро):** Settings → Connection → **Latency test URL** — выбор из списка
Default (gstatic, умолчание ядра), Cloudflare, Microsoft, Mozilla, Apple или свой адрес
(http/https). Хранится в `connCfg.testUrl` (`''` = умолчание), уходит в ядро как
`urlTest.url` плана (Fastest) и `url` каждого `/api/ping`. Работающий urltest берёт новый
URL со следующего подключения. Автодетект ниже — ещё план.

Karing использует статический список без автовыбора — пользователь выбирает вручную.
Мы делаем автодетект: при первом запуске (и при смене сети) проверяем список **напрямую** (без прокси) и кешируем первый рабочий.

Список (приоритет сверху вниз):
```
https://www.gstatic.com/generate_204          # Google — быстрый, заблокирован в CN/IR/RU
http://cp.cloudflare.com/generate_204         # Cloudflare
http://www.msftconnecttest.com/connecttest.txt # Microsoft
http://detectportal.firefox.com/success.txt   # Mozilla
http://connectivity-check.ubuntu.com          # Ubuntu
http://checkip.amazonaws.com                  # AWS (работает в большинстве стран)
```

Логика выбора:
1. Проверить все параллельно с таймаутом 3 сек (прямое соединение, без прокси)
2. Взять первый ответивший с кодом 200/204
3. Закешировать результат — перепроверять при смене сети (смена IP/интерфейса) или по запросу пользователя
4. Если все недоступны напрямую → fallback на `tcp_ping` (TCP-handshake к хосту ноды, без HTTP)
5. Пользователь может задать свой URL в настройках — он идёт первым в списке перед автодетектом

> **Karing-источник:** `setting_manager.dart:1621` — `kUrlTestList` — тот же набор URL,
> но без автовыбора. DNS по региону там есть (`getResolverDns`, `getDirectDns`),
> а urlTest URL — всегда статика.

**Важно:** latency-тест гоняется **через ноду** (через sing-box API `/proxies/{name}/delay`). TCP-ping как fallback даёт относительное ранжирование даже если все HTTP-цели заблокированы.

## Региональные правила маршрутизации

`regionCode` (страна пользователя, выбирается вручную или определяется автоматически) используется для автоматического добавления geo-правил в конфиг sing-box.

**Источник в Karing:** `setting_manager.dart:1418` — список "особых" регионов: `["af", "br", "cn", "id", "ru", "ir", "tr"]`. Для них автоматом включаются geosite/geoip правила.

Логика:
- Если `regionCode = "cn"` → добавить в direct: `geosite:cn`, `geoip:cn`, `geosite:private`
- Если `regionCode = "ru"` → добавить в direct: `geosite:ru`, `geoip:ru`
- Аналогично для остальных регионов из списка
- `*` (все регионы) → правило применяется всегда

Это позволяет локальному трафику (банки, госсайты, стриминг) не идти через прокси. Пользователь может добавить кастомные правила поверх.

DNS по региону работает аналогично (`getResolverDns`, `getDirectDns` в `setting_manager.dart:1015-1080`):
- CN → resolver: `223.5.5.5` (AliDNS), `119.29.29.29` (DNSPod)
- Остальные → `8.8.8.8`, `1.1.1.1`

## Что хранится на диске

```
ui-state.json  — снимок UI: sourcesData (подписки с nodes, gone[] с goneAt, uaStrategy с ETag,
```

Ноды кешируются локально — приложение работает без интернета с последним известным списком.
