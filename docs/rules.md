# Правила маршрутизации, DNS, режимы — план

Статус: **§0–§7 сделаны в макете**. Код макета: `js/40-rules.js` (экран правил, проверка адреса,
итоговый порядок, импорт/экспорт, наборы правил), `js/42-apps.js` (приложения),
`js/75-rule-form.js` (форма правила и JSON), `js/56-dns.js` (DNS и Settings → Connection).
Не в макете: «Импорт из подписки» (заглушка), десктопный выбор процесса по пути (поле Process
есть, пикера файлов нет).

**В ядре** (live-режим через jormd): свои правила, приложения, быстрые правила, «всё остальное»,
«If unavailable» и DNS собираются в конфиг sing-box — `core/lib/src/routing.dart`; UI шлёт свою
модель (`plan.routing`, `js/93-routing-plan.js`), а не JSON sing-box, так что Flutter возьмёт тот
же Dart-сборщик. Списки (geosite / geoip / свои rule-sets) качает и кэширует ядро —
`core/lib/src/rulesets.dart`. Контракт — `core.md` → «Правила в конфиге». В live-режиме правила
и приложения стартуют пустыми и хранятся в снимке состояния вместе с быстрыми правилами,
наборами правил и DNS. Не сделано: TUN, kill switch, Hijack DNS / FakeIP, «If unavailable» на
лету, автопереключение DNS. Пометка **«по умолчанию, требует решения»** — поведение, выбранное
без решения юзера.

Принцип: удобное приложение для прошаренных юзеров — всё, что умеет sing-box, но через
понятные формы; сырой JSON — как запасной выход, а не единственный способ.

## 0. Цели правил: каталог Nodes

- **Nodes** — единый каталог всего, куда можно слать трафик: подписки, ноды, профили,
  цепочки (вкладки Simple / Profiles). Создание / редактирование / удаление — только тут.
- **Route** — только основной поток: режим, Auto / Manual, приоритет (свой порядок поверх
  порядка Nodes). Подробно — `connect-model.md`, «Каталог (Nodes) и Route».
- **Цель правила / приложения** (`js/40-rules.js`, `targetInfo`): `''` = основной поток,
  `src:<id>` (подписка / группа: все её живые ноды, самая быстрая), `node:<sid>::<nid>`,
  `profile:<id>`, `chain:<id>`. **Не зависит от режима Route**: правило на профиль работает и
  в режиме Simple.
- **Пикер цели** (`js/44-target-picker.js`, лист поверх всего): Main flow (что сейчас в
  основном потоке), затем подписки и группы (тап — вся подписка, ⌄ — выбрать одну ноду),
  профили, цепочки обоих режимов; поиск. Карточки подробные, как в Nodes: формат, число нод,
  трафик / срок, сервер, через который пойдёт сейчас, и пинг. Выключенные — с пометкой off,
  но выбрать можно.
- **Недоступная цель**: выключена в Nodes, без живых серверов или удалена (ссылка
  сохраняется — правило показывает «deleted chain» и т. п.). Тогда трафик идёт по
  **«If unavailable»** правила: Default / Main flow / Block / Direct. Default = глобальная
  настройка **Rules → Target unavailable** (Main flow по умолчанию); приложения всегда
  используют глобальную. В списке правил у такого правила бейдж «down → Block».
  Сейчас «If unavailable» применяется **при сборке конфига**: цель, недоступная на момент
  подключения, заменяется запасным выходом (Main → основной поток, Direct → `direct`,
  Block → действие `reject`). Любая правка в Nodes, делающая цель недоступной, и так
  переподключает. Цель, упавшая уже во время работы (все серверы перестали отвечать), остаётся
  целью до переподключения — **по умолчанию, требует решения**. Вариант на лету: `selector`
  [цель, запасной выход] и переключение через API service (`SelectOutbound`). Block туда тоже
  кладётся: outbound `block` в 1.11.10 вернули (сняли deprecated) именно для selector'ов, так
  что пересборка конфига не нужна (шаг 6 плана).
- **Удаление цели**: окно удаления перечисляет правила и приложения, которые её теряют,
  и куда пойдёт их трафик (`targetImpact`).

## 1. Структура меню правил

Один упорядоченный список правил sing-box, показанный слоями:

1. **Приложения** — отдельный раздел (см. §3).
2. **Свои правила** — полная форма (см. §4), порядок меняется перетаскиванием.
3. **Быстрые правила** — гео тумблерами; сервисы — выпадающий список (ниже, §2).
4. **Всё остальное** — одна строка: Proxy / Direct / Block.

Итоговый порядок проверки (первое совпадение выигрывает): приложения → свои правила →
быстрые → «всё остальное». Кнопка «Итоговый порядок» — read-only список в том порядке,
в каком его увидит движок.

Также на экране правил:
- **Поиск-фильтр** по списку правил.
- **Проверка адреса**: ввёл `youtube.com` / `1.2.3.4:443` / выбрал приложение → «сработает
  правило #3 "Стриминг" → профиль Europe». Отвечает на вопрос «почему идёт не туда».
- **Импорт/экспорт**: фрагмент sing-box JSON, текст правил Clash (`DOMAIN-SUFFIX,x,PROXY`),
  правила из Clash YAML подписки, поделиться ссылкой. `MATCH,X` из Clash не становится правилом —
  он задаёт «Всё остальное». Экспорт в Clash пропускает правила, которые Clash не выразит
  (составные, «кроме», несколько групп) — строкой-комментарием.

## 2. Быстрые правила

- **Гео**: «Мой регион напрямую» (страна, по умолчанию из системы) = geosite + geoip страны
  → Direct. Тумблер: реклама → Block. **Локальные сети — всегда напрямую**, без тумблера (в строке
  «Always»): первым правилом, раньше приложений и своих правил, и в Global тоже — «это база».
  Ядро: регион = домены страны (RU: `.ru`, `.рф` = `xn--p1ai`, `.su`) + geosite (RU:
  `category-ru`, `ru-available-only-inside`) + geoip страны; локальные сети = `ip_is_private` +
  `.local` / `.localhost` / `.lan` / `.home.arpa`; реклама = `category-ads-all` + несколько известных доменов → `reject`.
  Порядок: локальные сети (до всего) → … свои правила … → реклама → сервисы → регион → «всё остальное». Пока список не
  скачан, регион работает по доменам страны, реклама — по встроенным доменам (с предупреждением).
- **Сервисы**: выпадающий блок. Свёрнутый — «N added» и список имён; раскрытый — добавленные
  сервисы, у каждого VPN / Direct и × (убрать = снова по общим правилам). «+ Add service» —
  остальные из встроенного списка (Telegram, YouTube, Discord, стриминги…; список зашит в
  приложение, свои сервисы юзер не добавляет). Поиск по правилам раскрывает блок. Внутри
  сервиса — geosite-категории, юзер их не видит.
- **Сервис ↔ приложение**: у сервиса есть свои пакеты приложений (Telegram → org.telegram…).
  Сервис ловит сайты сервиса из любого приложения (браузер тоже), а приложения в порядке
  проверки выше, поэтому правило приложения побеждает для трафика самого приложения. Это
  видно с обеих сторон: у сервиса строка «App: Direct — its own route wins in the app» (тап —
  к приложению); у приложения без своего правила в списке «VPN · service»; в окне приложения —
  что делает сервис и кто побеждает.

## 3. Приложения

- Список приложений (Android — пакеты; десктоп — запущенные процессы + «добавить по пути»).
  Поиск, фильтры: пользовательские / системные / только настроенные.
- **Общего переключателя сверху нет** — действие ставится каждому приложению персонально.
- Строка: иконка, имя, чип состояния (`—` / `Direct` / `→ Europe`).
- Тап → маленькое окно: По умолчанию / Direct / Proxy + цель (пикер цели, §0) / Block.
- Галка **«Разделить TCP / UDP»** → две цели вместо одной (пример: Discord TCP через одну
  ноду, голос по UDP — через другую; голос идёт на голые IP, по доменам его не поймать).
- В порядке проверки приложения стоят выше гео и сервисов (они точнее).
- Ядро: Android — `package_name`; десктоп — `process_name` / `process_path` (вид приложения
  `process` / `path` в модели). «Разделить TCP / UDP» — два правила, `network: tcp` и `udp`.
  Недоступная цель приложения — глобальная «Target unavailable».
- Десктоп: раздел Apps = процессы, а условие «Процесс» в своих правилах остаётся — одно и то же
  двумя путями. **По умолчанию, требует решения**: оставить оба (Apps — быстрый выбор, Процесс —
  в составе правил с другими условиями).

## 4. Свои правила

Правило = **условия** + **действие** + **DNS** + флаги.

### Условия

Отдельные поля по группам (без «умного» автоопределения типа). Значение → чип по Enter
или запятой; вставка столбиком разбивается на чипы; невалидный чип — красный.
Форма пустая, группы добавляются кнопкой «+ Условие». У каждой группы — «кроме» (инверсия).

| Группа | Поля |
|---|---|
| Домены | Домен · Суффикс · Ключевое слово · Regex · Geosite (пикер) · Rule-set (пикер) |
| IP | IP / CIDR / диапазоны в одном поле · GeoIP (пикер) · тумблер «локальные сети» |
| Порты | порты и диапазоны в одном поле |
| Источник | IP источника · порты источника (свёрнуто) |
| Сеть | TCP / UDP (чипы) · Протокол по сниффингу: tls, http, quic, bittorrent, stun, dns (чипы) |
| Процесс | **только десктоп**: имя или путь, путь с `*` |

Приложений (пакетов) в форме нет — у них свой раздел.

Логика: внутри группы — ИЛИ (любое значение любого поля: домен или суффикс или geosite…),
между группами — И (пояснение в [?]). Исключения внутри группы: у **Источника** IP и порт —
И (оба должны совпасть), у **Сети** TCP/UDP и протокол — тоже И.
Реализация: плоское правило sing-box ИЛИ-т домены с IP и И-т всё остальное, поэтому правило
с Доменами **и** IP (или с «кроме») ядро собирает как `logical and` из групп (группа с
несколькими видами значений — `logical or`); вкладка JSON показывает так же. Процесс: имя и
путь в sing-box — разные поля (И), поэтому вместе они тоже идут через `logical or`; путь с `*` —
`process_path_regex`. Диапазон IP → набор CIDR, порты `a-b` → `port_range` `a:b`.
Нет списка на диске (geosite / geoip / rule-set ещё не скачан): в обычной группе правило
сужается до остальных значений, группа из одних списков или «кроме» со списком — правило
пропускается; в обоих случаях предупреждение при подключении.
Составные правила (вложенные И/ИЛИ, `logical` в sing-box) в форму не выносим — только через
JSON; в списке такое правило помечено бейджем «составное · JSON».

Валидация на лету: regex, CIDR, диапазоны IP, порт ≤ 65535, диапазон «от ≤ до».

### Действие

Proxy через основной поток · через конкретную цель (профиль / цепочка / подписка / нода —
пикер цели, §0) · Direct · Block (тихо сбросить / ответить отказом).

Ядро: цель = свои группы серверов (подписка → urltest, нода → один сервер, профиль → как
юнит, цепочка → вход + выход с detour), одна на все правила и приложения с этой целью.
Block → `reject` (`method: drop` для «тихо»).

**Резолв перед IP-правилами** (**по умолчанию, требует решения**): перед первым своим правилом
с IP-условиями (IP / CIDR, локальные сети, GeoIP) ядро ставит `resolve` — домен резолвится по
DNS-правилам и глобальному списку, и IP-условия видят адрес; прокси всё равно получает домен.
Быстрые правила сами не резолвят: регион / сервисы ловят домены и адреса, пришедшие как IP.

- **If unavailable** (у Proxy с конкретной целью): Default / Main flow / Block / Direct —
  что делать, если цель выключена, пуста или удалена (§0). Заменил тумблер «Строго»
  (Строго = Block).

### DNS правила

«Авто» (по умолчанию): первый отмеченный сервер глобального списка с подходящим «Через» —
Direct-правило → прямой сервер, VPN-правило → сервер через VPN. Либо конкретный сервер из
глобального списка.

Реализация: для доменных условий правила — DNS-правило sing-box с тем же сервером (для шага
`resolve` и, с TUN, для запросов самих приложений); свои rule-sets в DNS-правила не идут.
Прямой трафик резолвит только `domain_resolver` исходящего (DNS-правила он не спрашивает),
поэтому Direct-правило со своим сервером получает свою копию `direct` — `direct@dns-<id>`.

### JSON

Вкладки **Форма | JSON**, синхронные. Поля JSON, которых нет в форме, не теряются — плашка
«доп. поля — редактируются в JSON». Невалидный JSON не сохраняется, ошибка со строкой.

## 5. Внешние rule-sets

Раздел списков: URL, формат (srs / json), период обновления (то же окно «число + единица»),
«качать через VPN / напрямую». Встроенные geosite/geoip — там же.

Ядро (`rulesets.dart`): качает само, кладёт в `<dataDir>/rulesets/<tag>.srs|json` и отдаёт
sing-box как `type: local` (sing-box при старте ничего не качает; заменённый файл перечитывает
сам). Встроенные: сначала runetfreedom (`russia-v2ray-rules-dat`, ветка `release`,
`sing-box/rule-set-geosite/geosite-<имя>.srs`, `…/rule-set-geoip/geoip-<cc>.srs`), при 404 —
SagerNet (`sing-geosite` / `sing-geoip`, ветка `rule-set`). Качается только то, что нужно
правилам. Свежий файл (моложе периода) — как есть; устаревший — используется, обновляется
после подключения; ответ, не похожий на rule-set (страница провайдера), отбрасывается и не
затирает старую копию; неудача — повтор не раньше чем через 5 минут.
«Через VPN» — только через туннель (служебный вход `tunnel-in`, мимо правил): при первом
подключении такого списка ещё нет — правила без него (предупреждение), ядро скачивает его через
новый туннель и само переподключается. «Напрямую» — с учётом системного `HTTP(S)_PROXY`.
Обновление по таймеру во время работы — не сделано (только при подключении).

## 6. DNS

**DNS — отдельный раздел Settings** (не внутри Connection). Карточка **DNS на главной**
ведёт туда же (как карточка Auto); при открытии раздела непропингованные серверы пингуются.

Раздел DNS:
1. **Глобальный DNS** — список серверов с галочками и приоритетом (перетаскивание),
   кнопка «+ Добавить». Галочка = используется, порядок = приоритет (первый не отвечает →
   следующий). У сервера: адрес (`udp` / `tls` / `https` / `quic`), **«Через: напрямую / VPN»**,
   **пинг** (в списке и в окне добавления — кнопка проверки).
   По умолчанию два сервера: **Локальный** (системный/провайдера, напрямую) и
   **Удалённый** (напр. `https://1.1.1.1`, через VPN).
2. **Hijack DNS** — тумблер. Доступен всегда (чтобы не прыгать настройки ↔ главная);
   при выключенном TUN — пометка «работает только в TUN». Отдельного пикера серверов нет:
   перехваченные запросы идут в DNS ядра, а оно отвечает по глобальному списку.
3. **FakeIP** — тумблер, **по умолчанию выключен**, [?] с объяснением, список исключений
   (банки, игры и т. п. — заполнен из коробки). Имеет смысл только в TUN.

Всё, что не попало в правила, резолвится глобальным списком по порядку.

Ядро: серверы `dns-<id>` (`system` → `local`, IP → udp, `udp://` `tcp://` `tls://` `quic://`
`https://`); «Через VPN» → `detour: proxy`. `dns.final` = первый отмеченный. Адреса серверов
прокси и прямой трафик резолвит первый отмеченный **прямой** сервер (`default_domain_resolver`),
иначе системный. Сервер с именем хоста (`tls://dns.google`) узнаёт свой адрес у системного.

Реализация: в sing-box у DNS нет встроенного fallback между серверами (один основной) —
переключение по приоритету делаем сами (пинг + смена основного), как Auto для нод.
Сейчас: смена галочек / порядка — переподключение; автопереключения при отказе сервера нет
(**по умолчанию, требует решения**: сделать его пингом + переподключением или оставить ручным).

DoH в браузерах обходит Hijack — не наше дело, не боремся.

## 7. Режимы и kill switch

- **System proxy** — третий переключатель в карточке режимов на главной (сверху название
  «Sys proxy», снизу рядом On | Off; плашка ездит вбок). Там же в Settings → Connection —
  **Proxy port**: порт локального HTTP + SOCKS5 прокси ядра (127.0.0.1, по умолчанию 2080),
  на него указывает системный прокси; 1024–65535, кроме занятых приложением (7788 jormd,
  9090 Clash API). Смена порта при подключении — переподключение с новым портом и тумблер в Settings → Connection; оба держат одно
  состояние. Позже с главной на мобилках
  уберём (на Android системный прокси большинство приложений игнорирует).
- **Kill switch** (глобальный, Settings → Connection, отдельный тумблер; там же пока
  заглушка TUN stack и выбор Latency test URL — см. subscription-parsing.md → URL для
  latency-теста). Подсказка: «Blocks traffic when the VPN is down. Works for apps that use the
  system proxy; full block needs TUN.» Он блокирует **только приложения, которые ходят через
  системный прокси** (и то, что настроено на наш порт вручную); всё остальное утекает
  напрямую — полная защита возможна лишь с TUN (не сделан). Ключи в `connCfg` (снимок
  состояния, бэкап), уходят в ядро вместе с connect, а при смене (в том числе `launchAtStartup` /
  `connectOnLaunch`, от которых зависит `killWhileClosed`) во время подключения или down —
  сразу через `POST /api/killswitch` с теми же четырьмя полями (в down прокси перестраивается
  по новым настройкам: kill switch вкл → удержан, выкл + Remove → снят):
  - `killSwitch` [выкл] — пока пользователь подключён, наш системный прокси не снимается ни при
    каком сбое: упало → интернет блокируется (прокси указывает на мёртвый порт), а не идёт
    напрямую. Выключение, пока он что-то защищает (подключено, down или блок после
    отключения), — только после подтверждения: шторка говорит, что будет (трафик пойдёт напрямую
    при падении / прямо сейчас, или блок снимется). Включение и выключение без подключения — сразу.
  - Под ним (видны и действуют только при включённом `killSwitch`, с отступом):
    `killOnDisconnect` [выкл] «Also after I disconnect» — отключение пользователем тоже не снимает
    прокси: интернет заблокирован до подключения или кнопки Remove на главной (плашка
    `status.blocking`). `killWhileClosed` [выкл] «Also while the app is closed» — закрытие
    приложения (остановка jormd) не восстанавливает прокси; доступен только при
    `genCfg.launchAtStartup` **и** `genCfg.connectOnLaunch` (иначе после закрытия интернет мёртв, пока
    юзер не запустит приложение сам): без них строка серая, в подсказке причина, тап предлагает
    включить оба. Снимешь автозапуск / автоподключение — опция снова серая (в ядро уходит false).
  - `downProxy` [`remove` | `keep`, по умолчанию `remove`] «If the VPN cannot recover» — видна
    только при **выключенном** `killSwitch`; двухпозиционный переключатель Remove proxy | Keep it.
    Remove: когда VPN не поднялся за 30 с («down», см. connect-model.md → ConnectDock), ядро
    возвращает сохранённый системный прокси, трафик идёт напрямую, пока VPN не вернётся. Keep: прокси
    остаётся, интернет мёртв до возврата (то же поведение, что при `killSwitch`, но без
    подопций).
  - **Фоновый перезапуск не настраивается.** sing-box упал при подключении → ядро сразу
    перезапускает его; системный прокси при этом **не снимается** (утечки во время
    перезапуска нет: приложения просто ждут порт), пользователь ничего не видит. Паузы 1 с, 4 с,
    15 с, дальше каждые 30 с, пока пользователь подключён; успех — та же запись, правила, сервер.
    После 30 с безуспешных попыток начинается «down» (кнопки Retry и Disable sys proxy на главной;
    Retry — перезапуск сейчас; Disable sys proxy / Remove — восстановить прежний системный
    прокси сейчас; попытки продолжаются). Отключение пользователя во время перезапуска / down
    прекращает попытки; прокси — по `killOnDisconnect`.
  «Упало всё» — ядро упало, ни одна запись Auto не пропускает трафик: блок. **Исключение —
  правило, у которого в «If unavailable» явно выбран Direct**: его трафик пропускается (это
  решение юзера для этих адресов); при включённом kill switch в таком правиле висит
  предупреждение. (Решено, не сделано.)
  Не путать с «Строго» у правила (§4).
- **Global**: всё в прокси (кроме локальных сетей — они всегда напрямую), правила не применяются
  вовсе — ни свои, ни приложения, ни Block
  (**по умолчанию, требует решения**; альтернатива — оставить Block и приложения). DNS-список
  работает и в Global.

## Отложено

- Наборы правил по сети (Wi-Fi SSID, «дом/работа») — пока нет, возможно никогда:
  задачу белых списков решают приоритеты.
