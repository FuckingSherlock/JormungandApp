# Правила маршрутизации, DNS, режимы — план

Статус: **§0–§7 сделаны в макете**. Код макета: `js/40-rules.js` (экран правил, проверка адреса,
итоговый порядок, импорт/экспорт, наборы правил), `js/42-apps.js` (приложения),
`js/75-rule-form.js` (форма правила и JSON), `js/56-dns.js` (DNS и Settings → Connection).
Не в макете: «Импорт из подписки» (заглушка), десктопный выбор процесса по пути (поле Process
есть, пикера файлов нет).

**В ядре** (live-режим через jormd): свои правила, приложения, быстрые правила, «всё остальное»,
«If unavailable» и DNS собираются в конфиг sing-box — `core/lib/src/routing.dart`; UI шлёт свою
модель (`plan.routing`, `js/93-routing-plan.js`), а не JSON sing-box, так что Flutter возьмёт тот
же Dart-сборщик. Списки (geosite / geoip / свои rule-sets) качает и кэширует ядро —
`core/lib/src/rulesets.dart`. Контракт — `core.md` → «Правила в конфиге». В live-режиме правила
и приложения стартуют пустыми и хранятся в снимке состояния вместе с быстрыми правилами,
наборами правил и DNS. «If unavailable» переключается на лету, DNS переключается по
приоритету сам (§0, §6). TUN (и Hijack DNS) в ядре есть — `core.md` → «TUN»; FakeIP убран до переработки (§DNS п. 3). Пометка **«по умолчанию, требует решения»** — поведение, выбранное
без решения юзера.

Принцип: удобное приложение для прошаренных юзеров — всё, что умеет sing-box, но через
понятные формы; сырой JSON — как запасной выход, а не единственный способ.

## 0. Цели правил: каталог Nodes

- **Nodes** — единый каталог всего, куда можно слать трафик: подписки, ноды, профили,
  цепочки (вкладки Simple / Profiles). Создание / редактирование / удаление — только тут.
- **Route** — только основной поток: режим, Auto / Manual, приоритет (свой порядок поверх
  порядка Nodes). Подробно — `connect-model.md`, «Каталог (Nodes) и Route».
- **Цель правила / приложения** (`js/40-rules.js`, `targetInfo`): `''` = основной поток,
  `src:<id>` (подписка / группа: все её живые ноды, самая быстрая), `node:<sid>::<nid>`,
  `profile:<id>`, `chain:<id>`. **Не зависит от режима Route**: правило на профиль работает и
  в режиме Simple.
- **Пикер цели** (`js/44-target-picker.js`, лист поверх всего): Main flow (что сейчас в
  основном потоке; тап выбирает), затем подписки и группы, профили, цепочки обоих режимов;
  поиск. Тап по карточке с серверами (подписка, профиль) **раскрывает** её и сам ничего не
  выбирает; кнопка AUTO слева от имени (как в строке Route) выбирает всю подписку / профиль
  целиком и светится, если она и есть цель. Внутри — режим Fastest / Priority (собственная
  настройка элемента, здесь только показ) и список серверов — тап по серверу выбирает
  `node:<sid>::<nid>`. Цепочки раскрываться не умеют: тап выбирает. Выбор **не закрывает**
  пикер, а лишь помечает: пока выбор отличается от исходной цели, снизу выезжает Save
  (применить и закрыть); закрытие иначе (×, свайп, Back) ничего не применяет. Повторный тап
  по выбранному снимает выбор → цель `''` = Main flow, над Save предупреждение. Если цель — сервер,
  карточка открывается раскрытой; поиск по имени сервера раскрывает карточку. Карточки подробные, как в Nodes: формат, число нод,
  трафик / срок, сервер, через который пойдёт сейчас, и пинг. Выключенные — с пометкой off,
  но выбрать можно.
- **Недоступная цель**: выключена в Nodes, без живых серверов или удалена (ссылка
  сохраняется — правило показывает «deleted chain» и т. п.). Тогда трафик идёт по
  **Fallback** правила (в форме: Default | Proxy | Direct | Block, Proxy = Main flow или своя цель,
  §2). Default = глобальная настройка **Rules → Target unavailable** (Main flow по умолчанию).
  Fallback есть и у правила Proxy с основным потоком (запасной выход на случай, если он упал). У приложения Fallback
  такой же (§3) — у каждой его половины Proxy со своей целью. В списке правил у такого правила
  бейдж «down → Block».
  «If unavailable» действует в двух местах.
  **При сборке конфига**: цель, недоступная на момент подключения, заменяется запасным
  выходом (Main → основной поток, Direct → `direct`, Block → действие `reject`). Любая правка
  в Nodes, делающая цель недоступной, и так переподключает.
  **На лету**: правило или приложение с доступной конкретной целью (не Main flow) ведёт не в
  саму цель, а в `selector` `[цель, запасной выход]` (`<цель>~<запасной>`, по умолчанию —
  цель; по одному на пару цель + запасной выход, его делят все правила с ней). Ядро
  (`core/lib/src/fallback.dart`) следит за целями и переключает selector через API service
  (`SelectOutbound`), без перезапуска sing-box: цель перестала отвечать → запасной выход
  правила (Block → outbound `block`: в 1.11.10 его вернули, сняв deprecated, именно для
  selector'ов; Direct → `direct`; Main → селектор `proxy`), цель ожила →
  обратно в цель. Проверка — измерение того сервера, на котором сейчас стоит группа цели
  (у цепочки — выхода через вход), теми же пробами и запасными проверками, что у Auto
  (probe inbound, второго пингера нет); группу Fastest, чей сервер промахнулся `failAfter`
  раз подряд, ядро переводит на самый быстрый ответивший по свежей проверке (как Auto; пока сервер отвечает —
  раз в `checkEvery` шаг улучшения), группу Priority ядро не двигает (сервер выбрал юзер: пока он молчит,
  цель считается упавшей). Гистерезис как у Auto: упала после `failAfter` промахов подряд,
  вернулась после `failAfter` ответов подряд, а у упавшей раньше — ещё и после паузы
  flap guard (1, 2, 4 … мин). Пока не отвечает вся сеть (Auto не видит ни одного
  ответившего маршрута), ничего не судится: мёртвая сеть — не мёртвая цель. При уходе на
  запасной выход соединения, всё ещё идущие через цель и стоящие без движения байтов,
  закрываются (приложение переподключится по-новому); при возврате открытые не
  трогаются. Выбор selector'ов переживает рестарт sing-box (`cache_file`), сервис
  стартует с того, что sing-box говорит. В журнал: `rules/fallback` (warn: правило, цель,
  куда) и `rules/targetBack` (info).
  **Запасной выход — настоящая цель** (подписка / нода / профиль / цепочка из каталога; у
  правила и приложения, не у глобального Rules → Target unavailable — там только Main / Block /
  Direct). В плане (`fallback`) это id цели (`src:…`, `node:…`, `profile:…`, `chain:…`) вместо
  слова; в UI у приложения это `fallback: 'main'` + `fallbackTarget` (Proxy → Via запасного
  варианта), `93-routing-plan.js` отдаёт его как id. Selector становится
  `[цель, запасная цель, основной поток]` (`<цель>~<запасная цель>`), запасная цель собирается в
  конфиг со своими группами и **наблюдается так же** (своя проверка, свой гистерезис). Цель
  упала → запасная цель; **упали обе → основной поток** (журнал: `rules/fallback` с
  `to: main`); запасная ожила → забирает трафик у основного потока; цель ожила → возвращает
  себе трафик откуда угодно (`rules/targetBack`). Если оба упали за один раунд — один переход,
  сразу в основной поток. В журнале `to` = id запасной цели (или `main` / `block` / `direct`).
  Запасная цель, равная самой цели (или пустая), = Main flow; запасная, недоступная при сборке
  (удалена, выключена, нет серверов) = Default (глобальная настройка), в `warnings` строка
  «<правило>: "If unavailable" target … is not available, the default applies». Цель
  недоступна сейчас, а запасная жива — трафик идёт сразу в запасную (с Main flow за ней).
  **Основной поток как «цель»**: приложение с Route = Default (или Proxy с пустой целью) и явным
  Fallback = Block / Direct / цель получает selector `proxy~<запасной>` = `[proxy, запасной]`
  (глобального Default здесь нет: Default / Main = без запасного; недоступная запасная цель =
  без запасного, с предупреждением). Такое приложение идёт по selector'у, а не по правилам ниже.
  Основной поток Auto уже лечит сам, поэтому ядро судит его по тому, что видит пользователь: тест
  через selector `proxy` (сервер, на котором его оставил Auto) — `failAfter` промахов подряд =
  упал. Мёртвый основной поток для Auto выглядит как мёртвая сеть, поэтому ядро различает их само:
  после промаха мерит прямой путь (`direct` в probe inbound) и запасные цели, и промах считается,
  только если что-то из них ответило (сеть жива, основной поток нет); не ответило ничего = мёртвая
  сеть, ничего не судится (как и пока ОС вообще офлайн). Запасная цель основного потока, упавшая
  вместе с ним, ничего не меняет: selector остаётся на ней (лучше некуда). Вернулся основной
  поток — selector назад.
- **Удаление цели**: окно удаления перечисляет правила и приложения, которые её теряют,
  и куда пойдёт их трафик (`targetImpact`).

## 1. Структура меню правил

Один упорядоченный список правил sing-box, показанный слоями:

1. **Приложения** — отдельный раздел (см. §3).
2. **Свои правила** — полная форма (см. §4), порядок меняется перетаскиванием.
3. **Быстрые правила** — гео тумблерами; сервисы — выпадающий список (ниже, §2).
4. **Всё остальное** — одна строка: Proxy / Direct / Block.

Итоговый порядок проверки (первое совпадение выигрывает): приложения → свои правила →
быстрые → «всё остальное». Кнопка «Итоговый порядок» — read-only список в том порядке,
в каком его увидит движок.

Также на экране правил:
- **Поиск-фильтр** по списку правил.
- **Проверка адреса**: ввёл `youtube.com` / `1.2.3.4:443` / выбрал приложение → «сработает
  правило #3 "Стриминг" → профиль Europe». Отвечает на вопрос «почему идёт не туда».
- **Импорт/экспорт**: фрагмент sing-box JSON, текст правил Clash (`DOMAIN-SUFFIX,x,PROXY`),
  правила из Clash YAML подписки, поделиться ссылкой. `MATCH,X` из Clash не становится правилом —
  он задаёт «Всё остальное». Экспорт в Clash пропускает правила, которые Clash не выразит
  (составные, «кроме», несколько групп) — строкой-комментарием.

## 2. Быстрые правила

- **Гео**: «Мой регион напрямую» (страна, по умолчанию из системы) = geosite + geoip страны
  → Direct. Тумблер: реклама → Block. **Локальные сети — всегда напрямую**, без тумблера (в строке
  «Always»): первым правилом, раньше приложений и своих правил, и в Global тоже — «это база».
  Ядро: регион = домены страны (RU: `.ru`, `.рф` = `xn--p1ai`, `.su`) + geosite (RU:
  `category-ru`, `ru-available-only-inside`) + geoip страны; локальные сети = `ip_is_private` +
  `.local` / `.localhost` / `.lan` / `.home.arpa`; реклама = `category-ads-all` + несколько известных доменов → `reject`.
  Порядок: локальные сети (до всего) → … свои правила … → реклама → сервисы → регион → «всё остальное». Пока список не
  скачан, регион работает по доменам страны, реклама — по встроенным доменам (с предупреждением).
- **Сервисы**: выпадающий блок. Свёрнутый — «N added» и список имён; раскрытый — добавленные
  сервисы, у каждого VPN / Direct и × (убрать = снова по общим правилам). «+ Add service» —
  остальные из встроенного списка (Telegram, YouTube, Discord, стриминги…; список зашит в
  приложение, свои сервисы юзер не добавляет). Поиск по правилам раскрывает блок. Внутри
  сервиса — geosite-категории, юзер их не видит.
- **Сервис ↔ приложение**: у сервиса есть свои пакеты приложений (Telegram → org.telegram…).
  Сервис ловит сайты сервиса из любого приложения (браузер тоже), а приложения в порядке
  проверки выше, поэтому правило приложения побеждает для трафика самого приложения. Это
  видно с обеих сторон: у сервиса строка «App: Direct — its own route wins in the app» (тап —
  к приложению); у приложения без своего правила в списке «VPN · service»; в окне приложения —
  что делает сервис и кто побеждает.

## 3. Приложения

- Список приложений (Android — пакеты; десктоп — запущенные процессы + «добавить по пути»).
  Поиск, фильтры: пользовательские / системные / только настроенные.
- **Общего переключателя сверху нет** — действие ставится каждому приложению персонально.
- Строка: иконка, имя, чип состояния (`—` / `Direct` / `→ Europe` / `TCP Default · UDP Block`).
- Тап → маленькое окно по центру экрана, заголовок — имя приложения. Первая карточка: **«Split TCP / UDP»**
  (иконка-звено, (?) с пояснением, переключатель справа) — для **любого** действия. Ниже карточка
  настроек; при Split — по одной на вкладку **TCP | UDP** (вкладки как Simple / Profiles в Nodes:
  пилюля скользит, свайп влево / вправо переключает; без Split вкладок нет, карточка одна на оба
  протокола):
  - **Route** — **Default / Proxy / Direct / Block**: сегмент в одной строке с подписью, пока
    помещается, иначе под ней на всю ширину (равные сегменты; то же для Fallback);
  - **Via** — цель (пикер цели, §0), активна только при Route = Proxy; пустая цель = основной поток;
    при Route = Default — неизменяемое «Main flow» с замком вместо шеврона (не приглушено: это
    настоящее значение), при Direct / Block — «—», приглушено;
  - **Fallback** — **Default / Proxy / Direct / Block**, активен при Route = Proxy или Default
    (при Direct и Block приглушён — откатываться некуда; при Default страхует основной поток, который
    может не содержать нужного, напр. Manual на Simple, а запасной — профиль): Default = глобальная настройка (Rules → Target unavailable),
    Proxy = через заданную цель, Direct, Block. Как «If unavailable» правила, §0;
  - **Via** запасного варианта — всегда на месте, активна только при Fallback = Proxy; пустая =
    «Main flow», иначе цель из пикера (первый пункт — Main flow; цель из Route → Via не предлагается).
  Строки приглушённых полей остаются на месте, под карточкой всегда есть пояснение (место под две
  строки зарезервировано): размер диалога не прыгает при смене Route / Fallback. Подписи Default / Proxy / Direct / Block остаются английскими и в русском UI. Примеры: Discord TCP через одну ноду, голос по UDP — через другую (голос
  идёт на голые IP, по доменам его не поймать); TCP Default + UDP Block — глушит QUIC, приложение
  откатывается на TCP. Default у половины = для этого протокола своего правила нет, трафик идёт по
  правилам ниже. Обе половины Default (или без разделения — Default) = у приложения нет своего
  маршрута, оно не хранится.
- Модель: `{ act, target, fallback, fallbackTarget, split, udp: { act, target, fallback, fallbackTarget } }`
  (`fallback`: `default` / `main` = кнопка Proxy / `direct` / `block`); при `split` поля
  верхнего уровня — TCP, `udp` — UDP. Старый вид `{ act: 'proxy', split, udpTarget }` при загрузке
  превращается в `udp: { act: 'proxy', target: udpTarget }`.
- В порядке проверки приложения стоят выше гео и сервисов (они точнее).
- Ядро: Android — `package_name`; десктоп — `process_name` / `process_path` (вид приложения
  `process` / `path` в модели). «Разделить TCP / UDP» — до двух правил, `network: tcp` и `udp` (у половины Default
  правила нет). Proxy с конкретной целью — тот же selector `[цель, запасной выход]` и та же
  живая логика «If unavailable», что у правил (§0); selector общий, если цель и запасной выход
  совпали. Запасной выход может быть настоящей целью (§0), а у половины с Route = Default (или
  Proxy с пустой целью) явный Fallback = Block / Direct / цель даёт основному потоку свой
  «If unavailable» (§0): для такой половины появляется правило, и она идёт по selector'у `proxy~…`,
  а не по правилам ниже. В журнале такое приложение названо по имени: «App Telegram goes direct».
  Карточки `site/blocked` / `site/unreachable` называют сработавшее правило и приложение, а когда у
  приложения свой маршрут и адрес поймало бы ещё и правило (или наоборот), показывают обе стороны:
  сработавшую («applied») и уступившую (приглушённо, «overridden by rule / by app»), обе со ссылкой
  (connect-model.md, строки причины).
- Android: список — установленные приложения устройства (имя, пакет, значок; Kotlin-канал
  `jormungand/apps`, `app/lib/platform/apps_io.dart`, шов `AppsIo.current` для тестов). Фильтры
  User / System / Configured; «системное» = `FLAG_SYSTEM` без `FLAG_UPDATED_SYSTEM_APP` (обновлённый
  Chrome / Play services считается пользовательским). Приложение с правилом, которого нет на
  устройстве (удалено), остаётся в списке (виден под User и Configured) — правило можно изменить
  или снять; имя берётся из сохранённого вместе с правилом (`AppRule.unknown['name']`), пока список
  устройства не прочитан (в план и журнал оно попадает так же: `Catalog.appLabel`). Список читается
  при старте приложения (имена для плана / журнала / диалога удаления) и перечитывается при каждом
  открытии листа (кэшированный показывается сразу): приложение, установленное позже, появляется
  без перезапуска. Лист ленивый (сотни приложений; значок запрашивается только у видимых строк,
  Kotlin отдаёт значки двумя потоками, Dart кэширует). Само Jormungand в списке нет: оно внутри VPN,
  а его соединения идут мимо правил пользователя — системное правило `package_name → direct`
  (`core.md` → «TUN», «Системные правила», п. 4; `platforms.md` → «Работа вне туннеля»).
  Видимость пакетов: `QUERY_ALL_PACKAGES` (манифест оверлея) — фильтр System показывает Play services,
  загрузки и т.п., у которых нет значка в лаунчере; `<queries>` с MAIN/LAUNCHER видел бы только
  запускаемые приложения. APK мы раздаём сами, не через магазин.
  Маршрутизация (проверено ядром, `core/test/routing_test.dart`, `tun_test.dart`): Proxy / Block /
  Direct / Default с Fallback — правила `package_name` (с `network: tcp|udp` при Split) первыми в
  порядке; приложение, целиком (оба протокола) на Direct в режиме Rules, дополнительно уходит в
  `exclude_package` TUN-входа (`VpnService.Builder.addDisallowedApplication`) и вообще не заходит
  в туннель; в Global правила приложений и `exclude_package` не действуют. `package_name` матчится по
  владельцу соединения (`ConnectivityManager.getConnectionOwnerUid`, Android 10+).
- Десктоп: раздел Apps = процессы, а условие «Процесс» в своих правилах остаётся — одно и то же
  двумя путями. **По умолчанию, требует решения**: оставить оба (Apps — быстрый выбор, Процесс —
  в составе правил с другими условиями).

## 4. Свои правила

Правило = **условия** + **действие** + **DNS** + флаги.

### Условия

Отдельные поля по группам (без «умного» автоопределения типа). Значение → чип по Enter
или запятой; вставка столбиком разбивается на чипы; невалидный чип — красный.
Форма начинается с одного пустого поля «Suffix» в карточке «Домены»; всё остальное добавляется
только кнопкой «+ Condition»: она предлагает каждое поле, которого ещё нет в форме, под
названием его карточки (Domains: Suffix / Exact domain / Keyword / Regex / Geosite / Rule set;
IP: IP-CIDR / GeoIP / Local networks; Ports; Source; Network / Protocol; Process). Выбранное поле
появляется в своей карточке (карточка создаётся, если её не было). Подсказок «+ Keyword» внутри
карточек нет. У каждого поля свой × (убирает поле; убрал последнее — карточка исчезает вместе с
ним), у карточки — свой × и «кроме» (инверсия).

| Группа | Поля |
|---|---|
| Домены | Домен · Суффикс · Ключевое слово · Regex · Geosite (пикер) · Rule-set (пикер) |
| IP | IP / CIDR / диапазоны в одном поле · GeoIP (пикер) · тумблер «локальные сети» |
| Порты | порты и диапазоны в одном поле |
| Источник | IP источника · порты источника (свёрнуто) |
| Сеть | TCP / UDP (чипы) · Протокол по сниффингу: tls, http, quic, bittorrent, stun, dns (чипы) |
| Процесс | **только десктоп**: имя или путь, путь с `*` |

Приложений (пакетов) в форме нет — у них свой раздел.

Логика: внутри группы — ИЛИ (любое значение любого поля: домен или суффикс или geosite…),
между группами — И (пояснение в [?]). Исключения внутри группы: у **Источника** IP и порт —
И (оба должны совпасть), у **Сети** TCP/UDP и протокол — тоже И.
Реализация: плоское правило sing-box ИЛИ-т домены с IP и И-т всё остальное, поэтому правило
с Доменами **и** IP (или с «кроме») ядро собирает как `logical and` из групп (группа с
несколькими видами значений — `logical or`); вкладка JSON показывает так же. Процесс: имя и
путь в sing-box — разные поля (И), поэтому вместе они тоже идут через `logical or`; путь с `*` —
`process_path_regex`. Диапазон IP → набор CIDR, порты `a-b` → `port_range` `a:b`.
Нет списка на диске (geosite / geoip / rule-set ещё не скачан): в обычной группе правило
сужается до остальных значений, группа из одних списков или «кроме» со списком — правило
пропускается; в обоих случаях предупреждение при подключении.
Составные правила (вложенные И/ИЛИ, `logical` в sing-box) в форму не выносим — только через
JSON; в списке такое правило помечено бейджем «составное · JSON».

Валидация на лету: regex, CIDR, диапазоны IP, порт ≤ 65535, диапазон «от ≤ до».

### Действие

Proxy через основной поток · через конкретную цель (профиль / цепочка / подписка / нода —
пикер цели, §0) · Direct · Block (тихо сбросить / ответить отказом).

Ядро: цель = свои группы серверов (подписка → группа-selector, нода → один сервер, профиль → как
юнит, цепочка → вход + выход с detour), одна на все правила и приложения с этой целью.
Сервер группы цели при подключении выбирает ядро (проверка перед стартом, параллельно с маршрутом; у
цепочки — вход, затем выход через него): подключение ждёт цели не дольше 1.5 с после выбора маршрута,
не успевшие ставятся на свой сервер после старта (`docs/core.md` → «Подключение: проверка перед стартом»).
Block → `reject` (`method: drop` для «тихо»).

**Резолв перед IP-правилами.** Через системный прокси / mixed-порт соединение приходит доменом,
без IP, и IP-условия (IP / CIDR, локальные сети, GeoIP) не сработают, пока ядро не разрешит имя.
В TUN адрес уже есть, там ничего не меняется (но порт пользователя открыт и в TUN: домен, пришедший
на него, ядро резолвит так же, как в режиме прокси — шаг ограничен входами порта). Поведением управляет пользователь:
- **Настройка** Settings → DNS → «Resolve for IP rules» (§6): Off / Auto / конкретный сервер.
  Ядро ставит один `resolve` перед первым своим правилом с IP-условиями; прокси всё равно
  получает домен. Off — шага нет, IP-условия работают только при пришедшем IP (всегда у трафика TUN).
- **Флажок правила** «IP conditions only in TUN» (форма правила, показывается только у правил
  с IP-условиями — IP / CIDR, локальные сети, GeoIP, IP в JSON): такое правило не заставляет ядро
  резолвить и срабатывает, только когда адрес уже известен. Resolve ставится перед первым IP-правилом
  **без** флажка. `resolve` один на конфиг: правило с флажком, стоящее ниже него, тоже
  увидит полученный адрес. Собственные rule-sets IP-условием не считаются (по .srs не видно, что
  внутри) — такому правилу резолв не ставится.
- Быстрые правила сами не резолвят: регион / сервисы ловят домены и адреса, пришедшие как IP.

- **Fallback** (блок в карточке «Then», при Then = Proxy — и с конкретной целью, и с основным
  потоком; тот же блок, что в диалоге приложения): сегмент Default | Proxy | Direct | Block + строка
  Via («Main flow» или цель, не та же, что Via правила; активна только при Fallback = Proxy). Что
  делать, если цель выключена, пуста или удалена / основной поток недоступен (§0). Блок всегда на
  месте: при Then = Direct / Block затемнён и неактивен. Данные правила: `fallback`
  (`default|main|direct|block`, `main` = Proxy) + `fallbackTarget` (id цели или `''` = основной
  поток); в плане `fallback: 'main'` + `fallbackTarget` уходит как id цели. Заменил тумблер
  «Строго» (Строго = Block).

### Блок про IP в форме правила

Только у правила с IP-условием (пустая группа IP не считается; у JSON-правила — любые `ip_cidr` /
`ip_is_private` / `geoip` внутри), между условиями и «Then»: чекбокс **IP conditions only in TUN**
(по умолчанию выкл.) с кнопкой **(?)** рядом — пояснение (через proxy-порт IP-условия работают,
только если включён «Resolve for IP rules») и текущее состояние (Off / via <сервер>) лежат в ней,
а не под чекбоксом — и ссылка **Open DNS settings ›**. Ссылка открывает Settings → DNS **поверх**
формы (строка «Resolve for IP rules» прокручена в центр и подсвечена), форма с черновиком остаётся
под ней; закрытие DNS любым способом (×, свайп, Back) возвращает к форме как была. Убрал IP-условия —
флажок сбрасывается при сохранении. В JSON-вкладке флажка нет (как «If unavailable» и DNS): живёт
в форме, при переключении вкладок сохраняется.

### DNS правила

«Авто» (по умолчанию): сторона трафика правила — Direct-правило → прямая сторона списка, VPN-правило →
сторона VPN (§6: их кандидаты и порядок). Либо конкретный провайдер глобального списка: его кандидаты
на стороне трафика правила (на другой его стороне, если на нужной его нет).

Реализация: для доменных условий правила — DNS-правила sing-box с кандидатами цепочки (для шага
`resolve` и, с TUN, для запросов самих приложений); свои rule-sets в DNS-правила не идут.
Прямой трафик резолвит только `domain_resolver` исходящего (DNS-правила он не спрашивает), поэтому
перед Direct-правилом с доменами в маршруте стоит шаг `resolve` без сервера — он идёт по DNS-правилам
(§6 «Шаг resolve»); отдельных исходящих `direct@dns-<id>` нет.

### JSON

Вкладки **Форма | JSON**, синхронные. Поля JSON, которых нет в форме, не теряются — плашка
«доп. поля — редактируются в JSON». Невалидный JSON не сохраняется, ошибка со строкой.
Форма читает обратно всё, что сама написала: Форма → JSON → Форма даёт те же карточки и значения
(с «кроме», Домены + IP как `logical and`, имя, If unavailable, DNS, «IP conditions only in TUN»,
способ блокировки). Пустые карточки и поля в JSON не попадают (`{}` внутри `logical` не читался
бы обратно) — при возврате на форму они восстанавливаются из прежнего черновика. Плашка «составное»
— только для чужого JSON, которого форма не выразит (`or`, вложенный `logical`, повтор группы).

## 5. Внешние rule-sets

Раздел списков: URL, формат (srs / json), период обновления (то же окно «число + единица»),
«качать через VPN / напрямую». Встроенные geosite/geoip — там же.

Ядро (`rulesets.dart`): качает само, кладёт в `<dataDir>/rulesets/<tag>.srs|json` и отдаёт
sing-box как `type: local` (sing-box при старте ничего не качает; заменённый файл перечитывает
сам). Встроенные: сначала runetfreedom (`russia-v2ray-rules-dat`, ветка `release`,
`sing-box/rule-set-geosite/geosite-<имя>.srs`, `…/rule-set-geoip/geoip-<cc>.srs`), при 404 —
SagerNet (`sing-geosite` / `sing-geoip`, ветка `rule-set`). Качается только то, что нужно
правилам. Свежий файл (моложе периода) — как есть; устаревший — используется, обновляется
после подключения; ответ, не похожий на rule-set (страница провайдера), отбрасывается и не
затирает старую копию. Скачивание — служебный трафик ядра (`ServiceFetch`, цель `ruleset`,
`core.md` → «Служебный трафик»); запись атомарная (`.part` → переименование).
«Через VPN» — только по путям туннеля (main / маршруты): при первом подключении такого списка
ещё нет — правила без него (предупреждение), ядро скачивает его через новый туннель и само
переподключается. «Напрямую» — гонка по путям, прямой предпочтительнее; без sing-box — обычный
прямой сокет.
Неудача: повтор по `RetryPolicy` (1 → 2 → 5 → 15 мин; сеть сменилась — сразу; сети нет — когда
появится; сбой нашего перезапуска — после `settled`, без события). Событие `rules/ruleSetFailed`
идёт через Sentinel (`docs/failures.md`), в данных `hasCopy` — есть ли прошлая копия («используется
последняя копия»).
Обновление во время работы: по таймеру ядра (раз в минуту смотрит, у какого списка вышел его
`every`), но только когда контекст Sentinel `settled` (не сразу после подключения) и sing-box не
перезапускается. Заменённый файл sing-box перечитывает сам — **перезапуска нет**; перезапуск
только когда список новый для запущенного конфига (его не было при старте). Источники списков —
данные (`RuleSetSource`: tag, urls, формат, via, every), свой список пользователя добавляется
в тот же перечень без изменения кода загрузки.

## 6. DNS

**DNS — отдельный раздел Settings** (не внутри Connection). Карточка **DNS на главной**
ведёт туда же (как карточка Auto); при открытии раздела непропингованные серверы пингуются.

Раздел DNS:
1. **Глобальный DNS** — список **провайдеров** с галочками и приоритетом (перетаскивание),
   кнопка «+ Добавить». Порядок списка = приоритет. Провайдер — набор адресов в разных транспортах:
   **DoH** (`https://`), **DoT** (`tls://`), **DoQ** (`quic://`), **UDP** (обычный, открытый текст) — или
   **Local** (`system`, резолвер ОС; один, без транспортов). У провайдера:
   - **Транспорты** (`use`) — какие виды адресов использовать; по умолчанию DoH + DoT (UDP и DoQ выключены).
     Внутри провайдера адреса пробуются в своём порядке, только включённых видов. В форме — ряд чипов
     DoH / DoT / DoQ / UDP: только виды, для которых у провайдера есть адрес; последний включённый чип не
     снимается; у Local чипов нет. Адреса встроенных провайдеров только показываются; у **своего** сервера —
     список адресов разных видов (вид определяется по схеме, подпись у поля; порядок = порядок проб; минимум
     один): новый вид включается сам, исчезнувший (убрали его последний адрес) выключается.
   - **Стороны** (`sides`) — **напрямую** и / или **через VPN**: на какой стороне провайдер отвечает.
     Local — только напрямую (резолвер ОС — на машине, не в туннеле): `vpn` для него не действует. Сервер,
     добавленный пользователем, по умолчанию — только через VPN.
   - галочка (`on`) и **пинг** (в окне добавления — кнопка проверки). В списке (Flutter) справа в строке — чипы
     сторон, и **под каждым чипом пинг этой стороны** (`pingDnsSides`: зелёные мс / предупреждение при отсутствии
     ответа / `—`, если сторона выключена или не измеряется, напр. VPN без подключения / спиннер); тап по пингу
     перемеряет провайдера, «Ping all» — всех. Адрес занимает всю оставшуюся ширину строки.

   По умолчанию, в таком порядке: **Cloudflare**, **Google**, **AdGuard** (без фильтров) — DoH + DoT на обеих
   сторонах — и **Local** (напрямую). Cloudflare и Google заданы по IP; у AdGuard зашифрованные транспорты только по
   имени `unfiltered.adguard-dns.com` (по IP он отвечает лишь обычным DNS), имя предрезолвится, как адреса нод. Порядок **прямой стороны** задаёт `dnsCfg.directPolicy`, он
   **закрепляет Local** независимо от места Local в `dnsOrder`: `localFirst` (по умолчанию) — Local всегда
   первый, `priority` — Local всегда последний; остальные провайдеры идут в порядке списка (как на стороне VPN).
   Local в списке не перетаскивается: приложение показывает его на закреплённом конце. Настройка при
   выключенном Local неактивна (серая): ставить нечего.

   **Выключить можно любого провайдера** (`on: false`), и Local тоже. **Встроенные** провайдеры (id из списка по
   умолчанию: `cloudflare`, `google`, `adguard`, `local`) **удалять нельзя, только выключать**; удаляются лишь
   свои. Встроенность выводится из id (`DnsServerCfg.builtin`, в сохранённых данных и плане отдельного поля нет).
   Выключенный Local — не кандидат; резолвер ОС остаётся только как загрузчик (имена хостов DoH / DoT-серверов
   находит он) и как последняя попытка предрезолва адресов нод.

   **Сторона без включённого провайдера** (пользователь выключил всех, либо ни у кого нет этой стороны) — штатное
   состояние, не ошибка; конфиг sing-box остаётся корректным. Что делает ядро: у пустой стороны нет кандидатов,
   флагов и проверочных правил; вопросы, которые должна была отвечать она, получают кандидаты **другой** стороны
   (пустая прямая — сторона VPN, пустая VPN — прямая; для шага «Resolve for IP rules» без VPN-кандидатов — шаг без
   сервера и предупреждение); `dns.final` и `default_domain_resolver` берут первого кандидата доступной стороны. Если
   пусты обе — отвечает один резолвер ОС (`local`), DNS-правил нет. В `status.dns.sides.<сторона>` у пустой стороны
   `active` и `provider` равны `null`, `active` верхнего уровня — `null`, если нет кандидатов вовсе. Предрезолв адресов
   нод не зависит от сторон: без прямых серверов его делает резолвер ОС. Приложение предупреждает: «на этой стороне нет DNS».

   **Адреса встроенных не хранятся.** Для Cloudflare, Google, AdGuard и Local в настройках лежит только то,
   что меняет пользователь: `on`, `sides`, `use`, `name` и место в `dnsOrder`; `transports` не записываются, а при
   каждой загрузке берутся из кода приложения (то, что записали прежние версии, отбрасывается), поэтому смена
   адресов во встроенном провайдере доходит до всех установок без миграции. Вид, который появился у встроенного
   в новой версии, у существующего пользователя выключен (его сохранённый `use` главнее); вид, которого в коде
   больше нет, в `use` остаётся и ни на что не влияет. У своих серверов адреса хранятся как раньше.

   **Миграция.** Список прежней версии (`remote`, `local`, `google`: один адрес и одна сторона `via` на сервер)
   при загрузке один раз заменяется списком по умолчанию; свои серверы пользователя дописываются следом в
   прежнем порядке (адрес — один транспорт своего вида, `via` — сторона; id, занятый новым, получает `-2`;
   ссылки правил и «Resolve for IP rules» на переименованный id переписываются, `remote` → `cloudflare`).
   Метка `dnsCfg.listVersion: 2` — миграция сделана; дальше загрузка список не трогает; неизвестные поля
   сохраняются при записи. Старый вид плана `{id, addr, via, on}` ядро по-прежнему принимает: провайдер с
   одним транспортом (вид — по адресу) на стороне `via`.
1a. **Resolve for IP rules** (блок «Without TUN»; `dnsCfg.resolve`) — select: **Off** /
   **Auto** (по умолчанию) / любой отмеченный провайдер списка. Auto = первый кандидат
   **стороны VPN** (запрос не уходит к DNS провайдера); нет такого — шаг без сервера (решают DNS-правила)
   и предупреждение об утечке. Выбранный провайдер — его первый кандидат (на стороне VPN, если она у него есть).
   Снят с галочки или удалён → снова Auto (выбор хранится, вернётся вместе с галочкой). Провайдер только с
   прямой стороной выбрать можно, но под строкой предупреждение. Подсказка: касается только
   соединений через proxy-порт (системный прокси, порт пользователя; он открыт и в TUN), трафик TUN не затрагивается. Уходит в
   `plan.routing.dns.resolve`, смена при подключении — переподключение; правила строит ядро
   (`core.md`, «Правила в конфиге»). Сервер в шаге называется явно, поэтому «DNS» правила на него не
   влияет, но он следует флагам своего списка: резолвит первый кандидат с включённым флагом (лестница, см. ниже
   «Что следует за флагами»), так что при падении сервера шаг уходит на следующий. Флажок у правила — §4.
2. **Hijack DNS** — тумблер. Доступен всегда (чтобы не прыгать настройки ↔ главная);
   при выключенном TUN — пометка «работает только в TUN». Отдельного пикера серверов нет:
   перехваченные запросы идут в DNS ядра, а оно отвечает по глобальному списку. Ядро:
   `plan.routing.dns.hijack`, правила `hijack-dns` по порту 53 и протоколу `dns` из TUN
   (`core.md` → «TUN»; запросы к собственному резолверу туннеля ядро отвечает и при выключенном).
3. **FakeIP** — убран до переработки (тумблер и список исключений были в UI, ядро их не применяло);
   `DnsCfg` больше не хранит `fakeip` / `fakeipExclude`, старые сохранённые значения при загрузке отбрасываются.

Всё, что не попало в правила, резолвится глобальным списком по порядку.

**Ядро — кандидаты и флаги.** Каждый включённый транспорт каждого включённого провайдера на каждой его
стороне — отдельный DNS-сервер sing-box, **кандидат**: `dns-<провайдер>-<вид><n>` (n с 1 внутри вида),
на стороне VPN суффикс `-v` и `detour: proxy`; Local — `dns-<id>` (`system` → `local`). Адрес-имя хоста
(`tls://dns.google`) узнаёт сервер начальной загрузки: Local, когда он включён, иначе системный резолвер.
id кандидата (в Sentinel, `status.dns`, событиях) — тег без `dns-`: `cloudflare-doh1`, `cloudflare-doh1-v`.
`RoutingInfo.dnsSides` / `dnsCandidates` отдают упорядоченный список кандидатов каждой стороны.

У каждого кандидата есть **флаг** — локальный rule-set (`route.rule_set`, `type: local`, `format: source`,
тег `flag-<тег>`, файл `<dataDir>/dns-flags/<тег>.json`). Включён: `{"version":3,"rules":[{"domain_regex":[".*"]}]}`
(совпадает с любым именем), выключен: `{"version":3,"rules":[{"domain":["never.invalid"]}]}` (ни с каким).
Файл пишется атомарно (`dns_flags.dart`: `writeDnsFlags`, `setDnsFlag`); sing-box следит за файлом и
подхватывает правку **без перезапуска и без вызова API**, открытые соединения не рвутся. Файлы должны
существовать до старта (нет файла — sing-box не запускается, `sing-box check` тоже): ядро пишет все флаги
включёнными перед каждым стартом. Флаг «включён» значит «кандидат жив».

**Что отвечает сторона.** DNS-правила стороны — по кандидату в порядке приоритета:
`AND(что сторона отвечает, флаг) → сервер`; отвечает первый кандидат с включённым флагом. Все флаги
выключены — отвечает первый кандидат стороны (правило без флага после них; для «остального» — `dns.final`).
Один кандидат — флаг не нужен. Что отвечает сторона:
- **прямая** — домены Direct-правил, прямых сервисов и регионов; правило со своим провайдером — его
  кандидаты на стороне трафика правила (на другой его стороне, если на нужной его нет);
- **VPN** — домены правил через VPN; «Auto» у правила = сторона его трафика;
- **остальное** (`dns.final`) — сторона «остального»: VPN, а когда «Everything else» = Direct (и не
  Global) — прямая; на ней нет серверов — другая.

Смежные группы с одной цепочкой сливаются в одну (OR по доменам); цепочка, равная цепочке «остального»,
своих правил не получает. Число правил растёт линейно с числом кандидатов.

**Размер** (измерено, список по умолчанию: Cloudflare, Google, AdGuard по DoH + DoT на обеих сторонах и
Local): 25 DNS-серверов (3 × 4 адреса × 2 стороны + Local), 25 флагов; с одним Direct-правилом 26 DNS-правил при
VPN как «остальном» и 13 при Direct, конфиг ≈ 8,7 и 6,6 КБ.

**Шаг `resolve`.** Прямой исходящий резолвит только по `default_domain_resolver` / `domain_resolver`, DNS-правил
он не спрашивает. Поэтому перед правилами, отправляющими имена напрямую (Direct-правила с доменами, прямые
сервисы и регионы, «остальное» = Direct), в маршруте стоит `{action: resolve}` **без `server`**: он идёт по
DNS-правилам (значит, по флагам и провайдеру правила), а исходящий берёт готовые адреса. Исходящих
`direct@dns-<id>` больше нет. `default_domain_resolver` = первый **не системный** кандидат прямой стороны (резолвер
ОС — только когда на стороне нет других; нет кандидатов — серверу начальной загрузки); он фиксирован и флагов не знает,
поэтому **ни одно соединение с именем не должно доходить до `direct` без шага `resolve`**. **Порядок разрешения адресов
правил и собственных назначений ядра: резолвер ОС (`local` / `system`) — последним**, какой бы ни был порядок в списке
(он не знает наших флагов и может быть тем, что сломан); порядок «Local первым / последним» в списке относится к DNS-правилам,
которыми отвечаются запросы самих приложений. Собственные запросы ядра, уходящие в `direct` с именем (служебный
трафик `svc-in`, пользователь `direct`; проверка сети пулом через probe inbound), получают перед правилом
лестницу `resolve` по флагам прямой стороны (`directResolveFirst`, как у прямых приложений выше): запрос
получает кандидат с включённым флагом, выключенный не получает ничего (репорт `20261014-phmbw7`: запрос
`raw.githubusercontent.com` ушёл выключенному AdGuard). Проверки DNS/flagcheck в `direct` с `override_address`
свой сервер называют сами.

**Что следует за флагами и что нет.** Следуют: домены Direct-правил, прямых сервисов и регионов, «остальное»
(DNS-правила и шаг `resolve` без сервера) и **прямые половины приложений и Direct-правила без доменных
условий, которые DNS-правило умеет назвать** (процесс, пакет, сеть, вход, исходный адрес, домены, геосписки).
Перед ними в маршруте стоит один обычный `resolve` без `server`, а выбор сервера уходит в DNS-правила: на
каждого кандидата прямой стороны одно правило `AND(OR(условия всех таких приложений и правил), флаг) →
сервер` (соседние группы с одной цепочкой сливаются в одно `OR`). Число правил растёт линейно — «приложения
+ правила» плюс «кандидаты», а не их произведением. Это работает, потому что запрос шага `resolve` несёт
данные соединения: проверено на живом sing-box 1.14.2 — DNS-правило узнаёт его по `process_name`,
`process_path`, `inbound`, `network`, `source_ip_cidr`, `source_port_range`; **порт назначения запрос не
несёт** (`package_name` читает то же поле, что `process_name`; на Windows не проверялось). Поэтому то, что
DNS-правило назвать не может, — **условие по порту или IP и неизвестные наборы правил** — и **«Resolve for IP
rules»** (один раз на конфиг) получают перед правилом шаг `resolve` с явным `server` в виде **лестницы по
флагам** цепочки (для «Resolve for IP rules» — кандидаты стороны VPN или выбранного провайдера, для прямых —
цепочка DNS правила, для приложения — прямая сторона): правило `i` = `AND(условия правила, флаг i, НЕ
флаги 0..i−1) → resolve сервером i`, последнее — все флаги выключены → первый кандидат. Лестница
**исключающая** и не зависит от того, «уже ли разрешено» (sing-box резолвит один раз); у цепочки из одного
кандидата — один обычный `resolve` с сервером. Правило, которому нужен IP, второго `resolve` не получает:
оно идёт после шага «Resolve for IP rules». Собственные запросы прямого приложения (его DNS-правило
называет по процессу) и собственные запросы приложения в TUN (`selfDnsRules`) тоже идут по цепочке прямой
стороны с флагами. Размер: стандартный список + 20 прямых приложений + 10 прямых доменных правил — 62
правила маршрута вместо 322, конфиг ≈ 30 КБ вместо ≈ 103 КБ (DNS-правил 53 в обоих случаях). Следует и **запасной выход селектора в Direct** («If unavailable → Direct» у правила или приложения): у такого
селектора `<цель>~direct` есть свой флаг (`flag-fb<i>`, файл `<dataDir>/dns-flags/fb<i>.json`), включённый, **пока селектор
стоит на Direct**; ядро (`FallbackService`) включает его раньше, чем селектор переключается, и выключает после возврата на цель
(старт — по тому, что говорит sing-box). Перед правилом, которое ведёт в такой селектор, стоит лестница `resolve` по флагам
прямой стороны (цепочка правила, для приложения — прямая сторона; резолвер ОС — последним), объединённая с этим флагом: пока
цель жива, лестница ничего не разрешает; когда цель упала и имена пошли напрямую, их разрешают кандидаты с включённым флагом,
а выключенный не получает запросов. Правилу, которому и так нужен IP, лестница не нужна. Трафик, который остаётся через прокси,
локально **никогда** не разрешается. Адреса серверов прокси и хосты DoH/DoT-серверов от
флагов не зависят вовсе: ядро резолвит их заранее (следующий абзац). Вердикты серверов, по которым ходят флаги, — общее правило
«Вердикт меняется только после перепроверки» (`docs/failures.md`).

**Предрезолв адресов узлов и DNS-серверов.** (Тестовый конфиг пинга и замера скорости резолвит непрописанные имена узлов тем же верхним сервером системной цепочки, что и основной конфиг.) Имя сервера узла и имя хоста DoH/DoT-сервера (в том числе
серверов правил, целей правил и тестового конфига) sing-box сам резолвил бы по `domain_resolver` — до
подключения, когда DNS ещё не работает, и в обход флагов. Поэтому ядро разрешает эти имена **заранее** и
кладёт в конфиг IP:
- **Когда.** При обновлении подписки (по таймеру и вручную — только имена новых и изменившихся узлов), при
  каждом connect (плана, который запускается) и при повторных попытках после сбоя узла (ниже).
- **Чем и каким путём.** Запрос идёт **вне туннеля** (самоправило `address-resolve`, `platforms.md` → «Работа
  вне туннеля»), а не через VPN, через прямую сторону DNS: сначала зашифрованные транспорты (DoH, затем
  DoT), потом UDP/TCP, **системный резолвер — последним** (где бы он ни стоял в списке, включён он или нет).
  Это служебная работа: DNS-правила пользователя, выбор правил и маршрутизация к ней не применяются. Порядок:
  1) **включённые** серверы прямой стороны; сервер с сохранённым вердиктом «мёртв» пропускается (вердикт меняет
  только его собственная перепроверка); 2) когда никто из них не дал адрес — **выключенные** встроенные серверы
  (провайдер выключен, вид не используется, нет прямой стороны; тот же порядок, Local последним) по одному: их никто
  не проверяет, поэтому попытка и есть проверка — ответ любого вида записывается им вердиктом «жив». Серверы
  пользователя, которых нет среди включённых, не спрашиваются. DoQ для этого не используется. **Ответ любого вида
  (адрес, NXDOMAIN, пустой ответ, SERVFAIL) значит «сервер работает»** и вердиктом мёртвого не становится; **нет
  ответа** (таймаут, обрыв соединения) — улика для проверки этого сервера (подозрение DNS-переключателя), а не
  вердикт. Если адреса нет ни у кого, а все ответившие серверы сказали «такого имени нет» (NXDOMAIN или пустой
  ответ), это проблема адреса узла (провайдер / подписка), а не DNS; SERVFAIL и т. п. такого вывода не дают. Это одно
  наблюдение: вердикт и событие `node/addressMissing` — после перепроверки через минуту, узлы на этом имени встают на
  лесенку недоступных (`failures.md` → «Имя сервера узла не существует»).
  Имя кандидата-хоста разрешается по уже закэшированному IP.
  Запрашиваются A и AAAA (AAAA — только если включён IPv6 плана). На один сервер 3 с, на имя — до 8 с, до 8
  имён параллельно; имя, на которое никто не ответил, не спрашивается повторно 2 минуты (момент неудачи хранится в
  `addresses.json`, поле `failed`, запись старше суток забывается при загрузке: перезапуск приложения не спрашивает
  раньше срока; ответ любого сервера запись снимает).
- **Кэш.** Постоянный (`addresses.json`, переживает перезапуск): адреса, TTL (в пределах 10 мин – 6 ч), чем
  получены, курсор выбранного адреса; запись старше 30 дней забывается. Просроченная запись используется как
  есть, а обновляется в фоне.
- **Connect.** Берёт кэш. Недостающие имена **узлов, с которых стартует выбранный маршрут** (группа main; у цепочки — группа входа), ждёт **не дольше ~1,5 с в сумме**: каждый DNS-сервер прямой стороны спрашивается **параллельно**, побеждает ответ сервера с наивысшим приоритетом, успевший в окно, иначе первый пришедший (системный резолвер — запасной, только когда все серверы не ответили). Не успели, а также узлы остальных маршрутов, целей правил и имена DNS-серверов — для них в конфиге остаётся имя с `domain_resolver` = **верхний сервер системной цепочки** на момент сборки конфига (первый включённый встроенный сервер с живым или неизвестным вердиктом; системный резолвер — только когда таких нет; DNS-правила и настройки пользователя не используются), разрешаются в фоне, IP берётся при ближайшем перезапуске, который и так случится (перезапуска ради пина нет). Выход цепочки (исходящий с `detour`) `domain_resolver` не получает: его имя уходит ко входу как есть и резолвится на дальней стороне, локально не разрешается вообще (проверено на sing-box 1.14.2; с `domain_resolver` sing-box разрешил бы его у себя и подключался бы ко входу по адресу). Ожидание пишется в журнал (`address: connect waited N ms …`). Перезапуск после падения sing-box ничего не ждёт:
  только кэш. Адреса, вшитые в запущенный конфиг, хранятся в записи для `adopt`.
- **Журнал.** Каждый ответ резолвера пишется строкой `address: <имя> → <IP> via <кто ответил> in N ms`
  (`cloudflare-doh1`, `udp:…`, `system`); конфиг connect'а и тестовый конфиг (пинг, спидтест) пишут первые 12
  закреплённых имён: `имя → IP (via кто, N s old)` и сколько имён осталось именами. Имена доменов отчёт не
  маскирует. Узлы, у которых в подписке уже IP (например «LTE»-узлы провайдера), в этом не участвуют: их
  адрес — тот, что в ссылке.
- **Что меняется в исходящем.** `server` = IP; домен переходит туда, где он нужен для проверки сертификата и
  маршрутизации на стороне сервера: `tls.server_name` (если пустое и не `disable_sni`; своё значение,
  в том числе Reality, не трогается), для `ws` — заголовок `Host`, для `httpupgrade` — `host` (оба в виде
  `имя:порт`, как отправил бы сам sing-box; своё значение остаётся как есть), для `http` (h2) — `host`.
  gRPC по TLS — ничего больше (authority берётся из `server_name`). Не подменяются: исходящие с `detour`
  (вход цепочки подменяется как обычный, выход резолвится удалённо), Shadowsocks с plugin, gRPC без TLS.
  DNS-серверы DoH / DoT / DoQ: `server` = IP, `tls.server_name` = имя, у DoH ещё заголовок `Host`; UDP/TCP —
  только IP; `domain_resolver` убирается. Серверы с IP-адресом в списке (по умолчанию) не трогаются.
- **Сбой узла.** Когда Auto объявляет узел упавшим (`failAfter` промахов), а он в плане подключён по
  закэшированному адресу, ядро (не чаще раза в 5 минут на имя; только при `settled` и сети `up`, не во время
  перезапуска) сначала пробует **следующий закэшированный адрес** (ещё не пробованный с последнего connect), а
  когда перебраны все — резолвит имя заново. **Набор IP изменился** — курсор в начало и перезапуск sing-box
  (причина `reresolve`, с отсрочкой 2 с, на текущем узле Auto); **набор тот же** — перезапуска нет. Следят
  за узлами, которые сейчас используются или входят в кандидатов активной группы; узлу, оставшемуся по
  имени, повторный предрезолв не нужен — его резолвит sing-box.

**Проверка флага (flagcheck).** Чтобы убедиться, что sing-box действительно подхватил файл, у каждой стороны
с несколькими кандидатами есть служебное имя `<сторона>.flagcheck.jorm.invalid` (`direct` / `vpn`): первые
в списке DNS-правил (до остальных) правила `predefined` по той же схеме `AND(имя, флаг)` отвечают на него
A-записью `127.77.<сторона>.<n>` — **номер кандидата, который сейчас отвечает стороне** (без сети и без
кэша). Ядро спрашивает имя через probe inbound (пользователь SOCKS `flag-check/<тег>`, маршрут по IP ответа
на порт пробы; `Probe.inbound(flagChecks:)`, `probeFlag`). Эти имена не попадают в пользовательский
трафик и в суждения Sentinel (правила пробы отнесены к DNS-проверкам). Старый sing-box без такого правила даёт
«нельзя узнать» (`null`) — это не ошибка.

Реализация: в sing-box у DNS нет встроенного fallback между серверами — переключение по приоритету делаем
сами, как Auto для нод, **на лету, без перезапуска** (`dns_failover.dart`: `DnsFailover` — только
**исполнитель**, здоровье судит Sentinel):
- **Switch automatically** (Settings → DNS, по умолчанию **включено**, `dnsCfg.auto`) — при
  включённом ядро само уводит DNS с молчащего кандидата на следующий по приоритету и
  возвращает, когда более приоритетный оживёт; каждая сторона (прямая и VPN) переключается **независимо**.
  Выключено — **все флаги включены** (отвечает первый кандидат каждой стороны); проверки, суждение и метки
  в списке остаются. Выключение возвращает первый сразу (`dns/switched`, `reason: off`), включение применяет
  текущие вердикты сразу. Настройка едет в теле connect
  (`dnsAuto`) и на лету — `POST /api/dns/auto`; в `plan.routing` её нет, так что её смена не переподключает.
- Проверка кандидата: настоящий DNS-запрос имени (`cp.cloudflare.com`, запасные —
  `www.gstatic.com`, `captive.apple.com`) через **один этот** сервер и по его же пути
  (напрямую или через VPN): probe inbound ядра, правило `resolve` с явным
  `server`, без кэша. Раунды идут с интервалом Auto (`checkEvery`, после промаха `retryPause`);
  при слабой сети (статус пула не `up`) не проверяются. После подключения (ядро settled) **все кандидаты
  проверяются параллельно** в первом раунде; флаги на старте — по хранимым вердиктам (ниже, «Вердикты хранятся»);
  нет вердикта — включён.
- Здоровье кандидата решает контроллер (Sentinel, `docs/failures.md` «DNS-серверы как узлы»), не
  само переключение: промах раунда — улика подозрения `dns.down` этого кандидата; если промахи
  держатся окно (`dnsDown`, 1 с) и он не отвечает сейчас, открывается корень `dns.down` и
  пишется `dns/failed`. **Промах двигает сторону сразу:** флаг кандидата гаснет и отвечает следующий по приоритету, не
  дожидаясь суда (суд идёт параллельно; сейчас это и на прямой стороне; живой трафик и поиск адреса узла этого не
  запускают). Промах при упавшей сети / туннеле / маршруте (для кандидата «через VPN») —
  следствие этого корня: ни события, ни переключения.
  **DNS на ноде (сторона VPN):** прежде чем назвать сервер мёртвым, ядро проверяет, жива ли нода выхода (нет — ни
  вердикта, ни события), и спрашивает тот же сервер через запасную работающую ноду. Ответил там — сервер мёртв **на этой
  ноде** (вердикт ноды, событие `dns/failedOnNode`; через другие ноды живёт); молчит и там — мёртв сам (вердикт сервера для
  всех нод, `dns/failed`). Нет запасной ноды или транспорт не спросить (DoQ, системный; молчание UDP-сервера по TCP ничего
  не доказывает) — прежнее поведение: мёртв на этой ноде, `dns/failed`. Мёртвый на стороне VPN проверяется заново
  **раз в 20 минут** (прямая сторона — своей лестницей). NXDOMAIN сайта DNS не переключает. Подробно — `docs/failures.md`,
  «DNS на ноде». Ответ закрывает корень. Свежий промах самого раунда
  (до 10 с) считается ответом на проверку «отвечает ли сейчас» (повторного вопроса нет), а проверка «отвечает ли другой сервер
  пути» (`dns.path`) не спрашивает серверы, мёртвые по вердикту.
- **Вердикты хранятся** (`docs/failures.md`, «Вердикт меняется только после перепроверки»): вердикт сервера (адрес +
  транспорт + сторона; на стороне VPN ещё и нода выхода) лежит в `<dataDir>/dns-verdicts.json` и не сбрасывается
  переподключением, сменой настроек, перезапуском ядра, выключением и включением провайдера. **Старт:** флаги ставятся по
  вердиктам — хранимые как мёртвые выключены и проверяются сразу, сторона отвечает лучшим из работавших в прошлый раз
  (вышестоящие, не проверенные, ждут своего первого ответа); промах уже мёртвого сервера нового `dns/failed` не пишет.
  **Смена сети** — сразу параллельная проверка отвечающего сервера каждой стороны. **Смена ноды выхода** — применяются
  вердикты новой ноды и сторона VPN проверяется заново (`dns/switched`, `reason: node`).
- Исполнитель (`DnsFailover`) действует по вердиктам: корень кандидата открылся → его флаг гаснет
  (`reason: verdict`), отвечает **самый приоритетный из тех, у кого флаг включён** (то есть из отвечающих без
  корня); корень закрылся и кандидат ответил `failAfter` раз подряд (плюс пауза flap guard, если он выпадал)
  → флаг снова включён (`reason: back`). Это касается **любого** кандидата, у которого есть флаг, в том числе
  более низкого и кандидатов цепочки правила (у системного резолвера `system` флага нет). Пока сеть не `up`
  или ядро не settled, ничего не пишется. Если **выключены все флаги стороны**, отвечает её первый кандидат
  и флаги больше не гоняются (мёртвая сторона не мигает). Корень, судимый пока сеть/ядро не готовы, ждёт.
- **Повторная проверка мёртвого.** Кандидат с открытым корнем `dns.down` в периодические раунды не попадает: его
  спрашивает своя лестница **30 с → 1 мин → 2 мин → 5 мин** (дальше каждые 5 мин) от момента открытия корня, только
  при сети `up` и пока ядро подключено (нет сети — тик откладывается на 10 с). Первый ответ закрывает корень и возвращает
  кандидата раундам; флаг включается по `failAfter` ответам подряд, как и раньше (`reason: back`). Лестница
  сбрасывается, когда корень закрыт. Выключенные провайдеры (не в конфиге) не проверяются вовсе; смена провайдера
  (галочка) — переподключение: новый `DnsFailover` проверяет **всех** кандидатов в первом раунде, а мёртвых по
  хранимому вердикту — сразу при старте; красное не снимается без проверки.
  Собственные запросы ядра за адресами узлов (`address_resolver`) не спрашивают кандидата с выключенным флагом или открытым корнем
  (`DnsFailover.alive`, живой, а не снимок памяти флагов). Строки `dns: lookup failed for cp.cloudflare.com / www.gstatic.com /
  captive.apple.com` в журнале sing-box — это проверки (`dns-check/<тег>` в probe-in), а не пользовательские запросы.
- **Пинг провайдера по сторонам.** `pingDnsSides {provider}` (`POST /api/dns/ping`) → `{provider, live, direct, vpn, servers}`:
  та же проверка (probe inbound, путь кандидата, имена по очереди), по всем кандидатам провайдера параллельно; сторона = лучший
  ms её кандидатов, `-1` — никто не ответил, `null` — на стороне нет кандидата. При сети `up` ответ считается как раундовый
  (ответ закрывает корень, промах — улика), иначе только замер. `live: false` — sing-box не запущен или провайдера нет в конфиге:
  приложение меряет прямую сторону в процессе (`dnsLatency`, лучший из транспортов), VPN — `null`.
- Каждая запись флага журналируется (кандидат, вкл/выкл, причина, файл, результат; `docs/logs.md`); после записи
  ядро спрашивает flagcheck стороны и пишет, через сколько мс sing-box подхватил файл, или предупреждение
  «flag not applied after N s». Один раз проверяются обе стороны после старта. Раунд пишет по строке на сторону
  (кто отвечает, у кого флаг включён, кто выключен). Не удалась сама запись — предупреждение, флаг остаётся
  как был, ничего не переключается.
- **Перезапуск sing-box** (свой перезапуск, восстановление после падения): состояние флагов не берётся из
  файлов, а **применяется заново** из памяти сервиса — те, что были выключены вердиктом, пишутся выключенными
  до старта (в журнале «flags off again after the restart»), вернутся включёнными по первому ответу (без
  `failAfter`). Подключение пользователем и `adopt` начинают с флагов по хранимым вердиктам (нет вердикта — включён);
  файлы флагов «If unavailable → Direct» пишутся выключенными, а состояние селектора выставляет `FallbackService`.
- **События.** `dns/failed` (warn, только подтверждённый) — **на провайдера и сторону**: если упал один
  транспорт, а другой транспорт того же провайдера на той же стороне отвечает, это только строка журнала
  (флаг транспорта всё равно гаснет); событие — когда не отвечает ни один; и только при **смене** вердикта (промах сервера,
  мёртвого по хранимому вердикту, события не даёт). `dns/switched` (info) пишется
  **на сторону**, когда меняется её отвечающий кандидат (`side`, `from`, `to`, их провайдеры, `reason`:
  `failover` / `back` / `node` / `off`).
- Серверы, которые живой переключатель не двигает, тоже под наблюдением: тот, что резолвит прямой трафик
  (`default_domain_resolver`), сервер «Resolve for IP rules», серверы, названные правилами (в том числе
  неотмеченные) — проверяются теми же пробами (только те, что реально в конфиге), судятся так же, корень
  и `dns/failed` открываются; их флаги (если сервер — кандидат цепочки правила) следуют вердикту, но
  стороны они не двигают. Системный резолвер ОС (`local`, когда своего `system`
  в списке нет) наблюдается так же под id `system` (без флага). `status.dns` показывает и наблюдаемые (после
  используемых, с `watched: true`).
- UI: `status.dns` = `{active, auto, sides: {direct: {active, provider}, vpn: {active, provider}},
  servers: [{id, ok, rechecking, ms, provider, side, kind, flag?, watched?}]}`. `active` — id кандидата, отвечающего трафику
  через VPN (если у VPN-стороны нет кандидатов — прямой стороны); `sides.<сторона>` — кандидат и провайдер,
  которые отвечают стороне сейчас (оба `null`, если сторона пуста); сервер: `provider`, `side` (`direct` / `vpn`),
  `kind` (`doh` / `dot` / `doq` / `udp` / `system`), `flag` — флаг сейчас включён (нет у `system`); `watched: true` —
  только наблюдается, на него не переключаются; приложение берёт `ok == false` по id и неизвестные поля не
  читает (`ok` — **хранимый вердикт**: `false` мёртв, `true` отвечает, `null` — не проверялся ни разу, тогда по последней пробе;
  `rechecking: true` — идёт перепроверка, а показан прежний вердикт — приложение отмечает это индикатором, цвет не меняет;
  `deadOn: 'node'` — мёртв только на ноде выхода в использовании, строка провайдера подписана «Dead on this node»). Список DNS в приложении
  (пока подключено): у строки провайдера чипы **direct** / **VPN** — они же переключают `sides`; на чипе стороны,
  чей кандидат отвечает сейчас (`status.dns.sides.<сторона>.provider`), медленно бегущая анимированная рамка;
  чип, мёртвый на своей стороне (у всех кандидатов провайдера на ней `ok == false`), приглушён красным.
  Выключенный провайдер (`on: false`) остаётся в основном списке на своём месте, с неотмеченной галочкой и
  серой строкой. Провайдер, который **включён, но мёртв на всех своих активных сторонах**, уходит в сворачиваемый
  раздел под списком (как Unavailable в Nodes). У провайдера всегда есть хотя бы одна сторона и хотя бы один
  вид транспорта: тап по единственному включённому чипу стороны (в списке и в форме) молча переключает
  провайдер на другую сторону; последний транспорт в форме снять нельзя; выключить провайдер целиком можно только
  галочкой. Выключение последнего
  включённого провайдера стороны предупреждает, что ядро ответит этой стороне с другой: пустая прямая сторона — DNS
  прямого трафика пойдёт через VPN-серверы; пустая VPN-сторона — DNS трафика через VPN пойдёт мимо туннеля, провайдер
  связи увидит открываемые сайты; пусты обе — только системный резолвер (для VPN-трафика это тоже обход туннеля). Local закреплён настройкой `directPolicy` (см. выше), настройка
  серая при выключенном Local. Событие журнала
  `dns/switched` (info: `side`, `from`, `to`, `fromProvider`, `toProvider`, `reason` = `failover` / `back` /
  `node` / `off`; `own` у `off`), уведомление под тумблером «When Auto switches».
Без ядра (мок) сервер «в работе» — первый, у которого пинг не −1.

Сейчас: смена галочек / порядка / транспортов / сторон — переподключение (кандидаты, флаги и правила пересобираются).

DoH в браузерах обходит Hijack — не наше дело, не боремся.

### Гонка протоколов (`dns_failover.dart`)

Провайдер на включённой стороне (direct / VPN — каждая отдельно) имеет несколько транспортов (DoH / DoT / DoQ / UDP).
Работает один — **победитель**; остальные в резерве (флаг выключен, но сервер не мёртв).
- **Гонка**: все транспорты провайдера на стороне спрашиваются параллельно (та же проверка, что у раундов; мёртвые по
  вердикту не спрашиваются — у них своя лестница). Победитель — первый зашифрованный (DoH / DoT / DoQ), который ответил;
  он включается сразу (флагом, без переподключения), не дожидаясь остальных. Остальные результаты доезжают в статус и
  вердикты. **UDP побеждает только если все зашифрованные транспорты провайдера молчат** (нет ответа или мёртвые).
- **Когда гонка идёт**: старт; смена сети; смена выходной ноды (только VPN-сторона, вердикты новой ноды применяются до
  гонки); отказ победителя. Гонка, назначенная при недоступной сети, идёт, когда сеть поднялась. Пинг провайдера,
  раунды и ответ быстрее на несколько мс победителя **не меняют** (нет дребезга).
- **Отказ победителя**: промах выключает флаг сразу (как раньше); побеждает лучший из уже известных рабочих
  транспортов **того же провайдера** (зашифрованный быстрее; UDP — если все зашифрованные молчат); нет такого —
  провайдер выбыл, отвечает следующий по приоритету (прежнее поведение). Параллельно идёт новая гонка провайдера.
  Транспорт, который выбыл по промаху и снова отвечает, возвращается в резерв только по правилам флап-гарда
  (`failAfter` ответов подряд, hold) и не отбирает работу у победителя.
- **Видимость**: каждая гонка — строка `dns race (провайдер, сторона; причина): doh 31 ms, dot no answer, …; winner …` в Raw
  логе; промахи транспортов идут обычным путём (подозрение → вердикт → `dns/failed`, повторы считаются). Победитель
  гонки на старте, при смене сети или ноды — обычный выбор, не переключение: события `dns/switched` нет, строки гонки
  достаточно. Смена победителя после **отказа** прежнего — `dns/switched` с `reason: failover` (в том числе когда новая
  гонка, назначенная отказом, нашла транспорт лучше выбранного сразу).
- **Резерв переживает рестарт sing-box**: транспорт в резерве — рабочий, а не выключенный. Ядро запоминает резерв вместе с
  флагами (`reserve`), и после перезапуска sing-box ядром (сбой, пересборка списков) такой транспорт остаётся резервом: не
  «выключен», не «мёртв», `alive()` для него истинно, сам поверх победителя не возвращается и становится готовым
  запасным, если победитель откажет (старт заново проводит гонку). Новое подключение пользователя начинает с чистого листа.
- **Нарушенная запись флага**: ошибка записи флага победителя / резерва видна (warn в Raw «dns flag … the write failed»),
  выбор сохраняется и записывается снова ближайшим раундом (через `retryPause`, не через обычный интервал); до записи
  сторона отвечает прежним флагом. «Switch automatically» выключен — гонка идёт и победитель отслеживается, флаги остаются
  все включёнными; включение применяет выбор.
- **Статус** (`status.dns.providers`, `POST /api/dns/ping` → `providers`): по провайдеру и стороне
  `{provider, side, racing, winner: {id, kind, ms}|null, transports: [{kind, ids, ms, state, dead?, reserve?}]}`.
  `state`: `testing` (проверка идёт — приложение показывает спиннер и спрашивает снова, пока не станет `ok` / `miss`),
  `ok`, `miss`, `untested`. Пинг провайдера спрашивает все транспорты и возвращает результат каждого. Провайдер из одного
  транспорта не гоняется: он «победитель», пока отвечает.

## 7. Режимы и kill switch

- **Режим подключения** на главной: TUN | Proxy, **по умолчанию Proxy** (TUN на Windows требует
  прав администратора). На Android переключателя TUN | Proxy нет — всегда VPN (TUN); Global |
  Rules есть, как и везде.
- **System proxy** — третий переключатель в карточке режимов на главной (сверху название
  «Sys proxy», снизу рядом On | Off; плашка ездит вбок). Там же в Settings → Connection —
  **Proxy port**: порт локального HTTP + SOCKS5 прокси ядра (127.0.0.1, по умолчанию 2080),
  на него указывает системный прокси; 1024–65535, кроме занятых приложением (7788 jormd,
  9090 Clash API). Смена порта при подключении — переподключение с новым портом и тумблер в Settings → Connection; оба держат одно
  состояние. Позже с главной на мобилках
  уберём (на Android системный прокси большинство приложений игнорирует).
- В блоке **Proxy port** всегда (и без пароля) две кнопки **Copy SOCKS5** / **Copy HTTP**: в буфер
  идёт `socks5://127.0.0.1:<порт>` / `http://…`, при включённом пароле — с
  `логин:пароль@` (в percent-кодировке).
- **Proxy password** (Settings → Connection, под Proxy port; по умолчанию **выкл**: порт открыт,
  как у Karing, — подсказка «any program on this PC can use the port»; оба текста подсказки
  занимают место одновременно, строка не меняет высоту). Включили — если логина и пароля ещё нет,
  генерируются случайные логин (8 знаков) и пароль (20); есть — берутся прежние. Оба видны в полях
  (общая колонка подписей, поля выровнены) и правятся (логин: непустой, без
  пробелов и `:`, до 64 знаков; пароль: 4–128 знаков без пробелов; неверное значение — тост и
  прежнее остаётся); справа внутри поля пароля иконка ⟳ — новый случайный пароль (логин остаётся).
  Выключили — логин и пароль **сохраняются**, но в план (`mixedAuth`) не уходят. Они лежат в `connCfg` (снимок состояния): **бэкап и экспорт содержат их**, как и
  всё остальное из Settings. Уходят в ядро в плане как `mixedAuth: {user, pass}`, смена при
  подключении — переподключение (как порт). Windows не умеет отдавать пароль системного прокси,
  поэтому при включённом пароле **и** системном прокси ядро открывает второй вход на своём
  свободном порту loopback без пароля, и системный прокси (в том числе удерживаемый kill switch'ем)
  указывает на него, а не на Proxy port; без пароля — как раньше, на Proxy port. Порт второго
  входа не показывается в UI (ставить в чужие программы нужно Proxy port с паролем); он доступен
  любой программе этого ПК, как и сам системный прокси. На Android в TUN пользовательский порт по
  умолчанию не открывается вовсе.
- **Kill switch** (глобальный, Settings → Connection, отдельный тумблер; там же пока
  выбор **TUN stack** (`connCfg.tunStack`: `mixed` по умолчанию / `system` / `gvisor`; подсказки:
  Mixed — TCP через системный стек, UDP через gVisor; System — самый быстрый, может конфликтовать
  с файрволами и антивирусами; gVisor — самый совместимый, больше нагружает CPU; в плане —
  `tunStack`; при подключённом TUN смена — переподключение, в режиме прокси просто сохраняется),
  тумблер **IPv6** (`connCfg.ipv6`, по умолчанию **выкл.**, как в Karing; подсказка «Leave off
  unless your network and servers carry IPv6 — otherwise apps hang on IPv6 addresses»): выкл. —
  DNS ядра отвечает без AAAA (`dns.strategy: ipv4_only`; это и в режиме прокси — клиенты порта
  тоже не получают непригодных AAAA), а в TUN IPv6-соединения сразу отклоняются (правило
  `reject` для `ip_version: 6`; сам TUN остаётся dual stack, чтобы IPv6 не уходил мимо VPN);
  вкл. — dual stack, как раньше. В плане — `ipv6`; смена при подключении —
  переподключение в обоих режимах; детали — `core.md` → «TUN» → IPv6)
  и выбор Latency test URL — см. subscription-parsing.md → URL для
  latency-теста). Подсказка: «Blocks traffic when the VPN is down. Works for apps that use the
  system proxy; full block needs TUN.» Он блокирует **только приложения, которые ходят через
  системный прокси** (и то, что настроено на наш порт вручную); всё остальное утекает
  напрямую — полная защита возможна лишь с TUN (в ядре есть, `strict_route`; своего kill switch у TUN пока нет). Ключи в `connCfg` (снимок
  состояния, бэкап), уходят в ядро вместе с connect, а при смене (в том числе `launchAtStartup` /
  `connectOnLaunch`, от которых зависит `killWhileClosed`) во время подключения или down —
  сразу через `POST /api/killswitch` с теми же четырьмя полями (в down прокси перестраивается
  по новым настройкам: kill switch вкл → удержан, выкл + Remove → снят):
  - `killSwitch` [выкл] — пока пользователь подключён, наш системный прокси не снимается ни при
    каком сбое: упало → интернет блокируется (прокси указывает на мёртвый порт), а не идёт
    напрямую. Выключение, пока он что-то защищает (подключено, down или блок после
    отключения), — только после подтверждения: шторка говорит, что будет (трафик пойдёт напрямую
    при падении / прямо сейчас, или блок снимется). Включение и выключение без подключения — сразу.
  - Под ним (видны и действуют только при включённом `killSwitch`, с отступом):
    `killOnDisconnect` [выкл] «Also after I disconnect» — отключение пользователем тоже не снимает
    прокси: интернет заблокирован до подключения или кнопки Remove на главной (плашка
    `status.blocking`). `killWhileClosed` [выкл] «Also while the app is closed» — закрытие
    приложения (остановка jormd) не восстанавливает прокси; доступен только при
    `genCfg.launchAtStartup` **и** `genCfg.connectOnLaunch` (иначе после закрытия интернет мёртв, пока
    юзер не запустит приложение сам): без них строка серая, в подсказке причина, тап предлагает
    включить оба. Снимешь автозапуск / автоподключение — опция снова серая (в ядро уходит false).
    **Включение — только через шторку подтверждения** «Keep blocking while closed?»: «Если приложение
    не запустится или будет удалено, интернет останется заблокированным. Снять вручную: Параметры
    Windows → Сеть и Интернет → Прокси-сервер → выключить «Использовать прокси-сервер»» [Turn on /
    Cancel]. Если автозапуск / автоподключение выключены, это та же единственная шторка: над текстом
    добавляется строка, что они тоже будут включены, а «Turn on» включает всё сразу. Выключение —
    сразу, без шторки. В будущем режиме TUN / WFP блок делается **непостоянными** WFP-фильтрами,
    их снимает перезагрузка (постоянные — только у явных опций «kill switch с загрузки» /
    «блокировать до VPN»); тогда в тексте шторки добавляется «In TUN mode a reboot also lifts the block».
  - `downProxy` [`remove` | `keep`, по умолчанию `remove`] «If the VPN cannot recover» — видна
    только при **выключенном** `killSwitch`; тумблер «Remove the proxy if the VPN cannot recover»
    (вкл = `remove`, выкл = `keep`), оба текста подсказки занимают место сразу — строка не прыгает.
    Remove: когда VPN не поднялся за 30 с («down», см. connect-model.md → ConnectDock), ядро
    возвращает сохранённый системный прокси, трафик идёт напрямую, пока VPN не вернётся. Keep: прокси
    остаётся, интернет мёртв до возврата (то же поведение, что при `killSwitch`, но без
    подопций).
  - **Фоновый перезапуск не настраивается.** sing-box упал при подключении → ядро сразу
    перезапускает его; системный прокси при этом **не снимается** (утечки во время
    перезапуска нет: приложения просто ждут порт), пользователь ничего не видит. Паузы 1 с, 4 с,
    15 с, дальше каждые 30 с, пока пользователь подключён; успех — та же запись, правила, сервер.
    После 30 с безуспешных попыток начинается «down» (кнопки Retry и Disable sys proxy на главной;
    Retry — перезапуск сейчас; Disable sys proxy / Remove — восстановить прежний системный
    прокси сейчас; попытки продолжаются). Отключение пользователя во время перезапуска / down
    прекращает попытки; прокси — по `killOnDisconnect`.
  «Упало всё» — ядро упало, ни одна запись Auto не пропускает трафик: блок. **Исключение —
  правило, у которого в «If unavailable» явно выбран Direct**: его трафик пропускается (это
  решение юзера для этих адресов); при включённом kill switch в таком правиле висит
  предупреждение. (Решено, не сделано.)
  Не путать с «Строго» у правила (§4).
- **Global**: всё в прокси (кроме локальных сетей — они всегда напрямую), правила не применяются
  вовсе — ни свои, ни приложения, ни Block
  (**по умолчанию, требует решения**; альтернатива — оставить Block и приложения). DNS-список
  работает и в Global.

### Запуск с системой (план, не сделано)

Цель (юзер): ничего пользовательского не уходит мимо VPN до его старта; трафик системы до входа —
вторичен. Гарантию дают только «До входа» или kill switch с загрузки; «При входе» лишь сужает окно
(задача стартует рано, но гонку с другими программами входа не исключает).

Настройка поведения в Settings → General (рядом с Launch at startup / Connect on launch), три уровня:

- **Выкл.**
- **При входе (по умолчанию для автозапуска)** — как у Karing: задача Планировщика «при входе
  пользователя», с наивысшими правами (без UAC-окна). Стартует раньше обычного автозапуска
  (Run / Startup Windows откладывает на несколько секунд), но до входа трафик не защищён.
- **До входа в систему (по желанию)** — ядро (jormd) как служба Windows, автостарт при загрузке;
  подключается в выбранном юзером режиме, UI при входе цепляется к работающему ядру. Права
  админа — один раз, при установке службы.
  - Работает с любым режимом по настройкам юзера. Оговорка: системный прокси — настройка
    пользователя (HKCU), до входа её нет и применить некому; до входа защищает только TUN.
    В режиме sys proxy служба поднимает ядро и порт заранее, а прокси ставится при входе.
  - Kill switch с загрузки (опция при включённом kill switch): постоянные фильтры Windows
    Filtering Platform (как у Mullvad) — пропускают только ядро к его серверам, локальные сети и
    DHCP, пока туннель не поднят. Ядро не поднялось → интернета нет: нужен понятный выход
    (переключатель в UI, аварийное снятие фильтров) и учёт сетей с авторизацией (гостиничный Wi-Fi).
- **Блок до старта VPN (отдельная опция «для параноиков», по умолчанию выкл)** — работает с «При
  входе» и «До входа», служба не нужна. Временный kill switch на старте для всех, независимо от
  своего kill switch юзера:
  - Ставится только при автозапуске + Connect on launch (без автоподключения туннель не
    планируется — блок снимается сразу при старте ядра).
  - Постоянные WFP-фильтры, ядро «взводит» их заранее (при включении опции и при каждом
    выходе), Windows применяет их с загрузки сама. Блокируются только процессы пользовательского
    сеанса; системные службы (DHCP, время, Windows Update), локальные сети и само ядро к своим
    серверам — пропускаются.
  - Снятие: TUN — когда туннель поднят; sys proxy — когда прокси выставлен и ядро слушает порт.
    Дальше действует обычный kill switch юзера (вкл или выкл).
  - Страховки: тайм-аут N секунд — если туннель не поднялся, а свой kill switch у юзера выкл,
    блок снимается с событием в журнале и уведомлением (при вкл — остаётся, это его выбор);
    аварийное снятие кнопкой в UI и `jormd --unblock`; выключение опции / автозапуска сразу
    разряжает фильтры; деинсталлятор их удаляет. Тайм-аут же спасает сети с авторизацией.
- Android: старт по BOOT_COMPLETED + подсказка включить системные «Постоянный VPN» и «Блокировать
  соединения без VPN» (их соблюдает сама ОС).
