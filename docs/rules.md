# Правила маршрутизации, DNS, режимы — план

Статус: **§0–§7 сделаны в макете**. Код макета: `js/40-rules.js` (экран правил, проверка адреса,
итоговый порядок, импорт/экспорт, наборы правил), `js/42-apps.js` (приложения),
`js/75-rule-form.js` (форма правила и JSON), `js/56-dns.js` (DNS и Settings → Connection).
Не в макете: «Импорт из подписки» (заглушка), десктопный выбор процесса по пути (поле Process
есть, пикера файлов нет).

**В ядре** (live-режим через jormd): свои правила, приложения, быстрые правила, «всё остальное»,
«If unavailable» и DNS собираются в конфиг sing-box — `core/lib/src/routing.dart`; UI шлёт свою
модель (`plan.routing`, `js/93-routing-plan.js`), а не JSON sing-box, так что Flutter возьмёт тот
же Dart-сборщик. Списки (geosite / geoip / свои rule-sets) качает и кэширует ядро —
`core/lib/src/rulesets.dart`. Контракт — `core.md` → «Правила в конфиге». В live-режиме правила
и приложения стартуют пустыми и хранятся в снимке состояния вместе с быстрыми правилами,
наборами правил и DNS. «If unavailable» переключается на лету, DNS переключается по
приоритету сам (§0, §6). Не сделано: TUN, Hijack DNS / FakeIP. Пометка **«по умолчанию, требует решения»** — поведение, выбранное
без решения юзера.

Принцип: удобное приложение для прошаренных юзеров — всё, что умеет sing-box, но через
понятные формы; сырой JSON — как запасной выход, а не единственный способ.

## 0. Цели правил: каталог Nodes

- **Nodes** — единый каталог всего, куда можно слать трафик: подписки, ноды, профили,
  цепочки (вкладки Simple / Profiles). Создание / редактирование / удаление — только тут.
- **Route** — только основной поток: режим, Auto / Manual, приоритет (свой порядок поверх
  порядка Nodes). Подробно — `connect-model.md`, «Каталог (Nodes) и Route».
- **Цель правила / приложения** (`js/40-rules.js`, `targetInfo`): `''` = основной поток,
  `src:<id>` (подписка / группа: все её живые ноды, самая быстрая), `node:<sid>::<nid>`,
  `profile:<id>`, `chain:<id>`. **Не зависит от режима Route**: правило на профиль работает и
  в режиме Simple.
- **Пикер цели** (`js/44-target-picker.js`, лист поверх всего): Main flow (что сейчас в
  основном потоке; тап выбирает), затем подписки и группы, профили, цепочки обоих режимов;
  поиск. Тап по карточке с серверами (подписка, профиль) **раскрывает** её и сам ничего не
  выбирает; кнопка AUTO слева от имени (как в строке Route) выбирает всю подписку / профиль
  целиком и светится, если она и есть цель. Внутри — режим Fastest / Priority (собственная
  настройка элемента, здесь только показ) и список серверов — тап по серверу выбирает
  `node:<sid>::<nid>`. Цепочки раскрываться не умеют: тап выбирает. Выбор **не закрывает**
  пикер, а лишь помечает: пока выбор отличается от исходной цели, снизу выезжает Save
  (применить и закрыть); закрытие иначе (×, свайп, Back) ничего не применяет. Повторный тап
  по выбранному снимает выбор → цель `''` = Main flow, над Save предупреждение. Если цель — сервер,
  карточка открывается раскрытой; поиск по имени сервера раскрывает карточку. Карточки подробные, как в Nodes: формат, число нод,
  трафик / срок, сервер, через который пойдёт сейчас, и пинг. Выключенные — с пометкой off,
  но выбрать можно.
- **Недоступная цель**: выключена в Nodes, без живых серверов или удалена (ссылка
  сохраняется — правило показывает «deleted chain» и т. п.). Тогда трафик идёт по
  **Fallback** правила (в форме: Default | Proxy | Direct | Block, Proxy = Main flow или своя цель,
  §2). Default = глобальная настройка **Rules → Target unavailable** (Main flow по умолчанию).
  Fallback есть и у правила Proxy с основным потоком (запасной выход на случай, если он упал). У приложения Fallback
  такой же (§3) — у каждой его половины Proxy со своей целью. В списке правил у такого правила
  бейдж «down → Block».
  «If unavailable» действует в двух местах.
  **При сборке конфига**: цель, недоступная на момент подключения, заменяется запасным
  выходом (Main → основной поток, Direct → `direct`, Block → действие `reject`). Любая правка
  в Nodes, делающая цель недоступной, и так переподключает.
  **На лету**: правило или приложение с доступной конкретной целью (не Main flow) ведёт не в
  саму цель, а в `selector` `[цель, запасной выход]` (`<цель>~<запасной>`, по умолчанию —
  цель; по одному на пару цель + запасной выход, его делят все правила с ней). Ядро
  (`core/lib/src/fallback.dart`) следит за целями и переключает selector через API service
  (`SelectOutbound`), без перезапуска sing-box: цель перестала отвечать → запасной выход
  правила (Block → outbound `block`: в 1.11.10 его вернули, сняв deprecated, именно для
  selector'ов; Direct → `direct` / `direct@dns-<id>`; Main → селектор `proxy`), цель ожила →
  обратно в цель. Проверка — измерение того сервера, на котором сейчас стоит группа цели
  (у цепочки — выхода через вход), теми же пробами и запасными проверками, что у Auto
  (probe inbound, второго пингера нет); у группы Fastest сначала urltest перетестирует и
  выберет заново, группу Priority ядро не двигает (сервер выбрал юзер: пока он молчит,
  цель считается упавшей). Гистерезис как у Auto: упала после `failAfter` промахов подряд,
  вернулась после `failAfter` ответов подряд, а у упавшей раньше — ещё и после паузы
  flap guard (1, 2, 4 … мин). Пока не отвечает вся сеть (Auto не видит ни одного
  ответившего маршрута), ничего не судится: мёртвая сеть — не мёртвая цель. При уходе на
  запасной выход соединения, всё ещё идущие через цель и стоящие без движения байтов,
  закрываются (приложение переподключится по-новому); при возврате открытые не
  трогаются. Выбор selector'ов переживает рестарт sing-box (`cache_file`), сервис
  стартует с того, что sing-box говорит. В журнал: `rules/fallback` (warn: правило, цель,
  куда) и `rules/targetBack` (info).
  **Запасной выход — настоящая цель** (подписка / нода / профиль / цепочка из каталога; у
  правила и приложения, не у глобального Rules → Target unavailable — там только Main / Block /
  Direct). В плане (`fallback`) это id цели (`src:…`, `node:…`, `profile:…`, `chain:…`) вместо
  слова; в UI у приложения это `fallback: 'main'` + `fallbackTarget` (Proxy → Via запасного
  варианта), `93-routing-plan.js` отдаёт его как id. Selector становится
  `[цель, запасная цель, основной поток]` (`<цель>~<запасная цель>`), запасная цель собирается в
  конфиг со своими группами и **наблюдается так же** (своя проверка, свой гистерезис). Цель
  упала → запасная цель; **упали обе → основной поток** (журнал: `rules/fallback` с
  `to: main`); запасная ожила → забирает трафик у основного потока; цель ожила → возвращает
  себе трафик откуда угодно (`rules/targetBack`). Если оба упали за один раунд — один переход,
  сразу в основной поток. В журнале `to` = id запасной цели (или `main` / `block` / `direct`).
  Запасная цель, равная самой цели (или пустая), = Main flow; запасная, недоступная при сборке
  (удалена, выключена, нет серверов) = Default (глобальная настройка), в `warnings` строка
  «<правило>: "If unavailable" target … is not available, the default applies». Цель
  недоступна сейчас, а запасная жива — трафик идёт сразу в запасную (с Main flow за ней).
  **Основной поток как «цель»**: приложение с Route = Default (или Proxy с пустой целью) и явным
  Fallback = Block / Direct / цель получает selector `proxy~<запасной>` = `[proxy, запасной]`
  (глобального Default здесь нет: Default / Main = без запасного; недоступная запасная цель =
  без запасного, с предупреждением). Такое приложение идёт по selector'у, а не по правилам ниже.
  Основной поток Auto уже лечит сам, поэтому ядро судит его по тому, что видит пользователь: тест
  через selector `proxy` (сервер, на котором его оставил Auto) — `failAfter` промахов подряд =
  упал. Мёртвый основной поток для Auto выглядит как мёртвая сеть, поэтому ядро различает их само:
  после промаха мерит прямой путь (`direct` в probe inbound) и запасные цели, и промах считается,
  только если что-то из них ответило (сеть жива, основной поток нет); не ответило ничего = мёртвая
  сеть, ничего не судится (как и пока ОС вообще офлайн). Запасная цель основного потока, упавшая
  вместе с ним, ничего не меняет: selector остаётся на ней (лучше некуда). Вернулся основной
  поток — selector назад.
- **Удаление цели**: окно удаления перечисляет правила и приложения, которые её теряют,
  и куда пойдёт их трафик (`targetImpact`).

## 1. Структура меню правил

Один упорядоченный список правил sing-box, показанный слоями:

1. **Приложения** — отдельный раздел (см. §3).
2. **Свои правила** — полная форма (см. §4), порядок меняется перетаскиванием.
3. **Быстрые правила** — гео тумблерами; сервисы — выпадающий список (ниже, §2).
4. **Всё остальное** — одна строка: Proxy / Direct / Block.

Итоговый порядок проверки (первое совпадение выигрывает): приложения → свои правила →
быстрые → «всё остальное». Кнопка «Итоговый порядок» — read-only список в том порядке,
в каком его увидит движок.

Также на экране правил:
- **Поиск-фильтр** по списку правил.
- **Проверка адреса**: ввёл `youtube.com` / `1.2.3.4:443` / выбрал приложение → «сработает
  правило #3 "Стриминг" → профиль Europe». Отвечает на вопрос «почему идёт не туда».
- **Импорт/экспорт**: фрагмент sing-box JSON, текст правил Clash (`DOMAIN-SUFFIX,x,PROXY`),
  правила из Clash YAML подписки, поделиться ссылкой. `MATCH,X` из Clash не становится правилом —
  он задаёт «Всё остальное». Экспорт в Clash пропускает правила, которые Clash не выразит
  (составные, «кроме», несколько групп) — строкой-комментарием.

## 2. Быстрые правила

- **Гео**: «Мой регион напрямую» (страна, по умолчанию из системы) = geosite + geoip страны
  → Direct. Тумблер: реклама → Block. **Локальные сети — всегда напрямую**, без тумблера (в строке
  «Always»): первым правилом, раньше приложений и своих правил, и в Global тоже — «это база».
  Ядро: регион = домены страны (RU: `.ru`, `.рф` = `xn--p1ai`, `.su`) + geosite (RU:
  `category-ru`, `ru-available-only-inside`) + geoip страны; локальные сети = `ip_is_private` +
  `.local` / `.localhost` / `.lan` / `.home.arpa`; реклама = `category-ads-all` + несколько известных доменов → `reject`.
  Порядок: локальные сети (до всего) → … свои правила … → реклама → сервисы → регион → «всё остальное». Пока список не
  скачан, регион работает по доменам страны, реклама — по встроенным доменам (с предупреждением).
- **Сервисы**: выпадающий блок. Свёрнутый — «N added» и список имён; раскрытый — добавленные
  сервисы, у каждого VPN / Direct и × (убрать = снова по общим правилам). «+ Add service» —
  остальные из встроенного списка (Telegram, YouTube, Discord, стриминги…; список зашит в
  приложение, свои сервисы юзер не добавляет). Поиск по правилам раскрывает блок. Внутри
  сервиса — geosite-категории, юзер их не видит.
- **Сервис ↔ приложение**: у сервиса есть свои пакеты приложений (Telegram → org.telegram…).
  Сервис ловит сайты сервиса из любого приложения (браузер тоже), а приложения в порядке
  проверки выше, поэтому правило приложения побеждает для трафика самого приложения. Это
  видно с обеих сторон: у сервиса строка «App: Direct — its own route wins in the app» (тап —
  к приложению); у приложения без своего правила в списке «VPN · service»; в окне приложения —
  что делает сервис и кто побеждает.

## 3. Приложения

- Список приложений (Android — пакеты; десктоп — запущенные процессы + «добавить по пути»).
  Поиск, фильтры: пользовательские / системные / только настроенные.
- **Общего переключателя сверху нет** — действие ставится каждому приложению персонально.
- Строка: иконка, имя, чип состояния (`—` / `Direct` / `→ Europe` / `TCP Default · UDP Block`).
- Тап → маленькое окно по центру экрана, заголовок — имя приложения. Первая карточка: **«Split TCP / UDP»**
  (иконка-звено, (?) с пояснением, переключатель справа) — для **любого** действия. Ниже карточка
  настроек; при Split — по одной на вкладку **TCP | UDP** (вкладки как Simple / Profiles в Nodes:
  пилюля скользит, свайп влево / вправо переключает; без Split вкладок нет, карточка одна на оба
  протокола):
  - **Route** — **Default / Proxy / Direct / Block**: сегмент в одной строке с подписью, пока
    помещается, иначе под ней на всю ширину (равные сегменты; то же для Fallback);
  - **Via** — цель (пикер цели, §0), активна только при Route = Proxy; пустая цель = основной поток;
    при Route = Default — неизменяемое «Main flow» с замком вместо шеврона (не приглушено: это
    настоящее значение), при Direct / Block — «—», приглушено;
  - **Fallback** — **Default / Proxy / Direct / Block**, активен при Route = Proxy или Default
    (при Direct и Block приглушён — откатываться некуда; при Default страхует основной поток, который
    может не содержать нужного, напр. Manual на Simple, а запасной — профиль): Default = глобальная настройка (Rules → Target unavailable),
    Proxy = через заданную цель, Direct, Block. Как «If unavailable» правила, §0;
  - **Via** запасного варианта — всегда на месте, активна только при Fallback = Proxy; пустая =
    «Main flow», иначе цель из пикера (первый пункт — Main flow; цель из Route → Via не предлагается).
  Строки приглушённых полей остаются на месте, под карточкой всегда есть пояснение (место под две
  строки зарезервировано): размер диалога не прыгает при смене Route / Fallback. Подписи Default / Proxy / Direct / Block остаются английскими и в русском UI. Примеры: Discord TCP через одну ноду, голос по UDP — через другую (голос
  идёт на голые IP, по доменам его не поймать); TCP Default + UDP Block — глушит QUIC, приложение
  откатывается на TCP. Default у половины = для этого протокола своего правила нет, трафик идёт по
  правилам ниже. Обе половины Default (или без разделения — Default) = у приложения нет своего
  маршрута, оно не хранится.
- Модель: `{ act, target, fallback, fallbackTarget, split, udp: { act, target, fallback, fallbackTarget } }`
  (`fallback`: `default` / `main` = кнопка Proxy / `direct` / `block`); при `split` поля
  верхнего уровня — TCP, `udp` — UDP. Старый вид `{ act: 'proxy', split, udpTarget }` при загрузке
  превращается в `udp: { act: 'proxy', target: udpTarget }`.
- В порядке проверки приложения стоят выше гео и сервисов (они точнее).
- Ядро: Android — `package_name`; десктоп — `process_name` / `process_path` (вид приложения
  `process` / `path` в модели). «Разделить TCP / UDP» — до двух правил, `network: tcp` и `udp` (у половины Default
  правила нет). Proxy с конкретной целью — тот же selector `[цель, запасной выход]` и та же
  живая логика «If unavailable», что у правил (§0); selector общий, если цель и запасной выход
  совпали. Запасной выход может быть настоящей целью (§0), а у половины с Route = Default (или
  Proxy с пустой целью) явный Fallback = Block / Direct / цель даёт основному потоку свой
  «If unavailable» (§0): для такой половины появляется правило, и она идёт по selector'у `proxy~…`,
  а не по правилам ниже. В журнале такое приложение названо по имени: «App Telegram goes direct».
- Десктоп: раздел Apps = процессы, а условие «Процесс» в своих правилах остаётся — одно и то же
  двумя путями. **По умолчанию, требует решения**: оставить оба (Apps — быстрый выбор, Процесс —
  в составе правил с другими условиями).

## 4. Свои правила

Правило = **условия** + **действие** + **DNS** + флаги.

### Условия

Отдельные поля по группам (без «умного» автоопределения типа). Значение → чип по Enter
или запятой; вставка столбиком разбивается на чипы; невалидный чип — красный.
Форма начинается с одного пустого поля «Suffix» в карточке «Домены»; всё остальное добавляется
только кнопкой «+ Condition»: она предлагает каждое поле, которого ещё нет в форме, под
названием его карточки (Domains: Suffix / Exact domain / Keyword / Regex / Geosite / Rule set;
IP: IP-CIDR / GeoIP / Local networks; Ports; Source; Network / Protocol; Process). Выбранное поле
появляется в своей карточке (карточка создаётся, если её не было). Подсказок «+ Keyword» внутри
карточек нет. У каждого поля свой × (убирает поле; убрал последнее — карточка исчезает вместе с
ним), у карточки — свой × и «кроме» (инверсия).

| Группа | Поля |
|---|---|
| Домены | Домен · Суффикс · Ключевое слово · Regex · Geosite (пикер) · Rule-set (пикер) |
| IP | IP / CIDR / диапазоны в одном поле · GeoIP (пикер) · тумблер «локальные сети» |
| Порты | порты и диапазоны в одном поле |
| Источник | IP источника · порты источника (свёрнуто) |
| Сеть | TCP / UDP (чипы) · Протокол по сниффингу: tls, http, quic, bittorrent, stun, dns (чипы) |
| Процесс | **только десктоп**: имя или путь, путь с `*` |

Приложений (пакетов) в форме нет — у них свой раздел.

Логика: внутри группы — ИЛИ (любое значение любого поля: домен или суффикс или geosite…),
между группами — И (пояснение в [?]). Исключения внутри группы: у **Источника** IP и порт —
И (оба должны совпасть), у **Сети** TCP/UDP и протокол — тоже И.
Реализация: плоское правило sing-box ИЛИ-т домены с IP и И-т всё остальное, поэтому правило
с Доменами **и** IP (или с «кроме») ядро собирает как `logical and` из групп (группа с
несколькими видами значений — `logical or`); вкладка JSON показывает так же. Процесс: имя и
путь в sing-box — разные поля (И), поэтому вместе они тоже идут через `logical or`; путь с `*` —
`process_path_regex`. Диапазон IP → набор CIDR, порты `a-b` → `port_range` `a:b`.
Нет списка на диске (geosite / geoip / rule-set ещё не скачан): в обычной группе правило
сужается до остальных значений, группа из одних списков или «кроме» со списком — правило
пропускается; в обоих случаях предупреждение при подключении.
Составные правила (вложенные И/ИЛИ, `logical` в sing-box) в форму не выносим — только через
JSON; в списке такое правило помечено бейджем «составное · JSON».

Валидация на лету: regex, CIDR, диапазоны IP, порт ≤ 65535, диапазон «от ≤ до».

### Действие

Proxy через основной поток · через конкретную цель (профиль / цепочка / подписка / нода —
пикер цели, §0) · Direct · Block (тихо сбросить / ответить отказом).

Ядро: цель = свои группы серверов (подписка → urltest, нода → один сервер, профиль → как
юнит, цепочка → вход + выход с detour), одна на все правила и приложения с этой целью.
Block → `reject` (`method: drop` для «тихо»).

**Резолв перед IP-правилами.** Через системный прокси / mixed-порт соединение приходит доменом,
без IP, и IP-условия (IP / CIDR, локальные сети, GeoIP) не сработают, пока ядро не разрешит имя.
В TUN адрес уже есть, там ничего не меняется. Поведением управляет пользователь:
- **Настройка** Settings → DNS → «Resolve for IP rules» (§6): Off / Auto / конкретный сервер.
  Ядро ставит один `resolve` перед первым своим правилом с IP-условиями; прокси всё равно
  получает домен. Off — шага нет, IP-условия работают только при пришедшем IP (всегда в TUN).
- **Флажок правила** «IP conditions only in TUN» (форма правила, показывается только у правил
  с IP-условиями — IP / CIDR, локальные сети, GeoIP, IP в JSON): такое правило не заставляет ядро
  резолвить и срабатывает, только когда адрес уже известен. Resolve ставится перед первым IP-правилом
  **без** флажка. `resolve` один на конфиг: правило с флажком, стоящее ниже него, тоже
  увидит полученный адрес. Собственные rule-sets IP-условием не считаются (по .srs не видно, что
  внутри) — такому правилу резолв не ставится.
- Быстрые правила сами не резолвят: регион / сервисы ловят домены и адреса, пришедшие как IP.

- **Fallback** (блок в карточке «Then», при Then = Proxy — и с конкретной целью, и с основным
  потоком; тот же блок, что в диалоге приложения): сегмент Default | Proxy | Direct | Block + строка
  Via («Main flow» или цель, не та же, что Via правила; активна только при Fallback = Proxy). Что
  делать, если цель выключена, пуста или удалена / основной поток недоступен (§0). Блок всегда на
  месте: при Then = Direct / Block затемнён и неактивен. Данные правила: `fallback`
  (`default|main|direct|block`, `main` = Proxy) + `fallbackTarget` (id цели или `''` = основной
  поток); в плане `fallback: 'main'` + `fallbackTarget` уходит как id цели. Заменил тумблер
  «Строго» (Строго = Block).

### Блок про IP в форме правила

Только у правила с IP-условием (пустая группа IP не считается; у JSON-правила — любые `ip_cidr` /
`ip_is_private` / `geoip` внутри), между условиями и «Then»: чекбокс **IP conditions only in TUN**
(по умолчанию выкл.) с кнопкой **(?)** рядом — пояснение (через proxy-порт IP-условия работают,
только если включён «Resolve for IP rules») и текущее состояние (Off / via <сервер>) лежат в ней,
а не под чекбоксом — и ссылка **Open DNS settings ›**. Ссылка открывает Settings → DNS **поверх**
формы (строка «Resolve for IP rules» прокручена в центр и подсвечена), форма с черновиком остаётся
под ней; закрытие DNS любым способом (×, свайп, Back) возвращает к форме как была. Убрал IP-условия —
флажок сбрасывается при сохранении. В JSON-вкладке флажка нет (как «If unavailable» и DNS): живёт
в форме, при переключении вкладок сохраняется.

### DNS правила

«Авто» (по умолчанию): первый отмеченный сервер глобального списка с подходящим «Через» —
Direct-правило → прямой сервер, VPN-правило → сервер через VPN. Либо конкретный сервер из
глобального списка.

Реализация: для доменных условий правила — DNS-правило sing-box с тем же сервером (для шага
`resolve` и, с TUN, для запросов самих приложений); свои rule-sets в DNS-правила не идут.
Прямой трафик резолвит только `domain_resolver` исходящего (DNS-правила он не спрашивает),
поэтому Direct-правило со своим сервером получает свою копию `direct` — `direct@dns-<id>`.

### JSON

Вкладки **Форма | JSON**, синхронные. Поля JSON, которых нет в форме, не теряются — плашка
«доп. поля — редактируются в JSON». Невалидный JSON не сохраняется, ошибка со строкой.
Форма читает обратно всё, что сама написала: Форма → JSON → Форма даёт те же карточки и значения
(с «кроме», Домены + IP как `logical and`, имя, If unavailable, DNS, «IP conditions only in TUN»,
способ блокировки). Пустые карточки и поля в JSON не попадают (`{}` внутри `logical` не читался
бы обратно) — при возврате на форму они восстанавливаются из прежнего черновика. Плашка «составное»
— только для чужого JSON, которого форма не выразит (`or`, вложенный `logical`, повтор группы).

## 5. Внешние rule-sets

Раздел списков: URL, формат (srs / json), период обновления (то же окно «число + единица»),
«качать через VPN / напрямую». Встроенные geosite/geoip — там же.

Ядро (`rulesets.dart`): качает само, кладёт в `<dataDir>/rulesets/<tag>.srs|json` и отдаёт
sing-box как `type: local` (sing-box при старте ничего не качает; заменённый файл перечитывает
сам). Встроенные: сначала runetfreedom (`russia-v2ray-rules-dat`, ветка `release`,
`sing-box/rule-set-geosite/geosite-<имя>.srs`, `…/rule-set-geoip/geoip-<cc>.srs`), при 404 —
SagerNet (`sing-geosite` / `sing-geoip`, ветка `rule-set`). Качается только то, что нужно
правилам. Свежий файл (моложе периода) — как есть; устаревший — используется, обновляется
после подключения; ответ, не похожий на rule-set (страница провайдера), отбрасывается и не
затирает старую копию; неудача — повтор не раньше чем через 5 минут.
«Через VPN» — только через туннель (служебный вход `tunnel-in`, мимо правил): при первом
подключении такого списка ещё нет — правила без него (предупреждение), ядро скачивает его через
новый туннель и само переподключается. «Напрямую» — с учётом системного `HTTP(S)_PROXY`.
Обновление по таймеру во время работы — не сделано (только при подключении).

## 6. DNS

**DNS — отдельный раздел Settings** (не внутри Connection). Карточка **DNS на главной**
ведёт туда же (как карточка Auto); при открытии раздела непропингованные серверы пингуются.

Раздел DNS:
1. **Глобальный DNS** — список серверов с галочками и приоритетом (перетаскивание),
   кнопка «+ Добавить». Галочка = используется, порядок = приоритет (первый не отвечает →
   следующий). У сервера: адрес (`udp` / `tls` / `https` / `quic`), **«Через: напрямую / VPN»**,
   **пинг** (в списке и в окне добавления — кнопка проверки).
   По умолчанию два сервера: **Локальный** (системный/провайдера, напрямую) и
   **Удалённый** (напр. `https://1.1.1.1`, через VPN).
1a. **Resolve for IP rules** (блок «Without TUN»; `dnsCfg.resolve`) — select: **Off** /
   **Auto** (по умолчанию) / любой отмеченный сервер списка. Auto = первый отмеченный сервер
   **«через VPN»** (запрос не уходит к DNS провайдера); нет такого — первый в работе и
   предупреждение об утечке. Выбранный сервер снят с галочки или удалён → снова Auto (выбор
   хранится, вернётся вместе с галочкой). Прямой сервер выбрать можно, но под строкой предупреждение. Подсказка: касается только
   соединений через proxy-порт (системный прокси), TUN не затрагивается. Уходит в
   `plan.routing.dns.resolve`, смена при подключении — переподключение; правила строит ядро
   (`core.md`, «Правила в конфиге»). Сервер в шаге называется явно, поэтому переключение DNS
   (Switch automatically) и «DNS» правила на него не влияют. Флажок у правила — §4.
2. **Hijack DNS** — тумблер. Доступен всегда (чтобы не прыгать настройки ↔ главная);
   при выключенном TUN — пометка «работает только в TUN». Отдельного пикера серверов нет:
   перехваченные запросы идут в DNS ядра, а оно отвечает по глобальному списку.
3. **FakeIP** — тумблер, **по умолчанию выключен**, [?] с объяснением, список исключений
   (банки, игры и т. п. — заполнен из коробки). Имеет смысл только в TUN.

Всё, что не попало в правила, резолвится глобальным списком по порядку.

Ядро: серверы `dns-<id>` (`system` → `local`, IP → udp, `udp://` `tcp://` `tls://` `quic://`
`https://`); «Через VPN» → `detour: proxy`. `dns.final` = первый отмеченный. Адреса серверов
прокси и прямой трафик резолвит первый отмеченный **прямой** сервер (`default_domain_resolver`),
иначе системный. Сервер с именем хоста (`tls://dns.google`) узнаёт свой адрес у системного.

Реализация: в sing-box у DNS нет встроенного fallback между серверами (один основной) —
переключение по приоритету делаем сами, как Auto для нод, **на лету, без перезапуска**:
- **Switch automatically** (Settings → DNS, по умолчанию **включено**, `dnsCfg.auto`) — при
  включённом ядро само уводит DNS с молчащего сервера на следующий по приоритету и
  возвращает, когда более приоритетный оживёт. Выключено — остаётся первый отмеченный, что
  бы с ним ни было (проверки идут, метки в списке остаются). Выключение возвращает первый
  сервер сразу. Настройка едет в теле connect (`dnsAuto`) и на лету — `POST /api/dns/auto`;
  в `plan.routing` её нет, так что её смена не переподключает.
- Механика: при **двух и более** отмеченных серверах у каждого `dns-<id>` есть DNS-правило
  `clash_mode: "dns-<id>"` (после всех остальных DNS-правил); ядро переключает режим через
  API service (`SetClashMode`, блок `clash_api` в конфиге не нужен). Один сервер —
  переключать некуда, правил режимов нет. `dns.final` остаётся первым отмеченным
  (стартовый режим `Rule` = он же).
- Проверка сервера: настоящий DNS-запрос имени (`cp.cloudflare.com`, запасные —
  `www.gstatic.com`, `captive.apple.com`) через **один этот** сервер и по его же пути
  (напрямую или через VPN, как в его «via»): probe inbound ядра, правило `resolve` с явным
  `server`, без кэша. Интервал и гистерезис как у Auto (`checkEvery`, `failAfter`, flap
  guard); на слабую сеть тоже не реагирует. Переключается на **самый приоритетный из
  отвечающих**; вернуться выше — после `failAfter` ответов подряд и паузы flap guard.
- Ограничение: адреса серверов прокси и прямой трафик резолвит `default_domain_resolver` —
  один, заранее выбранный (первый прямой), он режим не меняет. По режиму идёт то, что
  решают DNS-правила: `resolve` перед IP-правилами и запросы TUN / Hijack.
- UI: `status.dns` = `{active, auto, servers: [{id, ok, ms}]}`. В списке DNS у используемого
  сервера метка «In use», у не отвечающего — «No answer» (пока подключено). Событие журнала
  `dns/switched` (info: from, to, reason = `failover` / `back` / `off`; `own` у `off`),
  уведомление под тумблером «When Auto switches».
Без ядра (мок) сервер «в работе» — первый, у которого пинг не −1.

Сейчас: смена галочек / порядка — переподключение (`dns.final` и правила режимов пересобираются).

DoH в браузерах обходит Hijack — не наше дело, не боремся.

## 7. Режимы и kill switch

- **System proxy** — третий переключатель в карточке режимов на главной (сверху название
  «Sys proxy», снизу рядом On | Off; плашка ездит вбок). Там же в Settings → Connection —
  **Proxy port**: порт локального HTTP + SOCKS5 прокси ядра (127.0.0.1, по умолчанию 2080),
  на него указывает системный прокси; 1024–65535, кроме занятых приложением (7788 jormd,
  9090 Clash API). Смена порта при подключении — переподключение с новым портом и тумблер в Settings → Connection; оба держат одно
  состояние. Позже с главной на мобилках
  уберём (на Android системный прокси большинство приложений игнорирует).
- В блоке **Proxy port** всегда (и без пароля) две кнопки **Copy SOCKS5** / **Copy HTTP**: в буфер
  идёт `socks5://127.0.0.1:<порт>` / `http://…`, при включённом пароле — с
  `логин:пароль@` (в percent-кодировке).
- **Proxy password** (Settings → Connection, под Proxy port; по умолчанию **выкл**: порт открыт,
  как у Karing, — подсказка «any program on this PC can use the port»; оба текста подсказки
  занимают место одновременно, строка не меняет высоту). Включили — если логина и пароля ещё нет,
  генерируются случайные логин (8 знаков) и пароль (20); есть — берутся прежние. Оба видны в полях
  (общая колонка подписей, поля выровнены) и правятся (логин: непустой, без
  пробелов и `:`, до 64 знаков; пароль: 4–128 знаков без пробелов; неверное значение — тост и
  прежнее остаётся); справа внутри поля пароля иконка ⟳ — новый случайный пароль (логин остаётся).
  Выключили — логин и пароль **сохраняются**, но в план (`mixedAuth`) не уходят. Они лежат в `connCfg` (снимок состояния): **бэкап и экспорт содержат их**, как и
  всё остальное из Settings. Уходят в ядро в плане как `mixedAuth: {user, pass}`, смена при
  подключении — переподключение (как порт). Windows не умеет отдавать пароль системного прокси,
  поэтому при включённом пароле **и** системном прокси ядро открывает второй вход на своём
  свободном порту loopback без пароля, и системный прокси (в том числе удерживаемый kill switch'ем)
  указывает на него, а не на Proxy port; без пароля — как раньше, на Proxy port. Порт второго
  входа не показывается в UI (ставить в чужие программы нужно Proxy port с паролем); он доступен
  любой программе этого ПК, как и сам системный прокси. На Android в TUN пользовательский порт по
  умолчанию не открывается вовсе.
- **Kill switch** (глобальный, Settings → Connection, отдельный тумблер; там же пока
  заглушка TUN stack и выбор Latency test URL — см. subscription-parsing.md → URL для
  latency-теста). Подсказка: «Blocks traffic when the VPN is down. Works for apps that use the
  system proxy; full block needs TUN.» Он блокирует **только приложения, которые ходят через
  системный прокси** (и то, что настроено на наш порт вручную); всё остальное утекает
  напрямую — полная защита возможна лишь с TUN (не сделан). Ключи в `connCfg` (снимок
  состояния, бэкап), уходят в ядро вместе с connect, а при смене (в том числе `launchAtStartup` /
  `connectOnLaunch`, от которых зависит `killWhileClosed`) во время подключения или down —
  сразу через `POST /api/killswitch` с теми же четырьмя полями (в down прокси перестраивается
  по новым настройкам: kill switch вкл → удержан, выкл + Remove → снят):
  - `killSwitch` [выкл] — пока пользователь подключён, наш системный прокси не снимается ни при
    каком сбое: упало → интернет блокируется (прокси указывает на мёртвый порт), а не идёт
    напрямую. Выключение, пока он что-то защищает (подключено, down или блок после
    отключения), — только после подтверждения: шторка говорит, что будет (трафик пойдёт напрямую
    при падении / прямо сейчас, или блок снимется). Включение и выключение без подключения — сразу.
  - Под ним (видны и действуют только при включённом `killSwitch`, с отступом):
    `killOnDisconnect` [выкл] «Also after I disconnect» — отключение пользователем тоже не снимает
    прокси: интернет заблокирован до подключения или кнопки Remove на главной (плашка
    `status.blocking`). `killWhileClosed` [выкл] «Also while the app is closed» — закрытие
    приложения (остановка jormd) не восстанавливает прокси; доступен только при
    `genCfg.launchAtStartup` **и** `genCfg.connectOnLaunch` (иначе после закрытия интернет мёртв, пока
    юзер не запустит приложение сам): без них строка серая, в подсказке причина, тап предлагает
    включить оба. Снимешь автозапуск / автоподключение — опция снова серая (в ядро уходит false).
  - `downProxy` [`remove` | `keep`, по умолчанию `remove`] «If the VPN cannot recover» — видна
    только при **выключенном** `killSwitch`; тумблер «Remove the proxy if the VPN cannot recover»
    (вкл = `remove`, выкл = `keep`), оба текста подсказки занимают место сразу — строка не прыгает.
    Remove: когда VPN не поднялся за 30 с («down», см. connect-model.md → ConnectDock), ядро
    возвращает сохранённый системный прокси, трафик идёт напрямую, пока VPN не вернётся. Keep: прокси
    остаётся, интернет мёртв до возврата (то же поведение, что при `killSwitch`, но без
    подопций).
  - **Фоновый перезапуск не настраивается.** sing-box упал при подключении → ядро сразу
    перезапускает его; системный прокси при этом **не снимается** (утечки во время
    перезапуска нет: приложения просто ждут порт), пользователь ничего не видит. Паузы 1 с, 4 с,
    15 с, дальше каждые 30 с, пока пользователь подключён; успех — та же запись, правила, сервер.
    После 30 с безуспешных попыток начинается «down» (кнопки Retry и Disable sys proxy на главной;
    Retry — перезапуск сейчас; Disable sys proxy / Remove — восстановить прежний системный
    прокси сейчас; попытки продолжаются). Отключение пользователя во время перезапуска / down
    прекращает попытки; прокси — по `killOnDisconnect`.
  «Упало всё» — ядро упало, ни одна запись Auto не пропускает трафик: блок. **Исключение —
  правило, у которого в «If unavailable» явно выбран Direct**: его трафик пропускается (это
  решение юзера для этих адресов); при включённом kill switch в таком правиле висит
  предупреждение. (Решено, не сделано.)
  Не путать с «Строго» у правила (§4).
- **Global**: всё в прокси (кроме локальных сетей — они всегда напрямую), правила не применяются
  вовсе — ни свои, ни приложения, ни Block
  (**по умолчанию, требует решения**; альтернатива — оставить Block и приложения). DNS-список
  работает и в Global.

## Отложено

- Наборы правил по сети (Wi-Fi SSID, «дом/работа») — пока нет, возможно никогда:
  задачу белых списков решают приоритеты.
