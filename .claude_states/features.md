  ноды / маршруты Auto, сайты, «нет сети», TUN и т.д.). Переподключение, смена настроек (галочки, стороны, порядок),

  флагов (`docs/rules.md:605–608`, память `_dnsFlagMemory` только для своего перезапуска). Сделать: пройти все места,

## Следующая сессия — по порядку (решено 2026-10-12)

Разбор отчёта `20261011-6gml6m` (расшифрован в `core/.data-dev/reports/`). Вопросы и предложения по пунктам задаёт
следующая сессия, до реализации.

0. **Общий механизм служебного трафика с резервированием**: обновления, репорты, rule set'ы (и прочие служебные
   загрузки) идут через один механизм: выбор пути параллельными пробами напрямую / через туннель (как отправка репорта,
   `core/lib/src/report_upload.dart` в `0ea6660`), повтор после сбоя, расписание. Rule set'ы: обновляются и во время
   работы (сейчас — только при подключении: `service.dart:731,1185` → `_refreshLists`, бэкофф 5 мин `rulesets.dart:43,100`);
   закачка не стартует, пока подключение не устоялось (сейчас через ~200 мс после Connected и рвётся нашим же
   переподключением); сбой из-за своего перезапуска — повтор, а не бэкофф; честный текст события («the last copy is used»
   только если копия есть, `event_text.dart:315`). Настройки rule set'ов: свои адреса списков, период, автообновление.
   Не путать с «внутренним служебным прокси» из `to_think.md` — то отдельная тема, ещё обсуждается.
1. **Единый вид событий о сбоях**: каждое отвечает на «что» (приложение, адрес), «почему» (конкретная причина: сервер не
   ответил за N с / заблокировано Block ads / DNS-фильтром / трекер / Direct не открывается, через VPN — да) и «что
   делать» (действия) — по образцу уже сделанного `site/unreachable` с проверкой. Нельзя ответить «почему» — только
   журнал, без уведомления. `conn/failing` (`failures.dart`) сюда: сейчас без кнопок (`event_rows.dart:205` — только
   `cat=='site'`), Direct никто не перепроверяет (Auto Direct не видит, `auto.dart:717`), лог-подсказка не
   сопоставляется (IP vs домен, `failures.dart:357,418`), бросок запроса клиентом считается сбоем. Нужен общий вид уже
   сейчас — редизайн потом (`to_think.md`), так его будет проще переработать.
2. **Источник двойного подключения**: после обновления / запуска второй `connect()` через ~1 с (в отчёте 18:14, 18:41,
   20:56 UTC: `libbox stopped` → `starting libbox` ~100 мс; кандидаты — resume после обновления пакета,
   `runLaunchActions` `live_core_host.dart:1524`). Найти и убрать, сделать подключение идемпотентным. Проверить, не
   применяется ли что-то (правила, DNS) с опозданием после Connected, и нет ли окна без TUN при перезапуске ядра — утечка.
3. **Проверки Auto**: помечать свои проверки в Raw (`[auto]`), не смешивать с реальными ошибками. Мёртвый запасной
   сервер (2 промаха) → состояние «недоступен»: проверка с нарастающей паузой 1 → 2 → 4 → 8 → 15 мин, одним лёгким
   запросом вместо 4 чекеров, в журнал — только смена состояния; пауза сбрасывается сменой сети, ручной проверкой,
   переподключением. Сейчас мёртвая нода приоритета выше проверяется каждые ~65 с четырьмя запросами по 10 с
   (`auto.dart:538–543`, `_priorityBack` `:768`). Замерить, сколько батареи/трафика ест Auto (у пользователя всё
   приложение ~5 % потребления за несколько дней). Обсудить: проверки через сторонние сервисы из разных стран — польза
   vs оверхед.

- **Kill switch на Android** (P-H1, P-S2, S24; отложен решением пользователя 2026-10-12, перенесён из `apk_losted.md`).
  Сейчас `caps.killSwitch => !android` (`app/lib/platform/platform_caps.dart:24`), группа скрыта (`settings_conn.dart:222–291`),
  плашка blocking не возникает (`vpn_alert.dart:37–39`). Мокап: `50-home.js:27–46, 140–142`, `56-dns.js:241–267`;
  `docs/rules.md` §7. Нужен дизайн для TUN: держать TUN как blackhole при падении ядра, killOnDisconnect с плашкой
  «blocking» и Remove, killWhileClosed, подсказка про системные «Постоянный VPN» и «Блокировать соединения без VPN».
  Решение по дизайну — пользователя. Сюда же исключение «правила с явным Direct в If unavailable пропускаем» (S25,
  `rules.md:510–513`): блок, кроме таких правил, предупреждение в правиле, пока kill switch вкл. Связано с п. 3 выше
  (окно без TUN при перезапуске).
- **Разбор ложных и дублирующих сигналов при общей причине** (2026-10-11). Пример: нет интернета → приходит
  «нет сети» и вдобавок «сайт/ресурс недоступен», хотя ресурс ни при чём. Нужно пройти все такие случаи (нет сети,
  captive portal, сеть сменилась, ядро/туннель упали, сервер выхода мёртв, DNS) и решить: какое событие/уведомление
  первопричина, какие следствия подавляются или сворачиваются в неё, как это видно в Logs. То же для отправки репорта
  (без сети — не `network`/«сервер недоступен», а «нет интернета») и для прочих служебных запросов (обновления,
  подписки, пинги).
- **Реклама/трекеры и «чем заблокировано»** (решение пользователя 2026-10-12). Адреса классифицируются всегда, с
  блокировкой или без: реклама/трекеры/телеметрия (списки вроде `geosite-category-ads-all`) отдельно от обычных сайтов;
  их сбои — не «сайт не открывается» и не уведомления, только журнал. Если соединение заблокировано — явно писать чем
  (DNS-фильтр: `0.0.0.0`/`::`/NXDOMAIN/блок-IP AdGuard и др.; правило Block пользователя; системный Private DNS), иначе
  не писать вовсе. Повод: `conn/failing` на `network-lc.ru` / `hdrc.yandex.net` (телеметрия Яндекса, Direct) —
  отчёт `20261011-6gml6m`.
- **gVisor — стек TUN по умолчанию на Android** (S57). Решение пользователя 2026-10-11: делаем точно. Сейчас
  `tunStack = 'mixed'` (`core/lib/src/catalog/settings.dart:55`). Остальные стеки остаются выбором в Settings → Connection.
