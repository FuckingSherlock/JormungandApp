1. Карточка «сайт не открывается»

Что сейчас путает: два ряда Rule с разным смыслом. Первый — по какому правилу трафик реально шёл. Второй («New rule for …») — вообще не правило, а действие: открыть форму нового правила приложения (_appRuleRow, event_text.dart). Плюс заголовок «through any server», хотя проверили две ноды и чекер, а «The checker did not answer» висит отдельной строкой без статуса.

  • Route и серверы в Checked — одним видом: «подписка · протокол», под ней «└ нода».
  • Checker: тап в любом месте ряда — перепроверка чекером, ↻ справа как подсказка. «Check again» убран.
  • Сервер в Checked: тап по ряду (или ↻) — перепроверка через эту ноду; за разделителем › — переход в Routes к ноде (моргнёт 2 раза, Back — обратно к событию).

Предложения
  • Заголовок: «opens only through Amsterdam 2». Сейчас он называет сломанный маршрут; главное для пользователя — что работает. Имя ноды в заголовке (одна, короткая часть), подписка — в рядах. Без стрелок-цепочек «нода › нода» — имена длинные.
  • Route = упавший, Checked = открывший (зелёный ряд). Та же логика, что в site/unreachable: исходный маршрут в Checked не повторяется. Зелёный градиент вместо слов «it opens»; ↻ слева — перепроверить сайт через эту ноду (заменяет «Check again»), › справа — к ноде в Routes.
  • «Create video.example.net rule» остаётся рядом с приложением, форма с Fallback = маршрут, открывший сайт (via / viaServer) — как в согласованной спеке; малая подпись говорит, что предзаполнится. Если правило есть — «video.example.net rule» + «Proxy: …».
  • Приложение — без подписи «App»; «no own route» малым, если у приложения нет своего маршрута (то же, что в unreachable). Несколько приложений (×N) — «Firefox, Chrome» в шапке, в ряду — первое + «and 1 more» (тап — лист приложений).
  • Cause одной строкой вместо склейки whyText: сервер, который не открывает, и что это значит. Если Sentinel знает причину (why: смена сети и т.п.) — она в Cause.
  • Кнопки: Details ▾ (Why / Raw) первая, Ignore site ▾ (Everywhere / On this route only). «Create rule» из кнопок уходит в ряд Rule; Check again нет.
  • нужно новое поле: время открытия через via («opens in 410 ms») — опционально; без него подпись «opens through this server».

3. site/blocked: «не открывается через X, открывается через X»

Событие (logs.md:110): {host, entry, server, dest, via, viaServer, viaTarget?, rule, …}. server — нода, на которой соединение упало; via — нода, где сайт открылся (разведчик: рабочая нода той же подписки, другой страны, затем ноды других подписок); viaTarget: 'node:…' — только если открывшая нода это цель правила. Оба поля при записи приводятся из сырого тега sing-box (route0/src2::n…, chain:…) к ключу sid::nid, а имя ищется при показе (connect-model.md:975-981, «Строка ноды в событии»).

  • Откуда путаница. Событие хранило server и via как сырые теги sing-box. У одной и той же ноды тег зависит от того, кто его назвал: route0/src2::n518c… (исходящее маршрута), route0-entry/… (вход цепочки), chain:…. Приложение при показе доставало «имя» из тега и для обоих тегов получало одну и ту же ноду; протокол брался по ключу и совпадал. Два разных тега одной ноды выглядели как две строки с одинаковым именем: «не открывается через X — открывается через X».
  • Что починено (2026-10-20). Тег приводится к ключу sid::nid одной функцией «тег → ключ ноды» и при записи события, и при показе (уже сохранённые события тоже); показывается имя + протокол. В репорте 20261019-oiep7x ноды разошлись: NL не открывает, Германия открывает — то есть данные были верны, путала только подача.
  • Остаток. Если после исправления server и via дают один ключ, такого события быть не должно: via — всегда другая нода. Защита: ядро не пишет via, равный server (считать «не нашли»); приложение не рисует два одинаковых ряда. Нужно проверить в ядре (не в схеме), где при записи via сравнивается с server.
  • Ожидание следующего репорта: Fazhzcezbdi.interkh.com (из bugs.md).
  • Открытый вопрос (bugs.md): почему поздние site/unreachable не пробовали n518c… — это цель правила (viaTarget), а не основной маршрут. Гипотеза: лестница «tried» берёт ноды подписок и разведчика, а ноду-цель правила пропускает как «уже известную» из blocked; в unreachable её нет ни в tried, ни в Checked, хотя именно она открывала сайт ранее. Нужно ядро: сверить tried позднего unreachable с viaTarget первого blocked.
  • В новом виде: строка Route — маршрут, где упало; «Opens through» — только узел с зелёной подсветкой и переход к нему; тап по карточке ничего не делает.
Если ключи совпали (тот же узел дважды) — так читать нельзя, это баг данных

4. Сравнение: site/unreachable и site/blocked — одна карточка

В новом виде карточки совпадают ряд в ряд: приложение, Rule, Route, Checked, Cause, кнопки. Отличается только итог проверки — есть ли в Checked зелёный ряд. Ниже обе в одном шаблоне рядом.

  • Вывод: это не дубли, а два разных вердикта одной проверки. blocked — сайт закрыт на этом маршруте, есть рабочий; unreachable — рабочего не нашли (сайт лежит или закрыт везде, где пробовали).
  • Что от вердикта зависит (поэтому типов два): уведомление и его кнопки; предзаполнение правила — Fallback = открывший маршрут есть только у blocked; подсказка в Cause; срок игнора отвалов у мёртвого сайта (90 мин, failures.md).
  • Предложение: типы оставить, карточку — одну. Заголовок по одной формуле: «did not open on N servers» / «did not open on K of N servers». Вариант агента «opens only through X» из прошлой схемы (§2) — заменить на эту формулу.
  • Чекер в N не входит: он отдельный ряд Checked и говорит, открывается ли сайт у других.
  • Rule у blocked малым показывает, куда пойдёт Fallback нового правила; у unreachable малой строки нет (открывшего маршрута нет — Fallback Default).
