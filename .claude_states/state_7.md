# State 7: аудит перед Flutter, Job Object, kill switch closed-confirm, TUN

Отправная точка для новой сессии. Ограничения — `state_3.md` («Ограничения»), методология —

## Сделано
- Job Object (`core/lib/src/killjob.dart`): sing-box умирает вместе с ядром при любом килле;
  jormd при старте добивает наших сирот (тот же бинарник, родителя нет). `77a3caf`.
- Kill switch: включение «Also while the app is closed» — через шторку подтверждения (что будет,
  если приложение не запустится; как снять прокси в Параметрах Windows). `0856150`.
- TUN в ядре (docs/core.md → «TUN»): tun-in (dual stack, strict_route, LAN мимо, MTU 9000), правила
  юзера в Rules как у порта (без resolve), Global мимо правил, системные правила «ядро / наш
  sing-box → direct», Hijack DNS (выкл — перехват только DNS шлюза TUN), без админа — отказ +
  событие core/tunNeedsAdmin. Выбор TUN stack в Connection (Mixed / System / gVisor). Реально TUN не
  поднимался — юзер проверит руками. Риски для ручной проверки: DNS-петля local-резолвера в TUN,
  срабатывание self-правила (process_path_regex) для ядра и ping-инстансов.
- Мокап по умолчанию в режиме TUN → dev jormd без админа теперь отказывает в подключении, пока не
  переключить на Proxy (раньше молча подключал как прокси).
- Замечено, не чинили: `routing.dart` `_fallbackSelector` падает, если в плане нет `routing.targets`
  при fallback (UI всегда шлёт); через mixed-in в режиме TUN домены не резолвятся для IP-условий.
- Комп юзера: 02.10 два внезапных ребута (14:55 без дампа — питание / hard reset; 23:08 BSOD 0x139,
  дамп `C:\Windows\Minidump\100226-31156-01.dmp`), за 30 дней 6 случаев. Предложено: разбор дампов
  (WinDbg — нужна установка, ждёт ответа), memtest, питание.

## Решения юзера
- Flutter-приложение — отдельное нативное приложение; мокап остаётся спецификацией, общее только
  ядро `core/`. Ядро в процессе приложения, sing-box — его дочерний процесс (одно дерево).
- Первая сборка — под **Android** (libbox + VpnService), потом Windows. TUN нужен сразу; юзер
  тестирует TUN руками на собранном приложении.
- Системный прокси на Android не делаем (бесполезен), режим прячем.
- Данные юзера сейчас не сохранять; перенос состояния для сборки — потом, отдельной задачей.
- Kill switch для TUN/WFP — непостоянные фильтры (снимает перезагрузка); постоянные только у явных
  опций «с загрузки» / «блок до VPN», с предупреждением.
- Пока лимитов хватает — основная реализация через `coder-deep`.

## Аудит перед Flutter (кратко)
- Ядро чистое (analyze 0, тесты 310). Логика каталога / Auto-якоря / сборки плана живёт в JS
  мокапа (`20-profiles.js` effectiveConnectId, `94-live-auto.js`, `95-live.js`) — переносить на Dart.
- `daemon.dart` смешивает HTTP и логику (recovery, kill switch, sys proxy, события) — выделить
  `CoreService`, HTTP-адаптер тонкий; интерфейс `CoreApi` под будущий фоновый движок / службу.
- Android: sing-box через libbox (gomobile .aar), `runtime.dart` → интерфейс запуска (процесс /
  libbox); gRPC `daemon.StartedService` — тот же API у libbox (проверить первым делом); пинги и
  speed test сейчас отдельными sing-box — на Android через libbox.
- Тулчейн не стоит: Flutter SDK, Android SDK + NDK, JDK 17, Go + gomobile (для Windows позже — VS
  C++). Ответа юзера ещё нет: `app/` в этом репо или отдельном; ставит ли тулчейн сам; телефон или
  эмулятор.
- Ресурсы мокапа → Flutter: темы → ThemeExtension, `04-i18n-ru.js` → ARB, `geometry.mjs` → Path,
  Twemoji-шрифт ассетом, QR пакетом.
