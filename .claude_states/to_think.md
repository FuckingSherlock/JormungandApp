## Решения

- **FakeIP — переработать логику целиком** (2026-10-11; пока выпилен из UI и модели: ядро его не применяло, тумблер
  нельзя было выключить). Вопросы: в DNS был только список доменов-исключений (кому отдавать настоящий ответ) — нужен ли
  FakeIP для выбранных приложений / своих условий в правилах; нужен ли вообще; предупреждение при правке исключений;
  Direct FakeIP не требует. Только в TUN (`docs/rules.md` §DNS, S32).

- **DNS: сервер настраивается либо «через VPN», либо «напрямую» — странно** (2026-10-11). Сейчас (`docs/rules.md:359–388`):
  один глобальный список, у каждого сервера «Через: напрямую / VPN»; `dns.final` = первый отмеченный, адреса серверов прокси и
  прямой трафик резолвит первый отмеченный прямой сервер (`default_domain_resolver`). Обдумать модель (например, отдельно
  DNS для трафика через VPN и для прямого). **Сначала проверить, работает ли разделение на деле**: какой сервер реально
  отвечает на запросы прямых и проксируемых доменов (лог sing-box `dns: exchanged …`, тест ядра на loopback).

- **ПК: кто резолвит домены через порт прокси** (2026-10-12). Через системный прокси / порт пользователя приложение
  отдаёт имя, и по умолчанию его резолвит DNS ноды (спайк `dns_spike.md` Q1). В TUN так не бывает: запрос приложения
  отвечает наш DNS, нода получает IP. Вариант — настройка поведения на ПК: резолвить у себя шагом `resolve` перед
  прокси-правилами (не проверено, передаст ли sing-box ноде IP) или оставить ноде. Сначала разобраться, как работает.

- **Внутреннее («системное») соединение ядра для служебного трафика** (2026-10-11): обновления, отчёты и подобное —
  своим путём: напрямую, при недоступности — через VPN, независимо от правил пользователя.

- **Альтернативные адреса получения одной подписки** (2026-10-12): несколько URL на подписку; если доступны оба, а данные
  расходятся — ошибка. Пользователь проверит, видит ли панель HWID через VPN (HWID — заголовок клиента, VPN его не скрывает).

- **Путь обновлений приложения** (2026-10-12): переключатель «напрямую / основной маршрут» или «напрямую / любой рабочий
  маршрут» (через служебный вход `svc-in`). Пока — напрямую + основной маршрут.

- **Переподключение при изменении правила** (S2): sing-box без рестарта правила не меняет; варианты смягчения, libbox
  `StartOrReloadService`, boxdd (S64).

- **Скрины изменившихся экранов в TG-анонсе версий** (2026-10-12). Предложение: харнесс скриншотов во Flutter (каждый

  Шум (тема/шрифт меняют всё) — порог N, сверх него только экраны из строки `screens:` в `beta.txt`. Рендер не 1:1 с
  телефоном (без системных панелей) — для «что поменялось» хватает.

- **Новый встроенный DNS-провайдер в будущей версии** (отложено 2026-10-12): сейчас загрузка недостающий встроенный не дописывает (дойдёт только через bump `listVersion` + миграцию). Варианты: дописывать в конец выключенным (рекомендация) / включённым / как сейчас. Обновление адресов существующих встроенных уже доходит без миграций (адреса из кода).

- **Подписки в формате Xray JSON** (2026-10-13). У тестера узлы «LTE» (Quattro VPN) у нас не пингуются (TCP timeout на
  46.8.209.151, RST после connect на 94.139.255.199), а в Happ — да, и без VPN тоже. Узлы — IP-литералы, резолвер ни
  при чём (проверено). В Happ у них подпись «| JSON»: панель, видимо, отдаёт Happ полные Xray-конфиги (возможны
  `fragment` ClientHello, `dialerProxy`-цепочки), нам — base64-ссылки. Xray JSON мы не понимаем
  (`docs/subscription-parsing.md`). Конфиг узла от тестера получить нельзя. Решить: делать ли поддержку Xray JSON
  (UA, при котором панель его отдаёт; перевод `fragment` → `tls.fragment`, `dialerProxy` → `detour`).
