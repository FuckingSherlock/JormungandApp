## Решения юзера (к реализации)

### Правила / DNS
1. **Резолв перед IP-правилами** (`routing.dart` ~363, `{'action':'resolve'}` перед первым IP-правилом).
   Юзер спросил «нахуя, есть же отдельные поля IP и домен». Ответ, который надо дать:
   поля — это условия на соединение; через системный прокси соединение приходит только доменом
   (браузер: «соедини с youtube.com»), IP у него нет, и поле IP / GeoIP / «локальные сети» не
   сработает никогда (пример: «GeoIP RU → Direct» в режиме системного прокси не ловит ничего;
   «домен X AND IP Y» не совпадёт). В TUN адрес уже есть — `resolve` там ничего не делает.
   Риск — утечка DNS (резолв через провайдерский DNS светит домены). У Karing это общая настройка
   «Resolve Inbound Domain names» (тумблер, влияет на порт прокси) + канал резолва proxy/direct/FakeIP.
   **Решение юзера:**
   - Настройка (Settings → DNS или Rules): «Резолв для IP-правил» — выкл / через выбранный DNS из списка
     (по умолчанию тот, что через VPN — без утечки). Влияет на соединения через порт прокси.
   - В правиле — флажок «IP-условия только в TUN», с пояснением, что резолв под прокси можно включить в
     настройках, и кнопка-ссылка на эту настройку. Флажок, подпись-пояснение и кнопка — всё
     показывать ТОЛЬКО когда в правило добавлено IP-условие (IP / CIDR, GeoIP, локальные сети), т. к. IP
     в правила кладут нечасто.
2. **Global** = всё в прокси, правила отключены — подтверждено, так и есть.
   **Локальные адреса ВСЕГДА напрямую** (Rules, Global, TUN) — «это база». Сейчас LAN-direct —
   quick-toggle `quick.lan` (`routing.dart` ~536: `ip_is_private` + `domain_suffix local/localhost`),
   в Global его нет (`build()` ~194 возвращает сразу). Сделать: правило первым всегда, в т. ч. в Global;
   тумблер LAN в быстрых правилах убрать или показывать как фиксированный. Обновить `docs/rules.md` §7.
3. **If unavailable на ходу** — нужно. Юзер: «а если резерв недоступен? или обновлять их при
   периодическом пинге? читай актуальную доку sing-box, как это делается». Блок через тупик-outbound
   «можно, но лучше не костыль». TODO: прочитать sing-box docs (outbound selector/urltest, route rule
   actions, rule-set local auto-reload, changelog последних версий — нет ли нового fallback-типа), затем
   предложить. Наброски: цель в `selector` [цель, запасной] + проверка целей тем же периодическим пингом
   Auto + переключение через Clash API; Block — через local rule-set (sing-box перечитывает файл при
   изменении) или `clash_mode`, проверить. Запасной Main мёртв = мёртв весь туннель, это забота Auto.
4. **DNS без переподключения** — одобрено: все DNS списка в конфиге, основной выбирается DNS-правилами
   по `clash_mode`, ядро пингует DNS и при отказе меняет режим через Clash API. Ручная правка списка —
   перезапуск (ок). Тем же приёмом можно Rules↔Global без рестарта (Karing перезапускает: флаг `proxy_all`
   → reload; у них ещё `private_direct` и отдельный «forward» mixed-порт = всегда всё в прокси — идея).

### Auto (ядро `core/lib/src/auto.dart`, UI `94-live-auto.js`, настройки `55-automode.js`)
1. **При отказе текущей — проверить все записи Auto** параллельно **батчами по 10** (слабое устройство /
   медленный инет), выбрать первую ответившую по приоритету. Перед перебором — проверка, есть ли
   интернет вообще (прямой запрос): нет сети → ничего не помечать мёртвым и не переключать.
   Пока всё лежит — раз в 10 с (на мобилке потом растягивать).
2. **Пинг запасных — под контроль юзера**: вкл/выкл (это `keepWarm`) + **свой период** (сейчас общий
   `checkEvery`). Добавить поле периода в Settings → Auto mode.
3. **Подтверждение отказа**: после промаха текущего — быстрые повторы, `failAfter` промахов подряд →
   переключение. Сейчас пауза между повторами 10 с (`retryEvery`, зашито в ядре, в UI настройки НЕТ).
   **Решение юзера:** отдельная настройка в Settings → Auto mode «Пауза между повторами», **по умолчанию
   0,5 с**, можно вписать вручную или выключить повторы (тогда переход по первому промаху / по
   `failAfter` на обычном таймере — уточнить семантику «выкл» у юзера при реализации). **Максимум `failAfter` = 5** (решение юзера; сейчас степпер 1–4, ядро clamp 1–10).
   **`standby` (сколько запасных пинговать) — слайдер 0–20**, горизонтально таскаемая / прокручиваемая
   строка (решение юзера); 0 = не пинговать запасных (заменяет тумблер `keepWarm`, проверить при реализации).
4. **Защита от мигания** — одобрено: каждое падение удлиняет испытательный срок перед возвратом
   (1, 2, 4 … 30 мин), счёт забывается после ~15 мин стабильности; уведомление «X нестабильна».
5. **Возврат наверх** — одобрено моё: возврат БЕЗ разрыва соединений (сейчас у селекторов
   `interrupt_exist_connections: true` в `config.dart` 61/71/93 → поставить false на верхнем `proxy`,
   а при failover ядро само закрывает соединения мёртвого маршрута через Clash API `clashDelete`);
   возвращаться, когда верхняя стабильна (п. 4) и не медленнее текущей больше чем на `threshold`.
   **Липкий режим** опцией: «Возвращаться на запись выше: всегда / только если быстрее / не
   возвращаться до переподключения». Юзер спросил, где — ответ: Settings → Auto mode (это поведение
   Auto; глобально, не на запись).
6. **Все записи Auto в конфиг** (не окно верх…текущая+standby) — «пусть грузит все». Тогда failover
   никогда не требует рестарта. Если всё равно отвалилось — рестарт ок. Неиспользуемые urltest-группы
   sing-box сам ставит на паузу (`idle_timeout`).
7. **Уведомления — делать**: экран Settings → Notifications со всеми типами (Auto сменил запись /
   сервер Priority, связь потеряна/восстановлена, sing-box упал/перезапущен, подписка обновлена/ошибка,
   списки правил не скачались, запись нестабильна, постоянное уведомление со статусом на Android).
   Сейчас в General есть только «When Auto switches» и постоянное уведомление.
8. **Проверка по неудачным запросам** — нужна (быстрое обнаружение отказа по ошибкам соединений в
   Clash API / логе). НО открытый вопрос юзера: нода может быть ни при чём — заблокирован конкретный
   адрес назначения, а мы переключимся зря. Идея юзера: отдельная настройка + уведомление «с ноды N
   недоступен адрес A» + рекомендация с заготовкой правила. «Ещё обдумать» — не реализовывать.
   **В новой сессии первым делом задать юзеру конкретный вопрос по этой теме (AskUserQuestion) и
   разобрать варианты**, например: (а) при ошибках соединений пинговать сам сервер тест-URL'ом — жив →
   проблема адреса, не переключаться, а уведомить «с ноды N недоступен адрес A» + кнопка «Создать
   правило» (заготовка: адрес → другая цель / Direct); (б) проверять тот же адрес через другую запись /
   напрямую — доступен там → блок на ноде; (в) переключаться только если ошибки идут к нескольким разным
   адресам за окно времени; (г) отдельная настройка вкл/выкл переключения по ошибкам запросов.
   Плюсы/минусы каждого, рекомендация.

### Защита локальных портов
- Clash API уже под случайным секретом. Юзер: «добавляй» защиту mixed-порта; есть ручная настройка
  порта (Settings → Connection → Proxy port, 1024–65535) — «диапазон защищённых дать или убирать — хз».
- Ответ: диапазон не защищает (любая локальная программа достучится до любого порта 127.0.0.1); защищает
  только пароль. Системный прокси Windows пароль передать не умеет. Предложение: два inbound'а —
  системный прокси на своём порту без пароля (только пока включён системный прокси; адрес и так виден в
  реестре), а пользовательский порт — с логином/паролем (сгенерированы, копировать строкой
  `socks5://user:pass@127.0.0.1:port`). На Android в TUN mixed-порт по умолчанию не открывать.
  **Согласовано юзером** — реализовывать этот вариант.
