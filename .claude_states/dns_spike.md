# Спайк: DNS в двух независимо переключаемых сторонах (sing-box 1.14.2, loopback)

Стенд: mock-DNS на loopback (ответ 127.0.K.K, K = номер сервера), второй sing-box как «VPN» (ss), запросы
через `direct`-inbound + `hijack-dns` (как TUN). Регрессионный тест: `core/test/dns_sides_singbox_test.dart`
(3 теста, ~6 с, запускать одиночно). Сервер VPN-стороны = `{"type":"udp","server":"127.0.0.2","detour":"proxy"}`.

## Q1. Работает ли нынешнее разделение (dns-dir / dns-vpn)
Да, механика без сюрпризов (варианты final=dns-dir и final=dns-vpn):
- `dns.final` отвечает на всё без правила; DNS-правило `domain_suffix → server` отвечает своим сервером в обоих вариантах.
- VPN-сервер реально идёт через detour: ss-сервер видит «packet connection to 127.0.0.2:5302»; при остановке ss
  запрос к VPN-серверу таймаутится, а к direct-серверу отвечает.
- **Исходящий direct резолвит ТОЛЬКО своим `domain_resolver` / `route.default_domain_resolver`.** DNS-правила
  при этом не смотрятся (правило `trap.test → dns-vpn` не сработало, соединение ушло по ответу dns-dir).
- Route `action: resolve` без `server` идёт по DNS-правилам; с `server` — прямо этим сервером, правила не читаются.
  Результат кладётся в `DestinationAddresses`, и direct-outbound дальше свой resolver не использует.
- Кэш: ключ = вопрос + тег транспорта, поэтому кэш не пересекается между серверами; hijack и исходящий
  запрос через один сервер делят запись.
- Домен, идущий через прокси (`vpn.test` через proxy), клиентский DNS не резолвит вообще (резолвит серверная сторона).
  Значит VPN-сторона обслуживает только hijack, dns.final, «Resolve for IP rules» и `resolve`-действие.
- Missing `domain_resolver` и DNS-правило с `outbound` — deprecated (1.14.0), под `sing-box run` ФАТАЛЬНО; не вариант.

## Q2. Механизм двух независимых сторон
У sing-box нет DNS-сервера-обёртки/селектора, живых переключателей два: `SetClashMode` и `SelectOutbound`.

### A. Составные clash-режимы (рекомендую как основной)
Режим `d{i}v{j}` = (прямой сервер i, VPN-сервер j). Сервер-правил по одному на сервер, пары в OR-охранах:
```
{"type":"logical","mode":"and","rules":[{"domain_suffix":[…домены direct-целей…]},
   {"type":"logical","mode":"or","rules":[{"clash_mode":"d1v0"},{"clash_mode":"d1v1"},…]}],
 "action":"route","server":"d1"}                       // по одному на прямой сервер
{"type":"logical","mode":"or","rules":[{"clash_mode":"d0v2"},{"clash_mode":"d1v2"},…],
 "action":"route","server":"v2"}                       // по одному на VPN-сервер = catch-all
```
Стартовый режим `Rule` добавить алиасом в охраны d0 и v0. Список режимов sing-box строит сам из правил (API
принимает только его).
- Размер при 12×12 (= 4 провайдера × 3 транспорта × 2 стороны на сторону): 25 серверов, 24 правила, 338 items,
  12.8 КБ, старт 0.39 с, `check` проходит; 144 режима. Плоская схема «правило на режим и сторону» — 288 правил, 24.5 КБ.
- Переключение: вызов API ~1 мс, действует со следующего запроса. Долгое соединение через прокси (16 чанков)
  пережило все смены. Без перезапуска.
- `SetClashMode` чистит ВЕСЬ DNS-кэш (обе стороны), меняется только при смене режима; повтор того же режима кэш не трогает.
- Режим сохраняется в `cache_file` (`cache_id` тот же): после рестарта остаётся прежний `d3v2`, значит ядро
  обязано выставлять режим явно на каждом старте.
- Нагрузка (3 потока, ~5.6k запросов, 24 смены, 4×4 и 12×12): 0 таймаутов, 0 ответов старой парой через 300 мс, p50 ~1 мс.

### B. Файлы-флаги (запасной, если произведение режимов станет велико)
По одному локальному `rule_set` (source, version 3) на сервер: `{"domain_regex":[".*"]}` = включён, `{"domain":["never.invalid"]}`
= выключен. Правила по приоритету, побеждает первый включённый; мёртвый сервер = флаг выключается.
12×12: 24 правила, 48 items, 24 файла, 9 КБ. Реакция ~105 мс (fswatch; атомарный rename и запись на месте оба ок).
Кэш не чистится, но ключ кэша по серверу — устаревших ответов нет. Минусы: файловый ввод-вывод, eventual consistency,
при битом файле молча остаётся старое состояние; inotify на Android не проверен.

### C. Исходящий direct (то, что не покрывают DNS-правила)
- Селектор `directsel` из `direct`-outbound'ов `dsel{i}`, у каждого фиксированный `domain_resolver: d{i}`; переключается
  `SelectOutbound` с `interrupt_exist_connections:false`. Новые соединения идут по новому серверу, открытое раньше выжило. Покрывает
  только исходящий direct (не hijack-запросы direct-доменов).
- `resolve` без server перед direct-правилом + зеркальные DNS-правила (домены direct-целей) + режимные охраны: O(1) лишних route-правил на
  direct-правило, но сторона определяется только зеркалом доменов; direct-трафик без домена (IP) падает в dns.final.
- `resolve` с `server` под охраной режима работает, но стоит (#direct-правил × N_d) route-правил и резолвит весь подходящий трафик.
- Выбор: селектор (C1) для outbound'а + режимы (A) для hijack/final/resolve.
- Нативный `evaluate`+`match_response`+`respond` даёт фолбэк внутри запроса: каждое новое имя платит `timeout` (1 с при мёртвом d0,
  2 с при двух мёртвых). Годится только как статическая страховка, не как Sentinel-переключатель.

## Q3. Адреса серверов узлов
Outbound узла с `server: node.test` и `domain_resolver: d0` продолжает спрашивать d0 после смены режимов d0v0→d1v0→d2v1
(даже при очищенном кэше). `domain_resolver` фиксируется на экземпляр outbound'а и не переключается; без него — фатальная
deprecated-ошибка. Вывод: адреса узлов надо **резолвить заранее в IP** (SNI/Host остаются доменом: `tls.server_name`, `headers.Host`),
иначе узлы привязаны к одному серверу навсегда. То же для hostname DoH/DoT серверов: их bootstrap `domain_resolver` фиксирован.

## Рекомендация
1. Две стороны = составные clash-режимы (A) + `SetClashMode`, ядро выставляет режим явно на каждом старте (и после рестарта sing-box).
2. Исходящий direct = селектор `direct@d_i` (C1), Sentinel переключает оба вместе (режим + select).
3. Адреса узлов — pre-resolve в IP до построения конфига (Q3); сам pre-resolve идёт стороной direct.
4. Транспорты провайдера (DoH/DoT/DoQ/UDP) — отдельные серверы sing-box со своим тегом; порядок приоритета решает ядро по состоянию.
Лимит режимов: N_d×N_v; при ~12×12 ещё нормально, при существенно большем — перейти на B.

## Открытые риски
- Мок использует только udp: переключение DoH/DoT/DoQ идентично по устройству роутера (транспорт — просто тег), но живьём не проверено.
- Каждая смена режима чистит общий кэш (холодный старт для обеих сторон) — вероятно приемлемо, меряется редкостью смен.
- Алиас `Rule` и сохранённый в `cache_file` режим: ядро не должно полагаться на начальное состояние.
- Android libbox: `with_quic` для DoQ/H3 и fswatch для B не проверены.
