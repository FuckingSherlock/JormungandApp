## Сделано
- Мелочи из state_5: текст подтверждения kill switch; per-app диалог по центру; Default / Proxy без
  перевода (кроме подсказок); Proxy password, подсказка в (?); полоска выбранной строки в Route
  pinned и пикере целей, без галочки, флаг не липнет к подсветке.
- Per-app диалог: карточка Split TCP/UDP с (?) и переключателем; табы TCP | UDP (свайп как в Nodes)
  только при Split; сегменты Route (Default | Proxy | Direct | Block) и Fallback, строки Via
  постоянные (на Default — «Main flow» с замком; Via фолбэка активна только при Fallback = Proxy);
  стабильная высота, сегменты переносятся по ширине. Fallback на Route = Direct — отложен.
- Fallback на выбранную цель (ядро: селекторы [цель, запасная цель, основной поток], обе мертвы →
  основной поток) и фолбэк для основного потока (сверка с direct / запасной целью, чтобы отличать
  мёртвый поток от мёртвой сети). Контракт плана: fallback 'default'|'main'|'block'|'direct'|<id>.
- Общий пул проверок в ядре (`core/lib/src/pool.dart`): ключ = отпечаток сервера + URL + чекеры,
  склейка одновременных запросов, maxAge на вызывающего, промахи не кэшируются; статус сети
  up / down / unknown в /api/status `network`.
- Форма правила: тот же блок Fallback (и для основного потока), ru «ДЕЙСТВИЕ»; чипы условий
  редактируются; пунктир «+ Condition» сверху; префилл из события — точный Domain и настоящий id цели
  (баг «deleted profile»).
- Журнал: site/blocked — карточка в стиле меню (⚠️ / ✅ маршрут (узел) [Open], [Create rule],
  [In raw log]), сервер, через который открылось; site/unreachable — «не открылся нигде» с
  перечнем попробованных маршрутов и причиной, если пробовать было нечего. Настройка Auto mode →
  перебор: Off / Up to 3 / All. Смерть узла эти события не порождает. Строки «почему» (правило /
  приложение / сервис / быстрое правило / основной поток + процесс) со ссылками; если адрес ловят и
  per-app, и правило — применённое и overridden. Back из любого действия возвращает к записи.
- Home dock: тип без перевода (sub / chain / profile / set), протокол сервера между AUTO / MANUAL и
  именем узла.
- Crash-safe состояние (после потери ui-state.json при отключении света — файл был из NUL):
  `durable.dart` (запись с flush перед rename), ротация .bak / .bak2, битый файл откладывается как
  `ui-state.json.corrupt-<UTC>`, загрузка последней целой копии, события core/stateRestored /
  core/stateLost; нечитаемый файл sys proxy больше не ломает старт (реестр не трогаем). Flutter

- План (только docs/rules.md §7): запуск с системой — Выкл / При входе (задача Планировщика, как у

## На потом (юзер: «в долгий ящик» / «просто в план»)
- Проверка сервиса через узлы: в пикере цели правила второй индикатор у каждого узла —
  открывается ли хост из правила через этот узел (переиспользовать probeReach + пул). Категории
  ответа: 2xx/3xx ок, 403/451 отказ (геоблок / бан IP), сброс TLS (DPI), таймаут. 403 считать
  блоком, только если через другие узлы / напрямую 200 (иначе это защита сайта от ботов).
  Запуск по ⚡ в шапке пикера, не при каждом открытии.
- Аудит «проверок через сервер, который юзер явно не выбирал» + настройка (по умолчанию вкл,
  можно выключить). Причина: сервисы смотрят не только на IP — запросы к одному сервису с разных
  адресов при одинаковых прочих параметрах могут снизить траст. Различать: запросы на
  нейтральный test URL (безвредны) и запросы к реальным адресам юзера (site/blocked: повтор сайта
  через другой маршрут в auto.dart `_sites`; будущая проверка сервиса). Частично есть: перебор
  можно выключить (siteRetry Off).
- Диалог удаления цели (`targetImpact`) не называет запасную цель правила (fallbackTarget).
- Приоритет правил vs per-app: юзер считает, что адресное правило должно побеждать per-app
  (сейчас: приложения → свои правила → быстрые → остальное, docs/rules.md §1). Главное меню правил
  юзер будет переделывать сам. Порядок не трогать до этого.
- Запуск с системой — docs/rules.md §7. Проверять только на живом хосте с разрешения юзера.
- Fallback на Route = Direct — непонятно, как надёжно определять недоступность Direct.
